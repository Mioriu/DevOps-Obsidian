Снапшот LVM — это моментальный снимок состояния логического тома в конкретный момент времени. Вы можете спокойно экспериментировать, обновлять систему или тестировать изменения, зная, что в любой момент можете откатиться назад. Сегодня мы разберёмся, как работает эта технология и научимся эффективно её использовать.

### Что такое снапшот и почему это важно

Снапшот (snapshot) — это механизм, который позволяет зафиксировать состояние логического тома в определённый момент времени без полного копирования всех данных. Это происходит практически мгновенно, независимо от размера тома. Если ваш том занимает 100 гигабайт, создание снапшота займёт несколько секунд, а не час, как при обычном копировании.

Ключевое отличие снапшота от обычной резервной копии в том, что снапшот живёт на том же физическом носителе и тесно связан с оригинальным томом. Это делает его идеальным инструментом для быстрого отката изменений, но не заменяет полноценное резервное копирование. Если выйдет из строя физический диск, вы потеряете и оригинальные данные, и снапшот.

```1c
Сравнение снапшота и резервной копии:
┌────────────────────────────────────────────────┐
│           Снапшот LVM                          │
│  • Создание: секунды                           │
│  • Место: тот же диск/VG                       │
│  • Восстановление: минуты                      │
│  • Защита от: ошибок, неудачных обновлений     │
│  ✗ НЕ защищает от отказа диска                 │
└────────────────────────────────────────────────┘

┌────────────────────────────────────────────────┐
│         Резервная копия                        │
│  • Создание: минуты-часы                       │
│  • Место: другой носитель                      │
│  • Восстановление: часы                        │
│  • Защита от: всех видов потери данных         │
│  ✓ Защищает от отказа диска                    │
└────────────────────────────────────────────────┘
```

### Как работают снапшоты — технология Copy-on-Write

Снапшоты LVM работают по технологии Copy-on-Write (COW, копирование при записи). Когда вы создаёте снапшот, LVM не копирует все данные. Вместо этого он создаёт специальную таблицу соответствия и начинает отслеживать изменения в оригинальном томе.

В момент создания снапшота LVM запоминает текущее состояние всех блоков данных. Когда вы читаете данные из снапшота, система проверяет: если блок не изменился с момента создания снапшота, данные читаются прямо из оригинального тома. Это экономит место и время.

Когда происходит запись в оригинальный том, срабатывает механизм COW. Перед тем как перезаписать блок данных, система копирует его старую версию в область хранения снапшота. Таким образом, снапшот всегда содержит данные на момент своего создания, даже если оригинал изменился.

```makefile
Механизм Copy-on-Write:

Момент создания снапшота:
Оригинал: [A][B][C][D][E]
Снапшот:  [указатели на оригинал]
COW область: [пусто]

После изменения блока B на B':
Оригинал: [A][B'][C][D][E]
Снапшот:  [→A][→COW:B][→C][→D][→E]
COW область: [B - старая версия]

Чтение из снапшота блока B вернёт старое значение B
Чтение из оригинала вернёт новое значение B'
```

### Подготовка к работе со снапшотами

Прежде чем создавать снапшоты, нужно убедиться, что ваша система готова к этому. Главное требование — наличие свободного места в группе томов (Volume Group). Снапшот **не может существовать без выделенного пространства** для хранения изменённых блоков.

Проверим текущее состояние LVM-системы и убедимся, что у нас есть всё необходимое для работы со снапшотами:

```bash
# Проверяем состояние группы томов
$ sudo vgs
  VG       #PV #LV #SN Attr   VSize   VFree
  mainvg     2   3   0 wz--n- 199.99g 49.99g

# VFree показывает свободное место - у нас есть почти 50GB
```

Обратите внимание на колонку `VFree` — это свободное пространство в группе томов, которое можно использовать для снапшотов. Если свободного места нет или его мало, снапшот либо **не создастся**, либо быстро **переполнится** и станет непригодным для использования.

### Создание первого снапшота

Теперь создадим снапшот реального логического тома. Предположим, у нас есть том с важными данными, и мы хотим застраховаться перед обновлением системы.

```bash
# Смотрим существующие логические тома
$ sudo lvs
  LV       VG     Attr       LSize   
  root     mainvg -wi-ao---- 50.00g
  home     mainvg -wi-ao---- 100.00g

# Создаём снапшот тома home размером 5GB
$ sudo lvcreate -L 5G -s -n home_snapshot /dev/mainvg/home
  Logical volume "home_snapshot" created.

# Проверяем результат
$ sudo lvs
  LV            VG     Attr       LSize   Origin Snap%
  root          mainvg -wi-ao---- 50.00g
  home          mainvg owi-aos--- 100.00g
  home_snapshot mainvg swi-a-s--- 5.00g   home   0.00
```

Разберём параметры команды создания снапшота. Флаг `-L 5G` задаёт размер снапшота — это не размер данных, которые копируются, а **размер области** для хранения изменений. Флаг `-s` указывает, что мы создаём **именно снапшот**, а не обычный том. Параметр `-n home_snapshot` задаёт имя снапшота.

### Размер снапшота

Выбор размера снапшота — это важное решение, которое влияет на надёжность и эффективность. Слишком маленький снапшот может переполниться и стать нечитаемым. Слишком большой — напрасно занимает место в группе томов.

Размер снапшота зависит от того, сколько данных изменится в оригинальном томе за время жизни снапшота. Если вы создаёте снапшот на час для небольшого обновления, достаточно 5-10% от размера оригинального тома. Если снапшот будет жить несколько дней и в это время будет активная работа с данными, может потребоваться 20-30% или даже больше.

```1c
Рекомендации по размеру снапшота:
┌────────────────────────────────────────────────┐
│ Сценарий использования       │ Размер снапшота │
├──────────────────────────────┼─────────────────┤
│ Быстрое обновление (1 час)   │ 5-10% от тома   │
│ Тестирование ПО (1 день)     │ 15-20% от тома  │
│ Эксперименты (неделя)        │ 25-30% от тома  │
│ Долгосрочный снапшот         │ 50%+ от тома    │
└────────────────────────────────────────────────┘
```

### Монтирование и просмотр снапшота

Снапшот можно смонтировать как обычный том и работать с ним независимо от оригинала. Это полезно для восстановления отдельных файлов или для сравнения текущего состояния с сохранённым.

```shell
# Создаём точку монтирования
$ sudo mkdir /mnt/snapshot

# Монтируем снапшот (только для чтения рекомендуется)
$ sudo mount -o ro /dev/mainvg/home_snapshot /mnt/snapshot

# Теперь можем просматривать файлы на момент создания снапшота
$ ls /mnt/snapshot
Documents  Downloads  Pictures  old_config.conf

# Копируем нужный файл из снапшота
$ cp /mnt/snapshot/old_config.conf ~/config_backup.conf

# Размонтируем когда закончили
$ sudo umount /mnt/snapshot
```

Монтирование снапшота только для чтения (флаг `-o ro`) — это хорошая практика. Это защищает снапшот от случайных изменений и гарантирует, что он останется точной копией состояния на момент создания.

### Восстановление из снапшота

Существует **два** основных способа восстановления данных из снапшота: **восстановление отдельных файлов** и **полное восстановление тома**.

Полное восстановление означает **возврат всего логического тома к состоянию на момент создания снапшота**. 

```shell
# Сначала размонтируем оригинальный том
$ sudo umount /home

# Восстанавливаем том из снапшота
$ sudo lvconvert --merge /dev/mainvg/home_snapshot
  Merging of volume mainvg/home_snapshot started.
  mainvg/home: Merged: 100.00%

# После слияния снапшот автоматически удаляется
$ sudo lvs
  LV       VG     Attr       LSize   
  root     mainvg -wi-ao---- 50.00g
  home     mainvg -wi-ao---- 100.00g

# Монтируем восстановленный том обратно
$ sudo mount /dev/mainvg/home /home
```

Операция слияния (`merge`) уничтожает снапшот. После восстановления снапшот исчезает, и если вы хотите иметь возможность откатиться снова, **нужно создать новый снапшот**.

### Ограничения и подводные камни

Несмотря на всю полезность, у снапшотов LVM есть свои ограничения, о которых важно знать.

Производительность — это первое, на что стоит обратить внимание. Когда существует активный снапшот, каждая операция записи в оригинальный том требует дополнительной работы: сначала копирование старых данных в снапшот, потом запись новых.

Переполнение снапшота — критическая проблема. Если снапшот заполнится на 100%, он становится непригодным для использования и не может быть восстановлен.

Снапшоты не заменяют резервные копии. Они находятся на тех же физических дисках, что и оригинальные данные. Отказ диска уничтожит и данные, и снапшоты. Снапшоты — это инструмент для быстрого отката, а не для долгосрочного хранения.
