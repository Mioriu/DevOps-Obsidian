В предыдущих уроках мы научились **запускать контейнеры, заходить в них и копировать файлы.** Но чтобы понимать, _что происходит_ в контейнере во время работы, нужно уметь смотреть логи и базовые метрики. Docker даёт для этого несколько инструментов: **`docker logs`**, **`docker stats`**, а также дополнительные команды вроде **`docker top`** и **`docker events`**. Рассмотрим их по порядку.

### 1. `docker logs`: где и как смотреть вывод приложения?

Когда контейнер запускается, всё, что приложение пишет в STDOUT/STDERR, попадает во внутренний лог Docker. Команда `docker logs` показывает этот вывод:

```php-template
docker logs <container_name_or_id>
```

- **Пример**: `docker logs mynginx` – вы увидите все записи, которые Nginx вывел с момента запуска.
- Если контейнер говорлив, лог может быть очень длинным.

**Полезные флаги:**

- `-f` (follow): аналог `tail -f` – прямая трансляция новых строк лога.
- `--tail <N>`: показать последние N строк (удобно, если лог огромный).
- `--since <timestamp>`: показать логи, начиная с указанного времени (поддерживается в более новых Docker-версиях).

**Важно:** если контейнер завершился, `docker logs` всё равно доступен, пока вы не удалили контейнер. После `docker rm` логи тоже исчезают.

![](https://ucarecdn.stepik.net/8001c7ca-ea25-4e2e-8022-98a60de06c4d/)

### 2. Разовый просмотр логов внутри контейнера (диагностика)

Иногда приложение **не пишет в STDOUT/STDERR**, а складывает логи в файл (например, `/var/log/app.log`). В таком случае команда `docker logs <container>` **ничего не покажет**, потому что Docker читает именно стандартные потоки.  
Чтобы **один раз заглянуть** в такой файловый лог и быстро найти ошибку, можно временно «зайти» в контейнер и прочитать файл:

- Показать последние 200 строк:
- ```bash
    docker exec -it <container> sh -c "tail -n 200 /var/log/app.log"
    ```
    
- Смотреть новые строки в реальном времени (как `tail -f`), чтобы поймать момент ошибки:
- ```bash
    docker exec -it <container> sh -c "tail -f /var/log/app.log"
    ```
    
- Отфильтровать ошибки/предупреждения:
- ```bash
    docker exec -it <container> sh -c "grep -E 'ERROR|WARN' /var/log/app.log | tail -n 200"
    
    ```
    

> **Что важно понимать:**
> 
> - Это **разовая диагностика**: вы читаете файл _внутри_ контейнера, но логи **не станут** видны через `docker logs`.
>     
> - Путь к файлу зависит от приложения/образа. Иногда это не `/var/log/...`, а, например, `/app/logs/app.log`.
>     
> - В минимальных образах (alpine/busybox) вместо `bash` есть `sh`, а `grep -E` может называться `egrep`. Если команда ругается, попробуйте упростить: `sh -c "tail -n 200 /path/to/log"`.
>

### 3. Проксирование файловых логов в STDOUT (чтобы видеть их через `docker logs`)

Если нужно, чтобы **эти же файловые логи появились в `docker logs`** (а значит, попали и в лог-драйвер/централизованную систему), организуйте **постоянный вывод** содержимого файла в стандартный вывод контейнера (STDOUT).

### Вариант А: быстро включить на уже запущенном контейнере

Запускаем фоновый `tail`, который «перекачивает» файл в STDOUT процесса контейнера:

```bash
docker exec -d <container> sh -c "tail -F /var/log/app.log >&1 &"
```

Теперь:

```php-template
docker logs -f <container>
```

— будет показывать новые строки из файла.  
`-F` (с заглавной) «подхватывает» файл после ротации; `>&1` направляет вывод в STDOUT.

### Вариант Б: сделать это частью запуска контейнера (надёжно)

Лучше прописать перекидывание логов в **entrypoint/supervisor**, чтобы оно включалось при старте контейнера:

```nginx
# Пример идеи в Dockerfile/entrypoint:
# запустить приложение и параллельно переливать лог
CMD sh -c "/usr/local/bin/start-app & tail -F /var/log/app.log"
```

Либо использовать процесс-менеджер (supervisord, s6), который поднимает и приложение, и `tail -F`.

### Альтернатива без tail (если приложение поддерживает перенаправление)

Иногда проще **перенаправить** лог приложения сразу в STDOUT:

```bash
# Пример запуска приложения с выводом в STDOUT
/app/bin/myapp --log-file=/proc/1/fd/1
# или символической ссылкой файла лога на /proc/1/fd/1
ln -sf /proc/1/fd/1 /var/log/app.log
```

**Ключевая мысль:**  
В пункте 2 вы **разово читаете** файл внутри контейнера (снаружи этого не видно).  
В пункте 3 вы делаете так, что файл **постоянно «течёт» в STDOUT**, и его можно смотреть обычным `docker logs -f <container>` и собирать стандартными средствами Docker.

![](https://ucarecdn.stepik.net/b31ba728-6e45-464c-950e-a22d93230600/)

### 4. `docker top`: какие процессы внутри контейнера?

Если вы захотите увидеть, какие процессы сейчас работают внутри контейнера:

```css
docker top <container>
```

- Покажет PID, команду, время запуска и т. д. Это полезно, если в контейнере запущено несколько процессов
- В некоторых ОС (особенно Windows) вывод может отличаться.

![](https://ucarecdn.stepik.net/4868fdc3-393c-41ea-9510-da56b30f22a1/)

### 5. `docker events`: отслеживание событий Docker

Это более продвинутая команда, позволяющая слушать события Docker — запуск/остановка контейнеров, создание сети, монтирование томов и т. д.:

```matlab
docker events
```

- Вы увидите поток событий: `container start`, `container stop`, `network create` и проч.
- В большинстве случаев на базовом уровне не нужно, но иногда полезно для отладки в реальном времени.

![](https://ucarecdn.stepik.net/ed88a293-7746-4a29-b951-1cca053c830d/)

### 6. Разница между файловыми логами и `docker logs`

- **`docker logs`** читает именно потоки STDOUT/STDERR контейнера. Если ваше приложение пишет во `/var/log/app.log`, то Docker не видит это по умолчанию, если вы не настроили перенаправление (или log driver).
- Многие рекомендуют писать логи _в поток_ (stdout/stderr), чтобы `docker logs` мог всё поймать, и дальше перенаправлять в нужную систему.

## Как Docker работает с логами

Docker по умолчанию собирает всё, что приложение пишет в стандартные потоки вывода — STDOUT и STDERR. Эти данные доступны через команду `docker logs <container>`. Такой подход позволяет централизованно и удобно просматривать логи любого контейнера, не заходя внутрь и не разбираясь, где именно приложение пишет свои файлы.

Однако если приложение пишет логи не в STDOUT/STDERR, а в отдельный файл (например, `/var/log/app.log` внутри контейнера), стандартные средства Docker (`docker logs`) эти записи не увидят. В этом случае логи остаются внутри файловой системы контейнера и недоступны снаружи без дополнительных действий.

**Почему важно писать логи в STDOUT/STDERR?**

- Это позволяет использовать стандартные инструменты Docker (`docker logs`, log drivers, централизованные системы логирования).
    
- Логи автоматически доступны после запуска контейнера и сохраняются до его удаления.
    
- Можно легко настраивать ротацию, сбор и анализ логов на уровне инфраструктуры, а не приложения.
    

**Что делать, если приложение пишет логи только в файл?**

Если изменить поведение приложения или пересобрать образ нельзя, есть стандартные обходные пути, чтобы всё равно видеть эти логи снаружи контейнера:

### 1. Проброс (маунт) лог-файла на хост (про volume'ы будет отдельный модуль)

Можно смонтировать файл лога контейнера в файловую систему хоста с помощью опции `-v` (volume) при запуске контейнера. Тогда логи будут доступны на хосте по указанному пути.

**Пример:**

```swift
docker run -v /host/logs/app.log:/var/log/app.log myapp
```

Теперь можно читать логи на хосте:

```bash
tail -f /host/logs/app.log
```

### 2. Использовать docker exec для просмотра файла лога

Можно зайти внутрь контейнера и просмотреть файл лога напрямую:

```bash
docker exec myapp cat /var/log/app.log
```

### 3. Организовать вывод файла лога в STDOUT контейнера

Можно запустить дополнительный процесс в контейнере, который будет читать файл лога и выводить его в STDOUT. Например, с помощью `tail -f`:

```bash
docker exec -it myapp tail -f /var/log/app.log
```

## Итог

- **`docker logs <container>`**: смотрим текущие или прошлые логи приложения, `-f` для живого режима.
- **`docker stats`**: базовые метрики ресурсов (CPU, RAM, сети, диска).
- **`docker top`**: какие процессы внутри контейнера?
- **`docker events`**: мониторинг событий Docker.

Если приложение пишет логи только в файл внутри контейнера, а образ менять нельзя, есть три стандартных способа получить эти логи:

- Смонтировать лог-файл на хост и читать его там.
    
- Использовать `docker exec` для просмотра файла внутри контейнера.
    
- Организовать вывод файла в STDOUT контейнера с помощью `tail -f`, чтобы логи были видны через `docker logs`.
    

Таким образом, даже без изменений образа, доступ к логам сохраняется за счёт стандартных инструментов Docker и Linux.

С этими командами вы сможете _анализировать_, что происходит в контейнере прямо во время работы: понимать, почему он _падает или съедает ресурсы_, и быстро **обнаруживать ошибки,** выведенные приложением.
