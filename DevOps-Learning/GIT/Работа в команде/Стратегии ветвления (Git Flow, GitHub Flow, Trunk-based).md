Когда в проекте работает несколько человек, возникает вопрос: как организовать работу с ветками? Кто-то работает над новой функцией, кто-то исправляет баги, кто-то готовит релиз. Без чёткой стратегии быстро наступает хаос. Стратегия ветвления — это набор правил о том, как создавать, называть и сливать ветки. Рассмотрим три популярных подхода, от сложного к простому.

### Git Flow: структура для больших проектов

Git Flow — это стратегия, предложенная Vincent Driessen в 2010 году. Она создавалась для проектов с чётким циклом релизов, где версии выпускаются раз в несколько недель или месяцев.

#### Основные ветки в Git Flow

В Git Flow есть две постоянные ветки. Ветка **main** (раньше master) содержит только стабильный код, готовый к production. Каждый коммит в main — это новая версия продукта. Ветка **develop** — это интеграционная ветка для новых функций. Здесь собирается код для следующего релиза.

Правило простое: main всегда стабилен и готов к развёртыванию. Develop содержит последние завершённые разработки, но может быть нестабилен.

#### Вспомогательные ветки

**Feature branches** создаются от develop для разработки новых функций. Название обычно начинается с feature/. После завершения работы ветка сливается обратно в develop и удаляется.

```shell
# Создание feature ветки
$ git checkout -b feature/user-authentication develop

# После завершения работы
$ git checkout develop
$ git merge --no-ff feature/user-authentication
$ git branch -d feature/user-authentication
```

**Release branches** создаются от develop, когда набрано достаточно функций для релиза. В release ветке происходит финальная подготовка: исправление багов, обновление документации, тестирование. Новые функции не добавляются.

```ruby
# Создание release ветки
$ git checkout -b release/1.2.0 develop

# После стабилизации сливаем в main и develop
$ git checkout main
$ git merge --no-ff release/1.2.0
$ git tag -a v1.2.0 -m "Release version 1.2.0"

$ git checkout develop
$ git merge --no-ff release/1.2.0
```

**Hotfix branches** — это экстренные исправления для production. Создаются от main, после исправления сливаются и в main, и в develop.

```ruby
# Критический баг в production
$ git checkout -b hotfix/1.2.1 main

# После исправления
$ git checkout main
$ git merge --no-ff hotfix/1.2.1
$ git tag -a v1.2.1 -m "Hotfix version 1.2.1"

$ git checkout develop
$ git merge --no-ff hotfix/1.2.1
```

#### Преимущества и недостатки Git Flow

Git Flow даёт чёткую структуру. Всегда понятно, где какой код находится. Процесс релизов формализован. Можно одновременно поддерживать несколько версий продукта.

Но эта структура сложная. Много веток, много правил слияния. Для маленьких команд или проектов с continuous deployment это может быть избыточно. Процесс релиза занимает время.

### GitHub Flow: простота для веба

GitHub Flow — это радикальное упрощение Git Flow. Его создали в GitHub для своих нужд. Философия простая: если вы деплоите несколько раз в день, сложная структура веток не нужна.

#### Правила GitHub Flow

В GitHub Flow есть только одна постоянная ветка — main. Она всегда готова к deployment. Это железное правило: если код в main, его можно развернуть на production прямо сейчас.

Для любых изменений создаётся новая ветка от main. Название должно быть описательным: fix-login-bug, add-payment-system, update-documentation.

Работа ведётся в созданной ветке. Коммиты делаются часто, с понятными сообщениями. Ветка регулярно обновляется изменениями из main.

Когда работа готова, создаётся Pull Request. Это сигнал для code review. Другие разработчики проверяют код, оставляют комментарии, предлагают улучшения.

После одобрения PR и прохождения всех тестов, ветка сливается в main. Deploy происходит автоматически или по кнопке.

```csharp
# Типичный workflow в GitHub Flow
$ git checkout -b add-search-feature
# ... работа над функцией ...
$ git push origin add-search-feature
# Создаём PR через интерфейс GitHub
# После review и одобрения - merge в main
# Автоматический deploy
```

#### Когда работает GitHub Flow

GitHub Flow отлично подходит для веб-приложений с continuous deployment. Когда можно быстро откатить изменения. Когда нет необходимости поддерживать несколько версий одновременно.

Но для десктопных приложений или библиотек это может не подойти. Там нужны чёткие версии и более сложный процесс релизов.

### Trunk-Based Development: ещё проще

Trunk-Based Development (TBD) — это предельное упрощение. Все работают прямо в main (trunk) ветке или в очень короткоживущих feature ветках.

#### Принципы Trunk-Based

Главный принцип — минимизировать время жизни веток. В идеале, изменения попадают в trunk в течение одного дня. Максимум — несколько дней для сложных задач.

Вместо долгоживущих feature веток используются feature flags (feature toggles). Новая функциональность добавляется в код, но скрыта за флагом. Код попадает в production выключенным.

```kotlin
// Пример feature flag
if (featureFlags.isEnabled('new-search')) {
    // Новый поиск
    return newSearchAlgorithm(query);
} else {
    // Старый поиск
    return oldSearchAlgorithm(query);
}
```

Это позволяет постоянно интегрировать код, избегая больших merge конфликтов. Когда функция готова, просто включается флаг.

#### Требования для Trunk-Based

TBD требует высокой дисциплины. Нужны отличные автоматические тесты — каждый commit должен быть рабочим. CI/CD должен быть быстрым и надёжным.

Команда должна быть опытной. Junior разработчики могут случайно сломать production. Нужна культура быстрого исправления проблем.

Feature flags добавляют сложность. Нужно управлять ими, вовремя удалять старый код. Тестирование усложняется — нужно проверять разные комбинации флагов.

### Сравнение стратегий

Git Flow подходит для проектов с редкими релизами. Когда нужно поддерживать несколько версий. Когда важен формальный процесс подготовки релизов. Примеры: корпоративное ПО, мобильные приложения, desktop программы.

GitHub Flow хорош для веб-проектов с частыми деплоями. Когда можно быстро откатиться. Когда команда небольшая и процессы должны быть простыми. Примеры: веб-сервисы, SaaS продукты, внутренние инструменты.

Trunk-Based Development для опытных команд с отличными практиками. Когда скорость важнее формальных процессов. Когда есть инфраструктура для feature flags. Примеры: Google, Facebook, большие веб-платформы.

### Адаптация под свой проект

Не обязательно следовать стратегии догматично. Многие команды адаптируют их под свои нужды.

Можно взять Git Flow, но убрать develop ветку. Или использовать GitHub Flow, но добавить release ветки для подготовки версий. Или Trunk-Based, но с обязательными PR для junior разработчиков.

Важно, чтобы вся команда понимала и следовала выбранной стратегии. Документируйте процесс. Обсуждайте, что работает, а что нет. Эволюционируйте стратегию по мере роста проекта.

### Переход между стратегиями

Проекты растут и меняются. Стартап может начать с GitHub Flow, а потом перейти на Git Flow, когда появятся корпоративные клиенты с требованиями к версионированию.

Или наоборот — большая компания может упростить процессы, переходя от Git Flow к Trunk-Based для ускорения разработки.

Переход требует планирования. Нельзя просто объявить новые правила. Нужно обучить команду, адаптировать CI/CD, изменить привычки.

## Итог

Стратегия ветвления — это не технический вопрос, а организационный. Git Flow даёт структуру и предсказуемость ценой сложности. GitHub Flow упрощает процесс для быстрых релизов. Trunk-Based минимизирует накладные расходы для опытных команд.

Выбор зависит от типа продукта, размера команды, частоты релизов и культуры разработки. Начните с простого — можно всегда усложнить. Но помните: лучшая стратегия та, которой следует вся команда. Консистентность важнее идеальности.
