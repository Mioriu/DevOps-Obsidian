Представьте, что вам нужно найти точное состояние кода, которое было отправлено клиенту полгода назад. Или откатиться к последней стабильной версии после неудачного деплоя. Git-теги решают эту задачу, создавая неизменяемые метки для важных моментов в истории проекта. Правильное использование тегов превращает хаотичный процесс релизов в предсказуемую и управляемую систему.

### Что такое теги в Git

Тег — это именованная ссылка на конкретный коммит. В отличие от веток, которые двигаются вперёд с каждым новым коммитом, теги остаются на месте. Они как закладки в истории проекта, отмечающие важные моменты.

Теги обычно используются для обозначения релизов: v1.0.0, v2.1.3, release-2023-10-15. Но их можно использовать для любых важных точек: последняя рабочая версия перед большим рефакторингом, состояние кода для демонстрации, версия для аудита.

Важное свойство тегов — они не изменяются. Если v1.0.0 указывает на коммит abc123, он всегда будет указывать именно на него. Это даёт уверенность, что можно в любой момент получить точное состояние релиза.

### Два типа тегов

Git поддерживает два типа тегов: легковесные (lightweight) и аннотированные (annotated). Выбор между ними зависит от того, сколько информации нужно сохранить.

#### Легковесные теги

Легковесный тег — это просто имя для коммита. Никакой дополнительной информации не сохраняется. Это как простая закладка в книге.

```ruby
# Создать легковесный тег
$ git tag v1.0.0

# Создать тег для конкретного коммита
$ git tag v0.9.0 abc123def
```

Легковесные теги подходят для временных меток или личного использования. Например, чтобы отметить "последняя рабочая версия" перед экспериментами.

#### Аннотированные теги

Аннотированный тег — это полноценный объект в базе данных Git. Он содержит имя создателя, дату, сообщение и может быть подписан GPG-ключом.

```ruby
# Создать аннотированный тег
$ git tag -a v1.0.0 -m "First stable release"

# Создать тег с развёрнутым описанием
$ git tag -a v2.0.0
# Откроется редактор для написания описания релиза
```

Аннотированные теги — стандарт для релизов. Они сохраняют контекст: кто и когда создал релиз, что в него вошло. Это важно для истории проекта и аудита.

### Семантическое версионирование

Семантическое версионирование (SemVer) — это соглашение о том, как нумеровать версии. Формат простой: MAJOR.MINOR.PATCH (например, 2.1.3).

MAJOR версия увеличивается при несовместимых изменениях API. Если обновление сломает существующий код пользователей — это major версия. Переход с 1.x.x на 2.0.0 сигнализирует о серьёзных изменениях.

MINOR версия растёт при добавлении новой функциональности, совместимой с предыдущими версиями. Новые методы, параметры, возможности — всё это minor изменения. От 2.1.0 до 2.2.0.

PATCH версия для исправления багов, которые не меняют API. Безопасные обновления, которые только улучшают существующий код. От 2.1.3 до 2.1.4.

```bash
# Примеры версий и их значение
v1.0.0 - первый стабильный релиз
v1.0.1 - исправление багов
v1.1.0 - новые возможности, обратная совместимость
v2.0.0 - breaking changes, несовместимые изменения
```

### Работа с тегами

После создания тегов нужно уметь с ними работать: просматривать, отправлять на сервер, удалять при необходимости.

#### Просмотр тегов

```ruby
# Список всех тегов
$ git tag
v1.0.0
v1.0.1
v1.1.0
v2.0.0

# Теги по шаблону
$ git tag -l "v1.*"
v1.0.0
v1.0.1
v1.1.0

# Подробная информация о теге
$ git show v1.0.0
```

Команда `git describe` показывает, где вы находитесь относительно последнего тега. Это полезно для автоматической генерации версий для development сборок.

```ruby
$ git describe --tags
v1.2.0-14-g2fc4d8a
# Означает: 14 коммитов после тега v1.2.0, текущий коммит g2fc4d8a
```

#### Отправка тегов на сервер

Важно помнить: теги не отправляются автоматически при push. Их нужно отправлять явно.

```perl
# Отправить конкретный тег
$ git push origin v1.0.0

# Отправить все теги
$ git push origin --tags

# Отправить только аннотированные теги (рекомендуется)
$ git push origin --follow-tags
```

Опция `--follow-tags` отправляет только аннотированные теги, достижимые из отправляемых коммитов. Это безопаснее, чем отправлять все теги подряд.

#### Удаление тегов

Иногда тег создан по ошибке или с опечаткой. Его можно удалить, но с осторожностью.

```ruby
# Удалить локальный тег
$ git tag -d v1.0.0

# Удалить тег на сервере
$ git push origin --delete v1.0.0
# или старый синтаксис
$ git push origin :refs/tags/v1.0.0
```

Никогда не удаляйте и не перемещайте опубликованные теги релизов. Пользователи могут зависеть от них. Если нужно исправить проблемный релиз — создайте новую patch-версию.

### Стратегии управления релизами

Существует несколько подходов к организации релизов. Выбор зависит от типа проекта и команды.

#### Релизы из main ветки

Простейший подход — создавать теги прямо на main ветке. Подходит для проектов с continuous delivery, где main всегда готова к релизу.

```ruby
# Процесс релиза
$ git checkout main
$ git pull origin main
$ git tag -a v1.2.0 -m "Release version 1.2.0"
$ git push origin v1.2.0
```

#### Release branches

Для больших проектов часто создают отдельные ветки для подготовки релизов. Это позволяет стабилизировать версию, пока разработка новых фич продолжается в main.

```ruby
# Создание release ветки
$ git checkout -b release/1.2.0 main

# Только багфиксы в этой ветке
$ git cherry-pick abc123  # критический фикс из main

# После стабилизации
$ git tag -a v1.2.0 -m "Release version 1.2.0"
$ git push origin v1.2.0
```

#### Hotfix releases

Когда нужно срочно исправить баг в production, создают hotfix от последнего тега.

```ruby
# Создать ветку от тега
$ git checkout -b hotfix/1.2.1 v1.2.0

# Исправить баг
$ git commit -m "Fix critical security issue"

# Создать новый тег
$ git tag -a v1.2.1 -m "Hotfix: security patch"
```

### Автоматизация релизов

Ручное создание релизов подвержено ошибкам. Автоматизация делает процесс надёжным и повторяемым.

#### Changelog generation

Из истории коммитов можно автоматически генерировать changelog. Для этого нужны хорошие commit messages.

```perl
# Генерация changelog между тегами
$ git log v1.1.0..v1.2.0 --pretty=format:"- %s" > CHANGELOG.md

# Или с группировкой по типам
$ git log v1.1.0..v1.2.0 --grep="^feat:" --pretty=format:"- %s"
$ git log v1.1.0..v1.2.0 --grep="^fix:" --pretty=format:"- %s"
```

#### CI/CD интеграция

Современные CI/CD системы умеют автоматически создавать релизы при появлении новых тегов.

```yaml
# GitHub Actions пример
name: Release
on:
  push:
    tags:
      - 'v*'

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Build release artifacts
        run: npm run build
      - name: Create GitHub Release
        uses: actions/create-release@v1
        with:
          tag_name: ${{ github.ref }}
          release_name: Release ${{ github.ref }}
          draft: false
```

### Работа с тегами в команде

В команде важно договориться о правилах работы с тегами. Кто может создавать теги релизов — обычно это ответственность team lead или release manager. Это предотвращает хаос с версиями.

Формат версий должен быть единым для всех проектов компании. Если один проект использует v1.0.0, а другой — release-2023-10, это создаёт путаницу.

Документируйте процесс релиза. Чеклист помогает не забыть важные шаги: прогнать тесты, обновить документацию, создать тег, оповестить команду.

### Теги для разных типов проектов

Библиотеки и фреймворки строго следуют SemVer. Пользователи полагаются на версионирование для управления зависимостями. Нарушение SemVer может сломать чужие проекты.

Веб-приложения часто используют даты в тегах: v2023.10.15. Это понятно бизнесу и упрощает коммуникацию о релизах.

Мобильные приложения могут иметь отдельную нумерацию для маркетинга (2.0) и техническую для разработки (2.0.0-build.123).

### Полезные практики

Всегда тестируйте код перед созданием тега. Тег должен указывать на рабочее состояние. Сломанный релиз подрывает доверие к системе версионирования.

Ведите CHANGELOG.md файл. Автоматическая генерация — это хорошо, но ручное описание важных изменений понятнее для пользователей.

Используйте pre-release версии для тестирования: v1.0.0-beta.1, v1.0.0-rc.1. Это сигнализирует, что версия не финальная.

Создавайте теги только от проверенных коммитов. Не создавайте тег от последнего коммита в пятницу вечером — дайте коду "отлежаться".

## Итог

Теги превращают непрерывный поток коммитов в управляемые версии. Они создают стабильные точки отсчёта, к которым можно вернуться в любой момент. Семантическое версионирование делает номера версий информативными, сообщая о характере изменений. Правильное использование тегов вместе с автоматизацией делает процесс релизов предсказуемым и надёжным. Помните: тег — это обещание пользователям, что эта версия протестирована и готова к использованию. Относитесь к созданию тегов ответственно.
