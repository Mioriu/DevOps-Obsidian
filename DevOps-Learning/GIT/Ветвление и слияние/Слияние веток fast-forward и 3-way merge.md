После работы в отдельной ветке возникает необходимость интегрировать изменения обратно в основную линию разработки. Git предоставляет механизм слияния (merge), который объединяет истории двух веток. Понимание типов слияния критически важно для эффективной работы с Git.

### Концепция слияния веток

Слияние в Git — это способ объединения двух или более историй разработки. При слиянии Git анализирует изменения в обеих ветках и создаёт новое состояние, включающее модификации из всех источников.

Важно понимать, что Git не просто копирует изменения из одной ветки в другую. Система анализирует историю коммитов, находит общего предка веток и определяет оптимальный способ объединения изменений. Это обеспечивает сохранение полной истории разработки и контекста каждого изменения.

Существует два основных типа слияния: fast-forward (быстрая перемотка) и three-way merge (трёхстороннее слияние). Выбор типа определяется автоматически на основе истории веток.

### Fast-forward слияние

Fast-forward — самый простой тип слияния, возможный когда целевая ветка не содержит новых коммитов после точки ответвления. В этом случае Git просто перемещает указатель ветки вперёд по истории.

Рассмотрим ситуацию: от ветки main создана ветка feature, в которой сделано несколько коммитов. Если в main не было новых коммитов после создания feature, история выглядит линейно:

```less
main:    A---B
              \
feature:       C---D---E
```

При слиянии feature в main происходит fast-forward:

```ruby
$ git checkout main
$ git merge feature
Updating b1a2c3d..e5f6a7b
Fast-forward
 file1.txt | 10 ++++++++++
 file2.txt |  5 +++++
 2 files changed, 15 insertions(+)
```

После слияния обе ветки указывают на один коммит:

```lua
main:    A---B---C---D---E
              \         /
feature:       ---------
```

Fast-forward слияние не создаёт новый коммит слияния — история остаётся линейной. Это преимущество с точки зрения чистоты истории, но недостаток с точки зрения отслеживания, какие именно изменения пришли из отдельной ветки.

#### Предотвращение fast-forward

Иногда требуется явно зафиксировать факт слияния в истории. Флаг `--no-ff` заставляет Git создать коммит слияния даже при возможности fast-forward:

```sql
$ git merge --no-ff feature
```

Это создаёт явную точку в истории, показывающую интеграцию функциональности. Многие команды используют этот подход для сохранения информации о том, какие коммиты относились к конкретной задаче.

### Three-way merge (трёхстороннее слияние)

Когда обе ветки развивались независимо после точки расхождения, fast-forward невозможен. Git выполняет трёхстороннее слияние, анализируя три точки: общего предка и конечные состояния обеих веток.

Типичная ситуация выглядит так:

```css
          C---D---E  feature
         /
    A---B---F---G    main
```

Обе ветки имеют уникальные коммиты после точки B. При слиянии Git:

1. Находит общего предка (коммит B)
2. Определяет изменения в feature (B→E)
3. Определяет изменения в main (B→G)
4. Объединяет оба набора изменений
5. Создаёт новый коммит слияния

```ruby
$ git checkout main
$ git merge feature
Merge made by the 'ort' strategy.
 feature.txt | 25 +++++++++++++++++++++++++
 1 file changed, 25 insertions(+)
```

Результирующая история:

```css
          C---D---E
         /         \
    A---B---F---G---H
```

Коммит H — это merge commit, имеющий двух родителей: G (из main) и E (из feature). Такой коммит сохраняет полную историю обеих веток.

### Стратегии слияния

Git поддерживает несколько стратегий слияния для различных сценариев. Стратегия по умолчанию (ort с версии 2.33, recursive в более ранних) подходит для большинства случаев.

Стратегия **ours** создаёт коммит слияния, но полностью игнорирует изменения из сливаемой ветки. Используется для закрытия старых веток с сохранением истории:

```ruby
$ git merge -s ours obsolete-feature
```

Стратегия **octopus** позволяет слить более двух веток одновременно. Git автоматически выбирает эту стратегию при указании нескольких веток.

### Процесс слияния

Стандартный процесс слияния включает несколько этапов. Сначала необходимо переключиться на целевую ветку — ту, в которую будут интегрированы изменения. Затем выполняется команда merge с указанием исходной ветки.

Перед слиянием рекомендуется убедиться в чистоте рабочей директории. Незафиксированные изменения могут помешать процессу слияния или привести к их потере.

После успешного слияния Git автоматически создаёт коммит (при three-way merge) или перемещает указатель ветки (при fast-forward). В случае конфликтов процесс приостанавливается для ручного разрешения.

### Просмотр результатов слияния

Для анализа выполненных слияний полезны несколько команд Git. Опция `--graph` команды log визуализирует историю слияний:

```1c
$ git log --graph --oneline
*   a1b2c3d (HEAD -> main) Merge branch 'feature'
|\  
| * e5f6g7h Add new feature
| * i9j0k1l Initial feature work
* | m2n3o4p Fix bug in main
|/  
* q5r6s7t Common ancestor
```

Команда `git show` для коммита слияния показывает изменения относительно всех родителей. Флаг `--first-parent` ограничивает просмотр только основной линией разработки, игнорируя боковые ветки.

### Отмена слияния

Если слияние привело к нежелательным результатам, его можно отменить. Для неопубликованных коммитов используется `git reset`:

```lua
$ git reset --hard HEAD~1
```

Для опубликованных коммитов безопаснее использовать `git revert`, создающий новый коммит с обратными изменениями:

```ruby
$ git revert -m 1 HEAD
```

Флаг `-m 1` указывает, какого родителя считать основным при отмене слияния.

### Практические рекомендации

Выбор между разрешением fast-forward и принудительным созданием merge commit зависит от принятой в команде стратегии. Fast-forward создаёт линейную историю, упрощающую навигацию. Явные merge commits сохраняют информацию о логической группировке изменений.

Перед слиянием полезно просмотреть входящие изменения командой `git log` с указанием диапазона коммитов. Это помогает понять объём и характер интегрируемых модификаций.

Регулярное слияние изменений из основной ветки в рабочую минимизирует конфликты при финальной интеграции. Долгоживущие ветки накапливают расхождения, усложняющие слияние.

## Итог

Слияние веток — фундаментальная операция Git, обеспечивающая интеграцию параллельных линий разработки. Fast-forward слияние сохраняет линейную историю при отсутствии расхождений. Three-way merge создаёт явный коммит слияния при наличии независимых изменений в обеих ветках. Понимание механизмов слияния позволяет эффективно управлять интеграцией изменений и поддерживать чистую историю проекта. В следующем уроке будет рассмотрена работа с конфликтами, неизбежно возникающими при слиянии.
