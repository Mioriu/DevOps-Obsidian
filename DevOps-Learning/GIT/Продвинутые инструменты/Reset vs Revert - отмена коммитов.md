Ошибки случаются. Неправильный коммит, преждевременный merge, случайно закоммиченный файл с паролями — все эти ситуации требуют отмены изменений. Git предоставляет два принципиально разных подхода: reset и revert. Выбор между ними — это выбор между изменением истории и её сохранением. Понимание различий между этими командами и их правильное применение — критически важный навык для безопасной работы с Git.

### Фундаментальное различие подходов

**Git reset** — это перемотка истории назад. Команда перемещает указатели веток на более ранние коммиты, эффективно удаляя коммиты из истории. Это мощный инструмент, но он изменяет историю проекта.

**Git revert** — это создание новой истории. Команда создаёт новый коммит, который отменяет изменения из указанного коммита. История сохраняется полностью, включая ошибочный коммит и его отмену.

```1c
# Исходная история
A---B---C---D (main)

# После git reset --hard B
A---B (main)
# Коммиты C и D исчезли из истории ветки

# После git revert C (начиная с исходной истории)
A---B---C---D---C' (main)
# C' - новый коммит, отменяющий изменения из C
```

### Git reset: машина времени для веток

Reset — это не одна команда, а семейство операций с разным уровнем воздействия. Понимание трёх режимов reset — ключ к его эффективному использованию.

#### Три режима reset

**--soft** — перемещает только указатель ветки. Изменения из отменённых коммитов остаются в индексе (staging area), готовые к новому коммиту:

```1c
# Отменить последний коммит, сохранив изменения в индексе
$ git reset --soft HEAD~1

# Что происходит:
# - Указатель ветки перемещается на один коммит назад
# - Изменения из отменённого коммита остаются в staging area
# - Рабочая директория не меняется

# Можно создать новый коммит с теми же изменениями
$ git commit -m "Better commit message"
```

**--mixed** (режим по умолчанию) — перемещает указатель ветки и очищает индекс. Изменения остаются в рабочей директории:

```ruby
# Отменить последние 2 коммита
$ git reset HEAD~2
# или явно
$ git reset --mixed HEAD~2

# Что происходит:
# - Указатель ветки перемещается на два коммита назад
# - Индекс очищается
# - Изменения остаются в рабочей директории как неиндексированные

# Теперь можно пересмотреть изменения и закоммитить по-новому
$ git add -p  # выборочно добавить изменения
$ git commit -m "Reorganized changes"
```

**--hard** — полный сброс. Перемещает указатель ветки, очищает индекс и рабочую директорию:

```perl
# ОПАСНО: полностью удалить последние 3 коммита
$ git reset --hard HEAD~3

# Что происходит:
# - Указатель ветки перемещается на три коммита назад
# - Индекс очищается
# - Рабочая директория возвращается к состоянию выбранного коммита
# - ВСЕ изменения из отменённых коммитов УДАЛЯЮТСЯ
```

#### Reset с указанием конкретного коммита

```shell
# Вернуться к конкретному коммиту
$ git reset --hard abc123def

# Вернуться к состоянию origin/main
$ git reset --hard origin/main

# Отменить все локальные коммиты и изменения
$ git reset --hard @{u}  # @{u} = upstream branch
```

#### Опасности reset

Reset изменяет историю, что создаёт проблемы для других разработчиков:

```ruby
# Вы сделали reset опубликованных коммитов
$ git reset --hard HEAD~2
$ git push --force origin main

# У коллеги в это время
$ git pull origin main
# Конфликт! Git не может совместить расходящиеся истории
```

### Git revert: безопасная отмена

Revert создаёт новый коммит, который отменяет изменения из указанного коммита. Это безопасно для публичной истории.

#### Базовое использование revert

```ruby
# Отменить последний коммит
$ git revert HEAD

# Отменить конкретный коммит
$ git revert abc123def

# Git откроет редактор для сообщения коммита:
Revert "Add broken feature"

This reverts commit abc123def456789...

# Результат: новый коммит, который отменяет изменения
```

#### Как работает revert технически

Revert вычисляет обратные изменения:

1. Определяет, какие изменения внёс целевой коммит
2. Создаёт обратные изменения (добавленное удаляет, удалённое восстанавливает)
3. Применяет эти изменения к текущему состоянию
4. Создаёт новый коммит

```1c
# Коммит добавил строку
+ console.log('Debug info');

# Revert создаст коммит, который удалит эту строку
- console.log('Debug info');
```

#### Revert нескольких коммитов

```ruby
# Отменить диапазон коммитов (от старого к новому)
$ git revert HEAD~3..HEAD

# Git создаст отдельный revert-коммит для каждого
# В обратном порядке (сначала самый новый)

# Отменить несколько коммитов одним revert-коммитом
$ git revert -n HEAD~3..HEAD
$ git commit -m "Revert feature X implementation"
```

#### Revert merge-коммитов

Merge-коммиты требуют особого подхода, так как имеют два родителя:

```ruby
# История с merge-коммитом
      C---D---E (feature)
     /         \
A---B-----------M---F (main)

# Отменить merge, сохранив изменения из main (parent 1)
$ git revert -m 1 M

# Отменить merge, сохранив изменения из feature (parent 2)
$ git revert -m 2 M
```

Важно: после revert merge-коммита повторный merge той же ветки не применит изменения автоматически.

### Сравнение подходов: когда что использовать

#### Используйте reset когда:

- Работаете с локальными коммитами, которые не опубликованы
- Нужно реорганизовать недавнюю работу перед публикацией
- Исправляете последние коммиты в личной ветке
- Синхронизируетесь с удалённой веткой (`git reset --hard origin/main`)

#### Используйте revert когда:

- Отменяете изменения в опубликованной истории
- Работаете в общей ветке (main, develop)
- Нужно сохранить полную историю изменений
- Отменяете изменения в середине истории

### Практические сценарии

#### Сценарий 1: Случайный коммит конфиденциальных данных

```shell
# Локальный коммит - используем reset
$ git reset HEAD~1
$ rm config/secrets.yml
$ echo "config/secrets.yml" >> .gitignore
$ git add .gitignore
$ git commit -m "Add secrets to gitignore"

# Если уже опубликован - сложнее
$ git revert HEAD  # Отменить изменения
# НО: данные всё ещё в истории!
# Нужна полная очистка истории или ротация секретов
```

#### Сценарий 2: Неудачный merge

```shell
# Только что сделали merge
$ git merge feature/experimental
# Поняли, что не готово

# Если не опубликовано
$ git reset --hard HEAD~1

# Если опубликовано
$ git revert -m 1 HEAD
$ git push origin main
```

#### Сценарий 3: Реорганизация последних коммитов

```shell
# Серия мелких коммитов
$ git log --oneline -5
a5f4a0d Fix typo
d3e2f1g Add tests
b2c3d4e Fix bug in feature
e4f5g6h Implement feature
h7i8j9k Start feature

# Объединить в один
$ git reset --soft HEAD~5
$ git commit -m "Implement feature with tests and fixes"
```

### Восстановление после reset

Даже после `--hard` reset данные не удаляются немедленно. Git хранит историю всех операций в reflog.

#### Использование reflog

```perl
# Случайно сделали reset
$ git reset --hard HEAD~10
# Ой, слишком далеко!

# Смотрим историю операций
$ git reflog
abc123d HEAD@{0}: reset: moving to HEAD~10
def456e HEAD@{1}: commit: Important feature
ghi789f HEAD@{2}: commit: Critical bugfix

# Восстанавливаемся
$ git reset --hard HEAD@{1}
```

#### Восстановление конкретных файлов

```shell
# После reset --hard можно восстановить отдельные файлы
$ git checkout HEAD@{1} -- src/important-file.js
```

### Комбинирование подходов

Иногда нужно использовать обе команды:

```shell
# Отменили merge через revert
$ git revert -m 1 HEAD

# Позже хотим снова применить изменения из той ветки
# Сначала отменяем revert
$ git revert HEAD

# Теперь можно снова делать merge
$ git merge feature/branch
```

### Альтернативные подходы

#### Checkout для отдельных файлов

```shell
# Вернуть файл к состоянию из конкретного коммита
$ git checkout abc123 -- path/to/file.js
```

#### Clean для неотслеживаемых файлов

```ruby
# Reset не удаляет untracked файлы
$ git reset --hard HEAD
$ git clean -fd  # Удалить неотслеживаемые файлы и директории
```

#### Restore (новый синтаксис)

```shell
# Современная альтернатива для восстановления файлов
$ git restore --source=HEAD~2 path/to/file.js
```

### Правила безопасности

1. **Никогда не используйте reset для опубликованных коммитов**
2. **Всегда проверяйте git status перед reset --hard**
3. **Делайте backup важных веток перед экспериментами**
4. **Используйте revert для любых изменений в общих ветках**
5. **Помните про reflog как спасательный круг**

### Частые ошибки и их решения

#### Reset вместо revert в публичной ветке

```shell
# Ошибка: сделали reset и push --force
# Решение: восстановить из reflog и сделать правильно
$ git reflog show origin/main
$ git push --force origin abc123:main  # восстановить
$ git revert HEAD~3..HEAD  # сделать правильно
```

#### Потеря изменений после reset --hard

```shell
# Всегда можно создать backup перед опасными операциями
$ git branch backup/before-reset
$ git reset --hard HEAD~5
# Если что-то пошло не так
$ git checkout backup/before-reset
```

## Итог

Reset и revert — это два фундаментально разных подхода к отмене изменений в Git. Reset переписывает историю, перемещая указатели веток назад во времени — мощно, но опасно для общих веток. Revert сохраняет историю, создавая новые коммиты, которые отменяют старые — безопасно, но может усложнить историю. Выбор между ними определяется простым вопросом: опубликованы ли изменения? Для локальной работы reset даёт гибкость реорганизации истории. Для опубликованных изменений revert — единственный безопасный выбор. Помните: reflog — ваша страховка при работе с reset, но лучше семь раз отмерить, прежде чем использовать `--hard`.
