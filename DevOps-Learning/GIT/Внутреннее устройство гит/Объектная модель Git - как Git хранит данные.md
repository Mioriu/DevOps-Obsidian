Git часто называют "глупой системой хранения контента с версионированием". Это не оскорбление, а комплимент простоте и элегантности его дизайна. В основе Git лежит удивительно простая модель: всё является объектом, у каждого объекта есть уникальный идентификатор, объекты неизменяемы. Из этих простых принципов вырастает вся мощь Git. Понимание объектной модели — это ключ к мастерству в Git. Когда вы знаете, как Git хранит данные, команды перестают быть магией, а проблемы становятся решаемыми логически. Этот урок приоткроет завесу тайны над внутренним устройством Git.

### Философия хранения данных в Git

Прежде чем погружаться в детали, важно понять философские принципы, заложенные в основу Git.

#### Content-addressable storage

Git использует content-addressable storage — хранилище с адресацией по содержимому. Это означает, что адрес (имя) объекта вычисляется из его содержимого. Измените хоть один байт — получите совершенно другой адрес.

Представьте библиотеку, где книги расставлены не по алфавиту или тематике, а по уникальному коду, вычисленному из содержания книги. Две абсолютно одинаковые книги будут иметь один код и храниться в одном месте. Измените одну букву — книга получит новый код и новое место.

Это даёт Git суперспособности:

- **Дедупликация** — одинаковые файлы хранятся только один раз
- **Целостность** — невозможно изменить данные незаметно
- **Простота** — нужен только хеш, чтобы найти любой объект

#### Immutability (неизменяемость)

Объекты в Git неизменяемы. Однажды созданный объект нельзя изменить. Можно создать новый объект с изменениями, но старый останется нетронутым.

Это как фотографии: вы не можете изменить прошлое, но можете сделать новую фотографию. Каждый коммит — это снимок вашего проекта в определённый момент времени, и этот снимок останется неизменным навсегда.

#### Directed Acyclic Graph (DAG)

Коммиты в Git образуют направленный ациклический граф. Каждый коммит знает своих родителей, но родители не знают о детях. Это позволяет истории разветвляться и сливаться, но не позволяет создавать циклы.

### Четыре типа объектов

В Git всего четыре типа объектов. Из этих простых кирпичиков строится вся сложность системы контроля версий.

#### Blob (Binary Large Object)

**Blob** — это содержимое файла. Просто байты, без имени, без метаданных, без структуры. Blob не знает, как он называется или где находится в файловой системе.

Представьте blob как запечатанный конверт с содержимым файла. На конверте написан только его хеш — уникальный идентификатор, вычисленный из содержимого. Два файла с одинаковым содержимым будут представлены одним blob, даже если у них разные имена или они находятся в разных директориях.

Важное следствие: переименование файла без изменения содержимого не создаёт новый blob. Git эффективно хранит данные, не дублируя одинаковое содержимое.

#### Tree (дерево)

**Tree** — это снимок директории. Tree содержит список записей, каждая из которых включает:

- Режим (права доступа)
- Тип (blob для файлов, tree для поддиректорий)
- SHA-1 хеш объекта
- Имя файла или директории

Tree можно представить как оглавление книги. Оно не содержит сам текст глав (это делают blob), но говорит, где что находится. Tree может ссылаться на blob (файлы) и другие tree (поддиректории), создавая иерархическую структуру.

Важный момент: tree тоже имеет хеш, вычисленный из его содержимого. Если изменится любой файл в директории, изменится хеш blob, что изменит содержимое tree, что изменит хеш tree. Это каскадное изменение хешей обеспечивает целостность всей структуры.

#### Commit (коммит)

**Commit** — это снимок всего проекта в определённый момент времени плюс метаданные. Каждый commit содержит:

- Ссылку на tree (состояние проекта)
- Ссылки на родительские commits (историю)
- Автора (кто создал изменения)
- Committer (кто создал commit)
- Временные метки
- Сообщение commit

Commit — это как страница в дневнике проекта. Она фиксирует не только что было (tree), но и контекст: кто, когда, зачем, и что было до этого (родители).

У обычного commit один родитель. У merge commit — два или более. У первого commit в репозитории родителей нет. Эта цепочка родителей и создаёт историю проекта.

#### Tag (аннотированный тег)

**Tag** — это именованная ссылка на объект (обычно commit) с дополнительными метаданными. Аннотированный tag содержит:

- Ссылку на объект
- Имя тега
- Tagger (кто создал)
- Дату создания
- Сообщение
- Опционально: GPG подпись

Tag — это как закладка в книге истории проекта. Он отмечает важные моменты: релизы, вехи разработки, стабильные версии.

### SHA-1 и целостность данных

Каждый объект в Git идентифицируется SHA-1 хешем — 40-символьной шестнадцатеричной строкой. SHA-1 вычисляется из содержимого объекта, включая его тип и размер.

#### Почему именно SHA-1?

SHA-1 был выбран за баланс свойств:

- **Криптографическая стойкость** — сложно создать коллизию намеренно
- **Распределённость** — хеши равномерно распределены в пространстве
- **Скорость** — быстрое вычисление на любом железе
- **Размер** — 160 бит достаточно для уникальности

Важно: Git использует SHA-1 не для безопасности, а для целостности. Если кто-то изменит файл в истории, изменятся все хеши от этой точки до настоящего, что сразу будет заметно.

#### Вероятность коллизий

Теоретически два разных объекта могут иметь одинаковый хеш. На практике вероятность настолько мала, что ей можно пренебречь. Нужно около 10²³ объектов, чтобы вероятность коллизии достигла 50%. Для сравнения: в репозитории Linux около 10⁶ объектов.

### Как объекты связаны между собой

Объекты в Git образуют граф, где узлы — это объекты, а рёбра — ссылки между ними.

#### Пример структуры

Представим простой проект:

```css
myproject/
├── README.md
└── src/
    └── main.py
```

После коммита Git создаст:

1. Blob для README.md
2. Blob для main.py
3. Tree для директории src/ (ссылается на blob main.py)
4. Tree для корневой директории (ссылается на blob README.md и tree src/)
5. Commit (ссылается на корневой tree)

Каждый объект знает только о тех объектах, на которые ссылается. Blob не знает, в каких tree он используется. Tree не знает, какие commit на него ссылаются. Это односторонние связи.

#### Переиспользование объектов

Если в следующем коммите изменится только main.py:

- Создастся новый blob для main.py
- Создастся новый tree для src/ (теперь ссылается на новый blob)
- Создастся новый корневой tree (ссылается на старый blob README.md и новый tree src/)
- Создастся новый commit

README.md не изменился, поэтому его blob переиспользуется. Это экономит место и время.

### Структура .git директории

Вся магия Git происходит в директории .git. Понимание её структуры помогает понять, как работает Git.

#### objects/ — база данных объектов

Директория objects/ содержит все объекты Git. Для оптимизации объекты распределены по поддиректориям: первые 2 символа хеша становятся именем директории, остальные 38 — именем файла.

Например, объект с хешом `89abcdef...` будет храниться в `objects/89/abcdef...`

Объекты хранятся в сжатом виде (zlib compression). Это экономит место, но делает их нечитаемыми напрямую.

#### refs/ — ссылки

Люди плохо запоминают хеши. Refs (references) дают человеческие имена объектам:

- **refs/heads/** — локальные ветки
- **refs/remotes/** — удалённые ветки
- **refs/tags/** — теги

Каждый ref — это просто файл, содержащий SHA-1 хеш объекта.

#### HEAD — текущая позиция

HEAD — специальный ref, указывающий на текущую позицию в истории. Обычно HEAD указывает на ветку (symbolic ref), но может указывать и напрямую на commit (detached HEAD).

#### index — промежуточная область

Index (или staging area) — это бинарный файл, содержащий снимок следующего коммита. Когда вы делаете `git add`, информация о файле добавляется в index.

#### config — настройки

Локальные настройки репозитория. Переопределяют глобальные настройки из ~/.gitconfig.

#### hooks/ — скрипты автоматизации

Скрипты, выполняемые при определённых событиях Git.

### Pack файлы и оптимизация хранения

Хранить каждую версию каждого файла полностью было бы расточительно. Git использует умные оптимизации.

#### Loose objects vs Pack files

Изначально объекты хранятся как отдельные файлы (loose objects). Периодически Git упаковывает их в pack файлы — высокоэффективный формат хранения.

Pack файлы используют дельта-компрессию: вместо хранения полных версий файла, хранится одна версия и дельты (различия) для других версий. Git автоматически выбирает оптимальную базовую версию и порядок дельт.

#### Сборка мусора

Git периодически запускает сборку мусора (gc), которая:

- Упаковывает loose objects в pack файлы
- Удаляет недостижимые объекты
- Оптимизирует pack файлы
- Обновляет различные кеши

### Практические следствия объектной модели

Понимание объектной модели объясняет многие особенности Git.

#### Почему ветки легковесны

Ветка — это просто файл с хешем коммита. Создание ветки — это создание файла размером 41 байт. Никакого копирования данных не происходит.

#### Почему merge сохраняет историю

Merge commit имеет несколько родителей, сохраняя связь с обеими ветками. История не теряется, она объединяется.

#### Почему rebase переписывает историю

Изменение родителя коммита меняет его хеш. Изменение хеша коммита меняет хеш всех последующих коммитов. Поэтому rebase создаёт новые коммиты, а не изменяет существующие.

#### Почему Git быстрый

Большинство операций работают с локальной базой данных объектов. Сравнение версий — это сравнение хешей. Переключение веток — это обновление файлов до состояния, описанного в tree.

### Исследование объектной модели

Git предоставляет команды для изучения объектов:

```applescript
# Показать тип объекта
git cat-file -t 

# Показать содержимое объекта
git cat-file -p 

# Показать размер объекта
git cat-file -s 

# Список всех объектов
git rev-list --objects --all
```

Эти команды — ваш микроскоп для изучения внутренностей Git.

## Итог

Объектная модель Git элегантна в своей простоте. Четыре типа объектов — blob, tree, commit, tag — создают всю сложность системы контроля версий. Content-addressable storage обеспечивает целостность и эффективность. Неизменяемость объектов гарантирует, что история остаётся историей. SHA-1 хеши служат одновременно адресами и контрольными суммами. Понимание этой модели превращает Git из чёрного ящика в прозрачный и логичный инструмент. Когда вы знаете, что происходит под капотом, вы можете использовать Git эффективнее, диагностировать проблемы быстрее и даже создавать свои инструменты. Объектная модель — это фундамент, на котором построено всё остальное в Git.
