## Манифест целиком

За два урока манифесты уже встречались дважды, пора разобрать их. Манифест – это описание одного объекта Kubernetes в YAML. Команда `apply` отправляет его на API server, и с этого момента описание становится желаемым состоянием, которое кластер поддерживает. Структура у любого манифеста одна и та же, четыре верхнеуровневых поля.

Поле Что задает `apiVersion` Версия API, в которой описан этот тип объекта `kind` Тип объекта – `Pod`, `Deployment`, `Service` и десятки других `metadata` Имя, метки, аннотации – все, что идентифицирует объект `spec` Желаемое состояние, содержимое зависит от типа

Пара `kind` + `metadata.name` определяет объект в кластере. Повторный `apply` файла с тем же типом и именем обновляет существующий объект, с другим именем – создает новый. Это поведение уже знакомо по работе с Deployment, обновление образа было именно таким `apply` поверх существующего.

## apiVersion и группы API

Поле `apiVersion` выглядит непонятно. У пода это `v1`, у Deployment – `apps/v1`, дальше встретятся `networking.k8s.io/v1` и другие. Логика простая, API Kubernetes разбит на группы. Базовые объекты – поды, сервисы, конфиги – живут в core-группе, ее имя пустое, поэтому пишется просто `v1`. Объекты для приложений собраны в группе `apps`, сетевые – в `networking.k8s.io`, и запись складывается как `группа/версия`.

Запоминать соответствия наизусть не нужно. У kubectl есть команда, которая выводит все типы объектов кластера вместе с их группами:

kubectl api-resources

Копировать

```
NAME          SHORTNAMES   APIVERSION   NAMESPACED   KIND
pods          po           v1           true         Pod
services      svc          v1           true         Service
deployments   deploy       apps/v1      true         Deployment
replicasets   rs           apps/v1      true         ReplicaSet
```

Заодно в колонке `SHORTNAMES` видны сокращения – `kubectl get po`, `kubectl get deploy` и `kubectl get rs` означают то же самое, что полные имена, и в работе все пишут именно так.

## kubectl explain

Второй вопрос при написании манифеста – какие поля бывают внутри `spec` и что они значат. Для этого есть встроенная документация:

Bash

Копировать

```bash
kubectl explain pod.spec
kubectl explain deployment.spec.strategy
kubectl explain pod.spec.containers.resources
```

Команда принимает путь до любого поля через точку и выводит его описание, тип и вложенные поля. Флаг `--recursive` разворачивает все дерево полей сразу:

kubectl explain deployment.spec --recursive

Связка `api-resources` + `explain` закрывает вопрос как пишутся команды. Документация при этом всегда соответствует версии вашего кластера, в отличие от случайной статьи или нейронки.

## Несколько объектов в одном файле

YAML позволяет складывать несколько документов в один файл через разделитель `---`. Для Kubernetes это стандартный прием, связанные объекты приложения держат вместе:

YAML

Копировать

```yaml
# app.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  # ...
---

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  # ...
```

Один `apply -f app.yaml` создаст оба объекта. Второй вариант организации – отдельный файл на объект и применение целой директории:

kubectl apply -f manifests/

Все `.yaml` из директории применятся разом. Оба подхода рабочие, выбор зависит от размера проекта. Пока объектов несколько – удобен один файл с `---`, когда их десятки – раскладка по файлам с понятными именами вроде `deployment.yaml`, `service.yaml`, `configmap.yaml`.

## Ловушки YAML

Правила YAML те же, что были в Ansible, отступы пробелами и строгая вложенность. Но у манифестов есть пара собственных классических ловушек.

Первая – типы значений. Поля объектов типизированы, и YAML иногда угадывает тип не так, как нужно. Самый частый случай – переменные окружения, их значения обязаны быть строками:

YAML

Копировать

```yaml
env:
  - name: PORT
    value: "8080"      # правильно, строка
  - name: DEBUG
    value: "false"     # правильно, строка
```

Без кавычек `8080` станет числом, а `false` – булевым значением, и `apply` упадет с ошибкой про неверный тип.

Вторая ловушка – списки против словарей. `containers` это список, каждый элемент начинается с дефиса. `matchLabels` это словарь, дефисов нет. Пропущенный или лишний дефис меняет структуру документа, и ошибка от кластера придет не всегда понятная. Когда `apply` ругается на манифест странными словами, первым делом стоит проверить дефисы и отступы вокруг указанного поля.

## Labels

Теперь главная тема урока. **Метки (labels)** – произвольные пары ключ-значение в `metadata` объекта:

YAML

Копировать

```yaml
metadata:
  name: web
  labels:
    app: web
    environment: production
    team: backend
```

Ключи и значения придумываете вы, кластеру их смысл безразличен. Важно другое – **метки являются единственным механизмом группировки в Kubernetes**. Объекты в кластере не ссылаются друг на друга по именам и не содержат списков вида `мои поды такие-то`. Вместо этого объект несет на себе метки, а тот, кому нужно найти объекты, ищет по меткам. ReplicaSet находит свои поды по метке, и команда `get` фильтрует по меткам, и распределение трафика дальше в модуле будет строиться на метках.

Посмотреть метки можно флагом, а навесить и снять – командой `label`:

Bash

Копировать

```bash
kubectl get pods --show-labels
kubectl label pod web-7d4b9ccf94-fk2x8 debug=true     # навесить
kubectl label pod web-7d4b9ccf94-fk2x8 debug-          # снять (минус после ключа)
```

Императивное навешивание полезно для разовой пометки, постоянные метки живут в манифесте.

По ключам меток сложились соглашения. Минимальный рабочий набор – `app` с именем приложения, к нему по необходимости добавляются окружение, команда, компонент. У Kubernetes есть и официальный рекомендованный набор с префиксом `app.kubernetes.io/` – `name`, `instance`, `version`, `component`. Его проставляют инструменты и взрослые проекты, в учебных манифестах достаточно короткого `app`.

## Селекторы в командах

**Селектор** – выражение для выборки объектов по меткам. В kubectl это флаг `-l`, и он работает с любой командой над списками объектов:

Bash

Копировать

```bash
kubectl get pods -l app=web                       # поды с меткой app=web
kubectl get pods -l app=web,environment=production # обе метки сразу
kubectl get pods -l 'environment in (dev,staging)' # значение из списка
kubectl get pods -l app!=web                       # все, кроме
kubectl delete pods -l debug=true                  # удалить по выборке
```

Запятая означает «и», форма `in (...)` выбирает из нескольких значений. На пустом кластере польза неочевидна, но в реальном кластере сотни подов, и `get pods` без селектора превращается в простыню.

## Селекторы в объектах

Тот же механизм встроен в объекты. В манифесте Deployment селектор уже был:

YAML

Копировать

```yaml
spec:
  selector:
    matchLabels:
      app: web
```

`matchLabels` – простая форма, все перечисленные метки должны совпасть. Существует и выразительная форма `matchExpressions` с операторами `In`, `NotIn`, `Exists`:

YAML

Копировать

```yaml
spec:
  selector:
    matchExpressions:
      - key: app
        operator: In
        values: [web, web-canary]
```

На практике в Deployment почти всегда хватает `matchLabels`, про вторую форму достаточно знать, что она есть.

Общий принцип стоит сформулировать явно. Любой объект Kubernetes, которому нужно работать с группой других объектов, описывает эту группу селектором.

![Связь объектов через метки: selector Deployment и Service должны совпасть с labels подов, иначе связь рвется](https://prostodevops.ru/api/uploads/lessons/yaml-manifesty-s-nulya-01.webp)Связь объектов через метки: selector Deployment и Service должны совпасть с labels подов, иначе связь рвется

Не списком имен, не ссылками, а условием на метки. Группа при этом живая, объекты входят в нее и выходят из нее в момент изменения своих меток.

## Связь через метки вживую

Последнее утверждение легко проверить экспериментом. Берем Deployment `web` с тремя подами из прошлого урока и снимаем с одного пода метку `app`:

Bash

Копировать

```bash
kubectl label pod web-7d4b9ccf94-fk2x8 app-
kubectl get pods --show-labels
```

Копировать

```
NAME                   READY   STATUS    LABELS
web-7d4b9ccf94-fk2x8   1/1     Running   pod-template-hash=7d4b9ccf94
web-7d4b9ccf94-mq5zt   1/1     Running   app=web,pod-template-hash=7d4b9ccf94
web-7d4b9ccf94-w8jlp   1/1     Running   app=web,pod-template-hash=7d4b9ccf94
web-7d4b9ccf94-x4n7d   1/1     Running   app=web,pod-template-hash=7d4b9ccf94
```

Подов стало четыре. Под без метки выпал из селектора ReplicaSet, для контроллера подходящих подов осталось два, и он немедленно создал третий. Старый под при этом жив, но осиротел – никакой контроллер за ним больше не следит, тот самый голый под из второго урока. Связь `контроллер – его поды` оказалась не записью где-то в кластере, а живым вычислением селектора по текущим меткам.

## Annotations

Рядом с метками в `metadata` живут **аннотации** – тоже пары ключ-значение, но с другим назначением:

YAML

Копировать

```yaml
metadata:
  name: web
  labels:
    app: web
  annotations:
    kubernetes.io/change-cause: "update nginx to 1.27"
    company.io/oncall: "team-backend"
```

Разница в одном свойстве – по аннотациям нельзя выбирать, селекторы с ними не работают. Метки предназначены для выборки, поэтому их значения короткие и структурированные. Аннотации – для произвольной информации, в них кладут описания, контакты, ссылки на документацию, параметры для внешних инструментов. `change-cause` из урока про Deployment был именно аннотацией. Практическое правило выбора между ними – если по этому значению когда-нибудь понадобится фильтровать, это метка, все остальное – аннотация.

## dry-run и diff

Привычка проверять изменения до применения переезжает из прошлых модулей и сюда, инструменты встроены в kubectl:

Bash

Копировать

```bash
kubectl apply -f deployment.yaml --dry-run=server
kubectl diff -f deployment.yaml
```

Первая команда прогоняет манифест через все проверки API server без сохранения – синтаксис, типы полей, валидность селекторов, – и сообщает результат. Вторая показывает построчную разницу между объектом в кластере и вашим файлом, тот же формат, что `git diff`. Связка по смыслу повторяет `--check --diff` из Ansible и `terraform plan` – посмотреть глазами, что изменится, и только потом применять. Для манифестов на проде это такая же обязательная вещь.

## Генерация манифестов

Манифесты не пишут с чистого листа. Скелет генерируется самим kubectl – императивные команды принимают флаги `--dry-run=client -o yaml` и вместо создания объекта печатают его манифест:

kubectl create deployment web --image=nginx:1.25 --dry-run=client -o yaml > deployment.yaml

В файле окажется корректный каркас Deployment с правильными `apiVersion`, селектором и шаблоном – остается почистить пустые поля и дописать нужное. Это быстрее и надежнее, чем вспоминать структуру по памяти.

Второй источник – существующие объекты. `kubectl get deploy web -o yaml` выводит объект целиком, и его можно сохранить как основу. С одной оговоркой – в выводе будет служебный мусор, которому не место в манифесте: весь блок `status`, поля `creationTimestamp`, `resourceVersion`, `uid`, `managedFields`. Перед использованием как манифеста все это вычищается, в файле остается только то, что писали бы руками.
