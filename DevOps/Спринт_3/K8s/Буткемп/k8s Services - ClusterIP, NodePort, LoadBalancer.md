## Адреса подов ненадежны

После урока про Deployment в кластере работают три копии приложения, и у каждой свой IP из сети кластера. Попробуем этими адресами пользоваться – и сразу два тупика.

Первый – адреса живут до первого пересоздания. Под умер, ReplicaSet создал замену, у замены новый IP. Rolling update пересоздает все поды, и все адреса меняются разом. Прописать IP пода в конфиге другого приложения означает сломаться при первом же деплое.

Второй – копий несколько. Сегодня три, завтра после `kubectl scale` десять. Клиенту нужен один адрес, по которому он обращается к приложению, а не список из десяти, который к тому же постоянно устаревает.

В Compose эта задача решалась незаметно – контейнеры находили друг друга по имени сервиса, `db:5432` работал независимо от адресов. В Kubernetes для этого есть отдельный объект, и называется он так же.

## Service

**Service** – стабильная точка доступа к группе подов. У него есть постоянный IP-адрес и DNS-имя, которые не меняются всю жизнь объекта, а трафик с этого адреса распределяется по подам. Какие поды обслуживает сервис, задается селектором по меткам – механизмом из прошлого урока.

Связка получается такая. Deployment через свой селектор поддерживает нужное число подов с меткой. Service через свой селектор направляет на поды с этой же меткой трафик. Друг о друге эти два объекта не знают ничего, их соединяет только общая метка на подах. Поды приходят и уходят, а оба селектора вычисляются по живому состоянию – поэтому система не требует никакого ручного обновления связей.

У Service есть несколько типов, различаются они тем, откуда доступен адрес.

![Три типа Service: ClusterIP/NodePort/LoadBalancer и куда доходит трафик; kube-proxy подменяет адрес на живой под](https://prostodevops.ru/api/uploads/lessons/k8s-services-clusterip-nodeport-lb-01.webp)Три типа Service: ClusterIP/NodePort/LoadBalancer и куда доходит трафик; kube-proxy подменяет адрес на живой под

Разберем все три по очереди, начиная с типа по умолчанию.

## ClusterIP

**ClusterIP** – доступ изнутри кластера. Сервис получает виртуальный IP из специального диапазона, и этот адрес доступен любому поду на любой ноде, но не существует за пределами кластера.

YAML

Копировать

```yaml
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
```

Тип не указан, поэтому ClusterIP. В `selector` простая форма – метки, которые должны быть на подах, без `matchLabels`. А в `ports` два разных порта, и их легко перепутать.

Поле Что задает `port` Порт самого сервиса – куда обращаются клиенты `targetPort` Порт контейнера в поде – куда трафик уходит дальше

Здесь оба равны 80, но они независимы. Сервис может слушать 80, а контейнеры – 8080, тогда `port: 80` и `targetPort: 8080`. Применяем и смотрим:

Bash

Копировать

```bash
kubectl apply -f service.yaml
kubectl get services
```

Копировать

```
NAME         TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
kubernetes   ClusterIP   10.96.0.1       <none>        443/TCP   12d
web          ClusterIP   10.96.114.52    <none>        80/TCP    10s
```

Сервис `web` получил адрес `10.96.114.52`. Сервис `kubernetes` существует в любом кластере – это доступ к самому API server изнутри. Теперь самая информативная команда:

kubectl describe service web

Копировать

```
Name:              web
Selector:          app=web
IP:                10.96.114.52
Port:              <unset>  80/TCP
TargetPort:        80/TCP
Endpoints:         10.244.1.7:80,10.244.2.3:80,10.244.2.9:80
```

Строка `Endpoints` – сердце механизма. Это вычисленный по селектору список реальных адресов подов, и трафик с ClusterIP распределяется именно по нему. Эндпоинты существуют и как отдельный объект:

kubectl get endpoints web

Кластер пересчитывает этот список сам при каждом изменении подов. И в списке оказываются только живые поды – упавший выпадает из эндпоинтов, и трафик на него не идет.

## DNS-имя

IP сервиса стабилен, но руками его все равно никто не прописывает. У каждого сервиса есть DNS-имя, совпадающее с именем объекта, – за это отвечает `coredns`, который мелькал в выводе `kube-system` еще в уроке про архитектуру. Любой под кластера может обратиться к сервису просто по имени `web`. Полная форма имени выглядит как `web.default.svc.cluster.local`, где `default` – пространство имен, о них поговорим через урок, а внутри одного пространства хватает короткого имени.

В Compose приложение ходило в базу по адресу `db:5432`, и тот же конфиг продолжит работать в Kubernetes – достаточно, чтобы существовал Service с именем `db`, селектор которого указывает на поды базы. Имя сервиса в Kubernetes играет ту же роль, что имя сервиса в compose.yaml, только теперь за ним может стоять любое число подов на любых нодах.

## Проверка изнутри

ClusterIP снаружи недоступен, поэтому проверять его идем внутрь кластера. Поднимем временный под с шеллом:

kubectl run tmp --rm -it --image=busybox:1.36 -- sh

Флаг `--rm` удалит под после выхода – тот же прием, что у `docker run --rm`. Изнутри пода:

Shell

Копировать

```sh
wget -qO- http://web
wget -qO- http://10.96.114.52
```

Оба запроса возвращают страницу nginx. Имя отрезолвилось через DNS кластера, виртуальный IP сработал, трафик дошел до одного из трех подов. Если повторять запрос много раз и смотреть в логи подов, видно, что запросы расходятся по разным копиям – балансировка работает без какой-либо настройки.

## Под капотом

Виртуальность ClusterIP стоит понимать буквально. Этот адрес не принадлежит ни одной машине, на него нельзя сделать ping, у него нет сетевого интерфейса. Работает он через **kube-proxy** из урока про архитектуру. На каждой ноде kube-proxy поддерживает правила (iptables или IPVS), которые подменяют адрес назначения – пакет, отправленный на `10.96.114.52:80`, на лету переписывается на адрес одного из подов из списка эндпоинтов. Подмена происходит на той ноде, откуда ушел запрос, поэтому никакого центрального балансировщика в этой схеме нет, и точки отказа тоже.

Живость всей конструкции легко увидеть:

Bash

Копировать

```bash
kubectl scale deployment web --replicas=5
kubectl get endpoints web
```

Копировать

```
NAME   ENDPOINTS                                                     AGE
web    10.244.1.7:80,10.244.1.8:80,10.244.2.3:80 + 2 more...         15m
```

Эндпоинтов стало пять. Убьем под – через секунды список снова пересчитан, без единого действия с сервисом. Selector вычисляется по текущему состоянию, kube-proxy раскатывает свежие списки по нодам, и клиенты продолжают ходить по тому же имени `web`, не замечая ничего.

## NodePort

Внутреннего доступа мало, приложение нужно открывать наружу. Первый способ – тип **NodePort**:

YAML

Копировать

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080
```

NodePort открывает указанный порт **на каждой ноде кластера**. Запрос на `IP-любой-ноды:30080` попадает в сервис и дальше по обычной цепочке распределяется на поды – причем нода, принявшая запрос, и нода с подом могут быть разными машинами, kube-proxy дотащит трафик куда нужно.

kubectl get svc web

Копировать

```
NAME   TYPE       CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
web    NodePort   10.96.114.52   <none>        80:30080/TCP   5s
```

Диапазон для `nodePort` ограничен портами 30000–32767, и если поле не указать, порт выделится из диапазона случайно. ClusterIP при этом никуда не девается – NodePort работает поверх него, внутренний доступ по имени сохраняется.

Ограничения у типа очевидны из устройства. Порты странные, для пользователей адрес вида `203.0.113.5:30080` не годится. Адреса нод не предназначены быть публичной точкой входа – ноды добавляются, удаляются и меняют IP. И на входе нет распределения между нодами, клиент сам выбирает, в какую машину стучаться. Поэтому ниша NodePort – тестовые стенды, локальные кластеры и ситуации, когда перед кластером стоит свой внешний балансировщик, у которого ноды прописаны как бэкенды.

## LoadBalancer

Третий тип – для облачных кластеров:

YAML

Копировать

```yaml
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
```

При создании такого сервиса **cloud-controller-manager** – прослойка к API облака – заказывает у провайдера настоящий внешний балансировщик и направляет его на ноды кластера. Через минуту-другую у сервиса появляется внешний адрес:

kubectl get svc web

Копировать

```
NAME   TYPE           CLUSTER-IP     EXTERNAL-IP      PORT(S)        AGE
web    LoadBalancer   10.96.114.52   <pending>        80:31204/TCP   20s
web    LoadBalancer   10.96.114.52   84.201.158.77    80:31204/TCP   2m
```

`EXTERNAL-IP` сначала висит в `<pending>`, пока облако создает балансировщик, потом заполняется публичным адресом – и приложение доступно из интернета по нормальному порту. Внутри, как видно по `PORT(S)`, LoadBalancer построен поверх NodePort, а тот поверх ClusterIP, типы вложены друг в друга как матрешка.

Две оговорки. На кластере вне облака – на своем железе, в minikube – заказывать балансировщик не у кого, и `<pending>` останется навсегда; для локальной проверки внешнего доступа там используется NodePort. И вторая – каждый LoadBalancer-сервис означает отдельный платный балансировщик у провайдера. Поэтому в реальных системах внешних точек входа мало, обычно одна, а внутренние сервисы остаются ClusterIP – выставлять наружу базу или внутренний API не нужно ни технически, ни по соображениям безопасности.

## ExternalDNS

У LoadBalancer остается один ручной шаг. Сервис получил внешний IP, но пользователи ходят не по адресам, а по доменам – и запись `app.example.com → 84.201.158.77` кто-то должен создать у DNS-провайдера. Руками это делается один раз, а дальше начинаются сюрпризы: пересоздали сервис – балансировщик выдан заново, IP другой, запись устарела, сайт лежит при живом кластере.

Для автоматизации этого шага есть **ExternalDNS** – контроллер, который ставится в кластер отдельно и работает по принципу сверки. Желаемое имя задается аннотацией на сервисе:

YAML

Копировать

```yaml
metadata:
  annotations:
    external-dns.alpha.kubernetes.io/hostname: app.example.com
```

ExternalDNS отслеживает сервисы с такими аннотациями и через API DNS-провайдера создает и обновляет записи: появился внешний IP – появилась A-запись, сменился – запись обновилась, сервис удален – запись убрана. Поддерживаются десятки провайдеров, включая Cloudflare, Route 53 и Yandex Cloud DNS. В связке LoadBalancer + ExternalDNS публикация приложения целиком описывается манифестом: и балансировщик, и доменная запись появляются из YAML, без захода в консоль провайдера.

Не путайте с похожим по названию типом сервиса **ExternalName** – он решает обратную задачу. ExternalDNS публикует внутреннее наружу, а ExternalName дает внутреннее имя внешнему ресурсу:

YAML

Копировать

```yaml
apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  type: ExternalName
  externalName: rc1a-abc123.mdb.yandexcloud.net
```

Такой сервис – просто DNS-псевдоним внутри кластера. Селектора и эндпоинтов у него нет, обращение к `db` превращается в обращение к указанному внешнему имени. Типичный случай – managed-база за пределами кластера: приложения ходят на `db:5432`, как на обычный сервис, а куда это имя ведет, меняется в одном месте без правки конфигов.

## Какой тип когда

Тип Откуда доступен Типичное применение `ClusterIP` Только изнутри кластера Внутренние сервисы – базы, кэши, API между приложениями. Тип по умолчанию `NodePort` `IP-ноды:30000-32767` Тестовые стенды, локальные кластеры, кластер за своим балансировщиком `LoadBalancer` Внешний IP от облака Публичная точка входа в облачном кластере

Рабочее правило короткое. Все внутреннее – ClusterIP, и это подавляющее большинство сервисов. Наружу – LoadBalancer в облаке, NodePort на стендах. А полный пример связки выглядит так – приложение наружу, база только внутрь:

YAML

Копировать

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
---

apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  selector:
    app: db
  ports:
    - port: 5432
      targetPort: 5432
```

Приложение в подах ходит в базу по адресу `db:5432`, пользователи приходят на внешний IP балансировщика, и ни один реальный адрес пода нигде не прописан.

## Шпаргалка

Bash

Копировать

```bash
kubectl get services                        # список сервисов
kubectl describe service web                # детали, селектор, эндпоинты
kubectl get endpoints web                   # адреса подов за сервисом
kubectl run tmp --rm -it --image=busybox:1.36 -- sh   # временный под для проверки
kubectl expose deployment web --port=80     # создать сервис императивно
kubectl port-forward service/web 8080:80    # туннель до сервиса для отладки
kubectl delete service web                  # удалить сервис
```
