## Зачем нужен Deployment

Урок про поды закончился экспериментом с неприятным выводом. Удалили под – и никто его не пересоздал, потому что за голым подом не следит ни один контроллер. Желаемое состояние «копий приложения должно быть три» надо где-то хранить, и кто-то должен его постоянно сверять с реальностью.

Этим занимается **Deployment** – основной рабочий объект Kubernetes для приложений. В нем задается шаблон пода и число копий, а дальше кластер держит это состояние сам. Поды падают, ноды умирают, версии обновляются – Deployment продолжает приводить реальность к описанию. Подавляющее большинство того, что работает в кластерах, запущено именно через Deployment, и с этого урока поды руками мы больше не создаем.

## Манифест

YAML

Копировать

```yaml
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80
```

Четыре кита на месте, но есть отличия от манифеста пода. `apiVersion` теперь `apps/v1` – Deployment живет в другой группе API, в отличие от базовых объектов вроде пода. `kind: Deployment`. А внутри `spec` три ключевых поля.

Поле Что задает `replicas` Сколько копий пода должно работать `template` Шаблон пода – из чего штамповать копии `selector` По каким меткам Deployment узнает свои поды

Присмотритесь к `template`. Внутри него лежит знакомый манифест пода целиком – `metadata` с метками и `spec` с контейнерами, все из прошлого урока, только без имени и без `apiVersion`/`kind`. Имена подам Deployment придумает сам, а штамповать будет ровно по этому шаблону.

Поле `selector` требует отдельного внимания. В нем перечислены метки, по которым Deployment находит свои поды среди всех остальных, и `selector.matchLabels` обязан совпадать с метками в `template.metadata.labels`. Здесь и там стоит `app: web`. Если они разойдутся, `apply` завершится ошибкой – кластер откажется создавать контроллер, который штампует поды, не подпадающие под его же селектор. Подробно про механику меток будет отдельный урок, пока достаточно правила, что эти два места всегда совпадают.

Применяем и смотрим:

Bash

Копировать

```bash
kubectl apply -f deployment.yaml
kubectl get deployments
```

Копировать

```
NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    3/3     3            3           30s
```

Колонка `READY` показывает «работает/должно быть». `UP-TO-DATE` – сколько подов соответствует текущему шаблону, `AVAILABLE` – сколько доступно. Сейчас все три числа сходятся, желаемое состояние достигнуто. А вот сами поды:

kubectl get pods

Копировать

```
NAME                   READY   STATUS    RESTARTS   AGE
web-7d4b9ccf94-fk2x8   1/1     Running   0          45s
web-7d4b9ccf94-mq5zt   1/1     Running   0          45s
web-7d4b9ccf94-w8jlp   1/1     Running   0          45s
```

Три пода с именами вида `web-7d4b9ccf94-fk2x8`. Имя собрано из трех частей – имени Deployment, хэша шаблона и случайного суффикса. Про хэш в середине сейчас будет отдельный разговор.

## ReplicaSet

Между Deployment и подами есть еще один объект, и в выводе он уже засветился. Посмотрим:

kubectl get replicasets

Копировать

```
NAME             DESIRED   CURRENT   READY   AGE
web-7d4b9ccf94   3         3         3       2m
```

Это **ReplicaSet** – контроллер числа копий. Тот самый `7d4b9ccf94` из имен подов оказался именем ReplicaSet, точнее хэшем шаблона пода, который Deployment вычислил и вписал. Иерархия получается трехэтажная.

![Иерархия Deployment - ReplicaSet - Pods и self-healing: ReplicaSet пересоздает недостающие поды](https://prostodevops.ru/api/uploads/lessons/k8s-deployments-replicaset-scaling-01.webp)Иерархия Deployment - ReplicaSet - Pods и self-healing: ReplicaSet пересоздает недостающие поды

**ReplicaSet решает одну задачу** – чтобы подов конкретного шаблона было ровно `replicas` штук. Подов меньше – создать, больше – удалить лишние. Это и есть контроллер репликации из урока про архитектуру, его цикл сверки работает в `kube-controller-manager`. Но ReplicaSet ничего не понимает про версии и обновления. Один ReplicaSet всегда соответствует одной версии шаблона, отсюда и хэш в имени.

**Deployment управляет выше** – он создает ReplicaSet под текущий шаблон, а при изменении шаблона организует переход между старым и новым ReplicaSet.

Руками ReplicaSet не создают никогда. Это внутренний механизм Deployment, и знать о нем нужно для чтения вывода `get rs` и понимания обновлений, а не для написания манифестов. Принадлежность пода контроллеру, кстати, видна в `describe`:

kubectl describe pod web-7d4b9ccf94-fk2x8 | grep Controlled

Controlled By:  ReplicaSet/web-7d4b9ccf94

## Self-healing вживую

В прошлом уроке удаление пода было концом истории. Повторим эксперимент в новых условиях:

Bash

Копировать

```bash
kubectl delete pod web-7d4b9ccf94-fk2x8
kubectl get pods
```

Копировать

```
NAME                   READY   STATUS    RESTARTS   AGE
web-7d4b9ccf94-mq5zt   1/1     Running   0          5m
web-7d4b9ccf94-w8jlp   1/1     Running   0          5m
web-7d4b9ccf94-x4n7d   1/1     Running   0          3s
```

Подов снова три, и у одного из них возраст три секунды. ReplicaSet увидел расхождение – подов два, должно быть три – и создал замену. Удалять поды под Deployment можно совершенно спокойно, кластер воспринимает это как обычное расхождение и чинит его. Тот же механизм закрывает и смерть ноды из урока про архитектуру. Поды с умершей машины числятся за ReplicaSet, его желаемое состояние нарушено, и замены создаются на живых нодах.

Отсюда же одно следствие про отладку. Бороться с конкретным подом бессмысленно – удалили зависший под, ReplicaSet тут же создаст такой же, с тем же шаблоном и теми же проблемами. Чинится всегда шаблон в манифесте, а не отдельный под.

## Масштабирование

Число копий – это строчка `replicas: 3` в манифесте. Рабочий путь изменения уже понятен. Правим файл на `replicas: 5`, применяем:

Bash

Копировать

```bash
kubectl apply -f deployment.yaml
kubectl get pods
```

Подов стало пять, два новых созданы за секунды. В обратную сторону так же – уменьшили число, лишние поды удалились. Добавить мощностей приложению – это правка одной цифры.

Есть и императивная команда:

kubectl scale deployment web --replicas=10

Она меняет `replicas` прямо в кластере, минуя файл. Место у нее то же, что у всех императивных команд – эксперименты и инциденты, когда надо срочно и руками. Но манифест в Git после нее перестает совпадать с реальностью, и следующий `apply` молча вернет старое число копий.

Отдельно полезен ноль:

kubectl scale deployment web --replicas=0

Приложение выключено, но не удалено. Манифест, история и сам Deployment на месте, подов нет. Удобно для временного отключения и экономии ресурсов на тестовых стендах.

## Rolling update

Теперь главная способность Deployment. Меняем в манифесте версию образа с `nginx:1.25` на `nginx:1.27` и применяем:

Bash

Копировать

```bash
kubectl apply -f deployment.yaml
kubectl rollout status deployment/web
```

Копировать

```
Waiting for deployment "web" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "web" rollout to finish: 2 out of 3 new replicas have been updated...
deployment "web" successfully rolled out
```

Команда `rollout status` показывает ход обновления в реальном времени. А происходит за этими строчками вот что. Шаблон пода изменился, значит изменился его хэш – и Deployment создал **новый ReplicaSet** под новую версию. Дальше он пошагово увеличивает число копий в новом и уменьшает в старом.

![Rolling update без даунтайма: новый ReplicaSet наполняется, старый гасится в ноль и хранится для отката](https://prostodevops.ru/api/uploads/lessons/k8s-deployments-replicaset-scaling-02.webp)Rolling update без даунтайма: новый ReplicaSet наполняется, старый гасится в ноль и хранится для отката

Поднялся новый под – погасили старый, и так до конца. В каждый момент времени работает достаточно подов, чтобы обслуживать трафик, обновление проходит без остановки сервиса.

Следы этого процесса остаются в ReplicaSet:

kubectl get rs

Копировать

```
NAME             DESIRED   CURRENT   READY   AGE
web-7d4b9ccf94   0         0         0       25m
web-6f9c8b7d55   3         3         3       1m
```

Старый ReplicaSet никуда не делся – он смасштабирован в ноль и хранится. Зачем хранится, станет ясно в разделе про откат.

Темп перехода управляется двумя параметрами в `spec.strategy`. `maxSurge` задает, сколько подов можно создать сверх желаемого числа на время обновления, `maxUnavailable` – сколько может одновременно не хватать. По умолчанию оба равны 25%, и для большинства приложений умолчания нормальны. Жесткий вариант без просадки емкости выглядит так:

YAML

Копировать

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
```

Сначала всегда создается новый под, и только после его готовности гасится старый. Число работающих копий не опускается ниже заявленного ни на секунду.

Одна оговорка про слово готовность. Пока приложение отдельно не сообщает кластеру о своей готовности, готовым считается под с запустившимся контейнером. Процесс стартовал – для rolling update под уже готов, даже если приложение внутри еще прогревается. Настройка готовности делается через probes, и в производственных манифестах она обязательна – это тема следующего модуля, без нее rolling update доверяет процессам на слово.

Вернемся к началу пути. Третьей проблемой Compose из первого урока был даунтайм на каждом обновлении. Вот ее решение – `docker compose up -d` с паузой между погасили старое и подняли новое превратился в правку строчки образа и постепенный, контролируемый переезд без остановки.

## История и откат

Каждое изменение шаблона создает новую ревизию, и Deployment их помнит:

kubectl rollout history deployment/web

Копировать

```
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
```

`CHANGE-CAUSE` по умолчанию пуст. Если хочется видеть в истории осмысленные подписи, причина изменения записывается аннотацией в манифесте – поле `kubernetes.io/change-cause` в `metadata.annotations`, например «update nginx to 1.27». Посмотреть, что именно было в ревизии, можно с флагом:

kubectl rollout history deployment/web --revision=1

В выводе будет шаблон пода той версии, включая образ. А теперь представим штатную аварию. Выкатили новую версию, она формально запустилась, но работает неправильно. Откат – одна команда:

kubectl rollout undo deployment/web

Старый ReplicaSet, который хранился смасштабированным в ноль, снова наполняется подами, новый гасится – тот же rolling update, только в обратную сторону. Ради этого старые ReplicaSet и хранятся, это готовые к включению прошлые версии. Откат на конкретную ревизию делается флагом `--to-revision`:

kubectl rollout undo deployment/web --to-revision=1

Сколько ревизий хранить, задает поле `spec.revisionHistoryLimit`, по умолчанию десять. И одно уточнение дисциплины. `rollout undo` – инструмент инцидента, он спасает прод здесь и сейчас. Но манифест в Git после отката указывает на сломанную версию, и это то же расхождение, что после `kubectl scale`. Финальная точка любого инцидента – правка файла.

## Recreate

У `spec.strategy.type` есть второе значение:

YAML

Копировать

```yaml
spec:
  strategy:
    type: Recreate
```

Стратегия **Recreate** работает грубо. Сначала удаляются все старые поды, потом создаются новые, и между этими фазами сервис лежит. Звучит как шаг назад к Compose, но у нее есть своя ниша – приложения, у которых две версии не могут работать одновременно. Старая и новая версия пишут в одно хранилище в несовместимых форматах, приложение держит блокировку, лицензия одна. Для обычных stateless-приложений стратегия всегда `RollingUpdate`, она и стоит по умолчанию.

## rollout restart

Ходовой прием напоследок:

kubectl rollout restart deployment/web

Команда перекатывает все поды Deployment без изменения шаблона – тем же rolling update, без даунтайма. Нужна она, когда поменялось что-то снаружи шаблона. Приложение зачитало конфиг при старте и его надо заставить перечитать, обновился секрет, хочется получить свежие поды после сетевых проблем.
