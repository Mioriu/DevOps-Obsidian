# Istio

## Зачем это нужно?

У тебя в кластере много микросервисов. Проблемы:

- Как постепенно раскатить новую версию сервиса? (canary deployment)
- Как зашифровать трафик между всеми сервисами?
- Как получить метрики по всем запросам между сервисами?
- Как сделать retry и timeout для запросов?
- Как ограничить количество запросов (rate limit)?

Без Service Mesh это всё нужно писать в коде КАЖДОГО приложения. Копипаста, дублирование, сложно поддерживать.

**Istio** решает эти проблемы БЕЗ изменения кода приложений.

## 1. Что такое Istio?

**Istio** — это Service Mesh для Kubernetes.

**Service Mesh** — это дополнительный слой между твоими сервисами, который управляет всей коммуникацией между ними.

**Что делает:**

- Управляет трафиком между сервисами
- Шифрует трафик (mTLS)
- Собирает метрики
- Контролирует доступ

## 2. Как работает?

### Sidecar паттерн

Istio добавляет **Envoy proxy** рядом с каждым твоим подом.

![Под с Istio: App + Envoy Proxy](https://offers.prostodevops.ru/diagrams/k8s/istio-sidecar.png)Под с Istio: App + Envoy Proxy

**Envoy Proxy** — это специальный proxy, который:

- Перехватывает весь входящий и исходящий трафик
- Применяет правила маршрутизации
- Шифрует соединения
- Собирает метрики

### Как общаются сервисы?

**Без Istio:**

![Схема в материале «Service Mesh. Istio»: Service A → Service B](https://offers.prostodevops.ru/diagrams/extras/kubernetes/service-mesh-istio-1.png)Схема в материале «Service Mesh. Istio»: Service A → Service B

**С Istio:**

![Схема в материале «Service Mesh. Istio»: Service A → Envoy A → Envoy B → Service B](https://offers.prostodevops.ru/diagrams/extras/kubernetes/service-mesh-istio-2.png)Схема в материале «Service Mesh. Istio»: Service A → Envoy A → Envoy B → Service B

Приложение Service A думает что общается напрямую с Service B, но на самом деле трафик идет через два Envoy proxy.

## 3. Архитектура Istio

Istio состоит из двух частей:

### Data Plane

**Что это:** Все Envoy proxy во всех подах.

**Что делает:** Обрабатывает реальный трафик между сервисами.

### Control Plane

**Что это:** Компонент `istiod` (один под в кластере).

**Что делает:**

- Управляет настройками всех Envoy proxy
- Раздает конфигурацию
- Генерирует сертификаты для mTLS
- Отслеживает какие сервисы есть в кластере

![Istio Control Plane (istiod) и Data Plane (sidecars)](https://offers.prostodevops.ru/diagrams/k8s/istio-control-plane.png)Istio Control Plane (istiod) и Data Plane (sidecars)

## 4. Основные возможности

### Traffic Management

Управление трафиком между сервисами.

**Что можно:**

- Направить 90% трафика на старую версию, 10% на новую (canary)
- Роутинг по хедерам (если user=admin → направить на версию v2)
- Балансировка (round-robin, least connections)

**Пример: Canary deployment**

yamlcopy

```yaml
90% трафика → сервис версии v110% трафика → сервис версии v2
```

Постепенно увеличиваешь процент на v2.

### Security

**mTLS (mutual TLS):**

- Istio автоматически шифрует весь трафик между сервисами
- Сервисы идентифицируют друг друга через сертификаты
- Не нужно менять код приложений

**Авторизация:**

- Можешь настроить кто может обращаться к какому сервису
- Пример: только сервис A может обращаться к сервису B

### Observability

Istio автоматически собирает:

**Метрики:**

- Сколько запросов между сервисами
- Какая задержка
- Сколько ошибок (4xx, 5xx)
- Размер запросов/ответов

**Distributed Tracing:**

- Отслеживание запроса через все микросервисы
- Видишь весь путь: Service A → Service B → Service C → Service D
- Где самая большая задержка

**Логи:**

- Логи всех запросов через Envoy

## 5. Ключевые компоненты

### Virtual Service

Определяет **как** маршрутизировать трафик.

**Пример:**

- 90% запросов на v1
- 10% запросов на v2
- Если header содержит "beta" → на v2

### Destination Rule

Определяет **политики** для трафика.

**Что настраивается:**

- Load balancing (как распределять нагрузку)
- Connection pool (сколько соединений держать)
- Circuit breaker (когда отключить endpoint)

### Gateway

Входная точка для внешнего трафика в Service Mesh.

Работает как Kubernetes Ingress, но с большими возможностями.

## 7. Overhead от Istio

**CPU и Memory:**

- Каждый Envoy sidecar: ~50-200 MB памяти, ~0.5 vCPU
- Control Plane (istiod): ~1-2 GB памяти, ~1 vCPU

**Latency:**

- Дополнительно ~1-5ms на каждый hop через proxy

Для маленьких проектов это может быть слишком много.

## 8. Вопросы на собеседованиях

### Вопрос 1: "Что такое Service Mesh?"

**Ответ:** Service Mesh — это инфраструктурный слой для управления коммуникацией между микросервисами. Решает проблемы маршрутизации, безопасности и наблюдаемости без изменения кода приложений.

### Вопрос 2: "Как работает Istio?"

**Ответ:** Istio добавляет Envoy proxy sidecar в каждый под. Весь трафик идет через Envoy. Control Plane (istiod) управляет конфигурацией всех proxy. Приложения не знают про Istio.

### Вопрос 3: "Что такое Data Plane и Control Plane?"

**Ответ:**

- **Data Plane** — все Envoy proxy, которые обрабатывают реальный трафик
- **Control Plane** — istiod, который управляет конфигурацией всех proxy

### Вопрос 4: "Что такое Virtual Service?"

**Ответ:** Virtual Service определяет правила маршрутизации трафика. Например: 90% на v1, 10% на v2, или роутинг по headers.

### Вопрос 5: "Как Istio делает mTLS?"

**Ответ:** Istio автоматически генерирует сертификаты для каждого сервиса и настраивает Envoy proxy для шифрования трафика. Трафик между сервисами шифруется без изменения кода.

### Вопрос 6: "Какие метрики собирает Istio?"

**Ответ:**

- Request rate (запросов в секунду)
- Request duration (latency)
- Error rate (4xx, 5xx)
- Request/response size

Всё автоматически через Envoy proxy.

### Вопрос 7: "Что такое Sidecar Pattern?"

**Ответ:** Паттерн когда рядом с основным контейнером приложения запускается дополнительный контейнер (sidecar), который предоставляет вспомогательные функции. В Istio это Envoy proxy для управления трафиком.

### Вопрос 8: "В чем разница между Istio и Kubernetes Ingress?"

**Ответ:**

- **Ingress** — только входящий трафик извне в кластер
- **Istio** — управляет ВСЕМ трафиком (внешним и между сервисами внутри кластера), плюс security и observability

### Вопрос 9: "Зачем нужен Envoy?"

**Ответ:** Envoy — это L7 proxy который перехватывает весь трафик пода. Он применяет правила маршрутизации, делает load balancing, retry, timeout, собирает метрики, терминирует mTLS.

### Вопрос 10: "Когда НЕ стоит использовать Istio?"

**Ответ:** Когда мало сервисов (< 5-10), простая архитектура, ограниченные ресурсы, нет потребности в продвинутых возможностях. Overhead от Istio может быть не оправдан.

## Заключение

**Istio** — это Service Mesh, который управляет коммуникацией между микросервисами.

**Ключевые особенности:**

- Envoy proxy sidecar в каждом поде
- Control Plane управляет всеми proxy
- Traffic management, security, observability
- Работает без изменения кода приложений

**Используй когда:**

- Много микросервисов
- Нужны продвинутые возможности роутинга
- Нужна безопасность и наблюдаемость

**Не используй когда:**

- Мало сервисов
- Простая архитектура
- Ограниченные ресурсы

На собеседованиях обязательно спрашивают про архитектуру (Data Plane / Control Plane), как работает Sidecar Pattern, и зачем вообще нужен Service Mesh.
