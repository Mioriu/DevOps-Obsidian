## 1. Общая картина

Kubernetes кластер состоит из двух типов нод:

**Control Plane (Master Node)** — мозг кластера

- Управляет кластером
- Принимает решения (где запустить под, когда масштабировать)
- Хранит состояние кластера
- Обрабатывает API запросы

**Worker Nodes** — рабочие сервера

- Запускают поды (контейнеры)
- Выполняют инструкции от control plane
- Отчитываются о своем состоянии

![Архитектура Kubernetes: Control Plane → Worker Nodes](https://offers.prostodevops.ru/diagrams/k8s/k8s-arch.png)Архитектура Kubernetes: Control Plane → Worker Nodes

**Важно:** Control plane НЕ запускает пользовательские поды (обычно). Это только управление.

## 2. Control Plane компоненты

### API Server (kube-apiserver)

**Что это:** Единая точка входа в кластер. REST API для всего.

**Что делает:**

- Обрабатывает все API запросы (`kubectl` общается с ним)
- Валидирует запросы (правильный ли yaml?)
- Авторизует запросы (есть ли права?)
- Пишет данные в etcd
- Единственный компонент который пишет в etcd напрямую

**Взаимодействие:**![Схема в материале «Архитектура Kubernetes»: kubectl create pod → API Server → etcd (сохранить состояние)](https://offers.prostodevops.ru/diagrams/extras/kubernetes/arhitektura-kubernetes-3.png)Схема в материале «Архитектура Kubernetes»: kubectl create pod → API Server → etcd (сохранить состояние)

**Когда падает:**

- `kubectl` не работает
- Ничего нельзя создать/изменить/удалить
- Существующие поды продолжают работать (!)

### etcd

**Что это:** Распределенное key-value хранилище. База данных кластера.

**Что хранит:**

- Все объекты кластера (поды, сервисы, деплойменты, конфиги)
- Состояние кластера
- Metadata

**Важно:**

- Единственное место где хранятся данные
- Если etcd умер — кластер мертв
- Если потерял данные etcd — потерял весь кластер
- Поэтому etcd **обязательно** бекапить

**Взаимодействие:**

- Только API Server читает/пишет в etcd
- Другие компоненты НЕ общаются с etcd напрямую

**Когда падает:**

- API Server не может читать/писать данные
- Кластер перестает работать
- Существующие поды продолжают работать до перезапуска

### Scheduler (kube-scheduler)

**Что это:** Решает НА КАКУЮ ноду поместить под.

**Что делает:**

1. Следит за новыми подами без назначенной ноды
2. Выбирает лучшую ноду (по ресурсам, affinity, taints)
3. Назначает под на ноду (пишет в API Server)

**Не запускает под!** Только решает куда поместить.

**Как выбирает ноду:**

- Filtering — отбрасывает неподходящие ноды (мало ресурсов, taints)
- Scoring — ранжирует оставшиеся ноды (наименее загруженные, affinity)
- Выбирает ноду с наивысшим счетом

**Когда падает:**

- Новые поды не будут назначены на ноды (Pending)
- Существующие поды работают нормально

### Controller Manager (kube-controller-manager)

**Что это:** Коллекция контроллеров. Следит чтобы текущее состояние = желаемому.

**Какие контроллеры внутри:**

**Node Controller:**

- Следит за состоянием нод
- Помечает ноды как NotReady если не отвечают
- Вытесняет поды с мертвых нод

**Replication Controller / ReplicaSet Controller:**

- Следит чтобы количество реплик = желаемому
- Если под умер → создает новый

**Deployment Controller:**

- Управляет ReplicaSets
- Обновляет приложения (rolling update)

**Service Controller:**

- Создает LoadBalancer в облаке для Service type=LoadBalancer

**Job Controller:**

- Запускает поды для Job до завершения

**И еще ~20 других контроллеров**

**Как работает контроллер (паттерн):**

codecopy

```
1. Watch — следит за объектами через API Server2. Compare — сравнивает current state vs desired state3. Reconcile — приводит current к desired (создает/удаляет объекты)
```

Пример:

codecopy

```
Deployment: replicas: 3Текущее состояние: 2 пода Controller Manager:1. Видит что 2 < 32. Создает еще 1 под через API Server
```

**Когда падает:**

- Автомасштабирование не работает
- Умершие поды не перезапускаются
- Деплойменты не обновляются
- Но существующие поды продолжают работать

### Cloud Controller Manager (опционально)

**Что это:** Интеграция с облачным провайдером

**Что делает:**

- Создает LoadBalancer в облаке для Service
- Управляет облачными дисками (Persistent Volumes)
- Обновляет облачные маршруты

**Когда нужен:** Только если кластер в облаке и используешь облачные ресурсы.

## 3. Worker Node компоненты

### kubelet

**Что это:** Агент на каждой ноде. Главный компонент worker node.

**Что делает:**

1. Регистрирует ноду в кластере
2. Следит за подами назначенными на эту ноду (через API Server)
3. Запускает контейнеры через container runtime (Docker, containerd)
4. Следит чтобы контейнеры работали
5. Отправляет статус подов и ноды в API Server
6. Выполняет health checks (liveness, readiness probes)

**Взаимодействие:**![Схема в материале «Архитектура Kubernetes»: API Server: "Запусти под X на этой ноде"](https://offers.prostodevops.ru/diagrams/extras/kubernetes/arhitektura-kubernetes-1.png)Схема в материале «Архитектура Kubernetes»: API Server: "Запусти под X на этой ноде"

**Важно:** kubelet НЕ управляет контейнерами напрямую. Он общается с container runtime через CRI (Container Runtime Interface).

**Когда падает:**

- Поды на этой ноде перестают обновляться
- Новые поды не запускаются на этой ноде
- Существующие поды продолжают работать (но без хелзчеков)
- Нода помечается как NotReady

### kube-proxy

**Что это:** Сетевой прокси на каждой ноде. Реализует Service.

**Что делает:**

- Следит за Service и Endpoints через API Server
- Настраивает правила iptables/ipvs для маршрутизации трафика к подам
- Обеспечивает load balancing между подами Service

**Как работает:**

Создаешь Service:

yamlcopy

```yaml
apiVersion: v1kind: Servicemetadata:  name: my-servicespec:  selector:    app: myapp  ports:  - port: 80    targetPort: 8080
```

kube-proxy на каждой ноде:

1. Видит новый Service
2. Создает правила iptables:
    - Если трафик на ClusterIP:80 → перенаправить на поды с меткой app=myapp на порт 8080
3. Балансирует между всеми подами

**Режимы работы:**

- **iptables** (по умолчанию) — быстрый, но не очень масштабируемый
- **ipvs** — быстрее для большого количества сервисов
- **userspace** — старый, медленный

**Когда падает:**

- Service перестают работать на этой ноде
- Трафик не балансируется
- Существующие соединения могут продолжать работать

### Container Runtime

**Что это:** Софт который запускает контейнеры (Docker, containerd, CRI-O).

**Что делает:**

- Скачивает образы
- Запускает контейнеры
- Останавливает контейнеры
- Управляет жизненным циклом контейнера

**Взаимодействие с kubelet:**

kubelet → CRI (Container Runtime Interface) → Container Runtime

**Популярные runtime:**

- **containerd** — легкий, рекомендуется (Docker использует его под капотом)
- **CRI-O** — специально для Kubernetes
- **Docker** — раньше был дефолтным, но теперь deprecated

**Когда падает:**

- Контейнеры на ноде не запускаются
- Существующие контейнеры могут продолжать работать

## 4. Дополнительные компоненты

### CoreDNS

**Что это:** DNS сервер внутри кластера.

**Что делает:**

- Разрешает имена Service в IP адреса
- `my-service.default.svc.cluster.local` → ClusterIP

**Развернут как Deployment** в namespace kube-system.

**Когда падает:**

- Поды не могут найти Service по имени
- Нужно использовать ClusterIP напрямую

### Metrics Server

**Что это:** Собирает метрики с kubelet (CPU, память).

**Что делает:**

- Предоставляет метрики для `kubectl top`
- Используется HPA (Horizontal Pod Autoscaler) для автомасштабирования

**Не обязателен,** но нужен для автомасштабирования.

## 5. Как все работает вместе

### Сценарий: Создание пода

kubectl create -f pod.yaml

**Что происходит:**

1. **kubectl** отправляет запрос в **API Server**
    
2. **API Server:**
    
    - Проверяет аутентификацию (кто ты?)
    - Проверяет авторизацию (можешь ли ты?)
    - Валидирует yaml (правильный ли?)
    - Сохраняет под в **etcd** (пока без назначенной ноды)
    - Возвращает ответ kubectl: "Pod created"
3. **Scheduler** следит за API Server и видит новый под без ноды
    
4. **Scheduler:**
    
    - Выбирает подходящую ноду
    - Назначает под на ноду (пишет в API Server)
5. **kubelet** на выбранной ноде следит за API Server и видит под назначенный на эту ноду
    
6. **kubelet:**
    
    - Говорит **container runtime** скачать образ и запустить контейнер
    - Отправляет статус пода в API Server
7. **kube-proxy** видит что под запущен и обновляет iptables правила если нужно
    

**Под работает**

### Сценарий: Под упал

1. **kubelet** видит что контейнер умер
    
2. **kubelet:**
    
    - Отправляет статус "Pod Failed" в API Server
    - Пытается перезапустить контейнер (если restart policy позволяет)
3. **Replication Controller** (если под управляется ReplicaSet/Deployment) видит что под умер
    
4. **Controller Manager:**
    
    - Создает новый под через API Server
    - Scheduler назначит его на ноду
    - kubelet запустит

### Сценарий: Нода упала

1. **kubelet** на ноде перестает отправлять в API Server
    
2. **Node Controller** (часть Controller Manager) замечает что нода не отвечает
    
3. **Node Controller:**
    
    - Помечает ноду как NotReady
    - Ждет ~5 минут (на случай временных проблем)
    - Вытесняет поды с ноды (eviction)
4. **Scheduler** назначает вытесненные поды на здоровые ноды
    
5. **kubelet** на здоровых нодах запускает поды
