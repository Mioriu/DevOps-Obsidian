# Балансировка нагрузки

Балансировка — это распределение трафика между несколькими серверами. Она решает две задачи: производительность (больше серверов = больше запросов в секунду) и отказоустойчивость (один сервер упал — остальные работают).

## 1. Как работает балансировка

Базовая схема:

![Load balancer: round-robin к 3 backend'ам](https://offers.prostodevops.ru/diagrams/network/load-balancer.png)Load balancer: round-robin к 3 backend'ам

Клиент подключается к балансировщику. Балансировщик выбирает один из backend-серверов и направляет запрос туда. Клиент не знает, сколько серверов за балансировщиком и какой именно обработал его запрос.

### Что делает балансировщик

1. **Распределяет запросы** между backend-серверами по определённому алгоритму
2. **Проверяет здоровье** backend-ов (health checks) и исключает упавшие
3. **Терминирует SSL** (опционально) — расшифровывает HTTPS и отправляет на backend HTTP
4. **Поддерживает сессии** (опционально) — направляет запросы одного клиента на один backend

## 2. L4 vs L7 балансировка

Балансировка работает на разных уровнях модели OSI. Два основных: L4 (транспортный) и L7 (прикладной).

### L4 балансировка (TCP/UDP)

Работает на уровне TCP/UDP. Балансировщик видит:

- IP-адреса источника и назначения
- Порты
- Протокол (TCP/UDP)

Не видит: содержимое запроса, HTTP-заголовки, URL, cookies.

Как работает: балансировщик получает TCP-соединение и целиком перенаправляет его на один из backend-ов. Все пакеты одного соединения идут на один сервер.

Плюсы:

- Быстрее (не нужно разбирать содержимое)
- Проще
- Работает с любым протоколом поверх TCP/UDP (не только HTTP)

Минусы:

- Не может маршрутизировать по URL или заголовкам
- Не может модифицировать запросы
- Health check только на уровне TCP (порт открыт/закрыт)

Когда использовать:

- Базы данных
- Любые не-HTTP протоколы (gRPC без HTTP/2 терминации, кастомные протоколы)
- Когда нужна максимальная производительность
- TCP/UDP сервисы (DNS, игровые серверы)

### L7 балансировка (HTTP/HTTPS)

Работает на уровне приложения. Балансировщик видит:

- Всё, что видит L4
- HTTP-метод, URL, заголовки
- Cookies
- Тело запроса (если нужно)

Как работает: балансировщик полностью разбирает HTTP-запрос, принимает решение на основе его содержимого, может модифицировать запрос перед отправкой на backend.

Плюсы:

- Маршрутизация по URL: `/api/*` → api-серверы, `/static/*` → CDN
- Маршрутизация по заголовкам: мобильные клиенты → мобильный backend
- Sticky sessions по cookie
- Модификация запросов (добавить заголовки, переписать URL)
- HTTP health checks (проверить что `/health` возвращает 200)
- SSL termination

Минусы:

- Медленнее (нужно разбирать каждый запрос)
- Сложнее настраивать
- Работает только с HTTP/HTTPS

Когда использовать:

- Веб-приложения
- REST API
- Микросервисы с HTTP
- Когда нужна маршрутизация по содержимому

### Сравнение

|Характеристика|L4|L7|
|---|---|---|
|Скорость|Быстрее|Медленнее|
|Протоколы|Любые TCP/UDP|HTTP/HTTPS|
|Роутинг по URL|Нет|Да|
|Sticky sessions|По IP|По cookie|
|SSL termination|Passthrough или терминация|Полная терминация|
|Health checks|TCP connect|HTTP endpoint|
|Модификация запросов|Нет|Да|

## 3. Алгоритмы балансировки

### Round Robin

Запросы распределяются по очереди: первый → backend 1, второй → backend 2, третий → backend 3, четвёртый → снова backend 1.

![Схема в материале «Сети расширенные 3: Балансировка»: Запрос 1 → Backend 1](https://offers.prostodevops.ru/diagrams/extras/seti/seti-rasshirennye-3-balansirovka-5.png)Схема в материале «Сети расширенные 3: Балансировка»: Запрос 1 → Backend 1

Плюсы: простой, равномерное распределение.

Минусы: не учитывает, что серверы могут быть разной мощности или что один запрос может быть тяжелее другого.

Когда использовать: серверы одинаковой мощности, запросы примерно одинаковой сложности.

### Weighted Round Robin

Как Round Robin, но серверам присваиваются веса. Сервер с весом 3 получит в три раза больше запросов, чем сервер с весом 1.

codecopy

```
Backend 1 (weight=3): получает 3 из 5 запросовBackend 2 (weight=1): получает 1 из 5 запросовBackend 3 (weight=1): получает 1 из 5 запросов
```

Когда использовать: серверы разной мощности. Новый сервер мощнее старых — дай ему больше веса.

### Least Connections

Запрос направляется на сервер с наименьшим количеством активных соединений.

![Схема в материале «Сети расширенные 3: Балансировка»: Backend 1: 10 соединений](https://offers.prostodevops.ru/diagrams/extras/seti/seti-rasshirennye-3-balansirovka-4.png)Схема в материале «Сети расширенные 3: Балансировка»: Backend 1: 10 соединений

Плюсы: учитывает реальную нагрузку. Если один запрос выполняется долго, сервер не получит новые, пока не освободится.

Минусы: не учитывает мощность серверов.

Когда использовать: запросы сильно различаются по времени выполнения (одни — 10ms, другие — 10s).

### IP Hash

Хэш от IP-адреса клиента определяет, на какой сервер идёт запрос. Один и тот же клиент всегда попадает на один сервер.

![Схема в материале «Сети расширенные 3: Балансировка»: hash(192.168.1.100) % 3 = 1 → Backend 2](https://offers.prostodevops.ru/diagrams/extras/seti/seti-rasshirennye-3-balansirovka-3.png)Схема в материале «Сети расширенные 3: Балансировка»: hash(192.168.1.100) % 3 = 1 → Backend 2

Плюсы: простые sticky sessions без cookies.

Минусы: если клиенты за NAT (один внешний IP на тысячи клиентов), все пойдут на один сервер. При добавлении/удалении серверов распределение сбивается.

Когда использовать: нужна привязка к серверу, но нет возможности использовать cookies (L4, не-HTTP протоколы).

### Consistent Hashing

Улучшенная версия IP Hash. При добавлении/удалении серверов перераспределяется минимум клиентов.

Используется в: распределённых кэшах, базах данных, когда важно минимизировать перебалансировку.

### Random

Случайный выбор сервера. Как ни странно, при большом количестве запросов даёт равномерное распределение.

Плюсы: простейшая реализация, нет shared state между балансировщиками.

Когда использовать: много запросов, не критична точность распределения.

### Least Response Time

Запрос направляется на сервер с наименьшим временем отклика. Балансировщик измеряет latency до каждого backend-а.

Плюсы: учитывает реальную производительность, включая сеть.

Минусы: сложнее реализация, нужно постоянно измерять.

## 4. Health Checks

Балансировщик должен знать, какие backend-ы живы. Для этого он периодически проверяет их.

### Типы проверок

**TCP check**: попытка установить TCP-соединение. Если порт отвечает — сервер жив.

Проверка: можно ли подключиться к 10.0.0.1:8080?

**HTTP check**: HTTP-запрос на определённый endpoint. Проверяется код ответа (обычно 200).

Проверка: GET /health возвращает 200?

**Глубокий HTTP check**: проверка не только кода, но и тела ответа.

Проверка: GET /health возвращает 200 и тело содержит "ok"?

### Параметры health check

- **Interval** — как часто проверять (например, каждые 5 секунд)
- **Timeout** — сколько ждать ответа (например, 3 секунды)
- **Unhealthy threshold** — сколько неудачных проверок подряд, чтобы считать сервер мёртвым (например, 3)
- **Healthy threshold** — сколько успешных проверок, чтобы вернуть сервер в строй (например, 2)

## 5. Sticky Sessions (Session Affinity)

Иногда нужно, чтобы запросы одного клиента шли на один сервер. Например, если сессия хранится в памяти сервера, а не в Redis.

### Способы реализации

**По IP (L4)**:![Схема в материале «Сети расширенные 3: Балансировка»: hash(client_ip) → всегда один backend](https://offers.prostodevops.ru/diagrams/extras/seti/seti-rasshirennye-3-balansirovka-1.png)Схема в материале «Сети расширенные 3: Балансировка»: hash(client_ip) → всегда один backendПроблема: клиенты за NAT, смена IP при переключении сети.

**По cookie (L7)**:![Схема в материале «Сети расширенные 3: Балансировка»: Балансировщик ставит cookie: SERVERID=backend2](https://offers.prostodevops.ru/diagrams/extras/seti/seti-rasshirennye-3-balansirovka-2.png)Схема в материале «Сети расширенные 3: Балансировка»: Балансировщик ставит cookie: SERVERID=backend2Надёжнее, но работает только для HTTP.

**По заголовку**:![Схема в материале «Сети расширенные 3: Балансировка»: X-Session-ID: abc123 → hash(abc123) → backend](https://offers.prostodevops.ru/diagrams/extras/seti/seti-rasshirennye-3-balansirovka-6.png)Схема в материале «Сети расширенные 3: Балансировка»: X-Session-ID: abc123 → hash(abc123) → backend

Важно: sticky sessions — это костыль. Лучше хранить сессии в общем хранилище (Redis, база данных) и делать приложение stateless.

## 6. Основные инструменты

### Nginx

Самый популярный веб-сервер, умеет L7 балансировку.

Алгоритмы: round-robin (по умолчанию), least_conn, ip_hash, random.

Плюсы: простой, есть везде, хорошая документация. Минусы: health checks только в платной версии (Nginx Plus) или через сторонние модули.

### HAProxy

Специализированный балансировщик, L4 и L7. Стандарт в индустрии для высоких нагрузок.

Алгоритмы: roundrobin, leastconn, source (ip hash), uri, hdr (по заголовку), random.

Плюсы: очень быстрый, мощные health checks, подробная статистика, бесплатный. Минусы: конфиг сложнее nginx, не умеет отдавать статику.

### Envoy

Современный L7 прокси. Разработан в Lyft, используется в Istio (service mesh).

Плюсы: динамическая конфигурация через API, продвинутые возможности (circuit breaker, retry, rate limiting), интеграция с service mesh. Минусы: сложнее в настройке, больше потребление ресурсов.

### Облачные балансировщики

**Kubernetes**:

- Service type: LoadBalancer — создаёт облачный балансировщик
- Ingress — L7 балансировка внутри кластера
- Service type: ClusterIP — внутренняя L4 балансировка (kube-proxy)

### Сравнение инструментов

|Инструмент|Уровень|Сложность|Производительность|Когда использовать|
|---|---|---|---|---|
|Nginx|L7|Низкая|Высокая|Веб, простые случаи|
|HAProxy|L4/L7|Средняя|Очень высокая|Высокие нагрузки, TCP|
|Envoy|L7|Высокая|Высокая|Service mesh, микросервисы|
|Облачные|L4/L7|Низкая|Зависит|Облачная инфраструктура|

## Что запомнить

1. **Балансировка решает две задачи**: производительность (больше серверов) и отказоустойчивость (один упал — остальные работают)
    
2. **L4 работает на уровне TCP/UDP** — быстрее, проще, для любых протоколов. **L7 на уровне HTTP** — гибче, можно роутить по URL/заголовкам
    
3. **Round Robin** — просто и равномерно. **Least Connections** — когда запросы разные по тяжести. **IP Hash** — примитивные sticky sessions
    
4. **Health checks обязательны** — иначе трафик будет идти на мёртвые серверы
    
5. **Sticky sessions — костыль**. Лучше stateless приложение + внешнее хранилище сессий
    
6. **Nginx** — просто и достаточно для большинства случаев. **HAProxy** — когда нужна производительность и продвинутые фичи. **Envoy** — для service mesh и микросервисов
    
7. **В облаках используй облачные балансировщики** — они интегрированы с остальной инфраструктурой
    
8. **Weighted** версии алгоритмов нужны, когда серверы разной мощности
