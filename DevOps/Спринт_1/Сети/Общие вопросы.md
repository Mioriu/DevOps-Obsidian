# Сети

## Основы сетевой адресации

### Что такое IP и маска подсети?

IP-адрес - это адрес машинки в сети. В IPv4 это 32 бита, которые записывают как четыре числа через точку (192.168.1.1). IPv6 не будем трогать, на собесах редко спрашивают.  
Маска подсети определяет, где кончается адрес сети и начинается адрес конкретной железки. Пишется либо как 255.255.255.0, либо по-модному /24. Если видите 192.168.1.100/24 - первые 24 бита это сеть, последние 8 - конкретный комп. Каждое число между точками называется октет, их четыре штуки.

### Быстрый расчет маски подсети

На собесе могут спросить "сколько хостов в /23 сети?". Формула простая: 2^(32-маска). Для /23 получаем 2^9 = 512 адресов. Но! Два адреса всегда зарезервированы - первый для сети, последний для броадкаста. Итого для хостов остается 510. На собесе обязательно уточните - спрашивают общее количество или именно для хостов, покажете внимательность.  
Степени двойки от 0 до 10 было бы неплохо знать.

### Частные IP-адреса

Есть специальные диапазоны, которые не маршрутизируются в интернете и юзаются только внутри сетей:

- 127.0.0.0/8 - это localhost, для обращения к самому себе (127.0.0.1 все знают)
- 192.168.0.0/16 - классика для домашних роутеров
- 10.0.0.0/8 - часто в корпоративных сетях
- 172.16.0.0/12 - тоже для внутрянки

Благодаря этому миллионы контор могут использовать одинаковые айпишники внутри своих сетей и не париться.

## Транспортные протоколы

### Чем отличается TCP от UDP?

TCP. Устанавливает соединение, гарантирует доставку, следит за порядком пакетов, переотправляет потерянные. Надежно, но медленнее.  
UDP. Отправил данные и пофиг, дошли или нет. Зато быстро! Идеально для стриминга, игрушек и DNS-запросов, где лучше потерять пару пакетов, чем тормозить.

### Как TCP устанавливает соединение?

Трехстороннее рукопожатие:

1. Клиент отправляет SYN
2. Сервер: отвечает SYN-ACK
3. Клиент: шлет ACK и устанавливается соединение

### Как TCP поддерживает соединение?

TCP не тупо гонит данные, а ждет подтверждения (ACK) на каждый отправленный кусок. Не пришел ACK в течение таймаута - отправляем заново.  
Еще есть keep-alive пакеты - это такие пинги "ты еще жив?", которые периодически летают, когда долго нет данных. Чтобы соединение не отвалилось по таймауту.

### На каком уровне работает протокол TCP?

Транспортный уровень, четвертый в модели OSI.

## DNS и доменные имена

### Как работает DNS и зачем он нужен?

DNS - domain name system. Система, которая хранит связи домен-айпи. Вы вводите yandex.ru (это для людей), а DNS находит реальный IP 77.88.55.77 (это для железа). Потому что компы только по айпишникам общаются.  
Процесс такой: провайдер сначала чекает свой кэш, если нет - идет к корневым серверам, те отправляют к серверам .ru, а те уже к серверам яндекса. Вся эта цепочка происходит за доли секунды.

### Типы DNS записей

Основные типы:

- A запись - привязывает домен к IPv4 (самая частая)
- AAAA - то же самое для IPv6 (редко спрашивают)
- CNAME - алиас для другого домена, типа ссылки
- MX - почтовый
- TXT - просто текст
- NS - какие DNS серверы отвечают за зону
- SOA - главная инфа о зоне

### Почему DNS использует UDP?

Все просто - большинство DNS запросов влезает в один пакет (до 512 байт), и городить TCP соединение ради одного пакета - бессмысленно. UDP быстрее и проще.  
Но если ответ большой (например, с DNSSEC) или нужен зонный трансфер - тогда переключается на TCP.

### Что такое рекурсивный DNS?

Рекурсивный DNS-сервер - это сервер, который сам бегает по всей цепочке за клиента. Он сам опрашивает корневые серверы, потом .com серверы, потом серверы гугла. Получает ответ, отдает клиенту и кэширует на будущее.

### Что такое authority в DNS?

Authority означает, что сервер - официальный источник правды для домена. Авторитетный DNS хранит оригинальные записи и не бегает к другим серверам за ответами. В DNS ответах есть флаг AA (Authoritative Answer) - значит ответ пришел от главного по домену.

## HTTP и HTTPS

### Что происходит, когда в браузере вводишь yandex.ru?

Классика жанра на собесах, происходит следующее:

1. Браузер чекает DNS кэш
2. Если пусто - спрашивает у DNS сервера IP адрес
3. Получил IP - устанавливает TCP соединение (помним про трехстороннее рукопожатие)
4. Если HTTPS - делает TLS хендшейк для шифрования
5. Отправляет HTTP GET запрос за главной страницей
6. Сервер обрабатывает и отдает HTML
7. Браузер парсит HTML и догружает CSS, JS, картинки
8. Рендерит страницу юзеру

### Отличия HTTP от HTTPS

HTTP - данные летят открытым текстом, любой сниффер на пути может прочитать. HTTPS - добавляет шифрование через TLS. Обеспечивает конфиденциальность, целостность и аутентификацию сервера. Порт 443 вместо 80, нужен SSL сертификат.

### Какие существуют основные типы запросов HTTP?

Основные методы (часто спрашивают про идемпотентность):

- GET - взять данные (идемпотентный, можно кэшировать)
- POST - создать что-то новое (НЕ идемпотентный)
- PUT - заменить целиком (идемпотентный)
- PATCH - подправить частично (может быть и так и так)
- DELETE - удалить (идемпотентный)
- HEAD - дай только заголовки (идемпотентный)
- OPTIONS - что вообще можно делать с ресурсом (идемпотентный)

### Какие стандартные коды ответов есть у веб-серверов?

Запомните по категориям:

- 1xx - информационные (редко встречаются)
- 2xx - ок (200 OK, 201 Created, 204 No Content)
- 3xx - редиректы (301 навсегда переехали, 302 временно, 304 не изменилось)
- 4xx - проблема клиента (400 кривой запрос, 401 залогинься, 403 не положено, 404 нет такого)
- 5xx - проблема сервера (500 что-то сломалось, 502 прокси не дождался ответа, 503 перегружены)

### Что может содержаться в заголовках HTTP-запроса?

Куча всего, но основное:

- Host - куда стучимся (обязательный в HTTP/1.1)
- User-Agent - какой браузер/клиент
- Accept - что хотим получить в ответ
- Content-Type - что отправляем
- Authorization - логин/пароль/токен
- Cookie - кукисы для сессии
- Cache-Control - как кэшировать

### Базовая HTTP-аутентификация и авторизация

Базовая аутентификация - это когда `логин:пароль` кодируется в base64 и летит в заголовке Authorization. Типа "Basic YWRtaW46cGFzc3dvcmQ=".  
Авторизация - это уже про то, что юзеру можно делать после логина. Сейчас все юзают токены (JWT, OAuth) вместо базовой auth, потому что безопаснее.

## Шифрование и безопасность

### Что такое SSL и TLS?

SSL - дедушка, TLS - внук. Оба про шифрование данных в сети. SSL уже давно вышел из оборота, но все по привычке говорят SSL, хотя везде используется TLS (версии 1.2 и 1.3).  
Короче SSL устарел и сейчас юзают TLS.

### Чем симметричное шифрование отличается от асимметричного?

Симметричное - один ключ на двоих для шифровки и расшифровки. Быстро, но надо как-то безопасно передать ключ. Примеры: AES, DES.  
Асимметричное - два ключа: публичный (шифруем) и приватный (расшифровываем). Проблема передачи ключа решена, но работает медленне. Примеры: RSA, ECC.  
HTTPS хитрый - использует асимметрику для обмена симметричным ключом, потом гоняет данные по симметрике. Лучшее из двух миров.

### Опиши принцип работы SSL-шифрования

Принцип такой:

1. Сервер показывает сертификат с публичным ключом
2. Клиент проверяет, что сертификат не левый (через цепочку до корневого CA)
3. Клиент генерит рандомный симметричный ключ для сессии
4. Шифрует этот ключ публичным ключом сервера
5. Сервер расшифровывает приватным ключом
6. Дальше весь трафик идет через быструю симметрику

Профит!

### Как работает TLS-handshake?

TLS-handshake это когда клиент и сервер договариваются, как будут шифроваться:

1. Клиент: "Привет, я умею вот эти алгоритмы" (ClientHello)
2. Сервер: "Ок, давай вот этот, вот мой сертификат" (ServerHello)
3. Клиент проверяет сертификат, генерит pre-master secret
4. Оба высчитывают master secret и ключи сессии
5. Обмениваются финальными сообщениями - типа все готово

В TLS 1.3 это оптимизировали.

### Что такое SNI?

SNI (Server Name Indication) - это когда клиент сразу говорит, что идёт к сайту example.com, еще до того как увидит HTTP заголовки. Критично важно, когда на одном IP висит куча HTTPS сайтов - сервер должен знать, какой сертификат показать.  
Без SNI на одном IP можно было держать только один HTTPS сайт. Печаль была.

### Как работают сертификаты и как подтверждается соединение?

Сертификат - это как паспорт сайта. Там публичный ключ, инфа о владельце и подпись от доверенного CA (типа паспортного стола).  
Браузер проверяет:

- Сертификат выдан доверенным CA (он знает их список)
- Не просрочен
- Домен совпадает с тем, куда зашли

Проверка идет по цепочке до корневого CA, который вшит в браузер/ОС.

### Что такое Perfect Forward Secrecy (PFS)?

PFS - это когда даже если злодей украдет приватный ключ сервера, он не сможет расшифровать старый записанный трафик.  
Как это работает: для каждой сессии генерятся временные ключи через Диффи-Хеллмана. Сессия закончилась - ключи выкинули. Даже если потом взломают сервер, старые сессии не расшифруешь.

### Что знаешь про mTLS?

mTLS - это когда не только сервер показывает сертификат клиенту, но и клиент серверу. Взаимная проверка, короче.  
Часто юзается между микросервисами - чтобы левые сервисы не могли постучаться. Или для IoT устройств.

## Сетевые протоколы и утилиты

### Как узнать мой внешний IP адрес?

Варианты есть разные:

- В терминале: `curl ifconfig.me` или `curl ipinfo.io`
- Через dig: `dig +short myip.opendns.com @resolver1.opendns.com`
- Или тупо в браузере whatismyip.com

Внешний IP - это то, что видят сайты. Может отличаться от локального из-за NAT.

### Как работает NAT и зачем он нужен?

NAT - это когда роутер подменяет приватные IP на свой публичный для выхода в интернет.  
Роутер запоминает кто куда ходил и правильно раздает ответы обратно. Решает проблему нехватки IPv4 адресов (их всего 4 миллиарда, а устройств больше). Плюс добавляет безопасности - снаружи не видно структуру внутренней сети.

### Что такое и зачем нужен ARP протокол?

ARP связывает IP адреса с MAC адресами в локальной сети.  
Все это кэшируется в ARP таблице. Без ARP в локальной сети ничего работать не будет.

### Зачем нужен VLAN?

VLAN - это когда одну физическую сеть режут на несколько логических. Типа в одном офисе, но разные сети для разрабов, бухгалтерии и гостевого вайфая.  
Профиты:

- Безопасность (трафик изолирован)
- Меньше шума
- Проще управлять (группируешь по смыслу, а не по расположению)

### На каком порту работает ping и как работает ICMP?

Ping вообще не использует порты. Он работает через ICMP протокол на сетевом уровне (3й уровень OSI).  
ICMP - это протокол для служебных сообщений. Ping шлет Echo Request и ждет Echo Reply. Еще ICMP сообщает об ошибках типа `хост недоступен` или `время истекло`.

### Что такое TTL?

TTL (Time To Live) - это счетчик в IP пакете, сколько роутеров он может пройти. Каждый роутер уменьшает TTL на 1. Дошел до нуля - пакет выкидывается, отправителю летит ICMP Time Exceeded.  
Придумано, чтобы пакеты не гуляли по сети вечно при косяках маршрутизации.

### Как работает traceroute?

Traceroute показывает путь пакета до цели, используя TTL:

1. Шлет пакет с TTL=1 - первый роутер отвечает "я тут"
2. Шлет с TTL=2 - второй роутер отвечает
3. И так далее до цели

Видно все хопы и задержки по пути. В винде это ICMP, в линуксе по дефолту UDP. Полезная штука для диагностики.

### Что такое таблица маршрутизации?

Таблица маршрутизации - это правила куда слать пакеты. Типа навигатор для пакетов.  
В каждой записи:

- Сеть назначения
- Маска
- Куда слать (gateway)
- Через какой интерфейс

Смотреть через `route -n` или `ip route`. Запись 0.0.0.0/0 - это дефолтный шлюз, когда не знаешь куда слать - шли туда.

## SSH и удаленный доступ

### На каком уровне OSI работает SSH?

SSH работает на 7м уровне (прикладной), но шифрует на 6м (представительский). Использует TCP порт 22 для надежности.

### Как устанавливает соединение SSH и происходит авторизация?

**Установка соединения:**

1. Обмен версиями протокола
2. Договариваются о шифровании
3. Диффи-Хеллман для общего секрета
4. Сервер показывает свой `host key` (клиент чекает в `known\_hosts`)

**Способы авторизации:**

- Пароль - просто, но не очень безопасно
- SSH ключи - клиент доказывает, что у него есть приватный ключ от публичного в authorized_keys
- Сертификаты - для корпоративных параноиков
- Kerberos - для совсем корпоративных

## Модели сетевого взаимодействия

### Расскажи про модель TCP/IP

TCP/IP - это модель из 4 уровней:

1. **Канальный** (Link) - Ethernet, WiFi, работа с MAC адресами
2. **Сетевой** (Internet) - IP протокол, маршрутизация между сетями
3. **Транспортный** (Transport) - TCP/UDP, доставка между процессами
4. **Прикладной** (Application) - HTTP, SSH, FTP и прочие протоколы для юзерских программ

## Балансировка нагрузки

### Чем отличаются балансировщики L4 и L7?

L4 балансировщик - тупой и быстрый. Смотрит только на IP и порты, перекидывает TCP/UDP соединения. Не лезет в содержимое пакетов. Подходит когда нужна просто скорость.  
L7 балансировщик - умный, но медленнее. Понимает HTTP, может смотреть заголовки, куки, URL. Может отправить /api/* на одни серверы, /static/* на другие. Умеет в SSL termination, кэширование. Жрет больше ресурсов, но гибче.

### Что нам дает балансировщик трафика?

Балансировщик решает кучу проблем:

- Высокая доступность - упал сервер, трафик идет на живые
- Масштабирование - добавил серверов, сразу работают
- Равномерная нагрузка - никто не перегружен
- Обслуживание без даунтайма - обновляешь серверы по очереди

Бонусом может делать SSL termination, сжатие, защиту от DDoS.

### Почему latency до 8.8.8.8 всегда низкий?

8.8.8.8 - это гугловский DNS. Пинг быстрый из-за хитрой штуки - anycast. Один IP анонсируется кучей серверов по всему миру, и твой запрос автоматом идет к ближайшему.  
У гугла серверы во всех крупных городах и у всех провайдеров. Плюс этот адрес часто в кэше на промежуточных роутерах - все же его юзают.

### На каком протоколе работает DNS?

DNS хитрый - использует и UDP и TCP на 53 порту:

- UDP для обычных запросов (быстро, влезает в один пакет)
- TCP когда ответ большой (больше 512 байт) или для зонных трансферов

По дефолту UDP для скорости.

## Траблшутинг и настройка

### Сервис слушает на порту 80, локально работает, но из браузера нет доступа. Почему?

Классическая проблема, проверяем по порядку:

1. Сервис может слушать только localhost (127.0.0.1), а не 0.0.0.0 - чекаем через `netstat -tlnp`
2. Файрволл душит (iptables, firewalld, ufw) - смотрим правила
3. SELinux/AppArmor могут блокировать - проверяем
4. Может вы в браузере localhost пишете, а надо IP сервера

Обычно первые два пункта решают проблему.

### Как настроить проброс портов через iptables?

Проброс портов через iptables делается через DNAT. Например, внешний порт 8080 пробросить на внутренний сервер 192.168.1.100:80:

codecopy

```
# Включаем форвардинг (обязательно!)echo 1 > /proc/sys/net/ipv4/ip_forward # DNAT правило - куда перенаправлятьiptables -t nat -A PREROUTING -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.100:80 # Разрешаем форвардинг пакетовiptables -A FORWARD -p tcp -d 192.168.1.100 --dport 80 -j ACCEPT # SNAT для обратного трафика (если нужно)iptables -t nat -A POSTROUTING -j MASQUERADE
```

Сохраняем через `iptables-save`, а то после ребута все слетит.

### Есть две машинки в сети, но не могут установить соединение. Как понять проблему?

Этот вопрос может звучать по-разному, главное - если суть в том, чтобы понять почему нет сетевой доступности между хостами, то идём по пунктам.

1. Сначала проверям связность утилитой ping.
    1. Если пинг прошел, можем утилитой telnet проверить доступность нужного порта.
    2. Если и тут всё ок — проверям порты локально на машине, мб приложение нужное не тот порт слушает (ss tulpn, netstat tulpn)
    3. СМОТРИМ ЛОГИ — многие забывают об этом на собесе, но всегда смотрим логи в вопросах с траблшутингом.
2. Если пинг не прошел — делаем трассировку `traceroute`
    1. Если валится на промежуточном хосте — проблема на нём
    2. Если валится на последнем хопе, то проблема где-то на нашей машине.
    3. Смотрим файрволл (iptables, nftables, ufw) — проверяем правила, какие коннекты разрешены, а какие нет, скорее всего проблема тут.
3. Если у нас машинки общаются по доменным именам, а не по айпи —проверяем настройки DNS.
    1. Смотрим файлы:
        1. etc/hosts
        2. etc/resolv.conf
        3. etc/nsswitch
    2. Делаем пинг по домену — не проходит, пытаемся сделать пинг по айпи. Если пройдет — проблема именно в айпишке (см. шаг 3.1)
