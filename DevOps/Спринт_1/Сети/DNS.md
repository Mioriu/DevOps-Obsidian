# DNS

## Зачем это знать?

DNS — это первое, что происходит при любом сетевом запросе по доменному имени. Если DNS не работает или работает неправильно, ничего не работает. При этом проблемы с DNS часто неочевидны и маскируются под другие проблемы.

## 1. Что такое DNS

DNS (Domain Name System) — распределённая база данных, которая превращает доменные имена в IP-адреса. И не только — в DNS хранятся записи разных типов: адреса почтовых серверов, текстовые записи для верификации, алиасы и многое другое.

Когда ты вводишь `google.com` в браузере, происходит DNS-запрос. Браузер спрашивает: "какой IP у google.com?" DNS отвечает: "142.250.74.78". Браузер подключается к этому IP.

Без DNS пришлось бы запоминать IP-адреса всех сайтов. Или вести локальный файл с соответствиями (так и было до DNS — файл `/etc/hosts`).

### Почему "распределённая"

Нет единого сервера, который знает все домены мира. Это было бы единой точкой отказа и бутылочным горлышком. Вместо этого DNS — иерархическая система из тысяч серверов.

Каждый уровень доменов обслуживается своими серверами:

- Корневые серверы знают, где искать `.com`, `.org`, `.ru`
- Серверы `.com` знают, где искать `google.com`, `amazon.com`
- Серверы `google.com` знают адреса `www.google.com`, `mail.google.com`

## 2. Иерархия доменных имён

Доменное имя читается справа налево:

![Анатомия FQDN: subdomain · SLD · TLD · root](https://offers.prostodevops.ru/diagrams/network/dns-anatomy.png)Анатомия FQDN: subdomain · SLD · TLD · root

**Корневой домен (root)** — точка в конце. Обычно её не пишут, но она есть. `example.com` — это на самом деле `example.com.` (с точкой).

**TLD (Top-Level Domain)** — домены верхнего уровня:

- Общие (gTLD): `.com`, `.org`, `.net`, `.info`
- Национальные (ccTLD): `.ru`, `.uk`, `.de`, `.io`
- Новые: `.dev`, `.app`, `.cloud`

**SLD (Second-Level Domain)** — то, что ты регистрируешь: `example` в `example.com`.

**Поддомены** — всё, что слева от SLD: `www`, `api`, `mail`, `staging`. Можешь создавать любые, если владеешь доменом.

### FQDN

FQDN (Fully Qualified Domain Name) — полное доменное имя, включая все уровни до корня. `www.example.com.` — это FQDN. В конфигах и зонных файлах точка в конце важна — она показывает, что это абсолютное имя, а не относительное.

## 3. Как работает DNS-резолвинг

Когда приложение хочет узнать IP для `www.example.com`, происходит следующее:

### Шаг 1: Локальный кэш и /etc/hosts

Сначала система проверяет локальный кэш DNS и файл `/etc/hosts`. Если ответ там есть — запрос в сеть не уходит.

bashcopy

```bash
# Посмотреть /etc/hostscat /etc/hosts # Типичное содержимое:127.0.0.1   localhost::1         localhost192.168.1.10  myserver.local
```

`/etc/hosts` — способ задать соответствия локально. Полезно для тестирования или когда нужно переопределить DNS.

### Шаг 2: Запрос к резолверу

Если в кэше нет, система отправляет запрос DNS-резолверу. Адреса резолверов указаны в `/etc/resolv.conf`:

bashcopy

```bash
cat /etc/resolv.conf # Пример:nameserver 8.8.8.8nameserver 8.8.4.4search example.com
```

`nameserver` — IP DNS-сервера. Обычно это рекурсивный резолвер.

`search` — домен для дополнения коротких имён. Если написать `ping server`, система попробует `server.example.com`.

### Шаг 3: Рекурсивный запрос

Резолвер (например, 8.8.8.8) делает рекурсивный запрос. Если у него нет ответа в кэше, он идёт по иерархии:

![Схема в материале «Фундамент 2: DNS»: Клиент → Резолвер: "Какой IP у www.example.com?"](https://offers.prostodevops.ru/diagrams/extras/seti/fundament-2-dns-1.png)Схема в материале «Фундамент 2: DNS»: Клиент → Резолвер: "Какой IP у www.example.com?"

Резолвер кэширует все промежуточные ответы, чтобы не повторять запросы.

### Итеративный vs рекурсивный

**Рекурсивный резолвер** — делает всю работу за клиента. Клиент спросил — резолвер сам обошёл всю иерархию и вернул ответ. Так работают публичные DNS (8.8.8.8, 1.1.1.1) и локальные резолверы в сети.

**Авторитетный сервер** — отвечает только за свою зону. Он не ходит по иерархии, а отвечает итеративно: "я не знаю ответ, но спроси вот там".

## 4. Типы DNS-записей

### A и AAAA

**A-запись** — IPv4 адрес для домена.

codecopy

```
example.com.    IN  A     93.184.216.34www.example.com. IN  A     93.184.216.34
```

**AAAA-запись** — IPv6 адрес.

example.com.    IN  AAAA  2606:2800:220:1:248:1893:25c8:1946

Может быть несколько A-записей для одного домена — простейшая балансировка нагрузки (round-robin DNS).

### CNAME

**CNAME (Canonical Name)** — алиас, указывает на другое доменное имя.

codecopy

```
www.example.com.   IN  CNAME  example.com.blog.example.com.  IN  CNAME  myblog.wordpress.com.
```

Когда клиент запрашивает `www.example.com`, резолвер видит CNAME и делает ещё один запрос для `example.com`.

Важно: CNAME не может сосуществовать с другими записями для того же имени. Нельзя иметь CNAME и MX для одного поддомена. И нельзя делать CNAME для корня домена (`example.com`) — там должна быть A-запись.

Частая ошибка: пытаются сделать CNAME для `example.com` на CDN. Это не работает по стандарту. Некоторые DNS-провайдеры предлагают "ALIAS" или "ANAME" записи как обходной путь.

### MX

**MX (Mail Exchanger)** — почтовые серверы для домена.

codecopy

```
example.com.  IN  MX  10 mail1.example.com.example.com.  IN  MX  20 mail2.example.com.
```

Число — приоритет. Меньше = выше приоритет. Почта сначала пойдёт на `mail1`, и только если он недоступен — на `mail2`.

MX указывает на имя, не на IP. Для `mail1.example.com` нужна отдельная A-запись.

### TXT

**TXT** — текстовые записи. Используются для верификации и политик.

codecopy

```
example.com.  IN  TXT  "v=spf1 include:_spf.google.com ~all"example.com.  IN  TXT  "google-site-verification=abc123..."
```

Применения:

- **SPF** — указывает, какие серверы могут отправлять почту от имени домена
- **DKIM** — публичный ключ для проверки подписи писем
- **DMARC** — политика обработки писем, не прошедших проверку
- **Верификация** — подтверждение владения доменом для разных сервисов

### NS

**NS (Name Server)** — указывает авторитетные DNS-серверы для домена.

codecopy

```
example.com.  IN  NS  ns1.example.com.example.com.  IN  NS  ns2.example.com.
```

Когда регистрируешь домен, указываешь NS-серверы. Они будут отвечать за все записи в этом домене.

### SOA

**SOA (Start of Authority)** — метаданные о зоне. Одна на зону.

codecopy

```
example.com.  IN  SOA  ns1.example.com. admin.example.com. (                 2024010101  ; serial                 3600        ; refresh                 600         ; retry                 604800      ; expire                 86400       ; minimum TTL              )
```

Поля:

- **Serial** — версия зоны. Увеличивается при каждом изменении
- **Refresh** — как часто secondary DNS проверяет обновления
- **Retry** — через сколько повторить, если refresh не удался
- **Expire** — через сколько secondary перестанет отвечать, если не может связаться с primary
- **Minimum TTL** — минимальный TTL для негативного кэширования (NXDOMAIN)

### PTR

**PTR (Pointer)** — обратная запись, IP → имя. Используется для reverse DNS.

34.216.184.93.in-addr.arpa.  IN  PTR  example.com.

Обратите внимание: IP записывается в обратном порядке с суффиксом `in-addr.arpa`.

PTR важен для почты — многие серверы проверяют, что reverse DNS IP отправителя совпадает с доменом в HELO.

### SRV

**SRV (Service)** — указывает местоположение сервисов.

_sip._tcp.example.com.  IN  SRV  10 60 5060 sipserver.example.com.

Формат: `_сервис._протокол.домен`. Поля: приоритет, вес, порт, цель.

Используется для SIP, XMPP, LDAP и других протоколов, которые умеют SRV lookup.

### CAA

**CAA (Certification Authority Authorization)** — указывает, какие CA могут выпускать сертификаты для домена.

codecopy

```
example.com.  IN  CAA  0 issue "letsencrypt.org"example.com.  IN  CAA  0 issuewild "letsencrypt.org"
```

Если CAA настроен, CA обязан проверить его перед выпуском сертификата. Помогает предотвратить несанкционированный выпуск.

### Сводная таблица

|Тип|Назначение|Пример значения|
|---|---|---|
|A|IPv4 адрес|93.184.216.34|
|AAAA|IPv6 адрес|2606:2800:220:1:...|
|CNAME|Алиас на другое имя|www → example.com|
|MX|Почтовый сервер|10 mail.example.com|
|TXT|Текст (SPF, DKIM)|"v=spf1 ..."|
|NS|DNS-сервер зоны|ns1.example.com|
|SOA|Метаданные зоны|serial, refresh, ...|
|PTR|Reverse DNS|IP → имя|
|SRV|Сервис|_sip._tcp → host:port|
|CAA|Разрешённые CA|issue "letsencrypt.org"|

## 5. TTL — время жизни записи

**TTL (Time To Live)** — сколько секунд резолвер может кэшировать запись.

codecopy

```
example.com.  300  IN  A  93.184.216.34              ^^^              TTL = 300 секунд = 5 минут
```

После истечения TTL резолвер должен запросить запись заново.

### Как выбирать TTL

**Низкий TTL (60-300 секунд):**

- Плюс: быстрое распространение изменений
- Минус: больше запросов к DNS-серверам

Используй для записей, которые могут меняться: балансировка, failover, миграции.

**Высокий TTL (3600-86400 секунд):**

- Плюс: меньше нагрузка, быстрее резолвинг для пользователей
- Минус: изменения распространяются медленно

Используй для стабильных записей: MX, NS.

## 6. DNS-серверы

### Публичные резолверы

|Провайдер|Основной|Резервный|Особенности|
|---|---|---|---|
|Google|8.8.8.8|8.8.4.4|Быстрый, надёжный|
|Cloudflare|1.1.1.1|1.0.0.1|Фокус на приватность|
|Quad9|9.9.9.9|149.112.112.112|Блокирует вредоносные домены|
|OpenDNS|208.67.222.222|208.67.220.220|Фильтрация контента|
|Yandex|77.88.8.8|77.88.8.1|Для России|

### Локальные резолверы

В корпоративных сетях обычно свои DNS-серверы:

- Кэширование для ускорения
- Резолвинг внутренних доменов
- Политики безопасности

Популярные решения:

- **BIND** — классика, мощный, сложный
- **dnsmasq** — простой, часто используется на роутерах
- **Unbound** — современный, безопасный
- **CoreDNS** — облачно-ориентированный, используется в Kubernetes

### systemd-resolved

В современных Linux часто используется systemd-resolved. Он слушает на 127.0.0.53 и управляет DNS.

bashcopy

```bash
# Статус resolvedresolvectl status # Проверить, какой DNS используетсяresolvectl dns # DNS-статистикаresolvectl statistics
```

`/etc/resolv.conf` может быть симлинком на файл, управляемый systemd.

## 7. Диагностика DNS

### dig — основной инструмент

bashcopy

```bash
# Простой запрос A-записиdig example.com # Конкретный тип записиdig example.com MXdig example.com TXTdig example.com AAAA # Запрос к конкретному DNS-серверуdig @8.8.8.8 example.com # Короткий вывод — только ответdig +short example.com # Трассировка — показывает весь путь резолвингаdig +trace example.com # Reverse DNSdig -x 93.184.216.34
```

Что смотреть:

- **status: NOERROR** — запрос успешен. NXDOMAIN = домен не существует. SERVFAIL = ошибка сервера
- **ANSWER SECTION** — собственно ответ
- **86400** — TTL в секундах
- **Query time** — время ответа
- **SERVER** — какой DNS ответил

### nslookup

Старый инструмент, но иногда удобнее:

bashcopy

```bash
# Простой запросnslookup example.com # К конкретному серверуnslookup example.com 8.8.8.8 # Интерактивный режимnslookup> set type=MX> example.com
```

### host

Ещё проще:

bashcopy

```bash
# A-записьhost example.com # MX-записиhost -t MX example.com # Все записиhost -a example.com # Reversehost 93.184.216.34
```

### Проверка распространения DNS

Когда меняешь DNS-записи, полезно проверить, как они видны из разных точек:

bashcopy

```bash
# Проверить на разных публичных DNSdig @8.8.8.8 example.com +shortdig @1.1.1.1 example.com +shortdig @77.88.8.8 example.com +short
```

Или использовать онлайн-инструменты: whatsmydns.net, dnschecker.org.

### Очистка DNS-кэша

Локальный кэш:

bashcopy

```bash
# systemd-resolvedsudo resolvectl flush-caches # nscd (если используется)sudo nscd -i hosts # dnsmasqsudo systemctl restart dnsmasq
```

Браузеры имеют свой кэш DNS

## 8. Типичные проблемы и решения

### Проблема 1: Домен не резолвится (NXDOMAIN)

Симптомы:

- `dig example.com` возвращает `status: NXDOMAIN`
- Браузер показывает "DNS_PROBE_FINISHED_NXDOMAIN"

Причины:

- Домен не зарегистрирован или истёк → проверить whois, продлить
- Опечатка в имени → проверить написание
- NS-серверы не отвечают → проверить их работу
- Запись удалена → добавить обратно

### Проблема 2: Резолвится в неправильный IP

Симптомы:

- `dig` показывает старый IP
- Разные результаты с разных DNS

Причины:

- Кэш ещё не обновился → подождать TTL
- Запись не поменялась → проверить панель управления DNS
- DNS hijacking → проверить на авторитетном сервере

### Проблема 3: Резолвинг медленный

Симптомы:

- `dig` показывает Query time > 100-200 msec
- Страницы долго открываются первый раз

Причины:

- Медленный DNS-сервер → сменить на быстрый (1.1.1.1, 8.8.8.8)
- Сетевые проблемы до DNS → проверить ping/traceroute до DNS-сервера
- DNS-сервер далеко → использовать локальный кэширующий резолвер

### Проблема 4: Почта не доходит

Симптомы:

- Письма возвращаются с ошибками
- Письма попадают в спам

Частые проблемы:

- Нет MX-записи → добавить
- SPF не включает сервер отправки → добавить IP/домен в SPF
- Нет PTR для IP почтового сервера → настроить у хостера
- DMARC policy reject, но DKIM/SPF не настроены → настроить или смягчить policy

### Проблема 5: SERVFAIL

Симптомы:

- `dig` возвращает `status: SERVFAIL`
- Домен иногда резолвится, иногда нет

Причины:

- Авторитетный сервер не отвечает → проверить его работу
- Проблемы с DNSSEC → проверить подписи, отключить если не нужен
- Битая конфигурация зоны → проверить синтаксис зонного файла

## 9. DNS и безопасность

### DNSSEC

DNSSEC добавляет криптографические подписи к DNS-записям. Позволяет убедиться, что ответ пришёл от авторитетного сервера и не был изменён.

На практике DNSSEC используется не везде из-за сложности настройки и проблем с совместимостью.

### DNS over HTTPS (DoH) и DNS over TLS (DoT)

Классический DNS — нешифрованный UDP на порт 53. Провайдер видит все твои DNS-запросы.

**DoT (DNS over TLS)** — DNS поверх TLS, порт 853.

**DoH (DNS over HTTPS)** — DNS поверх HTTPS, порт 443.

Оба шифруют запросы, скрывая их от провайдера и атак man-in-the-middle.

Настройка в systemd-resolved:

inicopy

```ini
# /etc/systemd/resolved.conf[Resolve]DNS=1.1.1.1DNSOverTLS=yes
```

### DNS Rebinding и другие атаки

**DNS Rebinding** — атака, когда злоумышленник контролирует DNS и меняет ответ во время сессии. Сначала отдаёт свой IP, потом локальный (127.0.0.1 или внутренний). Браузер думает, что это тот же origin.

Защита: браузеры и резолверы блокируют резолвинг в приватные диапазоны для внешних доменов.

**DNS Amplification** — DDoS-атака через открытые DNS-резолверы. Маленький запрос с поддельным IP отправителя → большой ответ на жертву.

**Cache Poisoning** — подмена записей в кэше резолвера. DNSSEC защищает от этого.

## Что запомнить

1. **DNS — иерархическая система.** Корень → TLD → домен → поддомен. Резолвинг идёт по цепочке
    
2. **A-запись — IP, CNAME — алиас, MX — почта, TXT — верификация и политики**
    
3. **TTL определяет кэширование.** Низкий TTL = быстрые изменения. Перед миграцией — снижай TTL заранее
    
4. **dig — главный инструмент.** `dig @8.8.8.8 example.com` — быстрый способ проверить DNS
    
5. **NXDOMAIN = домен не существует, SERVFAIL = проблема с сервером**
    
6. **Для почты нужны MX + SPF + DKIM + PTR.** Без них письма будут в спаме
