## 1. Dockerfile: Основные инструкции

Команды в Dockerfile принято писать **UPPERCASE** (заглавными буквами), хотя это не строгое требование, а стандарт индустрии.

### Базовые команды

- **`FROM`** Первая строка любого Dockerfile. Задает базовый образ, от которого мы наследуемся.
    
- `FROM python:3.11-slim` — начинаем с Linux, где уже стоит Python.
    
- `FROM scratch` — пустой образ (для бинарников Go или Rust).
    
- **`WORKDIR`** Устанавливает рабочую директорию для всех последующих команд (`RUN`, `CMD`, `COPY`).
    
- _Аналог:_ `cd /app` в Linux.
    
- _Совет:_ Всегда используйте абсолютные пути. Если папки нет, Docker создаст её.
    
- **`COPY` vs `ADD**` Обе команды копируют файлы с хоста в образ.
    
- `COPY . .` — простой и предсказуемый вариант. Копирует файлы как есть. **Используйте его в 99% случаев.**
    
- `ADD` — умеет распаковывать `.tar.gz` архивы на лету и скачивать файлы по URL. Из-за неявного поведения используется редко.
    
- **`RUN`** Выполняет команду **на этапе сборки** образа. Результат выполнения (измененные файлы) сохраняется в новый слой.
    
- Пример: `RUN pip install flask` или `RUN apt-get update && apt-get install -y curl`.
    
- **`ENV`** Устанавливает переменные окружения. Они будут доступны и во время сборки, и во время работы контейнера.
    
- Пример: `ENV APP_ENV=production`.
    
- **`EXPOSE`** Декларативная инструкция. Она **не** публикует порт, а только сообщает человеку или оркестратору, что контейнер _слушает_ этот порт.
    
- Чтобы порт стал доступен, его все равно нужно пробрасывать флагом `-p` при запуске.
    

## 2. CMD и ENTRYPOINT

Это две инструкции, которые говорят контейнеру: «Что запустить, когда ты стартуешь?». Разница между ними критична.

### `CMD` (Command)

Задает команду по умолчанию и/или аргументы. Ее **легко переопределить** при запуске контейнера.

- Dockerfile: `CMD ["python", "app.py"]`
- Запуск: `docker run my-image` запустится питон.
- Запуск: `docker run my-image echo "hello"` питон **не** запустится, запустится `echo`.

### `ENTRYPOINT` (Точка входа)

Задает исполняемый файл, который будет запущен всегда. Аргументы из `docker run` будут переданы **внутрь** этой команды. Ее **сложно переопределить** (нужен флаг `--entrypoint`).

### Shell vs Exec форма

Всегда используйте формат JSON-массива (`["cmd", "arg"]`), а не строковый (`cmd arg`).

- **Плохо (Shell form):** `CMD python app.py`
    
- Запускает `/bin/sh -c python app.py`.
    
- Проблема: `PID 1` будет у оболочки `sh`, а не у вашего приложения. Сигналы остановки (`SIGTERM`) не дойдут до приложения, и Docker будет убивать его насильно.
    
- **Хорошо (Exec form):** `CMD ["python", "app.py"]`
    
- Запускает процесс напрямую. `PID 1` получает Python.
    

## 3. Контекст сборки и `.dockerignore`

Когда вы пишете `docker build .`, точка в конце означает **Build Context**. Docker CLI берет **все** файлы в этой папке, архивирует их и отправляет демону Docker.

Если у вас в папке лежит `.git` (100 МБ) или `node_modules` (500 МБ), сборка будет начинаться с долгой отправки этих данных демону, даже если вы их не используете в `COPY`.

**Решение:** Создайте файл `.dockerignore` (работает как `.gitignore`).

textcopy

```text
.gitnode_modules*.logtmp/
```

## 4. Оптимизация кэширования (Layer Caching)

Docker кэширует каждый слой. Если инструкция и файлы не изменились, он берет готовый слой из кэша. Порядок команд в Dockerfile критически важен для скорости сборки.

**Плохой пример:**

dockerfilecopy

```dockerfile
FROM python:3.9WORKDIR /appCOPY . .                  # <-- Копируем ВЕСЬ код (меняется часто)RUN pip install -r requirements.txt  # <-- Эта тяжелая операция будет выполняться заново при каждом изменении кодаCMD ["python", "main.py"]
```

**Хороший пример:**

dockerfilecopy

```dockerfile
FROM python:3.9WORKDIR /appCOPY requirements.txt .   # <-- Копируем только файл зависимостейRUN pip install -r requirements.txt  # <-- Если requirements.txt не менялся, этот слой берется из кэшаCOPY . .                  # <-- Теперь копируем код. Меняется часто, но это быстрая операция.CMD ["python", "main.py"]
```

## 5. Multi-Stage Builds (Многоэтапная сборка)

Это техника для уменьшения размера итогового образа. Например, для компиляции приложения на Go или C++ нужны компиляторы (GCC, Go tools), которые весят сотни мегабайт. Но для _запуска_ готового бинарника они не нужны.

**Суть:** В одном Dockerfile мы описываем несколько этапов (`FROM`).

1. **Stage 1 (Builder):** Большой образ с компиляторами. Собираем приложение.
2. **Stage 2 (Production):** Маленький образ (например, Alpine). Копируем туда _только_ готовый бинарник из первого этапа.

**Пример (Go):**

dockerfilecopy

```dockerfile
# ЭТАП 1: СборкаFROM golang:1.19 AS builderWORKDIR /appCOPY . .RUN go build -o myapp main.go # ЭТАП 2: Продакшн (начинаем с чистого листа)FROM alpine:latestWORKDIR /root/# Копируем только файл myapp из этапа builderCOPY --from=builder /app/myapp .CMD ["./myapp"]
```

_Результат:_ Образ весит 10 МБ вместо 800 МБ.

## 6. Итог

При написании Dockerfile смотрим, что есть:

1. **Конкретная версия в FROM:** Не используйте `latest`, пишите `node:16-alpine`.
2. **Порядок слоев:** Сначала зависимости (`package.json`, `requirements.txt`), потом установка, потом код приложения.
3. **Минимизация слоев:** Объединяйте связанные команды в один `RUN`: `RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*` (установка и очистка кэша в одном слое).
4. **Безопасность (User):** Не работайте под `root`. Создайте пользователя и переключитесь:

dockerfilecopy

```dockerfile
RUN adduser -D myuserUSER myuser
```

1. **Exec Form:** Используйте квадратные скобки для `CMD` и `ENTRYPOINT`.
2. **Dockerignore:** Исключите мусор и чувствительные данные.
