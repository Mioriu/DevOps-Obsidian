# Архитектура Docker

## 1. Введение: Почему важно понимать архитектуру

Когда вы набираете в терминале `docker run nginx`, происходит что-то простое: через пару секунд у вас запущен веб-сервер. Но за этой простотой скрывается цепочка компонентов

Docker построен по классической **клиент-серверной модели**. Есть три ключевых компонента:

1. **Docker Client** — то, с чем вы взаимодействуете (CLI).
2. **Docker Daemon (dockerd)** — фоновый процесс, который делает всю тяжёлую работу.
3. **Docker Registry** — удалённое хранилище образов.

Разберём каждый из них.

## 2. Docker Client (Клиент)

Docker Client — это ваш пульт управления. Когда вы вводите команду вроде `docker build`, `docker pull` или `docker run`, вы обращаетесь именно к клиенту.

Клиент сам по себе ничего не собирает, не скачивает и не запускает. Его задача — принять вашу команду, упаковать её в запрос и отправить по REST API в Docker Daemon.

### Клиент и демон не обязаны жить на одной машине

Это принципиальный момент. Docker Client может отправлять команды демону, который работает на другом сервере. Общение происходит через Unix-сокет (`/var/run/docker.sock`) на локальной машине или через TCP-соединение при удалённом подключении.

Именно поэтому возможны сценарии, когда вы с ноутбука управляете контейнерами на сервере в дата-центре, не заходя на него по SSH. Вы просто направляете клиент на удалённый демон:

bashcopy

```bash
# Указываем клиенту работать с удалённым демономexport DOCKER_HOST=tcp://192.168.1.100:2376docker ps  # Эта команда покажет контейнеры на удалённом сервере
```

## 3. Docker Daemon (dockerd)

Docker Daemon (`dockerd`) — это мозг всей системы. Он работает как фоновый процесс (системный сервис) на хостовой машине и берёт на себя всю работу:

- Сборку образов.
- Скачивание и хранение образов.
- Создание, запуск и остановку контейнеров.
- Управление сетями и томами.

Демон слушает входящие API-запросы от клиента и выполняет их. Но при этом он не работает с контейнерами напрямую. Для этого он обращается к нижележащему уровню — **Container Runtime**.

### Эволюция: от монолита к модулям

В ранних версиях Docker весь функционал был заложен в один монолитный бинарный файл. Демон и запускал контейнеры, и собирал образы, и управлял сетями. Это создавало проблемы:

- **Перезапуск демона убивал все контейнеры.** Если нужно было обновить Docker, все запущенные приложения останавливались.
- **Сложность разработки.** Изменение одного компонента требовало пересборки всего проекта.

Поэтому архитектура Docker была разделена на независимые компоненты. И ключевой из них — **containerd**.

## 4. Container Runtime: containerd и runc

Здесь мы спускаемся на уровень ниже — туда, где контейнеры рождаются и живут.

### containerd

**containerd** — это высокоуровневый рантайм контейнеров. Docker Daemon делегирует ему управление жизненным циклом контейнера:

- Скачивание образов из реестра.
- Управление хранилищем образов и слоёв.
- Создание и уничтожение контейнеров.
- Управление сетевыми подключениями.

containerd — это самостоятельный проект, который живёт отдельно от Docker и входит в экосистему CNCF (Cloud Native Computing Foundation). Именно поэтому Kubernetes может работать с containerd напрямую, без Docker.

### runc

**runc** — это низкоуровневый рантайм. Именно он выполняет финальный шаг: создаёт контейнер как процесс в операционной системе. runc обращается к ядру Linux и настраивает те самые **Namespaces** и **Cgroups**, о которых мы говорили ранее.

После того как runc создал контейнер и запустил процесс, он завершает свою работу. Контейнер продолжает жить как дочерний процесс containerd.

### Как это работает вместе

Вот упрощённая цепочка вызовов при запуске контейнера:

Именно благодаря этому разделению можно перезапустить Docker Daemon, не останавливая контейнеры. containerd продолжает работать, а контейнеры живут под его контролем.

## 5. Docker Registry (Реестр образов)

Registry — это склад, где хранятся Docker-образы. Когда вы собираете образ на своём компьютере, он существует только локально. Чтобы передать его коллегам или развернуть на сервере, вам нужен реестр.

### Docker Hub

**Docker Hub** (`hub.docker.com`) — это публичный реестр по умолчанию. Когда вы пишете `docker pull nginx`, Docker идёт именно туда. На Docker Hub хранятся:

- **Официальные образы** (Official Images): `nginx`, `postgres`, `python`, `node`. Они поддерживаются командой Docker и проходят проверки безопасности.
- **Образы сообщества**: Любой пользователь может загрузить свой образ. Формат имени: `username/image_name`.

### Приватные реестры

В реальной работе компании не хранят свой код в публичном реестре. Для этого существуют приватные решения:

- **Docker Hub Private Repositories** — платные приватные репозитории на том же Docker Hub.
- **Self-Hosted реестры**: Компания разворачивает собственный реестр на своих серверах.
    - **Harbor** — популярное решение с контролем доступа, сканированием уязвимостей и репликацией.
    - **Nexus Repository** — универсальное хранилище артефактов (не только Docker).
    - **Docker Registry** — минимальный open-source реестр от Docker.
- **Облачные реестры**: Реестры, встроенные в облачных провайдеров.
    - **Yandex Container Registry**
    - **AWS ECR (Elastic Container Registry)**
    - **Google Artifact Registry**
    - **Azure Container Registry**
    - **GitLab Container Registry** — встроен прямо в GitLab, что удобно для CI/CD.

### Push и Pull

Работа с реестром сводится к двум операциям:

bashcopy

```bash
# Скачать образ из реестра на локальную машинуdocker pull my-registry.company.ru/backend:v2.1 # Загрузить собранный образ в реестрdocker push my-registry.company.ru/backend:v2.1
```

Перед пушем образ нужно тегировать, указав адрес вашего реестра:

bashcopy

```bash
# Собрали образ локальноdocker build -t backend:v2.1 . # Пометили его для нужного реестраdocker tag backend:v2.1 my-registry.company.ru/backend:v2.1 # Отправилиdocker push my-registry.company.ru/backend:v2.1
```

## 6. Полная картина: Что происходит при `docker run`

Теперь, когда мы разобрали каждый компонент, давайте проследим весь путь команды от нажатия Enter до работающего контейнера.

Допустим, вы выполнили:

docker run -d -p 8080:80 --name web nginx

Вот что произойдёт:

1. **Docker Client** принимает команду и формирует API-запрос к демону.
    
2. **Docker Daemon** получает запрос и проверяет, есть ли образ `nginx` локально.
    
3. Образа нет → демон обращается к **Docker Registry** (Docker Hub) и скачивает образ `nginx:latest` послойно. Слои, которые уже есть локально от других образов, не скачиваются повторно.
    
4. Образ скачан. Демон отдаёт команду **containerd**: «создай контейнер из этого образа с такими параметрами».
    
5. **containerd** готовит окружение (файловую систему из слоёв образа, сетевой интерфейс) и вызывает **runc**.
    
6. **runc** обращается к ядру Linux: создаёт Namespaces (PID, NET, MNT), настраивает Cgroups, монтирует файловую систему и запускает процесс `nginx`. После этого runc завершается.
    
7. Контейнер работает. containerd следит за его состоянием. Порт 8080 хоста проброшен на порт 80 контейнера.
