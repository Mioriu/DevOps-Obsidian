## Чем отличается от Ansible

Ansible настраивает то, что внутри сервера: пакеты, конфиги, пользователей, сервисы. Но сам сервер при этом уже должен существовать – кто-то его создал, выдал IP и доступ по SSH.

![Terraform и Ansible: разные слои инфраструктуры](https://prostodevops.ru/api/uploads/lessons/terraform-providers-resources-state-01.webp)Terraform и Ansible: разные слои инфраструктуры

Terraform работает ниже, он создает саму инфраструктуру. Виртуальные машины, сети, диски, балансировщики, DNS-записи, managed-базы – все, что в облаке обычно заводится кликами в веб-консоли, описывается кодом и создается из кода.

Подход тот же, что в Ansible, декларативное описание желаемого состояния, файлы в Git, ревью, повторный запуск. Но есть два различия.

Первое – `state`. Все созданное Terraform фиксирует в файле состояния, и при каждом запуске код сравнивается с этим учетом: чего не хватает – создается, что изменилось – приводится к коду. У Ansible никакого учета нет, модули каждый раз сверяются с реальностью на самом сервере.

Второе вытекает из первого – полный жизненный цикл. Terraform умеет не только создавать и изменять, но и удалять. Убрали блок ресурса из кода – при следующем применении ресурс удалится из облака. В Ansible наоборот: удалили задачу из плейбука – на сервере ничего не произойдет, установленный пакет останется стоять.

|Слой|Ansible|Terraform|
|---|---|---|
|Где работает|Настройка внутри сервера|Создание инфраструктуры|
|Подключение|SSH к серверам|API облака|
|Язык|YAML|HCL|
|Учет созданного|Нет, сверка с реальностью|State-файл|
|Удаление убранного из кода|Нет|Да|


## HCL

Конфигурация Terraform пишется не на YAML, а на HCL – HashiCorp Configuration Language. Файлы имеют расширение `.tf`, и все `.tf`-файлы в директории читаются вместе, как один большой конфиг – раскладка по файлам нужна только для удобства нас с вами.

Язык построен на блоках. Блок – это тип, метки и тело в фигурных скобках, внутри тела аргументы в виде `имя = значение`:

HCL

Копировать

```hcl
resource "docker_container" "web" {
  name  = "web"
  image = "nginx:1.25"
}
```

Строки в кавычках, числа и логические значения без, комментарии через `#`. Отступы – для читаемости, на смысл не влияют, в отличие от YAML.

И главное про HCL: порядок блоков в файле не имеет значения. В Ansible задачи выполняются строго сверху вниз, здесь же описывается набор ресурсов, а порядок их создания выводится из зависимостей между ними – к этому вернемся ниже на примере.

## Providers

В самом Terraform нет поддержки ни одного облака. Вся работа с конкретными платформами вынесена в провайдеры – плагины, каждый из которых реализует API своей платформы: Selectel, Yandex Cloud, Docker. Провайдеров тысячи, лежат они в публичном реестре [registry.terraform.io](http://registry.terraform.io/).

Нужные провайдеры объявляются в блоке `terraform`, а их подключение настраивается в блоке `provider`:

![Блок HCL: провайдер дает типы ресурсов](https://prostodevops.ru/api/uploads/lessons/terraform-providers-resources-state-02.webp)Блок HCL: провайдер дает типы ресурсов

`source` – адрес провайдера в реестре, `version` – ограничение версии. Конструкция `~> 3.0` означает «любая 3.x, но не 4» – версию закрепляют по той же причине, что и везде. В блоке `provider` живут настройки подключения: для облака это токен и регион, для Docker-провайдера достаточно пустого блока – подключение идет к локальному демону.

Для первых уроков мы возьмем именно Docker-провайдер: он создает образы, контейнеры и сети – все то, что вы делали руками в модуле про Docker, – и для него не нужен аккаунт в облаке. Механика при этом ровно та же, что с виртуальными машинами: меняется только провайдер и типы ресурсов.

## Resources

Ресурс – основной блок Terraform, единица инфраструктуры: одна машина, одна сеть, один контейнер. У блока две метки – тип и имя:

HCL

Копировать

```hcl
resource "docker_image" "nginx" {
  name = "nginx:1.25"
}

resource "docker_container" "web" {
  name  = "web"
  image = docker_image.nginx.image_id

  ports {
    internal = 80
    external = 8080
  }
}
```

Тип (`docker_image`, `docker_container`) определяется провайдером – у каждого провайдера свой набор типов с префиксом: у Docker это `docker_*`, у Yandex Cloud – `yandex_compute_instance` и прочие `yandex_*`, у AWS – `aws_*`. Какие аргументы принимает тип, смотрится в документации провайдера на том же [registry.terraform.io](http://registry.terraform.io/).

Имя (`nginx`, `web`) – внутреннее, для ссылок внутри кода. На название реального объекта оно не влияет: контейнер будет называться `web` потому, что так задано аргументом `name`, а не меткой блока.

## Ссылки между ресурсами

В примере выше у контейнера стоит `image = docker_image.nginx.image_id` – без кавычек. Это ссылка на атрибут другого ресурса в формате `тип.имя.атрибут`: подставится идентификатор образа, который появится после его создания.

Из таких ссылок складываются зависимости.

![Ссылка между ресурсами задает зависимость и порядок создания](https://prostodevops.ru/api/uploads/lessons/terraform-providers-resources-state-03.webp)Ссылка между ресурсами задает зависимость и порядок создания

Контейнер ссылается на образ – значит образ создается первым, контейнер вторым. Прописывать порядок нигде не нужно, он вычисляется из ссылок, и блоки в файле могут стоять как угодно: хоть контейнер выше образа. Ресурсы, которые друг от друга не зависят, вообще создаются параллельно.
