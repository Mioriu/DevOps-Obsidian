Мы написали уже достаточно плейбуков, разобрались с шаблонами, хэндлерами, переменными. И если вы честно практиковались, то наверняка заметили одну проблему — плейбуки разрастаются. Сначала у вас было двадцать строк, потом пятьдесят, потом сто, потом двести. В какой-то момент вы открываете файл и понимаете, что тут и nginx, и PostgreSQL, и мониторинг, и пользователи, и файрвол — всё в одной простыне. Найти что-то конкретное — сложно. Переиспользовать кусок для другого проекта — невозможно без копипасты. И вот тут нам нужны роли

## Зачем нужны роли

Роль — это, по сути, способ разбить ваш огромный плейбук на логические блоки. Вместо одного файла, где всё свалено в кучу, вы получаете набор ролей: роль для nginx, роль для PostgreSQL, роль для мониторинга. Каждая роль — это отдельная папка со своей структурой, своими тасками, шаблонами, хэндлерами, переменными.

И вот ключевой момент — роль можно переиспользовать. Написали роль для nginx в одном проекте — подключили в другой. Коллега написал роль для Redis — вы её взяли к себе. Или вообще скачали готовую роль из Ansible Galaxy, подключили, и не писали ничего с нуля

## Создание роли через ansible-galaxy init

Можно, конечно, создать все папки руками. Но зачем, если есть команда, которая сделает это за вас:

ansible-galaxy init roles/nginx

Эта команда создаст полную структуру роли в папке `roles/nginx`. Давайте посмотрим, что она нагенерит:

## Директории роли — что где лежит

### tasks/

Тут лежат таски — то, что роль реально делает. Файл `tasks/main.yml` — это точка входа. Когда Ansible подключает роль, он первым делом идёт сюда.

yamlcopy

```yaml
# roles/nginx/tasks/main.yml---- name: Установить nginx  apt:    name: nginx    state: present    update_cache: yes - name: Сгенерировать основной конфиг  template:    src: nginx.conf.j2    dest: /etc/nginx/nginx.conf    owner: root    group: root    mode: "0644"  notify: Перезагрузить nginx - name: Сгенерировать конфиги сайтов  template:    src: site.conf.j2    dest: "/etc/nginx/conf.d/{{ item.domain }}.conf"  loop: "{{ nginx_sites }}"  notify: Перезагрузить nginx - name: Запустить и включить nginx  service:    name: nginx    state: started    enabled: yes
```

Обратите внимание — тут нет `hosts`, нет `become`, нет `vars`. Только таски. Всё остальное задаётся на уровне плейбука, когда роль подключается. Роль — это просто набор задач, она не знает, на каких серверах будет работать.

Если тасков становится много, можно разбить на несколько файлов и подключить через `include_tasks`:

yamlcopy

```yaml
# roles/nginx/tasks/main.yml---- name: Установка  include_tasks: install.yml - name: Настройка конфигов  include_tasks: configure.yml - name: Настройка SSL  include_tasks: ssl.yml  when: nginx_ssl_enabled | default(false)
```

И в каждом файле — свой кусок логики. Так гораздо читаемее, чем один файл на триста строк.

### handlers/

Тут лежат хэндлеры. Всё точно так же, как в плейбуке, только в отдельном файле:

yamlcopy

```yaml
# roles/nginx/handlers/main.yml---- name: Перезагрузить nginx  service:    name: nginx    state: reloaded - name: Перезапустить nginx  service:    name: nginx    state: restarted
```

Таски из `tasks/main.yml` могут вызывать эти хэндлеры через `notify` как обычно. Ansible сам подхватит хэндлеры из роли, не нужно ничего дополнительно подключать.

### templates/

Тут лежат шаблоны. И вот прикол — когда вы в таске пишете `src: nginx.conf.j2`, Ansible автоматически ищет этот файл в папке `templates/` текущей роли. Не нужно писать полный путь `src: roles/nginx/templates/nginx.conf.j2`. Просто `src: nginx.conf.j2` — и всё.

jinja2copy

```jinja2
{# roles/nginx/templates/nginx.conf.j2 #}# {{ ansible_managed }} user www-data;worker_processes {{ nginx_worker_processes | default(ansible_processor_cores) }};pid /run/nginx.pid; events {    worker_connections {{ nginx_worker_connections | default(1024) }};} http {    sendfile on;    keepalive_timeout 65;     include /etc/nginx/mime.types;    include /etc/nginx/conf.d/*.conf;}
```

### files/

Тут лежат файлы, которые копируются как есть, без шаблонизации. Через модуль `copy`. Аналогично шаблонам — Ansible сам ищет файлы в папке `files/` роли.

yamlcopy

```yaml
    - name: Скопировать кастомную страницу ошибки      copy:        src: 50x.html           # ищет в roles/nginx/files/50x.html        dest: /usr/share/nginx/html/50x.html
```

Типичный контент для `files/` — статические конфиги, скрипты, сертификаты, HTML-страницы. Всё, что не требует подстановки переменных.

### defaults/ — дефолтные значения переменных

Вот это прямо суперважная директория. Тут задаются значения переменных по умолчанию. У них самый низкий приоритет из всех переменных в Ansible. Это значит, что их легко переопределить из любого другого места — из `group_vars`, из `host_vars`, из плейбука, откуда угодно.

yamlcopy

```yaml
# roles/nginx/defaults/main.yml---nginx_worker_processes: autonginx_worker_connections: 1024nginx_keepalive_timeout: 65nginx_ssl_enabled: falsenginx_sites: []nginx_extra_configs: []
```

Зачем это нужно? Чтобы роль работала из коробки, даже если пользователь не задал ни одной переменной. Поставил роль, подключил — nginx встал с дефолтными настройками. Хочет кастомизировать — переопределяет нужные переменные в `group_vars` или `host_vars`. Не хочет — работает на дефолтах.

Открыл `defaults/main.yml` — и сразу видишь, какие переменные роль использует и какие значения у них по умолчанию. Хорошая практика — задавать тут все переменные, которые роль использует, даже если значение по умолчанию — пустая строка или пустой список.

### vars/

На первый взгляд похоже на `defaults/`, но разница принципиальная. Переменные из `vars/` имеют высокий приоритет — их сложно переопределить. Они перебивают `group_vars`, `host_vars` и много чего ещё.

yamlcopy

```yaml
# roles/nginx/vars/main.yml---nginx_config_dir: /etc/nginxnginx_log_dir: /var/log/nginxnginx_pid_file: /run/nginx.pid
```

Сюда кладут переменные, которые не должны меняться пользователем. Константы роли, так скажем. Путь к конфигу nginx — он всегда `/etc/nginx`, зачем его менять? Вот это — в `vars/`. А количество воркеров, которое пользователь может захотеть поменять — в `defaults/`.

### meta/

Тут описывается информация о самой роли и её зависимости:

yamlcopy

```yaml
# roles/nginx/meta/main.yml---galaxy_info:  author: your_name  description: Роль для установки и настройки nginx  license: MIT  min_ansible_version: "2.14"  platforms:    - name: Ubuntu      versions:        - focal        - jammy dependencies:  - role: common  - role: firewall    vars:      firewall_allowed_ports:        - 80        - 443
```

Самое полезное тут — `dependencies`. Если ваша роль nginx зависит от роли common (которая ставит базовые пакеты) и роли firewall (которая должна открыть порты) — вы указываете это здесь. Ansible автоматически выполнит зависимые роли перед вашей.

### tests/

Тут лежит минимальный плейбук для тестирования роли:

yamlcopy

```yaml
# roles/nginx/tests/test.yml---- name: Тестирование роли nginx  hosts: localhost  become: true  roles:    - nginx
```

На практике для серьёзного тестирования используют Molecule — это отдельный инструмент, который мы разберём позже. Но для быстрой проверки — `tests/` вполне достаточно.

## Подключение роли в плейбук

Окей, роль создана, таски написаны, шаблоны лежат. Теперь нужно её подключить в плейбук. Есть три способа.

### Способ 1: секция roles (классический)

yamlcopy

```yaml
---- name: Настройка веб-серверов  hosts: webservers  become: true   roles:    - nginx    - postgresql    - monitoring
```

Самый простой и распространённый способ. Ansible ищет роли в папке `roles/` рядом с плейбуком. Роли выполняются в том порядке, в котором указаны — сначала nginx, потом postgresql, потом monitoring.

Можно передать переменные прямо при подключении:

yamlcopy

```yaml
  roles:    - role: nginx      vars:        nginx_worker_processes: 8        nginx_sites:          - domain: app.company.com            upstream_host: 127.0.0.1            upstream_port: 8080     - role: postgresql      vars:        postgresql_version: 15
```

Или с тегами:

yamlcopy

```yaml
  roles:    - role: nginx      tags: nginx    - role: postgresql      tags: database
```

Тогда `ansible-playbook playbook.yml --tags nginx` выполнит только роль nginx.

### Способ 2: include_role (динамическое подключение)

yamlcopy

```yaml
  tasks:    - name: Что-то сделать перед nginx      debug:        msg: "Подготовка..."     - name: Подключить роль nginx      include_role:        name: nginx      vars:        nginx_worker_processes: 4     - name: Что-то сделать после nginx      debug:        msg: "Nginx настроен!"
```

`include_role` подключает роль прямо в середине тасков. Это полезно, когда нужно выполнить какие-то задачи до или после роли, и важен порядок. При использовании секции `roles` все роли выполняются до тасков из секции `tasks`.

### Способ 3: import_role (статическое подключение)

yamlcopy

```yaml
  tasks:    - name: Подключить роль nginx      import_role:        name: nginx
```

Похоже на `include_role`, но есть разница. `import_role` подключает роль на этапе парсинга плейбука (статически), а `include_role` — на этапе выполнения (динамически). На практике это значит:

— `import_role` — теги и хэндлеры из роли видны на верхнем уровне, `--list-tasks` покажет все таски роли. Но нельзя использовать в циклах и с динамическим `when`. — `include_role` — можно использовать в циклах, с динамическими условиями. Но теги из роли не всегда подхватываются, `--list-tasks` может не показать таски.

Для большинства случаев подойдёт секция `roles` или `include_role`. `import_role` используется реже.

### Порядок выполнения: roles vs tasks

Если в плейбуке есть и `roles`, и `tasks`:

yamlcopy

```yaml
- name: Настройка серверов  hosts: all  become: true   pre_tasks:    - name: Обновить кэш пакетов      apt:        update_cache: yes   roles:    - nginx    - postgresql   tasks:    - name: Финальная проверка      debug:        msg: "Всё настроено!"   post_tasks:    - name: Отправить уведомление      debug:        msg: "Деплой завершён"
```

Порядок выполнения:

1. `pre_tasks` — до ролей.
2. `roles` — сами роли.
3. `tasks` — после ролей.
4. `post_tasks` — в самом конце.

Хэндлеры вызываются после каждого из этих блоков. То есть, если таск в `pre_tasks` дернул хэндлер — он выполнится между `pre_tasks` и `roles`.

## Где Ansible ищет роли

По умолчанию Ansible ищет роли в нескольких местах:

1. Папка `roles/` рядом с плейбуком.
2. Путь из `roles_path` в `ansible.cfg`.
3. `~/.ansible/roles/` — глобальная папка.
4. `/etc/ansible/roles/` — системная папка.

На практике почти всегда роли лежат в `roles/` рядом с плейбуком. Можно изменить в конфиге:

inicopy

```ini
[defaults]roles_path = ./roles:/opt/shared-roles
```

Через двоеточие можно указать несколько путей. Удобно, если у вас есть общие роли для нескольких проектов.

## Полный пример — проект с ролями

Вот как выглядит нормально организованный проект:

![Ansible проект с ролями: common + nginx + postgresql + monitoring](https://offers.prostodevops.ru/diagrams/ansible/ansible-roles-project.png)Ansible проект с ролями: common + nginx + postgresql + monitoring

А плейбук `site.yml`:

yamlcopy

```yaml
---- name: Общая настройка всех серверов  hosts: all  become: true  roles:    - common - name: Настройка веб-серверов  hosts: webservers  become: true  roles:    - role: nginx      tags: nginx - name: Настройка баз данных  hosts: databases  become: true  roles:    - role: postgresql      tags: database - name: Настройка мониторинга  hosts: monitoring  become: true  roles:    - role: monitoring      tags: monitoring
```

Чистый, читаемый плейбук. Вся логика — в ролях. Переменные — в `group_vars` и `defaults`. Один взгляд на `site.yml` — и понятно, что происходит: сначала общая настройка на всех, потом nginx на вебах, PostgreSQL на базах, мониторинг на мониторинге.
