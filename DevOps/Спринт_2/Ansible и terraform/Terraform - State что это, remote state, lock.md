## Что внутри state

После первого `apply` в директории появляется `terraform.tfstate` – мы уже выяснили, что это учет созданного и что в Git ему не место.

Внутри state – JSON с соответствием между кодом и реальными объектами: для каждого ресурса записан его адрес в коде (`docker_container.web`), идентификатор реального объекта и все его атрибуты. Это соответствие и есть главная ценность. В коде написано «контейнер web», в облаке крутятся десятки контейнеров – без state не определить, какой из них принадлежит этому конфигу, что можно изменять, а что чужое.

Смотреть state удобнее не в самом JSON, а командами:

Bash

Копировать

```bash
terraform state list                        # все ресурсы под управлением
terraform state show docker_container.web   # атрибуты конкретного ресурса
```

Редактором state не правится никогда – одна кривая запятая, и учет поплыл. Для редких операций вроде переименования ресурса в учете есть команды `terraform state mv` и `terraform state rm`, но это инструменты на особый случай.

## Код, state, реальность

При каждом `plan` сравниваются три картины: код, state и реальное положение дел – атрибуты живых объектов перечитываются через API.

![State сравнивает три картины: код, state, реальность](https://prostodevops.ru/api/uploads/lessons/terraform-state-remote-lock-01.webp)State сравнивает три картины: код, state, реальность

Из этого складывается поведение, которое стоит проверить руками.

Допустим удалим контейнер мимо Terraform: `docker rm -f frontend`. В коде он есть, в state числится, в реальности пропал – `plan` покажет `+`, и `apply` создаст контейнер заново. Поменяем что-то руками – например, через консоль облака изменим параметр машины – `plan` покажет `~` обратно к значению из кода.

То есть ручные правки мимо кода живут до следующего `apply`.

## Проблемы локального state

Пока вы работаете один на своей машине, локальный файл всем устраивает. Но дальше (как обычно) начинаются проблемы.

Коллега клонирует репозиторий с кодом – но state в Git не лежит, у коллеги его нет. Он запускает `apply`, и по его пустому state выходит, что не создано ничего: Terraform пойдет создавать всю инфраструктуру заново. В лучшем случае упадет на занятых именах, в худшем – наплодит дублей, которые ни в одном месте толком не числятся.

## Remote state

Решение всех проблем – хранить state не на чьей-то машине, а в общем удаленном хранилище.

![Локальный state против remote backend](https://prostodevops.ru/api/uploads/lessons/terraform-state-remote-lock-02.webp)Локальный state против remote backend

Это называется backend: блок в конфигурации, который задает, где живет state. Все участники работают с одной версией.

Самый ходовой backend – `s3`, любое S3-совместимое объектное хранилище. В наших реалиях это Yandex Object Storage или что-то наподобие:

HCL

Копировать

```hcl
terraform {
  backend "s3" {
    endpoints = {
      s3 = "https://storage.yandexcloud.net"
    }
    bucket = "myproject-tfstate"
    key    = "infra/terraform.tfstate"
    region = "ru-central1"

    skip_region_validation      = true
    skip_credentials_validation = true
    skip_requests_signing       = true
  }
}
```

`bucket` – имя бакета, `key` – путь к файлу state внутри него: в одном бакете спокойно живут state нескольких проектов под разными `key`. Флаги `skip_*` отключают AWS-специфичные проверки, которые к Yandex-хранилищу неприменимы. Ключи доступа к бакету в код не пишутся – передаются через переменные окружения (`AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`, имена исторически от AWS).

После добавления блока запускается `terraform init` – обнаружив смену backend, он предложит перенести существующий локальный state в хранилище. Дальше все команды работают как раньше, только state читается и пишется в бакет.

Два обязательных штриха к такому бакету. Доступ – только участникам проекта: в state открытым текстом лежат все атрибуты вплоть до паролей. И версионирование – включенная история версий объекта превращает побитый или ошибочно перезаписанный state из катастрофы в откат на предыдущую версию.

## Lock

Общий state открывает новую проблему: двое запускают `apply` одновременно. Оба читают, оба меняют инфраструктуру, оба пишут state – кто записал последним, тот затер изменения первого. Учет разъехался с реальностью.

Для этого есть блокировка: на время любой операции, меняющей state, ставится lock, и параллельный запуск не начнется, а упадет с ошибкой:

![Lock: защита state от параллельной записи](https://prostodevops.ru/api/uploads/lessons/terraform-state-remote-lock-03.webp)Lock: защита state от параллельной записи

В ошибке видно, кто держит блокировку и с какого момента – обычно это значит «коллега сейчас катит, подожди». У S3-бэкенда блокировка делается через DynamoDB-совместимую таблицу, в Yandex Cloud для этого используется YDB – ее адрес и имя таблицы добавляются в тот же блок backend:

HCL

Копировать

```hcl
    endpoints = {
      s3       = "https://storage.yandexcloud.net"
      dynamodb = "https://docapi.serverless.yandexcloud.net/ru-central1/b1g.../etn..."
    }
    dynamodb_table = "tf-lock"
```

Отдельный случай – повисшая блокировка: процесс упал посреди `apply`, lock снять не успел, и теперь все запуски падают с той же ошибкой, хотя никто ничего не катит. Снимается руками по ID из сообщения:

terraform force-unlock b2f3...

Команда именно для таких ситуаций. Снимать чужой живой lock, чтобы «не ждать», – прямой путь к побитому state: сначала выясняется, не идет ли у кого-то применение прямо сейчас.
