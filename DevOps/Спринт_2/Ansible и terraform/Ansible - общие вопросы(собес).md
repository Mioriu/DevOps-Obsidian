Ну например вам нужно через за 5 минут проверить версию Python на сотне серваков или быстро перезапустить сервис на всех веб серверах. Писать полноценный плейбук для такой простой задачи избыточно - можно юзать ad-hoc команды. Это одноразки (команды), которые выполняются прямо из командной строки без создания каких-либо доп файлов  
Вы указываете группу хостов, модуль Ansible и его параметры, и команда выполняется. Например, команда `ansible webservers -m ping` пропингует все сервера в группе webservers. Более сложный пример: `ansible all -m yum -a "name=nginx state=latest" --become` обновит Nginx на всех серверах.

# Что такое роли в ansible, пример

Роли в Ansible - это структура, способ, который позволяет в удобном виде писать и пользоваться всем функционалом ансибла. Например вам чтобы настроить сервер нужно поставить туда nginx, настроить его, поставить БД (postgre), настроить ее, поставить всякие доп. утилиты, что-то сделать с пользователями и т.д., можно до бесконечности продолжать. Так вот, если писать это все в одном плейбуке, то это получится огромная портянка на кучу строк, с которой невозможно работать ни вам, ни тем более другим. Поэтому придумали роли, у которых есть своя структура. Вот пример:

diagramcopy

```
# Структура директорий роли nginx
nginx/
├── tasks/              # Основные задачи
│   └── main.yml       
├── handlers/           # Обработчики 
│   └── main.yml       
├── templates/          # Шаблоны конфигов
│   └── nginx.conf.j2  
├── files/              # Статические файлы
│   └── index.html    
├── vars/               # Переменные роли
│   └── main.yml       
├── defaults/           # Значения по умолчанию
│   └── main.yml       
├── meta/               # Метаданные и зависимости
│   └── main.yml       
└── README.md           # Документация

# tasks/main.yml - основная логика роли
---
- name: Установка Nginx
  package:
    name: nginx
    state: present
  tags:
    - nginx
    - packages

- name: Копирование конфигурации
  template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    backup: yes
  notify: restart nginx
  tags:
    - nginx
    - configuration

- name: Обеспечение запуска сервиса
  service:
    name: nginx
    state: started
    enabled: yes
  tags:
    - nginx
    - service
```

Роль разделяет всю логику настройки Nginx: установку пакета, конфигурирование, управление сервисом. При этом роль параметризована - через переменные можно изменить порт, количество воркеров, пути к логам. Любую роль можно использовать в плейбуках простой строкой: `roles: - nginx`

# Приоритеты переменных в Ansible

Переменные в Ansible имеют строгую иерархию. Значения, определённые на более высоком уровне, переопределяют значения с более низкого уровня.

_(от наименьшего приоритета к наибольшему)_

1. **defaults/main.yml** Значения по умолчанию для роли. Самый низкий приоритет, предназначены для базовых настроек.
    
2. **Переменные в inventory** Переменные, определённые для групп и хостов непосредственно в файле инвентаря.
    
3. **group_vars/all** Переменные, применяемые ко всем хостам.
    
4. **group_vars/groupname** Переменные для конкретных групп хостов.
    
5. **host_vars/hostname** Переменные для конкретного хоста, обеспечивают точечную настройку.
    
6. **Факты хоста (Facts)** Информация, автоматически собранная Ansible с управляемого узла (ОС, IP-адреса, память).
    
7. **vars/main.yml (в роли)** Основные переменные роли. Имеют более высокий приоритет, чем `defaults`.
    
8. **Переменные Playbook (`vars`, `vars_prompt`)** Переменные, определённые непосредственно в плейбуке.
    
9. **Переменные из `include_vars` и `set_fact`** Переменные, загруженные из файлов или созданные динамически во время выполнения задачи.
    
10. **Переменные задачи (`task vars`)** Переменные, определённые на уровне конкретной задачи.
    
11. **Extra vars (`-e`)** Переменные, переданные через командную строку при запуске `ansible-playbook`. Имеют наивысший приоритет и переопределяют абсолютно всё.
    

# Как выполнить плейбук на тысяче серверов параллельно

Ключевой параметр - forks, определяющий количество параллельных процессов. По умолчанию это 5, то бишь только 5 хостов одновременно. Для тысячи серверов это около вечности. Увеличиваем forks в ansible.cfg или через терминал: `ansible-playbook -f 100 site.yml`. Однако устанавливать слишком большие значения не очень круто - каждый fork потребляет память и CPU на управляющей машинке Также нам важна стратегия. По умолчанию используется linear стратегия - Ansible ждет завершения задачи на всех хостах перед переходом к следующей. Для массовых вещей лучше подходит free стратегия, где каждый хост продвигается по таскам независимо: `strategy: free` в плейбуке.

# Что такое идемпотентность?

Идемпотентность - это свойство операции давать одинаковый результат независимо от количества применений.

Например посмотрим на идемпотентную операцию: "убедиться, что пакет nginx установлен". Первый запуск установит пакет, последующие запуски проверят его наличие и не будут ничего делать.

Противоположный пример - неидемпотентная операция: "добавить строку в файл". Каждый запуск добавит еще одну копию строки, постепенно засоряя файл дублями. Или команда "увеличить счетчик на 1" - каждое выполнение изменяет состояние.  
Ansible обеспечивает идемпотентность через декларативный подход. Вы описываете желаемое состояние, а не последовательность действий. Модуль `user` с параметром `state: present` создаст пользователя, если его нет, или оставит существующего без изменений. Модуль `lineinfile` может добавить строку в файл идемпотентно, проверяя её наличие перед добавлением. Даже модуль `command` можно сделать идемпотентным с параметром `creates`: команда выполнится только если указанный файл не существует.

# Для чего нужны хендлеры, handlers?

Handlers - это специальные задачи, которые выполняются только при необходимости, в ответ на изменения, произведенные другими задачами. Классический пример - перезапуск сервиса после изменения конфига. Вы не хотите перезапускать nginx каждый раз при запуске плейбука - это какие-то лишние действия. Но если конфиг изменился, перезапуск нужен. Handlers решают эту дилемму: задача копирования конфига дергает handler о необходимости перезапуска, но только если файл реально изменился.  
Во-первых, handlers выполняются в конце play, после всех обычных задач, независимо от того, где в play они были вызваны. Это предотвращает множественные перезапуски - даже если десять задач дернули один handler, он выполнится только один раз. Во-вторых, handlers выполняются в порядке их определения в секции handlers, а не в порядке уведомления.

codecopy

```
# Пример использования handlers---- name: Настройка веб-сервера  hosts: webservers  tasks:    - name: Установка конфигурации nginx      template:        src: nginx.conf.j2        dest: /etc/nginx/nginx.conf      notify:        - проверить конфигурацию nginx        - перезапустить nginx     - name: Установка SSL сертификата      copy:        src: server.crt        dest: /etc/nginx/ssl/      notify:        - перезапустить nginx   handlers:    - name: проверить конфигурацию nginx      command: nginx -t     - name: перезапустить nginx      service:        name: nginx        state: restarted
```

Handler "перезапустить nginx" будет вызван только если изменилась конфигурация или сертификат, и выполнится только один раз в конце, даже если обе задачи произвели изменения.

# Основные примитивы Ansible

Ansible использует несколько ключевых компонентов для автоматизации задач.

- 📜 **Playbooks** (Сценарии) YAML-файлы, содержащие один или несколько `plays`. Плейбук — это полный сценарий, описывающий весь процесс автоматизации от начала до конца.
    
- 🎭 **Plays** (Пьесы) Основной блок плейбука, который связывает набор задач (`tasks`) с определённой группой хостов (`hosts`) из инвентаря.
    
- 🖥️ **Inventory** (Инвентарь) Список хостов, которыми управляет Ansible. Может быть статическим файлом (INI/YAML) или динамическим скриптом. Позволяет группировать хосты по логическому признаку (`webservers`, `databases`).
    
- ✅ **Tasks** (Задачи) Конкретное действие, выполняемое модулем с заданными параметрами. Например, "использовать модуль `user` для создания пользователя `john`". Задачи могут содержать условия (`when`) и циклы (`loop`).
    
- 🧩 **Modules** (Модули) Небольшие программы или скрипты, выполняющие атомарную работу: установка пакета, копирование файла, перезапуск сервиса [, ]. Ключевое свойство модулей — **идемпотентность** (повторный запуск не меняет состояние, если оно уже целевое).
    
- 📦 **Roles** (Роли) Способ структурировать и переиспользовать плейбуки. Роль объединяет задачи, шаблоны, переменные и обработчики для выполнения определённой функции (например, настройка веб-сервера).
    
- 🔄 **Handlers** (Обработчики) Особые задачи, которые выполняются только один раз в конце плея и только если их "уведомила" другая задача об изменении состояния (например, перезапуск сервиса после обновления конфига).
    
- 📝 **Variables & Facts** (Переменные и Факты) **Переменные** делают плейбуки гибкими. **Факты** — это переменные, автоматически собираемые с хостов (версия ОС, IP-адрес, память), которые можно использовать в задачах.
    
- 📄 **Templates** (Шаблоны) Файлы с использованием шаблонизатора Jinja2 для динамической генерации конфигурационных файлов на основе переменных.
