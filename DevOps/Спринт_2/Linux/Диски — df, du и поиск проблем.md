# Диски — df, du и поиск проблем

## Место на серверах заканчивается всегда

Тут действует такой закон — место на серверах заканчивается всегда. Это неизбежно, и обычно это происходит в самый неожиданный момент. Приходит алерт, вы смотрите — и действительно, корень занят на 95%. Дальше нужно быстро разобраться, куда делось место и что с этим делать. Для этого есть две основные команды, и работают они в связке.

## df -h — общая картина

`df` — disk free. Показывает, сколько места занято на всех дисках и разделах:

df -h

Флаг `-h` — human readable, то есть в гигабайтах и мегабайтах, а не в блоках. Вывод будет примерно такой:

codecopy

```
Filesystem      Size  Used Avail Use% Mounted on/dev/sda1       100G   89G   11G  89% //dev/sdb1       500G  312G  188G  63% /datatmpfs           3.9G     0  3.9G   0% /dev/shm
```

Тут вы сразу видите общую картину — какой раздел на сколько процентов забит. В нашем примере корень занят на 89%, `/data` — на 63%. Корень вызывает беспокойство, дальше идём разбираться, что именно его забило.

`df` отвечает на вопрос «где проблема?» — на каком разделе кончается место. А чтобы узнать, что именно сожрало это место, нужна вторая команда.

## du -sh * — поиск тяжёлых директорий

`du` — disk usage. Показывает, сколько весит каждая директория:

du -sh /*

Флаг `-s` — summary, только итог по каждой директории, без рекурсии внутрь. `-h` — человекочитаемый формат. Звёздочка — все директории в текущем месте.

Вывод:

codecopy

```
4.0K    /bin156M    /boot0       /dev12M     /etc2.1G    /home1.2G    /opt0       /proc52G     /var24G     /usr0       /sys180M    /tmp
```

Сразу видно — `/var` весит 52 гига. Заходим туда и повторяем:

du -sh /var/*

codecopy

```
48G     /var/log2.1G    /var/lib1.4G    /var/cache512M    /var/spool
```

48 гигов логов. Копаем дальше:

du -sh /var/log/*

codecopy

```
42G     /var/log/nginx3.2G    /var/log/journal1.8G    /var/log/syslog1.0G    /var/log/auth.log
```

Вот он — `nginx/access.log` разросся до 42 гигов, потому что кто-то забыл настроить ротацию логов

## Связка df → du

По сути, это всегда одна и та же последовательность:

![Drill-down: df -h → du -sh → ls -lh](https://offers.prostodevops.ru/diagrams/linux/disk-drilldown.png)Drill-down: df -h → du -sh → ls -lh

Вот эта связка `df` для общей картины → `du` для конкретики — это база в работе с дисками.

## Ротация логов — logrotate

Раз уж мы нашли раздувшийся лог, давайте разберёмся, как сделать так, чтобы это не повторялось. Для этого существует **logrotate** — утилита, которая автоматически ротирует логи. Ротация — это когда старый лог переименовывается (например, `access.log` → `access.log.1`), опционально сжимается, и создаётся новый пустой файл. Старые логи удаляются по расписанию.

Конфиг logrotate лежит в `/etc/logrotate.conf`, а отдельные конфиги для сервисов — в `/etc/logrotate.d/`. Когда вы ставите nginx через пакетный менеджер, он обычно сам кладёт свой конфиг ротации. Но если вы ставите что-то руками или пишете своё приложение — ротацию надо настроить самим.

Пример конфига для nginx:

codecopy

```
/var/log/nginx/*.log {    daily    rotate 14    compress    delaycompress    missingok    notifempty    postrotate        [ -f /var/run/nginx.pid ] && kill -USR1 $(cat /var/run/nginx.pid)    endscript}
```

Что тут написано:

- **daily** — ротировать каждый день.
- **rotate 14** — хранить 14 старых файлов. То есть, логи за последние две недели. Старше — удаляются.
- **compress** — сжимать старые логи gzip-ом. Логи сжимаются очень хорошо, раз в 10-20.
- **delaycompress** — не сжимать самый свежий ротированный файл (access.log.1 останется несжатым, access.log.2.gz уже сжат). Это нужно, потому что некоторые процессы могут ещё писать в старый файл какое-то время.
- **missingok** — не ругаться, если файла нет.
- **notifempty** — не ротировать пустой файл.
- **postrotate** — команда, которая выполняется после ротации. `kill -USR1` отправляет nginx сигнал переоткрыть лог-файлы. Без этого nginx будет продолжать писать в старый (переименованный) файл.

Проверить, что ротация работает:

logrotate -d /etc/logrotate.d/nginx

Флаг `-d` — dry run, покажет, что будет делать, но ничего не выполнит. Полезно для отладки.

Принудительно ротировать прямо сейчас:

logrotate -f /etc/logrotate.d/nginx

Logrotate сам по себе запускается через systemd-таймер (или cron на старых системах) раз в сутки. Он не демон, он не висит в памяти — просто запускается, ротирует что нужно и завершается.

## lsblk — просмотр блочных устройств

`lsblk` показывает все блочные устройства в системе — диски, разделы, LVM-тома:

lsblk

![Вывод lsblk: sda + sdb с partitions](https://offers.prostodevops.ru/diagrams/linux/lsblk-output.png)Вывод lsblk: sda + sdb с partitions

Тут сразу видно структуру: два физических диска (`sda` и `sdb`), у первого два раздела (корень и своп), у второго один раздел, примонтированный в `/data`.

`lsblk` удобен, когда нужно быстро понять, как устроены диски на сервере — сколько их, как разбиты, куда примонтированы. Особенно когда вы впервые зашли на незнакомый сервер и хотите сориентироваться.

С дополнительной информацией:

lsblk -f

Флаг `-f` покажет ещё тип файловой системы (ext4, xfs) и UUID. Полезно, когда нужно прописать монтирование в `/etc/fstab`.

## iostat — мониторинг I/O

В теме про CPU мы говорили про iowait — когда процессор ждёт диск. `iostat` — это утилита, которая показывает нагрузку на диски в деталях.

iostat -xz 1

Флаги: `-x` — расширенная статистика, `-z` — не показывать неактивные устройства, `1` — обновлять каждую секунду.

Вывод для каждого диска:

codecopy

```
Device   r/s     w/s    rkB/s    wkB/s  await  %utilsda     12.00  245.00   48.00  3920.00   8.50  89.20sdb      0.50    1.20    4.00    16.00   1.20   0.80
```

На что смотреть:

- **r/s, w/s** — количество операций чтения и записи в секунду.
- **rkB/s, wkB/s** — скорость чтения и записи в килобайтах в секунду.
- **await** — среднее время ожидания операции в миллисекундах. Если await растёт — диск не успевает обрабатывать запросы. Для SSD нормально до 1-5 мс, для HDD — до 10-20 мс. Если видите 50+ мс — диск явно перегружен.
- **%util** — процент утилизации диска. 100% означает, что диск загружен полностью и не справляется.

В нашем примере видно: `sda` утилизирован на 89%, на него идёт 245 операций записи в секунду. Это, скорее всего, тот самый лог, который раздувается, или база данных, которая активно пишет.

`iostat` входит в пакет `sysstat`:

apt install sysstat

## Инод-проблема

Бывает ситуация: `df -h` показывает, что место есть, но файлы создать не получается — система ругается `No space left on device`. Если место на диске есть, а ошибка всё равно вылетает — проверяйте иноды:

df -i

codecopy

```
Filesystem      Inodes   IUsed   IFree IUse% Mounted on/dev/sda1      6553600 6553600       0  100% /
```

Инод (inode) — это структура данных, которая хранит метаинформацию о файле: права, владелец, размер, расположение на диске. Каждый файл занимает один инод. Количество инодов на разделе фиксировано при создании файловой системы. Если иноды кончились — файлы создать нельзя, даже если место есть.

Когда это бывает? Обычно когда какое-то приложение нагенерировало миллионы мелких файлов. Например, сессии PHP, которые не чистятся, или кэш почтового сервера. Файлы крошечные, каждый по несколько байт, место на диске они почти не занимают, но каждый забирает инод.

## Быстрый чеклист по дискам

![Disk troubleshoot tree: df → ветки Use%/lsof/df-i](https://offers.prostodevops.ru/diagrams/linux/disk-troubleshoot.png)Disk troubleshoot tree: df → ветки Use%/lsof/df-i

Кстати, в чеклисте есть пункт «удалённые, но открытые файлы» — это ещё один частый кейс. Вы удалили огромный лог-файл, но процесс всё ещё держит его открытым. `df` показывает, что место не освободилось. Потому что Linux не освобождает место, пока хоть один процесс держит файл. Найти такие файлы:

lsof +L1

Решение — перезапустить процесс, который держит файл, или отправить ему сигнал переоткрыть логи.
