# SSH

## Базовое подключение

SSH — это то, через что вы будете взаимодействовать с серверами каждый день. Всё, что связано с работой на удалённых машинах, происходит через SSH. Зашли на сервер, выполнили команды, вышли — это SSH. Скопировали файл на сервер — SSH. Настроили туннель до базы данных — SSH. Git pull/push — тоже SSH.

Базовое подключение:

bashcopy

```bash
ssh user@192.168.1.100ssh devops@myserver.example.com
```

По умолчанию SSH подключается на порт 22. Если порт другой:

ssh -p 2222 user@host

При первом подключении к серверу SSH спросит: «Я не знаю этот сервер, его fingerprint такой-то, доверяем?» Вы пишете `yes`, и fingerprint сохраняется в `~/.ssh/known_hosts`. При следующих подключениях SSH сверяет fingerprint — если он вдруг изменился, выдаст предупреждение. Это защита от man-in-the-middle атак — если кто-то подменил сервер, fingerprint не совпадёт.

## Ключи — ssh-keygen и ssh-copy-id

Подключаться по паролю — это для начала сойдёт, но в реальной работе все используют ключи. Ключи и безопаснее (нельзя подобрать брутфорсом), и удобнее (не нужно вводить пароль каждый раз).

SSH-ключи — это пара: **приватный** (остаётся у вас, никому не показываете) и **публичный** (кладёте на сервер).

### Генерация ключа

ssh-keygen -t ed25519 -C "devops@mycompany"

- `-t ed25519` — тип ключа. ed25519 — современный, быстрый, безопасный. Можно ещё `rsa`, но ed25519 предпочтительнее.
- `-C "devops@mycompany"` — комментарий, чтобы потом понимать, чей это ключ. Необязательно, но полезно.

Спросит, куда сохранить — по умолчанию `~/.ssh/id_ed25519` (приватный) и `~/.ssh/id_ed25519.pub` (публичный). Спросит passphrase — это пароль для самого ключа. Можно оставить пустым, но для безопасности лучше задать. Если зададите — придётся вводить его при каждом подключении (или настроить ssh-agent, который запомнит).

### Копирование ключа на сервер

ssh-copy-id user@host

Эта команда берёт ваш публичный ключ и добавляет его в файл `~/.ssh/authorized_keys` на сервере. После этого можно подключаться без пароля — SSH предъявит приватный ключ, сервер сверит его с публичным, и пустит.

Если `ssh-copy-id` недоступна, можно вручную:

cat ~/.ssh/id_ed25519.pub | ssh user@host "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

Длинно, но делает то же самое. Права на директорию `.ssh` и файл `authorized_keys` — критичны. Если права слишком открытые, SSH откажется работать с ключами. `.ssh` — 700, `authorized_keys` — 600, приватный ключ — 600.

### Как это работает

![SSH аутентификация по ключам: challenge/response в 5 шагов](https://offers.prostodevops.ru/diagrams/linux/ssh-keys-handshake.png)SSH аутентификация по ключам: challenge/response в 5 шагов

Приватный ключ никогда не покидает вашу машину. Сервер никогда не узнаёт ваш приватный ключ. Он только проверяет, что подпись сделана правильным ключом.

## Конфиг ~/.ssh/config

Когда у вас один сервер — ничего настраивать не нужно. Но когда серверов десять, у каждого свой порт, свой пользователь, свой ключ — каждый раз набирать `ssh -p 2222 -i ~/.ssh/special_key devops@10.0.15.23` становится утомительно.

Для этого есть конфиг `~/.ssh/config`:

codecopy

```
Host prod-web    HostName 10.0.1.10    User devops    Port 22    IdentityFile ~/.ssh/id_ed25519 Host prod-db    HostName 10.0.1.20    User postgres    Port 2222    IdentityFile ~/.ssh/id_rsa Host staging-*    HostName %h.staging.example.com    User deploy    IdentityFile ~/.ssh/staging_key Host *    ServerAliveInterval 60    ServerAliveCountMax 3    AddKeysToAgent yes
```

Теперь вместо длинных команд:

bashcopy

```bash
ssh prod-web          # вместо ssh -i ~/.ssh/id_ed25519 devops@10.0.1.10ssh prod-db           # вместо ssh -p 2222 -i ~/.ssh/id_rsa postgres@10.0.1.20ssh staging-api       # подставит staging-api.staging.example.com
```

Блок `Host *` — настройки по умолчанию для всех подключений:

- **ServerAliveInterval 60** — каждые 60 секунд SSH отправляет keep-alive пакет. Без этого соединение может оборваться, если вы долго ничего не делаете (NAT или файрвол по таймауту закроет сессию).
- **ServerAliveCountMax 3** — если три keep-alive подряд не получили ответа — отключаемся. Без этого SSH может зависнуть намертво при обрыве сети, и вы будете сидеть в мёртвой консоли.
- **AddKeysToAgent yes** — автоматически добавлять ключи в ssh-agent при первом использовании.

SSH-конфиг — файл, который нужно настроить один раз, и дальше он экономит кучу времени каждый день. Плюс его понимают scp, rsync, git — все, что работает через SSH.

## Безопасность — отключение пароля и root

После того как настроили ключи и убедились, что вход по ключам работает, нужно закрутить безопасность. Два обязательных действия.

Конфиг SSH-сервера лежит в `/etc/ssh/sshd_config`. Редактируем:

vi /etc/ssh/sshd_config

### Отключить вход по паролю

PasswordAuthentication no

После этого подключиться можно только по ключу. Брутфорс пароля становится невозможен. Перед тем как включить — **убедитесь, что вход по ключам работает**. Иначе заблокируете себе доступ.

### Отключить вход под root

PermitRootLogin no

Под root напрямую по SSH подключаться нельзя. Подключаетесь под обычным пользователем, а потом `sudo` для административных задач. Это и безопаснее (root — известный логин, первая цель для брутфорса), и для аудита лучше (видно, кто именно зашёл на сервер).

Применяем:

bashcopy

```bash
# Проверяем синтаксис конфига (аналог nginx -t)sshd -t # Перезапускаем SSH-серверsystemctl restart sshd
```

Именно `restart`, не `reload` — sshd обычно не поддерживает reload для большинства параметров. Текущая сессия при этом не оборвётся — она уже установлена. Но на всякий случай: не закрывайте текущую сессию, пока не проверили, что новое подключение работает. Откройте второй терминал, попробуйте подключиться. Если всё ок — закрывайте старую сессию. Если что-то пошло не так — у вас ещё есть доступ через первую сессию, чтобы исправить.

### Дополнительно — fail2ban

Есть утилита **fail2ban**, которая мониторит логи SSH и автоматически блокирует IP-адреса, с которых идут попытки подбора паролей:

bashcopy

```bash
apt install fail2bansystemctl enable --now fail2ban
```

По умолчанию банит IP на 10 минут после 5 неудачных попыток входа. Конфигурируется через `/etc/fail2ban/jail.local`. Даже если вход по паролю отключён — fail2ban не помешает, потому что он снизит шум в логах от ботов, которые всё равно долбятся.

## SSH-туннели

SSH-туннели — штука, которая решает целый класс задач. Суть: вы прокидываете порт через SSH-соединение, и трафик идёт по зашифрованному каналу.

### -L (Local) — прокинуть удалённый порт к себе

Типичная задача: на сервере крутится PostgreSQL на порту 5432, но порт закрыт файрволом. Напрямую подключиться нельзя. Но SSH-доступ есть.

ssh -L 5432:localhost:5432 user@server

Что происходит: на вашей локальной машине открывается порт 5432. Всё, что туда придёт, SSH прокидывает через зашифрованный канал на сервер и отдаёт на `localhost:5432` сервера (то есть на PostgreSQL).

Теперь можно подключиться к базе:

psql -h localhost -p 5432 -U myuser mydb

Вы работаете как будто база на вашем компьютере, а на самом деле трафик летит через SSH на сервер.

![SSH-туннель: localhost:5432 ⇄ PostgreSQL на сервере](https://offers.prostodevops.ru/diagrams/linux/ssh-tunnel.png)SSH-туннель: localhost:5432 ⇄ PostgreSQL на сервере

Можно прокидывать не только на localhost сервера. Допустим, с сервера доступна внутренняя база на `db.internal:5432`, а с вашей машины она недоступна:

ssh -L 5432:db.internal:5432 user@server

Теперь ваш локальный 5432 → SSH → сервер → `db.internal:5432`.

### -R (Remote) — прокинуть свой порт на сервер

Обратный туннель. У вас локально крутится приложение на порту 3000, и вы хотите, чтобы оно было доступно на сервере.

ssh -R 8080:localhost:3000 user@server

На сервере откроется порт 8080, и трафик с него будет прокидываться к вам на `localhost:3000`. Используется реже, но бывает полезно для демонстрации локальной разработки коллегам или для дебага.

### Флаги для туннелей

ssh -L 5432:localhost:5432 -N -f user@server

- **-N** — не открывать shell, только туннель. Без этого откроется обычная SSH-сессия, которая вам не нужна — вы хотите только туннель.
- **-f** — уйти в фон. SSH уйдёт в фоновый режим после подключения. Без этого туннель будет работать, пока открыт терминал.

## Jump-хост — ProxyJump

В реальной инфраструктуре серверы обычно не торчат в интернет напрямую. Есть bastion-сервер (он же jump-host), через который вы попадаете на внутренние серверы.

  Вы ──► Bastion (публичный IP) ──► Внутренний сервер (приватная сеть)

Без настройки приходится делать два подключения:

bashcopy

```bash
# Сначала на bastionssh user@bastion.example.com # Потом с bastion на внутренний серверssh user@10.0.1.15
```

С флагом `-J` — одной командой:

ssh -J user@bastion.example.com user@10.0.1.15

SSH сам подключится к bastion, а через него — к внутреннему серверу. Вы окажетесь сразу на `10.0.1.15`.

В `~/.ssh/config` это прописывается так:

codecopy

```
Host bastion    HostName bastion.example.com    User devops Host internal-*    User devops    ProxyJump bastion    Host internal-web    HostName 10.0.1.15 Host internal-db    HostName 10.0.1.20
```

Теперь:

bashcopy

```bash
ssh internal-web    # автоматически прыгнет через bastionssh internal-db     # аналогично
```

![SSH jump host: вы → bastion → internal-web](https://offers.prostodevops.ru/diagrams/linux/ssh-jump.png)SSH jump host: вы → bastion → internal-web

Туннели тоже работают через jump-хост:

ssh -J bastion -L 5432:localhost:5432 internal-db

Прокинет порт PostgreSQL с внутреннего сервера к вам на машину через bastion. Одна команда.

## scp и rsync — копирование файлов

### scp

Простое копирование файлов через SSH:

bashcopy

```bash
# С локальной машины на серверscp file.txt user@host:/tmp/ # С сервера на локальную машинуscp user@host:/var/log/nginx/error.log ./ # Целую директорию (рекурсивно)scp -r ./configs/ user@host:/opt/app/configs/
```

scp работает, использует тот же SSH-конфиг, те же ключи. Для простых задач — скопировать файл туда-сюда — scp хватает.

### rsync

Для всего остального — rsync. Он умнее scp:

- Копирует только изменившиеся файлы (delta transfer). Если у вас директория на 10 ГБ, и изменился один файл на 1 МБ — rsync скопирует только этот 1 МБ, а не всю директорию.
- Может докачивать при обрыве.
- Сохраняет права, владельцев, временные метки.
- Показывает прогресс.
- Умеет сжимать трафик.

bashcopy

```bash
# Базовое копирование директории на серверrsync -avz ./project/ user@host:/opt/project/ # С прогрессомrsync -avzP ./project/ user@host:/opt/project/ # Синхронизация (удалить на сервере то, чего нет локально)rsync -avz --delete ./project/ user@host:/opt/project/
```

Флаги:

- **-a** — archive mode. Рекурсивно, сохраняет права, симлинки, временные метки. Стандартный набор.
- **-v** — verbose, показывает, что копирует.
- **-z** — сжатие при передаче. Экономит трафик.
- **-P** — прогресс + partial (докачка при обрыве).
- **--delete** — удалить на приёмной стороне файлы, которых нет на отправляющей. Осторожно с этим флагом — он реально удаляет.

Обратите внимание на слэш в конце пути: `./project/` — копирует содержимое директории. `./project` (без слэша) — копирует саму директорию. Разница:

bashcopy

```bash
rsync -avz ./project/ user@host:/opt/project/    # содержимое project → /opt/project/rsync -avz ./project  user@host:/opt/project/     # создаст /opt/project/project/
```

Для бэкапов, деплоя, синхронизации конфигов — rsync. Для «быстро скинуть один файл» — scp.

rsync понимает SSH-конфиг, jump-хосты, всё то же самое:

rsync -avzP ./configs/ internal-web:/opt/app/configs/

Если в `~/.ssh/config` прописан ProxyJump — rsync автоматически пойдёт через bastion.
