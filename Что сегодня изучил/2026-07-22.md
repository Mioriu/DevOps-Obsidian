[[gitlab-ci.yaml]] + примеры реализаций cicd в маленьких - средних - крупных компаниях
# Саммари: GitLab CI — `.gitlab-ci.yml`

---

## Основная структура

yaml

stages:
  - build
  - test
  - deploy
build-job:
  stage: build
  script:
    - echo "Building..."
    - npm install
    - npm run build
test-job:
  stage: test
  script:
    - echo "Running tests..."
    - npm test
deploy-job:
  stage: deploy
  script:
    - echo "Deploying..."
    - ./deploy.sh

---

## Stages — этапы пайплайна

- **Порядок:** джобы внутри одного `stage` выполняются **параллельно**.
    
- Следующий `stage` запускается только когда все джобы предыдущего **успешно завершились**.
    
- Если одна джоба упала — следующий `stage` не запускается.
    

---

## Jobs — джобы

### `script` — команды

yaml

job:
  script:
    - echo "Step 1"
    - npm install
    - npm run build

- Команды выполняются последовательно.
    
- Любая команда с ненулевым exit code → джоба падает.
    

### `image` — Docker-образ для джобы

yaml

job:
  image: python:3.11-slim
  script:
    - pytest

Глобально через `default`:

yaml

default:
  image: python:3.11-slim

### `before_script` / `after_script`

- `before_script` — выполняется **перед** `script`. Подготовка окружения.
    
- `after_script` — выполняется **после** `script`, даже если он упал. Очистка, нотификации.
    

yaml

job:
  before_script:
    - pip install -r requirements.txt
  script:
    - pytest
  after_script:
    - docker-compose down

## `rules` — когда запускать джобу

`rules` — основной способ управления запуском (заменяет старые `only`/`except`).

### Условия в `rules`

yaml

rules:
  # По ветке
  - if: $CI_COMMIT_BRANCH == "main"
  - if: $CI_COMMIT_BRANCH == "develop"
  # По тегу
  - if: $CI_COMMIT_TAG
  # По источнику пайплайна
  - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  - if: $CI_PIPELINE_SOURCE == "push"
  - if: $CI_PIPELINE_SOURCE == "web"          # запуск руками из UI
  - if: $CI_PIPELINE_SOURCE == "schedule"     # по расписанию
  # По переменной
  - if: $DEPLOY_ENV == "production"
  # По изменённым файлам
  - changes:
      - backend/**/*
      - requirements.txt

**Важно:** правила проверяются **сверху вниз**. Первое совпавшее — применяется.

### `when` — управление запуском

|`when`|Значение|
|---|---|
|`on_success` (по умолчанию)|Запускается, если все джобы предыдущего стейджа успешны|
|`on_failure`|Запускается, только если что-то упало в предыдущем стейдже|
|`always`|Запускается всегда|
|`manual`|Ждёт ручного нажатия кнопки в UI|
|`never`|Не запускается|

yaml

deploy-prod:
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual

**`when: manual`** — частый паттерн для деплоя в прод.

## `allow_failure`

- По умолчанию: джоба упала → пайплайн останавливается.
    
- `allow_failure: true` → джоба может упасть, но пайплайн продолжается (джоба помечается как "failed", но не блокирует).
    

yaml

lint:
  script: npm run lint
  allow_failure: true

---

## `needs` — DAG (нарушение порядка стейджей)

По умолчанию джобы выполняются стейдж за стейджем.

`needs` говорит: "запускайся сразу, как только завершилась конкретная джоба, не жди весь стейдж".

yaml

test-backend:
  stage: test
  needs: ["build-backend"]     # не ждёт build-frontend
  script: make test-backend
deploy:
  stage: deploy
  needs: ["test-backend", "test-frontend"]
  script: make deploy

**Ограничение:** `needs` может ссылаться только на джобы из **предыдущих или текущего** стейджей.

## Полезные директивы

### `extends` — наследование

yaml

.base-test:
  image: python:3.11-slim
  before_script:
    - pip install -r requirements.txt
unit-tests:
  extends: .base-test
  script: pytest tests/unit/
integration-tests:
  extends: .base-test
  script: pytest tests/integration/

### `include` — подключение внешних файлов

yaml

include:
  - local: ci/build.yml
  - local: ci/test.yml
  - local: ci/deploy.yml
  # Из другого репозитория
  - project: 'devops/ci-templates'
    ref: main
    file: '/templates/docker-build.yml'
  # По URL
  - remote: 'https://example.com/ci-template.yml'

### `tags` — на каком раннере запускать

yaml

build-job:
  tags:
    - docker
    - linux
  script: make build

## Шпаргалка: основные переменные окружения

|Переменная|Значение|
|---|---|
|`CI_COMMIT_BRANCH`|Имя ветки (для пушей)|
|`CI_COMMIT_TAG`|Имя тега (если запуск по тегу)|
|`CI_COMMIT_SHORT_SHA`|Короткий хеш коммита (8 символов)|
|`CI_PROJECT_PATH`|Путь к проекту (`namespace/project`)|
|`CI_PIPELINE_SOURCE`|Источник запуска (`push`, `merge_request_event`, `web`, `schedule`)|
|`CI_JOB_NAME`|Имя текущей джобы|
|`CI_REGISTRY_IMAGE`|URL образа в GitLab Container Registry|

## Итог

|Что нужно|Как сделать|
|---|---|
|Определить этапы|`stages: [build, test, deploy]`|
|Создать джобу|`job-name: { stage: ..., script: ... }`|
|Задать образ|`image: python:3.11-slim`|
|Условия запуска|`rules: - if: $CI_COMMIT_BRANCH == "main"`|
|Ручной деплой|`when: manual`|
|Параллельный запуск без ожидания стейджа|`needs: ["build-job"]`|
|Разбить на файлы|`include: - local: ci/build.yml`|
|Переиспользовать настройки|`extends: .template`|
