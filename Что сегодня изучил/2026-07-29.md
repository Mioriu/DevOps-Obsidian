[[K8s Архитектура]]  [[Устройство пода]]  

## Статья 1: Архитектура Kubernetes

### Два типа нод

|Тип|Назначение|
|---|---|
|**Control Plane (Master)**|Управление кластером, хранение состояния, API|
|**Worker Nodes**|Запуск подов (контейнеров), выполнение работы|

---

### Control Plane — компоненты управления

|Компонент|Назначение|Важно|
|---|---|---|
|**kube-apiserver**|Единая точка входа, REST API, валидация и авторизация запросов. **Единственный компонент, который пишет в etcd**|Если падает — `kubectl` не работает, но существующие поды продолжают работать|
|**etcd**|Распределённое key-value хранилище. Хранит **всё** состояние кластера|**Обязательно бекапить**. Если etcd умер — кластер мёртв|
|**kube-scheduler**|Решает, **на какую ноду** поместить под. Выполняет фильтрацию → ранжирование → назначение|Если падает — новые поды зависают в `Pending`|
|**kube-controller-manager**|Коллекция контроллеров. Следит, чтобы текущее состояние = желаемому|Управляет ReplicaSets, Deployment, Node Controller и др.|

#### Что делают контроллеры:

- **Node Controller** — следит за нодами, помечает `NotReady`, вытесняет поды
    
- **ReplicaSet Controller** — поддерживает нужное количество реплик
    
- **Deployment Controller** — rolling update, откат
    
- **Service Controller** — создаёт LoadBalancer в облаке
    

**Паттерн работы контроллера:** `Watch` → `Compare` → `Reconcile`

### Worker Node — компоненты выполнения

|Компонент|Назначение|Если падает|
|---|---|---|
|**kubelet**|Агент на каждой ноде. Регистрирует ноду, запускает контейнеры через CRI, отправляет статус, выполняет health checks|Новые поды не запускаются, нода — `NotReady`|
|**kube-proxy**|Сетевой прокси. Реализует Service через iptables/ipvs, балансирует трафик между подами|Service перестают работать на этой ноде|
|**Container Runtime**|containerd, CRI-O. Запускает и управляет контейнерами|Контейнеры не запускаются|

### Дополнительные компоненты

|Компонент|Назначение|
|---|---|
|**CoreDNS**|DNS внутри кластера, разрешает имена Service → IP|
|**Metrics Server**|Собирает метрики с kubelet для `kubectl top` и HPA|

---

### Как всё работает вместе: создание пода

text

1. kubectl create → API Server
2. API Server → проверка auth/валидация → сохранение в etcd
3. Scheduler → выбирает ноду → назначает под (пишет в API Server)
4. kubelet на ноде → видит под → через CRI запускает контейнеры
5. kube-proxy → обновляет iptables для Service

**Что при падении пода:**

- kubelet перезапускает (если RestartPolicy)
    
- Если под управляется ReplicaSet → Controller Manager создаёт новый
    

**Что при падении ноды:**

- Node Controller ждёт ~5 минут → помечает `NotReady` → вытесняет поды
    
- Scheduler назначает их на здоровые ноды

## Статья 2: Pod изнутри

### Что такое Pod

**Pod** — минимальная развёртываемая единица. Группа контейнеров с **общим сетевым пространством и хранилищем**.

### Компоненты Pod

|Компонент|Описание|
|---|---|
|**Pause контейнер**|Держит network/ipc/uts namespace'ы. Запускается первым|
|**Init контейнеры**|Выполняются последовательно **перед** основными. Для миграций, ожидания БД, подготовки конфигов|
|**Основные контейнеры**|Запускаются параллельно **после** init. Приложение|
|**Volumes**|Общие директории для всех контейнеров в поде|

### Pause контейнер — основа пода

**Зачем:** держит `network namespace`, даже если основной контейнер упал. Если контейнер A умер — pause сохраняет сеть, контейнер B продолжает работать.

**Что общее между контейнерами в поде:**

- ✅ Network (один IP, localhost работает)
    
- ✅ IPC (shared memory)
    
- ✅ UTS (hostname)
    

**Что раздельное:**

- ❌ PID (каждый контейнер видит только свои процессы)
    
- ❌ Mount (своя ФС)
    
- ❌ User
    

---

### Init контейнеры

**Выполняются последовательно до основных контейнеров.** Если init упал — под не запускается.

**Типичные задачи:**

- Миграции БД
    
- Ожидание зависимостей (БД, API)
    
- Подготовка конфигов
    
- Настройка прав
    

**Пример — ожидание БД:**

yaml

initContainers:
  - name: wait-for-db
    image: busybox:1.35
    command:
      - sh
      - -c
      - |
        until nc -z postgres-service 5432; do
          sleep 2
        done

---

### Sidecar контейнеры

Дополнительные контейнеры, расширяющие функциональность основного.

**Типичные use case:**

- Логирование (fluentd, filebeat)
    
- Мониторинг (prometheus exporter)
    
- Service mesh (envoy)
    
- Обновление сертификатов
    

**Пример — логирование через shared volume:**

yaml

volumes:
  - name: logs
    emptyDir: {}
containers:
  - name: app
    volumeMounts:
      - name: logs
        mountPath: /var/log/app
  - name: log-shipper
    image: fluent/fluent-bit:1.9
    volumeMounts:
      - name: logs
        mountPath: /var/log/app
        readOnly: true

---

### Static Pods

**Static Pod** — под, создаваемый напрямую kubelet **без участия API Server**.

**Как работает:**

- kubelet читает YAML-файлы из `/etc/kubernetes/manifests/`
    
- Запускает поды напрямую
    
- Нельзя удалить через `kubectl delete` (только удалить файл)
    

**Зачем нужны:** для запуска control plane компонентов (kube-apiserver, etcd, scheduler, controller-manager) — пока API Server не работает, нужно как-то его запустить.

**Создание Static Pod:**

bash

# 1. Найти директорию
cat /var/lib/kubelet/config.yaml | grep staticPodPath
# → /etc/kubernetes/manifests/
# 2. Создать манифест
sudo nano /etc/kubernetes/manifests/static-nginx.yaml
# 3. kubelet сам подхватит через ~20 секунд
kubectl get pods

**Static Pods vs DaemonSets:**

||Static Pods|DaemonSets|
|---|---|---|
|Управление|kubelet напрямую|API Server|
|Создание|Файл в `/manifests/`|`kubectl apply`|
|Use case|Control plane|Мониторинг, логирование|
