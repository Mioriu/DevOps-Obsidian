### Саммари 1: Изменение последнего коммита (Amend)

**Что такое amend:**  
`git commit --amend` — создаёт **новый** коммит, заменяющий последний. Старый коммит остаётся в базе данных, но становится недостижимым (позже удаляется сборщиком мусора). SHA-1 хеш меняется.

**Основные сценарии:**

1. **Исправление сообщения:**
    
    bash
    
    git commit --amend -m "Новое сообщение"
    
2. **Добавление забытых файлов:**
    
    bash
    
    git add forgotten-file.js
    git commit --amend --no-edit   # сохраняет старое сообщение
    
3. **Исправление содержимого файлов:**
    
    bash
    
    vim src/file.js                # правим код
    git add src/file.js
    git commit --amend --no-edit
    

**Продвинутые возможности:**

- Изменение автора: `git commit --amend --author="Name <email>"`
    
- Изменение даты: `git commit --amend --date="now"`
    
- Подпись GPG: `git commit --amend -S`
    

**Золотое правило:**  
**Никогда не изменяйте уже опубликованные коммиты.** Amend безопасен только для локальных коммитов, которые ещё не были отправлены (`push`). Если коммит уже в удалённом репозитории, amend вызовет расхождение историй.

**Восстановление после ошибочного amend:**

bash

git reflog                          # найти старый коммит
git reset --hard HEAD@{1}           # вернуться к состоянию до amend

### Саммари 2: Rebase (перемещение коммитов)

**Что такое rebase:**  
Процесс перемещения последовательности коммитов на новую базу. Вместо создания merge-коммита (как при `git merge`), rebase переписывает историю, создавая впечатление, что работа велась поверх актуальной версии кода.

**Как работает:**

1. Находит общего предка между ветками
    
2. Сохраняет ваши коммиты как временные патчи
    
3. Перемещает указатель ветки на вершину целевой ветки
    
4. Применяет сохранённые патчи по одному, создавая **новые коммиты** (с новыми SHA-1)
    

bash

# Переключиться на feature-ветку и выполнить rebase на main
git checkout feature
git rebase main
# Или короче
git rebase main feature

**Разрешение конфликтов при rebase:**  
Конфликты разрешаются для каждого коммита отдельно:

bash

# Разрешить конфликт в файле
git add conflicted-file.js
git rebase --continue   # продолжить
# Или отменить rebase
git rebase --abort

**Преимущества линейной истории:**

- Читается как книга (последовательно, без merge-коммитов)
    
- `git bisect` и `git blame` работают эффективнее
    
- Чистые pull requests без лишних коммитов
    

**Золотое правило rebase:**  
**Никогда не делайте rebase веток, которые уже опубликованы.** Другие разработчики могли на них основывать свою работу — это вызовет хаос при синхронизации.

**Безопасные сценарии:**

- Локальные ветки до `push`
    
- Личные feature-ветки до создания pull request
    

**Настройка pull с rebase:**

bash

git pull --rebase origin main
git config --global pull.rebase true   # сделать поведением по умолчанию

**Восстановление:**

bash

git reflog
git reset --hard HEAD@{n}   # вернуться до rebase

### Саммари 3: Интерактивный Rebase (Interactive Rebase)

**Что это:**  
Интерактивный rebase (`git rebase -i`) позволяет не просто переместить коммиты, а **переписать историю**: объединить, переупорядочить, отредактировать или удалить коммиты.

bash

git rebase -i HEAD~3        # изменить последние 3 коммита
git rebase -i main          # изменить все коммиты в feature-ветке относительно main

**Команды интерактивного rebase:**

|Команда|Сокращение|Действие|
|---|---|---|
|`pick`|`p`|Использовать коммит как есть|
|`reword`|`r`|Изменить сообщение коммита|
|`edit`|`e`|Остановиться для внесения изменений в содержимое|
|`squash`|`s`|Объединить с предыдущим коммитом (сохранить сообщения)|
|`fixup`|`f`|Объединить, отбросив сообщение|
|`drop`|`d`|Удалить коммит|
|`exec`|`x`|Выполнить команду (например, `npm test`)|
|`break`|`b`|Остановиться для ручной проверки|

**Основные сценарии:**

1. **Squash (объединение) — превратить несколько WIP-коммитов в один:**
    
    text
    
    pick e3b8a1c Initial implementation
    squash f7f3f6d WIP: authentication
    squash 310154e Add tests
    
2. **Reword — исправить опечатку в сообщении**
    
3. **Reorder — изменить порядок коммитов** (просто переставить строки)
    
4. **Edit — изменить содержимое старого коммита:**
    
    bash
    
    # Остановиться на коммите, внести правки
    git add .
    git commit --amend
    git rebase --continue
    
5. **Drop — удалить коммит** (или просто удалить строку)
    

**Автоматизация с autosquash:**

bash

git commit --fixup=abc123     # создаёт коммит с пометкой fixup
git rebase -i --autosquash main  # Git автоматически расставит fixup

**Важные предостережения:**

- **Не изменяйте опубликованную историю**
    
- Делайте backup перед сложным rebase: `git branch backup/feature`
    
- Тестируйте после больших изменений
    
- Используйте `git rebase --abort` при проблемах
    

**Восстановление:**

bash

git rebase --abort            # отменить незавершённый rebase
git reflog                    # найти старые коммиты после завершённого

---

### Итоговое резюме

|Инструмент|Что делает|Когда использовать|Опасность|
|---|---|---|---|
|**Amend**|Заменяет последний коммит|Исправление опечаток, добавление забытых файлов|Только для локальных коммитов|
|**Rebase**|Перемещает коммиты на новую базу|Обновление feature-веток перед merge|Перезаписывает историю|
|**Interactive Rebase**|Переписывает несколько коммитов|Очистка истории перед публикацией|Можно потерять коммиты|

**Главное правило всех трёх инструментов: никогда не изменяйте историю, которая уже была опубликована в общем репозитории.**
