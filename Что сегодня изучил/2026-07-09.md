## Статья 1: Типы балансировки

### Что такое Load Balancing

**Load Balancer** распределяет запросы между несколькими серверами для увеличения пропускной способности и отказоустойчивости.

### Уровни балансировки

|Уровень|Что видит|Плюсы|Минусы|
|---|---|---|---|
|**L4** (TCP/UDP)|IP, порты, протокол|Быстро, меньше ресурсов|Нет роутинга по HTTP|
|**L7** (HTTP/HTTPS)|URL, headers, cookies|Роутинг по содержимому, SSL termination|Медленнее, больше ресурсов|

### Алгоритмы балансировки

|Алгоритм|Принцип|Когда использовать|
|---|---|---|
|**Round Robin**|По кругу|Серверы одинаковой мощности|
|**Weighted Round Robin**|С весами|Серверы разной мощности|
|**Least Connections**|На сервер с мин. соединениями|Запросы разной длительности|
|**IP Hash**|hash(IP) → сервер|Sticky sessions|
|**Random**|Случайно|Простая настройка|

### Health Checks

- **Passive** — смотрит на ошибки от серверов
    
- **Active** — периодически отправляет проверочные запросы (`GET /health`)
    

### Sticky Sessions

Привязка клиента к серверу (через cookie или IP). **Лучшее решение:** stateless приложение + внешнее хранилище сессий (Redis).

### Популярные LB

- **Nginx** — L7, reverse proxy
    
- **HAProxy** — L4 + L7, очень быстрый
    
- **Kubernetes Service** — L4 (встроенный)
    
- **Cloud LB** — AWS ALB/NLB, GCP LB

## Статья 2: CPU и память

### `top` / `htop` — сортировка

|Команда|Действие|
|---|---|
|`Shift+P` (top)|Сортировка по **CPU**|
|`Shift+M` (top)|Сортировка по **памяти**|
|`F6` (htop)|Выбрать поле для сортировки|

### Load Average — три цифры

text

load average: 2.15, 1.80, 0.95
              ↑      ↑      ↑
            1 мин   5 мин   15 мин

**Интерпретация:** среднее количество процессов в очереди.

- Делим на число ядер (`nproc`)
    
- `> 1` = перегруз
    
- `>> 1` = серьёзная проблема
    

**Динамика:**

- Растущая нагрузка: `8.5, 2.1, 1.05` → что-то случилось сейчас
    
- Стабильная: `8.5, 8.4, 8.3` → системная проблема
    
- Падающая: `1.2, 5.8, 8.1` → проблема уходит
    

### `free -m` — память

bash

free -m

text

              total   used   free  buff/cache  available
Mem:           7982   5241    312       2429       2341
Swap:          2048    156      0

**Важно:** смотреть на `available`, а не на `free` — это реально доступная память (free + освобождаемый кэш).

### Своп (Swap)

- Когда память кончается → Linux выгружает данные на диск
    
- Диск в тысячи раз медленнее RAM → всё тормозит
    

**Проверка:**

bash

vmstat 1   # смотреть si (swap in) и so (swap out)
free -m    # если used в Swap растёт — плохо

### iowait — процессор ждёт диск

В `top`: параметр `wa` — процент времени CPU в ожидании диска.

- `wa > 20-30%` → проблема с диском
    

**Диагностика:**

bash

iotop -o   # процессы, делающие I/O прямо сейчас

### OOM Killer

Когда память совсем кончилась — ядро убивает процесс, чтобы не дать системе зависнуть.

bash

dmesg | grep -i "oom"
journalctl -k | grep -i "oom"

**Защита процесса от OOM:**

bash

echo -1000 > /proc/PID/oom_score_adj

### Практический сценарий: память 95%

bash

free -m                    # available близок к 0, своп забит
top → Shift+M              # сортировка по памяти → java-процесс жрёт 70%
ps aux | grep 8421         # понять, что это за приложение
systemctl restart myapp    # или kill -15, потом kill -9

**Ограничение памяти в systemd:**

ini

[Service]
MemoryMax=8G
MemoryHigh=7G

## Статья 3: Диски — df, du и поиск проблем

### `df -h` — общая картина

bash

df -h

text

Filesystem   Size  Used Avail Use% Mounted on
/dev/sda1    100G   89G   11G  89% /
/dev/sdb1    500G  312G  188G  63% /data

### `du -sh *` — поиск тяжелых директорий

bash

du -sh /*                    # корень
du -sh /var/*                # копаем глубже
du -sh /var/log/*            # ещё глубже
du -sh /var/log/nginx/*      # нашли виновника

### Связка: df → du

text

df -h  →  какая директория забита?
du -sh →  что внутри неё весит больше всего?

### Ротация логов — logrotate

Конфиг: `/etc/logrotate.conf` и `/etc/logrotate.d/`

**Пример nginx:**

text

/var/log/nginx/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    postrotate
        [ -f /var/run/nginx.pid ] && kill -USR1 $(cat /var/run/nginx.pid)
    endscript
}

**Проверка:**

bash

logrotate -d /etc/logrotate.d/nginx   # dry-run
logrotate -f /etc/logrotate.d/nginx   # принудительно

### `lsblk` — блочные устройства

bash

lsblk
lsblk -f   # + ФС и UUID

### `iostat` — I/O нагрузка

bash

iostat -xz 1

- `await` — среднее время ожидания (мс). >50ms = медленно
    
- `%util` — утилизация. 100% = диск забит
    

### Иноды (`df -i`)

- Каждый файл занимает один инод
    
- Иноды кончились → нельзя создать файл, даже если место есть
    
- Частая причина: миллионы мелких файлов (сессии, кэш)
    

### Удалённые, но открытые файлы

bash

lsof +L1   # файлы с 0 линков (удалены, но открыты)
# → перезапустить процесс, который держит файл

## Статья 4: Общий траблшутинг Linux

### Методология

1. Собрать информацию (что, когда, что менялось)
    
2. Проверить основы (сервер жив, сеть есть, сервисы запущены)
    
3. Собрать метрики (CPU, память, диск, сеть, процессы)
    
4. Проверить логи (системные и приложения)
    
5. Выдвинуть гипотезу
    
6. Проверить гипотезу
    
7. Исправить
    
8. Проверить
    
9. Задокументировать
    

### Быстрый чек-лист (7 команд)

bash

uptime                          # load average
top                             # что жрёт CPU/память
df -h                           # место на дисках
free -h                         # свободная память
dmesg | tail                    # сообщения ядра
journalctl -xe                  # события systemd
ss -tulpn                       # открытые порты

### Диагностика по проблемам

|Проблема|Команды|Решение|
|---|---|---|
|**Высокий CPU**|`top`, `ps aux --sort=-%cpu`, `strace -p PID`|Kill, ограничить CPU, оптимизация|
|**Нехватка памяти**|`free -h`, `ps aux --sort=-%mem`, `dmesg \| grep killed`|Перезапустить, ограничить в systemd, увеличить RAM|
|**Медленный диск**|`iostat -x 1`, `iotop`, `lsof`|Ротация логов, очистка, SSD|
|**Закончилось место**|`df -h`, `du -sh *`, `find / -size +1G`|Очистить логи, кэш, Docker|
|**Процесс висит**|`strace -p PID`, `lsof -p PID`|`kill -15`, потом `kill -9`|
|**Connection refused**|`ss -tulpn`, `telnet host port`, `iptables -L`|Запустить сервис, открыть порт|
|**Connection timeout**|`ping`, `traceroute`, `firewall-cmd`|Открыть фаервол, проверить маршрут|

### Логи

**Где искать:**

- Системные: `/var/log/syslog`, `/var/log/auth.log`, `journalctl`
    
- Приложений: `/var/log/nginx/`, `/var/log/postgresql/`, `journalctl -u service`
    

**Полезные команды:**

bash

tail -f /var/log/app.log
grep ERROR /var/log/app.log
journalctl -u nginx -f
journalctl --since "1 hour ago"

### Чек-лист быстрой диагностики

bash

uptime
top                          # или htop
free -h
df -h
df -i
iostat -x 1 5
ss -s
ss -tulpn
ping 8.8.8.8
dmesg | tail -20
journalctl -xe
tail -100 /var/log/syslog
ps aux | wc -l
ps aux --sort=-%cpu | head -5
ps aux --sort=-%mem | head -5
systemctl status <your-app>
journalctl -u <your-app> -n 50

### Вопрос на собеседовании: "Твой подход к траблшутингу"

**Хороший ответ:**

1. Не паникую
    
2. Собираю информацию (что, когда, что менялось)
    
3. Базовая диагностика (чек-лист)
    
4. Выдвигаю гипотезу
    
5. Проверяю гипотезу
    
6. Применяю фикс или митигирую (откат, перезапуск)
    
7. Проверяю решение
    
8. Документирую
    

**Главное: сначала диагностика, потом действия.**
