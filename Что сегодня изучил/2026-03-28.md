### Саммари 1: Ветвление (Branching)

**Концепция:**  
Ветка в Git — это не копия файлов, а **подвижный указатель на коммит** (41 байт). Это делает операции с ветками (создание, переключение, удаление) мгновенными независимо от размера проекта.

**Создание и переключение:**

- Создать ветку (оставаясь на текущей): `git branch feature-login`
    
- Создать и переключиться (современный способ): `git switch -c feature-login`
    
- Классический способ: `git checkout -b feature-login`
    
- Переключиться на существующую ветку: `git switch main` (или `git checkout main`)
    
- Вернуться на предыдущую ветку: `git switch -`
    

**Безопасность:**  
Git не позволяет переключить ветку, если есть незафиксированные изменения, конфликтующие с целевой веткой.

**Просмотр информации:**

- `git branch` — список локальных веток (* — текущая)
    
- `git branch -v` — с последним коммитом каждой ветки
    
- `git branch --merged` / `--no-merged` — слитые/неслитые ветки
    
- `git branch -a` — все ветки (включая удалённые)
    

**Удаление веток:**

- Безопасное удаление (только слитую): `git branch -d feature-login`
    
- Принудительное удаление: `git branch -D feature-login`
    

**Практические принципы:**

- Именование с префиксами: `feature/`, `bugfix/`, `hotfix/`, `release/`
    
- Регулярная синхронизация долгоживущих веток с основной линией
    
- Визуализация: `git log --graph --oneline --all`

### Саммари 2: Слияние (Merge)

**Два типа слияния:**

1. **Fast-forward (быстрая перемотка):**
    
    - Возможен, когда целевая ветка не имеет новых коммитов после точки ответвления
        
    - Git просто перемещает указатель ветки вперёд
        
    - Не создаёт отдельный коммит слияния, история остаётся линейной
        
    - Принудительное создание merge commit: `git merge --no-ff feature`
        
2. **Three-way merge (трёхстороннее слияние):**
    
    - Когда обе ветки развивались независимо
        
    - Git анализирует три точки: общего предка и конечные состояния обеих веток
        
    - Создаётся merge commit с двумя родителями
        

**Процесс слияния:**

1. Переключиться на целевую ветку (`git switch main`)
    
2. Выполнить слияние (`git merge feature`)
    
3. При успехе Git автоматически создаёт коммит (или перемещает указатель)
    

**Просмотр результатов:**

- `git log --graph --oneline` — визуализация истории слияний
    
- `git show` для merge commit — показывает изменения относительно всех родителей
    

**Отмена слияния:**

- Для неопубликованных коммитов: `git reset --hard HEAD~1`
    
- Для опубликованных (безопаснее): `git revert -m 1 HEAD`

### Саммари 3: Разрешение конфликтов (Conflict Resolution)

**Природа конфликтов:**  
Конфликт возникает, когда Git не может автоматически объединить изменения из разных веток (одни и те же строки кода изменены противоречиво). Это нормальная ситуация, а не ошибка.

**Маркеры конфликта в файле:**

text

<<<<<<< HEAD
[код из текущей ветки]
=======
[код из сливаемой ветки]
>>>>>>> feature/branch

**Процесс разрешения:**

1. **Идентификация:** `git status` показывает файлы с конфликтами (both modified)
    
2. **Анализ:** открыть файл, изучить маркеры конфликта
    
3. **Решение:** выбрать один вариант, объединить оба или написать новый код
    
4. **Редактирование:** удалить маркеры конфликта, оставить нужный код
    
5. **Завершение:** `git add <файл>` → `git commit`
    

**Инструменты:**

- `git mergetool` — запуск визуального инструмента (VS Code, Beyond Compare и др.)
    
- `git show :1:file` — базовая версия
    
- `git show :2:file` — версия из текущей ветки (ours)
    
- `git show :3:file` — версия из сливаемой ветки (theirs)
    

**Стратегии предотвращения:**

- Частая синхронизация ветки с основной (`git merge main` или `git rebase main`)
    
- Атомарные коммиты (одно логическое изменение на коммит)
    
- Коммуникация в команде о больших изменениях
    
- Модульная архитектура кода
    

**Специальные случаи:**

- **При rebase:** конфликты разрешаются для каждого коммита; после разрешения `git rebase --continue`
    
- **Бинарные файлы:** `git checkout --ours file` или `git checkout --theirs file`
    
- **Автоматический выбор:** `git merge -X ours branch` (при конфликте берётся наша версия)
    

**Откат слияния:**

- В процессе: `git merge --abort`
    
- После завершения: `git reset --hard HEAD~1`
