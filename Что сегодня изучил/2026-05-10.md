# Саммари статей по Docker: Продвинутый Dockerfile, оптимизация и сети

## Статья 1: Multi-stage Builds — многоэтапная сборка

### Основная идея

**Multi-stage builds** позволяют разделить Dockerfile на несколько стадий (этапов). В финальный образ попадает только то, что нужно для **запуска** (runtime), а все инструменты сборки (компиляторы, dev-зависимости, кэш) остаются в промежуточных стадиях. → **образ меньше, безопаснее, быстрее сборка**.

### Синтаксис

dockerfile

# Стадия 1: сборка (builder)
FROM <образ> AS <имя_стадии>
... инструкции сборки ...
# Стадия 2: финальный образ
FROM <лёгкий_образ>
COPY --from=<имя_стадии> <источник> <назначение>

### Примеры по языкам

|Язык|Builder-образ|Runtime-образ|Экономия|
|---|---|---|---|
|**Go**|`golang:1.18-alpine`|`alpine:3.17` или `scratch`|~99% (800MB → 10MB)|
|**Node.js + React**|`node:16-alpine`|`nginx:alpine`|~90% (1GB → 100MB)|
|**Java (Spring Boot)**|`maven:3.8-openjdk-17`|`eclipse-temurin:17-jre-alpine`|~75% (500MB → 120MB)|
|**Python**|`python:3.9`|`python:3.9-slim`|~70%|

### Go + scratch (экстремальная минимизация)

dockerfile

FROM golang:1.18-alpine AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp
FROM scratch   # пустой образ!
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /app/myapp /myapp
CMD ["/myapp"]

### Node.js с разделением зависимостей и кода

dockerfile

# Стадия 1: только зависимости
FROM node:16-alpine AS deps
COPY package*.json ./
RUN npm ci --only=production
# Стадия 2: сборка
FROM node:16-alpine AS builder
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build
# Стадия 3: production
FROM nginx:1.21-alpine
COPY --from=builder /app/dist /usr/share/nginx/html

### Дополнительные возможности

**Выбор конкретной стадии при сборке:**

bash

docker build --target builder -t myapp:builder .

**ARG в multi-stage (нужно объявлять в каждой стадии заново):**

dockerfile

ARG VERSION=latest
FROM golang:1.18 AS builder
ARG VERSION
RUN echo "Building $VERSION"

**Секреты в multi-stage (не попадают в финальный образ):**

bash

RUN --mount=type=secret,id=npm_token \
    cat /run/secrets/npm_token > .npmrc && npm install && rm .npmrc

### Итог

Multi-stage builds — стандарт для production-образов. Отделяем сборку от запуска, получаем маленькие, безопасные и быстрые образы.

## Статья 2: Оптимизация Dockerfile — Best Practices

### 1. Кэширование слоёв — порядок инструкций

**Правило:** самое редко меняющееся — выше, часто меняющееся — ниже.

**Плохо:**

dockerfile

COPY . /app
RUN npm install   # пересобирается при любом изменении любого файла!

**Хорошо:**

dockerfile

COPY package*.json /app
RUN npm install          # кэшируется, пока не изменился package.json
COPY . /app

### 2. Объединение RUN команд (один слой вместо многих)

**Плохо:**

dockerfile

RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

**Хорошо:**

dockerfile

RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

### 3. Удаление временных файлов в том же слое

dockerfile

RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*
RUN pip install --no-cache-dir -r requirements.txt

### 4. `.dockerignore` — исключить лишнее из контекста

bash

.git
node_modules
__pycache__
*.env
*.log

### 5. Выбирайте минимальные базовые образы

- `alpine` вместо `ubuntu` (5MB vs 70MB)
    
- `-slim` варианты для Python, Node
    
- `scratch` для Go/статически скомпилированных приложений
    

### 6. Пользователь non-root (безопасность)

dockerfile

RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

### 7. Не храните секреты в Dockerfile

**Плохо:**

dockerfile

ENV DB_PASSWORD="secret"

**Хорошо:**

bash

docker run -e DB_PASSWORD=secret myimage

### 8. Закрепляйте версии (воспроизводимость)

dockerfile

FROM node:16-alpine          # хороший тег
# а не FROM node:latest

### Итоговая структура Dockerfile

dockerfile

FROM минимальный-образ
WORKDIR /app
# 1. Копируем файлы зависимостей (редко меняются)
COPY package*.json ./
RUN npm install
# 2. Копируем остальной код (часто меняется)
COPY . .
# 3. Настройки
ENV NODE_ENV=production
USER appuser
EXPOSE 3000
CMD ["npm", "start"]

## Статья 3: Типовые ошибки в Dockerfile

|Ошибка|Проблема|Решение|
|---|---|---|
|Запуск от root|Высокий риск при взломе|`USER appuser`|
|`COPY . .` без `.dockerignore`|Лишние файлы в образе|Добавить `.dockerignore`|
|Отдельные `RUN` для каждой команды|Много слоёв + мусор|Объединять в один `RUN`|
|Сначала `COPY .`, потом установка зависимостей|Кэш не работает|Сначала копировать только package.json|
|Не удалять временные файлы|Образ раздувается|Удалять в том же `RUN`|
|Хранение `.env` в образе|Утечка секретов|Использовать `-e` или Docker Secrets|
|Нет multi-stage для компилируемых языков|В образе остаются компиляторы|Использовать multi-stage|
|`latest` тег для базового образа|Воспроизводимость сломана|Указывать конкретную версию|

### Диагностика размера образов

bash

docker history myimage           # размер каждого слоя
docker image ls                  # общий размер

## Статья 4: Сети в Docker

### Типы сетей

|Тип|Команда|Когда использовать|
|---|---|---|
|**bridge** (дефолт)|`docker run`|Один хост, изоляция, проброс портов через `-p`|
|**host** (только Linux)|`--network=host`|Максимальная производительность, без NAT overhead|
|**none**|`--network=none`|Полная изоляция от сети|
|**overlay**|`docker network create --driver=overlay`|Несколько хостов (Docker Swarm / K8s)|

### Bridge Network (самый частый)

- Контейнер получает **внутренний** IP (172.17.x.x)
    
- Доступ извне: `-p хост:контейнер` (NAT через iptables)
    
- **User-defined bridge**: контейнеры могут обращаться друг к другу **по имени** (встроенный DNS Docker)
    

bash

docker network create my-bridge
docker run --network=my-bridge --name web nginx
docker run --network=my-bridge --name app myapp
# app может пинговать "web" по имени

### Host Network (только Linux)

- Контейнер использует сетевой стек **хоста напрямую**
    
- Нет изоляции, порты контейнера = порты хоста
    
- Выше производительность (нет NAT)
    

### None Network

- Только loopback (`lo`), нет внешней сети
    
- Максимальная изоляция
    

### Overlay Network (многохостовой)

- Объединяет контейнеры на **разных физических хостах** в одну логическую сеть
    
- Использует VXLAN-туннели
    
- Требует Docker Swarm или Kubernetes
    

### Docker DNS в user-defined сетях

В user-defined bridge и overlay сетях работает **автоматическое разрешение имён**:

- `ping web` → DNS возвращает IP контейнера с именем `web`
    
- Не нужно знать IP, достаточно имени сервиса
    

### Как работает NAT для bridge

text

host:8080 → iptables → контейнер:80

- На хосте правила iptables (или nftables) перенаправляют трафик
    
- Создаётся виртуальный интерфейс `docker0`
    

### Итог: когда что использовать

|Сценарий|Тип сети|
|---|---|
|Локальная разработка, один хост|`bridge` (по умолчанию)|
|Высокая сетевая нагрузка, максимум производительности (Linux)|`host`|
|Контейнер без сети (полная изоляция)|`none`|
|Кластер из нескольких Docker-хостов|`overlay` (Swarm) или Kubernetes CNI|
