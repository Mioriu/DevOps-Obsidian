## Статья 1: Типичные сетевые ошибки и их решение

### 1. Конфликты портов

|Симптом|Причина|Решение|
|---|---|---|
|`Could not bind to port 80`, `Address already in use`|Порт на хосте уже занят другим процессом или контейнером|1. Остановить процесс  <br>2. Использовать другой порт хоста: `-p 8080:80`  <br>3. Проверить запущенные контейнеры|

### 2. Firewall блокирует доступ

|Симптом|Причина|Решение|
|---|---|---|
|Контейнер с `-p 8080:80` запущен, но недоступен с другой машины|Firewall (UFW, iptables, Security Group) блокирует входящий трафик|1. `sudo ufw allow 8080`  <br>2. В облаке — настроить Security Group/Inbound Rules|

### 3. Забыли указать `-p`

|Симптом|Причина|Решение|
|---|---|---|
|Сервис внутри контейнера слушает порт, но доступа снаружи нет|Без `-p` Docker не публикует порты наружу|Запустить контейнер с `-p хост:контейнер` (или `-P` для автопубликации)|

### 4. Контейнер не может выйти в интернет

|Симптом|Причина|Решение|
|---|---|---|
|`curl google.com` не работает, `Temporary failure in name resolution`|Проблемы с DNS, firewall, корпоративный прокси|1. Проверить DNS в `/etc/docker/daemon.json`  <br>2. Настроить HTTP_PROXY|

### 5. Контейнеры на разных хостах не видят друг друга

|Симптом|Причина|Решение|
|---|---|---|
|Контейнеры на разных серверах не пингуются|Docker сети изолированы внутри одного хоста|1. Docker Swarm + overlay network  <br>2. Kubernetes  <br>3. VPN / ssh tunnel|

### 6. Приложение внутри контейнера слушает `localhost`

|Симптом|Причина|Решение|
|---|---|---|
|`-p 8080:80` настроен, но приложение недоступно|Приложение слушает `127.0.0.1`, а не `0.0.0.0`|Настроить приложение на `0.0.0.0` (все интерфейсы)|

**Проверка внутри контейнера:**

bash

docker exec <container> netstat -tulpn   # или ss -lntp

### 7. SELinux / AppArmor блокируют доступ

|Симптом|Причина|Решение|
|---|---|---|
|`Permission denied` при монтировании папок|SELinux или AppArmor блокируют доступ|1. `chcon -Rt svirt_sandbox_file_t /path`  <br>2. Или отключить для конкретного контейнера|

## Статья 2: Macvlan и Ipvlan — прямые IP в LAN

### Основная идея

**Macvlan** и **Ipvlan** — драйверы сетей Docker, которые позволяют контейнеру получить **прямой IP в физической сети хоста**. Контейнер выглядит для LAN как отдельное устройство (со своим MAC или IP), **без NAT**.

### Macvlan (уровень L2)

- Контейнер получает **собственный MAC-адрес**
    
- Внешние устройства видят контейнер как отдельный физический узел
    
- Можно задавать IP из того же диапазона, что у хоста (например, `192.168.1.x`)
    

**Создание macvlan-сети:**

bash

docker network create -d macvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o parent=eth0 \
  my-macvlan

**Запуск контейнера:**

bash

docker run -d --network my-macvlan --name test1 --ip 192.168.1.50 nginx

→ Контейнер доступен по IP `192.168.1.50` из любой машины в LAN

### Ipvlan (уровень L3)

- Контейнеры **делят MAC-адрес хоста**, различаются только IP
    
- Лучше, если свитчи не любят появление новых MAC-адресов
    

bash

docker network create -d ipvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o parent=eth0 \
  my-ipvlan

### Сравнение macvlan и ipvlan

|Характеристика|Macvlan|Ipvlan|
|---|---|---|
|Уровень|L2 (канальный)|L3 (сетевой)|
|MAC-адреса|У каждого контейнера свой|Общий с хостом|
|Совместимость со свитчами|Может быть проблема (много MAC)|Лучше|
|Изоляция хост ↔ контейнер|❌ Нет (нужен workaround)|❌ Нет|

### Ключевая проблема macvlan/ipvlan

**Хост не может общаться с контейнером по этому интерфейсу напрямую** (без дополнительной настройки).

**Решение (workaround):**

bash

# Создать дополнительный macvlan-интерфейс на хосте
ip link add macvlan0 link eth0 type macvlan mode bridge
ip addr add 192.168.1.10/24 dev macvlan0
ip link set macvlan0 up

### Когда использовать macvlan/ipvlan

✅ **Хорошо подходит:**

- Каждому контейнеру нужен **реальный IP в LAN** (без NAT)
    
- Нужно избежать коллизий портов (много сервисов на порту 80)
    
- Высокая производительность (нет NAT overhead)
    

❌ **Не подходит:**

- Нет прав root на хосте
    
- Не хотите возиться с маршрутизацией хост ↔ контейнер
    
- Сетевой администратор не одобряет новые MAC-адреса (тогда ipvlan)
    

### Пример удобного сценария

**Домашний сервер (`192.168.1.10`)**:

- Контейнер Nextcloud → `192.168.1.101`
    
- Контейнер Home Assistant → `192.168.1.102`
    
- Контейнер Plex → `192.168.1.103`
    

→ Вход из LAN напрямую по IP, без `-p` и без конфликта портов (каждый может слушать 80)

### Итог по сетям

|Тип сети|IP контейнера|Доступ снаружи|NAT|Связь между хостами|
|---|---|---|---|---|
|**bridge** (default)|Внутренний (172.17.x.x)|Через `-p`|Да|Нет|
|**host** (Linux)|IP хоста|Напрямую|Нет|Нет|
|**macvlan**|Из LAN (например, 192.168.1.x)|Напрямую|Нет|Нет (без overlay)|
|**overlay**|Внутренний|Через ingress|Да|**Да** (Swarm)|
