## Статья 1: Введение в Docker — зачем и почему

### Основная идея

Docker — это **инструмент контейнеризации**, который упаковывает приложение со всеми зависимостями (библиотеки, конфиги) в изолированный контейнер. Главное обещание: _"Если работает здесь, значит будет работать везде"_ — на ноутбуке разработчика, тестовом сервере и в production.

### Почему Docker стал популярным

|Причина|Объяснение|
|---|---|
|**Простота**|До Docker контейнеры требовали глубоких знаний cgroups/namespaces. Docker дал удобный CLI|
|**Быстрый старт**|Контейнер запускается за секунды (а не минуты, как VM)|
|**Широкая поддержка**|Все современные языки, фреймворки и облачные платформы|
|**Гибкость**|В контейнер можно включить любые версии библиотек и утилит|

### Аналогия

Приложение — это **чемодан** (контейнер), в котором сложены все вещи (зависимости). Docker помогает сформировать чемодан и перевезти его куда угодно, не разбирая заново.

### Итог

Docker — базис современных DevOps-практик и микросервисной архитектуры. Он решает проблему "на моей машине работает" и обеспечивает одинаковое окружение везде.

## Статья 2: VM vs Контейнеры — сравнение технологий

### Виртуальные машины (VM)

**Что это:** Гипервизор (VirtualBox, VMware) создаёт **полноценные ОС** — каждая со своим ядром, драйверами, процессами.

**Плюсы:** высокая изоляция, зрелые технологии.

**Минусы:**

- Большое потребление ресурсов (каждая VM тянет всю ОС)
    
- Долгий запуск (десятки секунд)
    
- Сложность обновлений (патчить каждую гостевую ОС)
    

### Контейнеры (Docker)

**Что это:** Контейнер **не имеет своего ядра** — использует ядро хоста, но изолирует файловую систему, процессы и сеть через **namespaces**, **cgroups**, **capabilities**.

**Плюсы:**

- Лёгковесность (нет накладных расходов на ОС)
    
- Быстрый запуск (секунды)
    
- Управление через Docker/Kubernetes
    

**Минусы:**

- Чуть менее жёсткая изоляция (общее ядро)
    
- Зависимость от ОС хоста (Linux)
    

### Технологии под капотом контейнеризации

|Технология|Назначение|
|---|---|
|**Namespaces**|Изоляция ресурсов — процессы в контейнере "думают", что они в отдельной системе|
|**Cgroups**|Ограничение ресурсов — CPU, RAM, дисковый ввод-вывод (справедливое распределение)|
|**Capabilities**|Разделение root-привилегий на отдельные права (например, только слушать порты <1024)|

### Сравнительная таблица

|Критерий|VM|Контейнеры|
|---|---|---|
|Изоляция|Полная ОС|Общее ядро + namespaces|
|Запуск|Десятки секунд|Секунды|
|Ресурсы|Много RAM/диска|Легковесно|
|Масштабирование|Сложно|Мгновенно|

### Когда VM всё ещё актуальны

- Требуется абсолютная ОС-изоляция (регуляторы, банки)
    
- Старые enterprise-приложения, которые не контейнеризуются
    
- Юридические требования к модели безопасности с VM
    

### Итог

Контейнеры — стандарт для новых разработок и DevOps. VM не ушли в прошлое, но для быстрого масштабирования и CI/CD контейнеры — однозначный выбор.

## Статья 3: Архитектура Docker

### Основные компоненты

│ Docker CLI  │ ────────────────── │ Docker Daemon   │
│ (docker run)│                     │ (dockerd)       │

                                              │

                                    │ containerd + runc │
                                    └───────────────────┘

### 1. Docker Daemon (dockerd)

- **Фоновый процесс**, сердце системы
    
- Принимает запросы от клиента, управляет контейнерами, образами, сетями, томами
    
- Если Daemon не запущен → команды `docker` не работают
    

### 2. Docker Client (CLI) и API

- CLI — команды вроде `docker run`, `docker ps`
    
- Под капотом CLI отправляет **HTTP-запросы** к Docker Daemon по Docker API
    

### 3. Docker Engine (обобщённо)

- Daemon + containerd + runc
    
- **Containerd** — вспомогательный слой, создаёт и контролирует процессы контейнеров
    
- **runc** — непосредственно запускает контейнеры через ядро Linux
    

### 4. Registry (реестр образов)

- Хранилище образов (Docker Hub, GitHub Container Registry, self-hosted)
    
- `docker pull` — скачать образ из registry
    
- `docker push` — отправить образ в registry
    

### Взаимодействие на примере `docker run nginx`

1. CLI отправляет запрос к Daemon
    
2. Daemon проверяет, есть ли образ `nginx` локально
    
3. Если нет — скачивает из Docker Hub
    
4. Daemon создаёт контейнер, настраивает сеть/ФС, запускает процесс nginx
    

### Почему важно понимать архитектуру

- **Устранение ошибок** — знаете, где искать причину
    
- **Безопасность** — Daemon выполняет привилегированные действия
    
- **Автоматизация** — CI/CD может управлять контейнерами через Docker API

## Статья 4: Ключевые сущности Docker

### 1. Образы (Images)

**Шаблон контейнера** — базовая ФС (Ubuntu/Alpine), установленные программы, инструкции (порты, процесс).

- Хранятся в локальном кэше
    
- Состоят из **слоёв** (layered filesystem) — экономия места и кеширование
    
- Имеют теги (версии): `myapp:v1`, `myapp:latest`
    

### 2. Контейнеры (Containers)

**Запущенный экземпляр образа**:

- Docker создаёт namespaces (процессы, сеть, монтирование)
    
- Создаётся **слой записи** (Copy-on-Write) — изменения не портят образ
    
- Запускается основной процесс
    

Образ = чертёж дома  
Контейнер = построенный дом

Один образ → множество контейнеров (параллельно или последовательно).

### 3. Сети (Networks)

Каждый контейнер получает изолированный сетевой стек со своим IP.

**Типы сетей:**

- `bridge` — дефолтный, изолированная сеть между контейнерами
    
- `host` — контейнер использует сеть хоста напрямую
    
- `none` — без сети
    
- `overlay` — для Docker Swarm (кластер из нескольких хостов)
    

Проброс портов: `-p 8080:80` (порт хоста → порт контейнера)

### 4. Тома (Volumes) — хранение данных

По умолчанию данные в контейнере **живут только в слое записи и исчезают при удалении контейнера**.

**Решения:**

- **Volumes** — специальные тома вне контейнера (Docker управляет)
    
- **Bind mounts** — монтирование директории хоста в контейнер
    

Позволяют сохранять данные между перезапусками и обмениваться файлами с хостом.

### 5. Инструментарий Docker

|Инструмент|Назначение|
|---|---|
|**Dockerfile**|Шаблон для сборки образа (COPY, RUN, CMD)|
|**docker-compose**|Описание (YAML) нескольких сервисов, сетей, томов — запуск одной командой|
|**Registry**|Хранилище образов (Docker Hub, GHCR, self-hosted)|
|**Docker CLI**|Основные команды: `run`, `build`, `pull`, `push`, `ps`|

### Итог

Docker — это не только контейнеры, но и экосистема:

- **Образы** → шаблоны
    
- **Контейнеры** → запущенные экземпляры
    
- **Сети** → изоляция и связь
    
- **Тома** → постоянное хранение
    
- **Инструменты** → Dockerfile, compose, registry, CLI
