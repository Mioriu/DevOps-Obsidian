## Статья 1: Продвинутые тома — tmpfs, шифрование и бэкапы

### 1. tmpfs-тома — хранение в оперативной памяти

**Основная идея:** Том, который хранится **в RAM** и не записывается на диск. Данные исчезают при остановке контейнера.

**Когда использовать:** Временные файлы, кэш, сессии — то, что не нужно сохранять.

**Запуск с tmpfs:**

bash

docker run -d --name mycontainer --tmpfs /app/tmp:rw,size=64m alpine

|Плюсы|Минусы|
|---|---|
|Очень высокая скорость (RAM)|Ограничен объёмом RAM|
|Безопасность (данные не остаются на диске)|Риск OOM (Out Of Memory)|

---

### 2. Шифрованные тома

**Основная идея:** Хранить данные томов в зашифрованном виде для защиты при утечке диска.

**Способы реализации:**

|Способ|Описание|
|---|---|
|**Внешний драйвер**|Например, `blockbridge`, `rexray` — сами шифруют данные|
|**LUKS/dm-crypt на хосте**|Шифруется раздел, где лежат все Docker-тома|
|**Docker Enterprise**|Встроенная опция шифрования (устаревшая)|

**Пример с внешним драйвером:**

bash

docker volume create --driver blockbridge --opt encryption=on --name securedata
docker run -v securedata:/app/data ...

---

### 3. Бэкапы томов

#### Способ 1: `docker run` с tar (классический)

bash

docker run --rm -v mydata:/data:ro alpine tar -czf - /data > backup.tar.gz

- `:ro` — read-only (безопаснее)
    
- На хосте получаем `backup.tar.gz` с содержимым тома
    

#### Способ 2: `docker volume export/import` (экспериментальный)

bash

docker volume export mydata > backup.tar
docker volume import mydata backup.tar

#### Способ 3: Внешние инструменты

- Если том на NFS/облаке — использовать snapshot'ы средствами этой системы
    
- Cron внутри контейнера, делающий бэкап БД
    

---

### Итог по продвинутым томам

|Тип|Хранение|Сценарий|
|---|---|---|
|**tmpfs**|RAM (временные данные)|Кэш, временные файлы|
|**Шифрованный том**|Зашифрованный диск|Конфиденциальные данные|
|**Бэкап через tar**|Внешний файл|Резервное копирование|

## Статья 2: Docker Compose — оркестрация нескольких контейнеров

### Основная идея

**Docker Compose** — инструмент для описания и запуска **нескольких контейнеров** (сервисов) из одного YAML-файла. Вместо множества `docker run` с кучей флагов — один `docker-compose up`.

### Структура `docker-compose.yml`

yaml

version: "3.8"          # версия синтаксиса
services:               # секция с сервисами (контейнерами)
  web:                  # имя сервиса
    image: nginx:latest
    container_name: my_web
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html
    depends_on:
      - db
    networks:
      - mynetwork
  db:
    image: postgres:14
    container_name: my_db
    environment:
      - POSTGRES_PASSWORD=secret
    volumes:
      - dbdata:/var/lib/postgresql/data
    networks:
      - mynetwork
volumes:
  dbdata:               # именованный том
networks:
  mynetwork:            # пользовательская сеть

### Ключевые элементы

|Элемент|Назначение|Пример|
|---|---|---|
|`services`|Список контейнеров|`web:`, `db:`, `redis:`|
|`image`|Какой образ использовать|`nginx:alpine`|
|`container_name`|Имя контейнера (опционально)|`my_web`|
|`ports`|Проброс портов|`- "8080:80"`|
|`environment`|Переменные окружения|`- POSTGRES_PASSWORD=secret`|
|`volumes`|Тома (именованные или bind mount)|`- dbdata:/data`, `- ./html:/app`|
|`depends_on`|Порядок запуска|`- db` (db запустится раньше)|
|`networks`|Подключение к сетям|`- mynetwork`|

### Важно про `depends_on`

- Гарантирует **порядок запуска** контейнеров
    
- **НЕ гарантирует**, что сервис **готов** принимать соединения (база может инициализироваться)
    
- Для ожидания готовности нужны `healthcheck` или скрипты типа `wait-for-it`
    

### Основные команды Compose

|Команда|Действие|
|---|---|
|`docker-compose up`|Запустить все сервисы (логи в консоль)|
|`docker-compose up -d`|Запустить в фоне|
|`docker-compose down`|Остановить и удалить контейнеры, сети|
|`docker-compose down --volumes`|Удалить **и тома** (внимание!)|
|`docker-compose logs`|Посмотреть логи (можно `-f` или указать сервис)|
|`docker-compose ps`|Статус сервисов|

### Почему Compose лучше, чем ручные `docker run`?

|Проблема ручных команд|Решение Compose|
|---|---|
|Длинные команды с кучей флагов|Всё в YAML|
|Сложно помнить порядок запуска|`depends_on`|
|Контейнеры не видят друг друга по имени|Автоматический DNS: сервис `db` доступен по имени `db`|
|Сложно делиться с командой|`docker-compose.yml` в репозитории|

### Итог

**Docker Compose** — стандартный инструмент для локальной разработки и тестирования многоконтейнерных приложений:

- Один файл описывает всю инфраструктуру
    
- Одна команда поднимает всё
    
- Сервисы общаются по именам (встроенный DNS)
    
- Легко масштабировать и делиться с командой
