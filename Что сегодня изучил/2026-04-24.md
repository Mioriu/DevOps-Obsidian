## Статья 1: Git Worktree — параллельная работа

### Основная идея

**Git worktree** — механизм, позволяющий иметь несколько рабочих директорий для одного репозитория. Каждая директория — отдельный checkout (например, разных веток), но все они делят общую `.git` базу. Экономия места и возможность работы над несколькими ветками **одновременно** без `stash` или временных коммитов.

### Ключевые моменты

**Создание worktree:**

bash

git worktree add ../project-feature feature/new-design   # из существующей ветки
git worktree add -b feature/experiments ../project-experiments  # новая ветка
git worktree add ../project-debug abc123def              # из конкретного коммита (detached HEAD)

**Просмотр и удаление:**

bash

git worktree list                    # все worktree
git worktree remove ../project-feature
git worktree prune                    # очистка информации об удалённых

**Практические сценарии:**

- **Code review без прерывания работы** — создать worktree для ветки PR, проверить, вернуться к своей
    
- **Срочный hotfix** — worktree от `main`, исправить баг, не трогая незавершённую feature-ветку
    
- **Тестирование разных версий** — worktree для `v1.0`, `v2.0`, `latest` и скрипт параллельного тестирования
    
- **Разные конфигурации** — в каждом worktree свой `.env`
    

**Продвинутые техники:**

- Блокировка worktree от случайного удаления: `git worktree lock --reason "production" ../dir`
    
- Перемещение: `git worktree move ../old /new/path`
    
- Автоматическая настройка окружения через `post-worktree` hook (установка зависимостей, копирование `.env`)
    

### Ограничения

- Нельзя одновременно проверить одну и ту же ветку в двух worktree (без `--force`)
    
- Submodules требуют отдельной инициализации в каждом worktree
    

### Альтернативы

- `git clone` — полная копия (дублирует данные)
    
- `git stash` — нельзя работать параллельно
    
- `sparse checkout` — экономит место, но сложнее
    

### Итог

Worktree идеален для частого переключения между задачами: ревью, hotfix, тестирование. Экономит место (общий `.git`) и время. Организуйте worktree в папках `features/`, `bugs/`, `releases/` для порядка.

## Статья 2: CI/CD интеграция — автоматизация workflow

### Основная идея

Git стал центром CI/CD: каждое событие (push, PR, tag) запускает автоматические пайплайны — тесты, сборку, деплой. **Configuration as Code** — конфигурация хранится в репозитории (`.github/workflows/*.yml`, `.gitlab-ci.yml`, `Jenkinsfile`).

### Ключевые концепции

**Pipeline — последовательность этапов (stages):**

- Build → Test → Security → Deploy → Verify
    
- Jobs внутри этапа могут выполняться **параллельно**
    

**Триггеры:**

- `push` (с фильтром по веткам/путям)
    
- `pull_request` (создание, обновление, merge)
    
- `tag` (релизы)
    
- `schedule` (cron)
    
- `workflow_dispatch` (ручной)
    

### Сравнение инструментов

|Инструмент|Особенности|Хорош для|
|---|---|---|
|**GitHub Actions**|Marketplace готовых actions, матричные сборки (OS × версии), бесплатно для публичных репозиториев|Маленькие и средние команды, проекты на GitHub|
|**GitLab CI**|Встроенный, собственные runners (shared/specific), Review Apps (временные окружения для MR), environments|Комплексное решение, enterprise|
|**Jenkins**|Pipeline as Code (Declarative/Scripted), распределённые агенты, огромная экосистема плагинов|Enterprise, кастомизация, legacy|

### Стратегии ветвления и CI/CD

- **Git Flow**: `develop` → dev/staging, `release/*` → staging, `main` → production, `hotfix/*` → hotfix-окружение
    
- **GitHub Flow**: PR → тесты + preview, merge в `main` → автоматический деплой в production
    
- **Trunk-Based**: очень быстрые проверки (секунды), feature flags, канареечные деплои
    

### Секреты и безопасность

- Никогда не хранить секреты в репозитории
    
- Использовать встроенные механизмы (GitHub Secrets, GitLab CI variables, Jenkins Credentials)
    
- Принцип наименьших привилегий: production-секреты доступны только production-jobs
    

### Оптимизация производительности

- **Параллелизация** независимых задач
    
- **Кеширование** зависимостей (npm, pip, Docker-слои)
    
- **Fail fast**: быстрые проверки (линтеры) первыми
    
- **Инкрементальные сборки** (особенно для monorepo)
    

### GitOps — следующий уровень

Git становится единым источником правды **и для кода, и для инфраструктуры** (декларативное описание). Операторы (ArgoCD, Flux) следят за репозиторием и автоматически приводят реальное состояние к желаемому.

### Итог

CI/CD превращает Git в центр автоматизации. Начните с простого: автоматические тесты на push. Добавляйте этапы постепенно. Культура: сломанный pipeline — приоритет №1, быстрая обратная связь (минуты, не часы).

## Статья 3: Troubleshooting — решение типичных проблем

### Основная философия

1. **Git почти никогда не теряет данные** — reflog, fsck, восстановление через reflog
    
2. **Диагностика прежде лечения** — поймите текущее состояние
    
3. **Понимание, а не запоминание** команд
    

### Частые проблемы и решения

|Проблема|Решение|
|---|---|
|Коммит в неправильную ветку (не запушен)|`git reset --soft HEAD~1`, переключиться на нужную ветку, `git commit -c ORIG_HEAD`|
|Коммит в неправильную ветку (запушен)|`cherry-pick` в нужную ветку, `revert` или `reset` в неправильной (с force push)|
|Неправильное сообщение коммита (последний)|`git commit --amend -m "new message"`|
|Неправильное сообщение (старый коммит)|`git rebase -i` → `reword` (опасно, переписывает историю)|
|Потерянные коммиты после `reset --hard`|`git reflog` → найти хеш → `git reset --hard <hash>`|
|`detached HEAD`|Если коммиты есть: `git branch rescue-branch`. Если нет: просто переключиться на ветку|
|Merge conflict|`git merge --abort` для отмены; визуальные инструменты (VS Code, Meld)|
|Diverged branches|`git pull --rebase` (сохраняет линейную историю) или `git push --force` (осторожно!)|
|Ошибки аутентификации|Проверить `git remote -v`, SSH ключи, токены|
|Large files rejected|Если локально: `git reset`, удалить файл, коммит. Если в истории: `git filter-branch` или BFG|
|Медленный clone|`--depth 1` (shallow), `--single-branch`, `--filter=blob:none` (partial clone)|
|Line endings (CRLF/LF)|`git config core.autocrlf true` (Windows) / `input` (Unix). `.gitattributes`|
|Corrupt repository|`git fsck --full`, копия из remote, `git fetch --all`|
|Случайно запушили секреты|Немедленно отозвать credentials, удалить из истории (BFG/filter-branch), force push|

### Ключевые инструменты диагностики

- **`git reflog`** — машина времени, история HEAD за 90 дней
    
- **`git fsck`** — проверка целостности, поиск dangling commits
    
- **`git bisect`** — бинарный поиск коммита, сломавшего функциональность
    
- **`git blame`** — кто изменил каждую строку
    

### Превентивные меры

- Регулярные backup (push в несколько remote)
    
- Hooks: `pre-commit` (линтеры, секреты), `pre-push` (тесты, защита main)
    
- Обучение команды
    

### Итог

Не паниковать. Reflog — лучший друг. Диагностировать перед исправлением. Каждая проблема решаема.

## Статья 4: Объектная модель Git — как Git хранит данные

### Основная философия

Git — **content-addressable storage** (адресация по содержимому): адрес объекта = SHA-1(содержимое + тип + размер). Четыре типа неизменяемых объектов. История — направленный ациклический граф (DAG).

### 4 типа объектов

|Тип|Что хранит|Содержит ссылки на|Пример|
|---|---|---|---|
|**Blob**|содержимое файла (байты)|ничего|`blob c2d4a3...`|
|**Tree**|снимок директории: {режим, тип, хеш, имя}|blob, другие tree|корневая директория проекта|
|**Commit**|состояние проекта в момент времени|tree, родительские commit(s), автор, сообщение|`commit a1b2c3`|
|**Tag (annotated)**|метка с метаданными|commit (обычно)|`tag v1.0.0`|

### Как связаны объекты на примере

text

Repository:
  README.md
  src/main.py
Объекты:
  blob (README.md)
  blob (main.py)
  tree (src/) → blob main.py
  tree (корень) → blob README.md + tree src/
  commit → корневой tree + автор + сообщение

### Ключевые свойства

- **Неизменяемость**: объект нельзя изменить, только создать новый (новый хеш)
    
- **Дедупликация**: одинаковые файлы → один blob
    
- **Целостность**: изменение любого байта меняет хеш от него до корневого коммита
    

### Структура `.git/`

text

.git/
├── objects/      # база объектов (первые 2 символа хеша = директория)
├── refs/         # ссылки: heads/ (ветки), remotes/, tags/
├── HEAD          # текущая позиция (symbolic ref на ветку или прямой хеш)
├── index         # staging area (бинарный файл)
├── config        # настройки репозитория
└── hooks/        # скрипты автоматизации

### Pack-файлы и дельта-компрессия

- **Loose objects** — отдельные файлы (просто, но неэффективно)
    
- **Pack-файлы** — упакованные объекты с **дельта-компрессией** (хранятся различия между версиями)
    
- Git автоматически запускает `git gc` (сборку мусора) для упаковки
    

### Итог

Понимание объектной модели превращает Git из чёрного ящика в логичный инструмент. Blob (файлы) → Tree (директории) → Commit (снимки) → Tag (метки). Content-addressable storage обеспечивает дедупликацию и целостность.

## Статья 5: Ссылки, индекс и pack-файлы — механизмы Git

### Ссылки (refs) — человеческие имена для объектов

**Файлы в `.git/refs/`**, содержащие SHA-1 хеш или другой ref (symbolic ref).

|Тип|Путь|Подвижность|
|---|---|---|
|Локальные ветки|`refs/heads/main`|Да (двигаются с коммитами)|
|Удалённые ветки|`refs/remotes/origin/main`|Нет (обновляются только при fetch)|
|Теги (легковесные)|`refs/tags/v1.0`|Нет|
|HEAD|`.git/HEAD`|Да (symbolic ref или хеш)|

### Reflog — история изменений refs

- Локальный журнал: каждое изменение ref записывается
    
- Хранится 90 дней для достижимых коммитов, 30 для недостижимых
    
- Позволяет восстановить "потерянные" коммиты: `git reflog` → `git reset --hard HEAD@{n}`
    

### Индекс (staging area) — промежуточная область

**Бинарный файл `.git/index`** — снимок следующего коммита. Для каждого файла хранит:

- Путь, SHA-1 blob, метаданные (размер, mtime), флаги
    
- **Номер стадии** (stage):
    
    - Stage 0 — обычный файл
        
    - Stage 1,2,3 — при конфликтах (общий предок, наша версия, их версия)
        

**Три состояния файла:**

1. Modified (рабочая директория)
    
2. **Staged** (индекс) ← `git add`
    
3. Committed (репозиторий) ← `git commit`
    

Индекс позволяет выборочно коммитить изменения и разрешать конфликты.

### Pack-файлы — оптимизация хранения

**Проблема loose objects:** много мелких файлов, неэффективно.

**Решение:** периодическая упаковка в pack-файлы с **дельта-компрессией**:

- Один файл целиком (base object)
    
- Остальные — различия (дельты) от base или других дельт
    

**Типы pack-файлов:**

- Thin pack — дельты ссылаются на объекты вне pack (используется при сетевой передаче)
    
- Shallow pack — для shallow clone (ограниченная история)
    

Git автоматически запускает `git gc` (сборку мусора) для упаковки.

### Как всё работает вместе на примере коммита:

1. `git add` → вычисляется SHA-1 файла → создаётся blob (loose object) → индекс обновляется
    
2. `git commit` → создаётся tree из индекса → создаётся commit → ref ветки обновляется → reflog записывает изменение
    
3. `git gc` (периодически) → упаковывает loose objects в pack-файлы с дельтами
    

### Полезные команды для исследования

bash

git cat-file -t <hash>          # тип объекта
git cat-file -p <hash>          # содержимое объекта
git ls-files --stage            # содержимое индекса
git verify-pack -v .git/objects/pack/*.idx   # содержимое pack-файлов
git count-objects -v            # статистика упаковки
git fsck --full                 # проверка целостности

### Итог

Refs → человеческие имена объектов  
Index → подготовка коммита и разрешение конфликтов  
Pack-файлы → эффективное хранение через дельта-компрессию

Эти механизмы превращают низкоуровневую объектную модель в практичную, быструю и надёжную систему контроля версий.
