# Саммари статей по Linux: Пользователи, группы и права доступа для DevOps

## Статья 1: Многопользовательская система в Linux

### Основная идея

Linux с самого начала проектировался как **многопользовательская система**: на одном физическом сервере работают несколько людей или процессов с **разными правами**. У каждого — свой логин, пароль, домашняя директория и набор прав. Пользователи объединяются в **группы** для упрощения управления.

### Зачем это DevOps-инженеру

|Задача|Почему важно|
|---|---|
|**Безопасность и контроль доступа**|Соблюдать принцип минимальных прав: пользователь/сервис должен иметь ровно тот доступ, который необходим|
|**Управление сервисными аккаунтами**|CI/CD, мониторинг, контейнеризация требуют специальных пользователей со строго ограниченными правами|
|**Совместная работа**|Разработчики, QA, админы работают на одном сервере — без разграничения прав хаос неизбежен|

### Основные понятия

|Понятие|Описание|Где хранится|
|---|---|---|
|**UID** (User ID)|Числовой идентификатор пользователя. Системные: <1000, обычные: ≥1000|`/etc/passwd`|
|**GID** (Group ID)|Числовой идентификатор группы|`/etc/group`|
|**Primary group**|Основная группа пользователя (задаётся в `/etc/passwd`)|`/etc/passwd`|
|**Secondary groups**|Дополнительные группы|`/etc/group`|

### Ключевые файлы

- **`/etc/passwd`** — хранит логин, UID, GID, домашнюю директорию, shell (пароль — `x`, реальный хеш в `/etc/shadow`)
    
- **`/etc/shadow`** — зашифрованные пароли + политика паролей (доступ только root)
    

### Типичные DevOps-задачи

1. Создание/удаление пользователей при онбординге/увольнении
    
2. Назначение прав через группы (`usermod -aG`)
    
3. Создание сервисных аккаунтов (GitLab Runner, Jenkins, Prometheus)
    
4. Автоматизация управления через Ansible, Bash-скрипты
    

### Итог

Многопользовательский режим — фундамент безопасности и организации работы в Linux. Понимание UID/GID, `/etc/passwd` и `/etc/shadow` необходимо для грамотного разграничения доступа.

## Статья 2: Модель прав rwx (read, write, execute)

### Основная идея

У каждого файла/директории в Linux есть три набора прав — для **владельца (user)**, **группы (group)** и **всех остальных (others)**. Права: `r` (чтение), `w` (запись), `x` (исполнение).

### Две нотации

**Символьная** (пример: `rwxr-xr--`):

- Владелец: `rwx` (читать, писать, исполнять) — 7
    
- Группа: `r-x` (читать, исполнять) — 5
    
- Остальные: `r--` (только читать) — 4
    

**Числовая (октальная)**:

- `r` = 4, `w` = 2, `x` = 1
    
- Пример: `754` = владельцу 7 (`rwx`), группе 5 (`r-x`), остальным 4 (`r--`)
    

### Права для директорий (отличаются от файлов!)

|Право|Для директории|
|---|---|
|`r`|Просматривать список содержимого (нужен `x` для входа)|
|`w`|Создавать, удалять, переименовывать файлы внутри|
|`x`|Входить в директорию (`cd`)|

### Зачем DevOps-инженеру

1. **Безопасное CI/CD** — пайплайн не должен падать из-за `Permission denied`, но и не должен иметь лишних прав
    
2. **Снижение риска** — запрет `chmod 777` везде, разумное разделение доступа
    
3. **Docker/Kubernetes** — права файловой системы в контейнерах и монтированных томах
    

### Типичные задачи

|Задача|Действие|
|---|---|
|Сервис Nginx|Создать пользователя `nginx`, права на `/var/www/html` — `750`|
|Конфиги с паролями|`chmod 600` (только владелец читает и пишет)|
|Логи приложения|Права `640` (владелец пишет, группа читает), группа `adm`|

### Итог

Вместо случайного `chmod 777` — точное понимание: кому, какие права и зачем. Это основа безопасности и стабильности инфраструктуры.

## Статья 3: Команды `chmod`, `chown`, `chgrp`

### `chmod` — изменение прав доступа

**Символьный режим:**

bash

chmod u+rwx script.sh      # добавить владельцу всё
chmod g-w config.cfg       # убрать у группы запись
chmod u=rwx,g=rx,o=r file  # явно задать всем

**Числовой режим:**

bash

chmod 755 script.sh   # rwxr-xr-x
chmod 600 secret.txt  # rw-------
chmod 644 file.txt    # rw-r--r--

### `chown` — смена владельца (и группы)

bash

chown devuser myapp.conf              # только владельца
chown devuser:devgroup logs/ -R       # владельца и группу рекурсивно

### `chgrp` — смена только группы

bash

chgrp devteam docs/

### Применение в DevOps

|Сценарий|Команды|
|---|---|
|Jenkins-агент|`chown jenkins:jenkins /builds && chmod 750`|
|Разграничение команд (QA, Dev, Ops)|назначать разные группы и права для каталогов|
|Автоматизация (Ansible)|модуль `file` с параметрами `owner`, `group`, `mode`|

### Итог

- `chmod` → какие права (r, w, x)
    
- `chown` → кто владелец (и группа)
    
- `chgrp` → только группа

## Статья 4: Настройки пользователей по умолчанию

### `/etc/login.defs` — глобальные параметры системы

bash

PASS_MAX_DAYS   90      # срок действия пароля
UID_MIN         1000    # диапазон UID для обычных пользователей
UID_MAX         60000

### `chage` — управление политикой паролей для конкретного пользователя

bash

chage -M 90 -W 7 alice   # пароль на 90 дней, предупреждение за 7 дней
chage -l alice           # посмотреть настройки

### Конфигурация shell и домашней директории

- **Файлы пользователя**: `~/.bashrc`, `~/.bash_profile`, `~/.zshrc`
    
- **Глобальные**: `/etc/bashrc`, `/etc/profile`
    
- **Шаблоны для новых пользователей**: `/etc/skel/` — содержимое копируется в домашнюю директорию при создании учётной записи
    

### Итог

Централизованный контроль: через `/etc/login.defs` (глобально), `chage` (пользователь), `/etc/skel` (шаблоны окружения). Единообразие + безопасность.

## Статья 5: Управление пользователями — `useradd`, `userdel`, `passwd`

### Основные команды

|Команда|Назначение|Пример|
|---|---|---|
|`useradd`|Создание пользователя|`useradd -m -s /bin/bash devuser`|
|`userdel`|Удаление пользователя|`userdel -r olduser` (с домашней директорией)|
|`passwd`|Установка/смена пароля|`passwd devuser`|

### Ключевые файлы

**`/etc/passwd`** — строка пользователя:

text

devuser:x:1001:1001:Developer User:/home/devuser:/bin/bash

Поля: логин | пароль (x) | UID | GID | комментарий | домашняя директория | shell

**`/etc/shadow`** — хеш пароля и политика (только для root):

text

devuser:$6$4AG..../...:18956:0:99999:7:::

### Политика безопасных паролей

- Длина ≥ 8-10 символов
    
- Сложность (регистры, цифры, спецсимволы)
    
- Срок действия (например, 90 дней)
    
- Автоматизация: `pam_pwquality`, `chage`, `passwd -x`
    

### DevOps-практики

- Сервисные аккаунты: shell = `/sbin/nologin` или `/bin/false`
    
- Блокировка уволенных: `userdel` или `usermod --lock`
    
- Автоматизация: Ansible, скрипты массового создания
    

### Итог

Управление пользователями — повседневная рутина DevOps. Понимание `useradd`/`userdel`/`passwd` и структуры `/etc/passwd` + `/etc/shadow` критично для безопасности и автоматизации.

## Статья 6: Управление группами

### Зачем нужны группы

- **Упрощение управления правами** — добавил пользователя в группу → он получил все права этой группы
    
- **Гибкое разграничение** — проектные группы (`devteam`), функциональные (`ops`), сервисные (`jenkins`)
    

### Основные команды

|Команда|Назначение|Пример|
|---|---|---|
|`groupadd`|Создать группу|`groupadd devteam`|
|`groupdel`|Удалить группу|`groupdel oldteam`|
|`gpasswd`|Пароль группы и управление членами|`gpasswd -a alice devteam` (добавить), `-d` (удалить)|
|`usermod -aG`|Добавить пользователя в дополнительные группы|`usermod -aG docker,adm alice`|

### Основная vs. дополнительные группы

- **Primary group** — указана в `/etc/passwd` (обычно совпадает с логином)
    
- **Secondary groups** — остальные группы, в которых состоит пользователь
    

**Проверка:** `groups alice` — показать все группы пользователя

### DevOps-примеры

- Разработчик: основная группа `devuser`, дополнительные — `testers`, `docker`
    
- Окружения: `prod-deploy` — доступ только для ограниченного круга
    
- CI/CD: отдельные группы для Jenkins-агентов, Prometheus и т.д.
    

### Итог

Группы — ключевой механизм коллективного доступа. `groupadd`/`groupdel` создают группы, `usermod -aG` добавляет пользователей. Один пользователь может состоять в нескольких группах, что даёт гибкость при разграничении ролей.
