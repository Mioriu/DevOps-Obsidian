# Саммари статей по Linux: Umask, спецбиты, ACL, sudo и практики безопасности

## Статья 1: Umask — маска создания файлов

### Основная идея

**Umask** (user file-creation mode mask) — параметр, определяющий, **какие права будут "отняты"** у новых файлов и директорий. Работает как "анти-маска": если в umask есть бит, он вычитается из максимальных прав (666 для файлов, 777 для директорий).

### Как работает

|Объект|Максимальные права|Umask|Итоговые права|
|---|---|---|---|
|Файл|666 (rw-rw-rw-)|022|**644** (rw-r--r--)|
|Файл|666|002|**664** (rw-rw-r--)|
|Директория|777 (rwxrwxrwx)|022|**755** (rwxr-xr-x)|
|Директория|777|002|**775** (rwxrwxr-x)|

### Типичные значения

|Umask|Файлы|Директории|Когда использовать|
|---|---|---|---|
|`022`|644|755|**Стандарт по умолчанию** — владелец всё, остальные только читают|
|`002`|664|775|**Командная работа** — группа имеет право записи|
|`027`|640|750|**Безопасная среда** — группа только читает, остальные без прав|
|`077`|600|700|**Максимальная изоляция** — только владелец|

### Команды

bash

umask                    # просмотр текущей маски (например, 0022)
umask 002                # установка для текущей сессии

### Глобальная настройка

Прописать в `/etc/profile`, `~/.bashrc` или `~/.profile`:

bash

umask 002

### Итог

Umask — невидимый, но важный параметр. Для командной работы удобен `002` (файлы доступны группе на запись), для повышенной безопасности — `027` или `077`.

## Статья 2: Специальные биты — SUID, SGID, Sticky bit

### SUID (Set UID) — на исполняемых файлах

**Эффект:** Программа запускается с правами **владельца файла**, а не того, кто её запустил.

**Классический пример:** `/usr/bin/passwd` (принадлежит root, имеет SUID) — обычный пользователь может менять пароль (писать в `/etc/shadow`).

**Обозначение:** `-rwsr-xr-x` (буква `s` вместо `x` у владельца)

**Установка:**

bash

chmod u+s файл       # символьный способ
chmod 4755 файл      # числовой (4 перед правами)

### SGID (Set GID)

**На файлах:** запуск с правами **группы** файла (аналогично SUID)

**На директориях:** новые файлы наследуют **группу директории**, а не основную группу пользователя

**Обозначение:** `drwxr-sr-x` (буква `s` вместо `x` у группы)

**Установка:**

bash

chmod g+s каталог     # символьный
chmod 2775 каталог    # числовой (2 перед правами)

### Sticky bit — на директориях

**Эффект:** Только **владелец файла** (или root) может удалить/переименовать файл внутри директории, даже если у всех есть права на запись.

**Классический пример:** `/tmp` — `drwxrwxrwt` (буква `t` вместо `x` у others)

**Установка:**

bash

chmod +t каталог      # символьный
chmod 1777 каталог    # числовой (1 перед правами)

### Таблица спецбитов

|Бит|Числовое значение|На файлах|На директориях|
|---|---|---|---|
|SUID|4xxx|Запуск от владельца|(не используется)|
|SGID|2xxx|Запуск от группы|Новые файлы → группа директории|
|Sticky|1xxx|(устарело)|Только владелец удаляет|

### Итог

SUID/SGID/Sticky — мощные, но опасные инструменты. Неправильно настроенный SUID может дать обычному пользователю права root. Всегда проверяйте, зачем вы их ставите.

## Статья 3: ACL (Access Control Lists) — расширенные права

### Зачем нужны ACL

Классические права (`rwx` для user/group/others) не позволяют дать доступ **конкретному пользователю** или **конкретной группе** отдельно. ACL решает эту проблему.

### Обозначение

В `ls -l` наличие ACL обозначается символом `+`:

bash

-rw-rw-r--+ 1 user1 devgroup report.txt

### Основные команды

|Команда|Назначение|Пример|
|---|---|---|
|`getfacl файл`|Просмотреть ACL|`getfacl report.txt`|
|`setfacl -m u:user2:rw файл`|Добавить права пользователю|`setfacl -m u:alice:rw secret.txt`|
|`setfacl -m g:devteam:rx файл`|Добавить права группе|—|
|`setfacl -x u:user2 файл`|Удалить запись|—|
|`setfacl -b файл`|Удалить все ACL|—|

### Наследование (default ACL) для директорий

bash

setfacl -m d:u:user2:rw /shared_dir/
# Буква "d" — все новые файлы внутри унаследуют права

### Маска (mask)

Ограничивает **максимальные права** для всех дополнительных ACL-записей (не влияет на владельца и others). Если mask = `r--`, то никто из дополнительных пользователей не получит `w` или `x`.

### Итог

ACL — гибкое расширение для сложных сценариев доступа. Не злоупотребляйте, но знайте, что они существуют.

## Статья 4: sudo и суперпользователь root

### Root (UID 0) — абсолютные привилегии

**Риски:** одна неосторожная команда (`rm -rf /`, изменение прав) может уничтожить систему.

### Рекомендации по безопасности

1. **Никогда не работайте постоянно под root**
    
2. Не логиньтесь как root по SSH
    
3. Используйте `sudo` для отдельных команд
    
4. Ведите логи действий
    

### su vs sudo

|Команда|Действие|Требует|Риск|
|---|---|---|---|
|`su -`|Переключение на root (новая сессия)|пароль root|высокий (забываешь, что ты root)|
|`sudo cmd`|Выполнить одну команду от root|пароль **своего** пользователя|низкий (явно и на одну команду)|

### Настройка `/etc/sudoers` (редактировать только через `visudo`!)

bash

# Пользователь alice может всё (с вводом своего пароля)
alice ALL=(ALL:ALL) ALL
# Группа admin — всё без пароля
%admin ALL=(ALL:ALL) NOPASSWD:ALL
# bob может только перезапускать nginx
bob ALL=(root) /bin/systemctl restart nginx
# devops может запускать любые systemctl команды
%devops ALL=(root) /bin/systemctl *

### Итог

`sudo` — ключевой инструмент безопасного делегирования root-прав. Настраивайте через `visudo`, давайте минимально необходимые права.

## Статья 5: Практики безопасности и управления доступом

### Типовые сценарии на production-серверах

|Сценарий|Решение|
|---|---|
|Разделение команд (Dev, QA, Ops)|Группы (`devteam`, `qatest`, `ops`) + SGID/ACL для общих директорий|
|Ограничение root|`sudo` с точечными разрешениями, никакого прямого входа|
|Сервисные аккаунты|`nginx`, `postgres`, `jenkins` — отдельные пользователи с минимальными правами|
|Чувствительные файлы (ключи, пароли)|`chmod 600`, ACL для точечного доступа|

### Массовое создание пользователей (онбординг)

1. **Единая схема именования** (`имя.фамилия`, `first.last`)
    
2. **Шаблон `/etc/skel`** — базовые конфиги (.bashrc, .gitconfig)
    
3. **Группы по ролям** — добавлять сотрудников в группы, а не менять права вручную
    
4. **Автоматизация** — Ansible, Bash-скрипты для массового создания
    
5. **Политика паролей** — временный пароль + принудительная смена при первом входе
    

### Логирование и аудит

|Инструмент|Что даёт|Пример команды|
|---|---|---|
|`/var/log/auth.log` (или `/var/log/secure`)|Все логины, sudo, su|`grep "sudo" /var/log/auth.log`|
|`last`|История входов пользователей|`last -a` (с IP-адресами)|
|`auditd`|Отслеживание конкретных файлов/действий|`auditctl -w /etc/passwd -p wa`|

### Итог

Производственная безопасность — это система:

- **Пользователи и группы** → разграничение доступа
    
- **sudo** → контролируемое повышение привилегий
    
- **ACL/спецбиты** → тонкая настройка
    
- **Логи** → прозрачность и расследование инцидентов
    
- **Автоматизация** → воспроизводимость и скорость
