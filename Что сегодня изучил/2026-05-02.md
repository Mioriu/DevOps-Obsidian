## Docker образы и слои — полное резюме

### 1. Что такое образ

**Образ** — это иммутабельный (неизменяемый) шаблон файловой системы, из которого создаются контейнеры. Это не монолитный файл, а **стопка из нескольких read-only слоёв**, объединённых файловой системой UnionFS (обычно Overlay2).

Образ = стопка слоёв-диффов + метаданные (CMD, ENV, EXPOSE, порты и т.д.)

---

### 2. Что такое слой

**Слой** — это атомарная, адресуемая по SHA256-хешу единица образа. Технически это набор файлов, представляющий **разницу (diff)** относительно родительского слоя.

- Лежит на хосте в `/var/lib/docker/overlay2/<hash>/diff/`
    
- Создаётся **каждой инструкцией** `RUN`, `COPY` или `ADD` в Dockerfile
    
- Содержит **только изменённые/добавленные файлы** — не дублирует всю файловую систему
    

Инструкции `CMD`, `EXPOSE`, `ENV` не создают файлового слоя — это только метаданные образа.

**Аналогия:** слой Docker'а — как коммит в Git: хранит не полную копию, а только дельту изменений.

---

### 3. Почему каждая инструкция создаёт отдельный слой

Это архитектурный компромисс ради трёх ключевых свойств:

- **Дедупликация (экономия места):** 10 контейнеров на базе одного `ubuntu:22.04` хранят базовые слои только один раз на диске
    
- **Кэширование (скорость сборки):** Docker переиспользует готовый слой, если инструкция и все родительские слои не изменились
    
- **Иммутабельность и безопасность:** базовые слои нельзя повредить из контейнера, они read-only
    

---

### 4. Кэширование слоёв — почему порядок инструкций критичен

Правило кэша: **Docker переиспользует слой, если та же инструкция выполняется над тем же родительским слоем.**

Как только в цепочке встречается cache miss — все последующие слои пересобираются заново, даже если для них кэш был.

**Поэтому best practice:** дорогие и редко меняющиеся операции — в начало Dockerfile.

dockerfile

# ✅ ПРАВИЛЬНО: зависимости кэшируются
COPY package.json package-lock.json ./
RUN npm ci --only=production    # этот слой в кэше, пока манифесты не менялись
COPY . .                        # меняется часто, но выполняется быстро
# ❌ ПЛОХО: при любом изменении кода — установка зависимостей заново
COPY . .
RUN npm ci --only=production    # cache miss при каждом изменении кода

### 5. UnionFS и Copy-on-Write — как слои объединяются в контейнер

При запуске контейнера Overlay2 создаёт:

- **LowerDir:** стопка всех read-only слоёв образа (поиск файла — сверху вниз до первого совпадения)
    
- **UpperDir:** новый тонкий read-write слой для всех изменений в контейнере
    
- **MergedDir:** объединённое представление — то, что видит процесс в контейнере
    

**Copy-on-Write (CoW):**

- При **чтении** файла — он берётся из первого слоя, где найден (UpperDir → LowerDir сверху вниз)
    
- При **изменении** файла — он копируется из read-only слоя в UpperDir, изменения пишутся туда. Оригинал в образе не трогается
    
- При **удалении** — в UpperDir создаётся whiteout-файл (заглушка "файла нет"), образ не меняется и не уменьшается
    

**Следствие:** `RUN apt install что-то && rm -rf /кэш` в **одной** инструкции — правильно. Разнесение на два `RUN` — мусорные файлы останутся в промежуточном слое навсегда.

### 6. Почему в образах (node, python, etc.) есть все стандартные директории Linux

Потому что **образ — это изолированный userspace ОС**, а не просто бинарник с приложением.

- Python/node — это не статические бинарники "всё в себе"
    
- Им нужны: динамические библиотеки (`/lib`, `/usr/lib`), конфиги (`/etc/ssl/`, `/etc/resolv.conf`), временные папки (`/tmp`, `/var/tmp`), файлы устройств (`/dev/null`, `/dev/urandom`)
    
- Всю эту структуру (FHS) предоставляет **базовый образ** в `FROM` — будь то `debian`, `ubuntu`, `alpine`
    
- `FROM scratch` — пустой образ без ничего. В нём можно сделать "только Python", но придётся вручную собрать и положить все зависимости — адский труд, поэтому так делают редко (distroless-образы как компромисс)

### 7. Практические выводы и best practices

|Принцип|Почему|
|---|---|
|Редко меняющееся — в начало Dockerfile|Кэширование дорогих слоёв (установка пакетов)|
|Часто меняющееся — в конец|Пересобирается быстро (`COPY . .`)|
|`apt-get update && apt-get install -y ... && rm -rf /var/lib/apt/lists/*` в одном RUN|Не оставлять мусор в промежуточных слоях|
|Использовать `.dockerignore`|Не отправлять лишнее в контекст сборки и не портить кэш|
|Несколько Dockerfile'ов в папке — флаг `-f`|`docker build -f Dockerfile.prod -t app:prod .`|
|Контекст (`.`) — то, что видит Docker при сборке|Нельзя скопировать файлы "выше" контекста|
|Overlay2 — рекомендуемый драйвер хранения|Дедупликация, производительность, стабильность|

### Ключевая ментальная модель

> **Образ Docker'а — это content-addressable стопка иммутабельных диффов файловой системы, каждый из которых закэширован по хешу родителя + инструкции. Контейнер — это образ с добавленным сверху тонким рантайм-слоем и механизмом Copy-on-Write.**
