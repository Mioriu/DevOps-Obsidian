## Статья 1: Service — стабильная точка доступа к подам

### Проблема, которую решает Service

- IP-адреса подов **ненадёжны** — под пересоздаётся → новый IP
    
- Подов несколько (реплики) — клиенту нужен один адрес, а не список
    

**Service** — стабильная точка доступа к группе подов. У него есть постоянный IP и DNS-имя, трафик распределяется по подам через селектор по меткам.

### Структура Service

yaml

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80

- `selector` — метки подов, на которые направляется трафик
    
- `port` — порт сервиса (куда обращаются клиенты)
    
- `targetPort` — порт контейнера (куда идёт трафик)
    

**Endpoints** — вычисленный по селектору список реальных адресов подов:

bash

kubectl get endpoints web

### DNS-имя

У каждого сервиса есть DNS-имя. Короткое: `web`. Полное: `web.default.svc.cluster.local`. Внутри одного namespace хватает короткого имени.

### Типы Service

|Тип|Доступ|Применение|
|---|---|---|
|**ClusterIP** (по умолчанию)|Только изнутри кластера|Внутренние сервисы (БД, кэши, API)|
|**NodePort**|`IP-ноды:30000-32767`|Тестовые стенды, локальные кластеры|
|**LoadBalancer**|Внешний IP от облака|Публичная точка входа в облаке|

### ClusterIP

- Виртуальный IP, доступный только внутри кластера
    
- Работает через **kube-proxy** (iptables/IPVS) — подмена адреса назначения на один из подов
    
- Балансировка работает без настройки
    

### NodePort

- Открывает порт **на каждой ноде кластера** (диапазон 30000–32767)
    
- Запрос на `IP-любой-ноды:30080` → попадает в сервис → распределяется на поды
    
- ClusterIP сохраняется
    

### LoadBalancer

- Для облачных кластеров (Yandex Cloud, AWS, GCP)
    
- `cloud-controller-manager` создаёт внешний балансировщик
    
- Появляется `EXTERNAL-IP`
    

bash

kubectl get svc web
# TYPE LoadBalancer, EXTERNAL-IP 84.201.158.77

**Оговорки:**

- Вне облака (minikube, своё железо) — `<pending>` навсегда
    
- Каждый LoadBalancer-сервис → отдельный платный балансировщик
    

### ExternalDNS — автоматизация DNS-записей

yaml

metadata:
  annotations:
    external-dns.alpha.kubernetes.io/hostname: app.example.com

Контроллер отслеживает такие аннотации и через API DNS-провайдера создаёт/обновляет A-записи.

### ExternalName — псевдоним для внешнего ресурса

yaml

spec:
  type: ExternalName
  externalName: rc1a-abc123.mdb.yandexcloud.net

Сервис-псевдоним. Обращение к `db` внутри кластера превращается в обращение к внешнему имени.

### Шпаргалка

bash

kubectl get services
kubectl describe service web
kubectl get endpoints web
kubectl run tmp --rm -it --image=busybox:1.36 -- sh   # временный под
kubectl expose deployment web --port=80
kubectl port-forward service/web 8080:80
kubectl delete service web

## Статья 2: ConfigMap, Secret, Namespaces

### ConfigMap — конфигурация отдельно от образа

Объект с конфигурационными данными в виде пар ключ-значение.

yaml

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  APP_MODE: "production"
  LOG_LEVEL: "info"
  nginx.conf: |
    server {
        listen 80;
        root /usr/share/nginx/html;
    }

**Императивное создание:**

bash

kubectl create configmap web-config --from-literal=APP_MODE=production
kubectl create configmap nginx-config --from-file=nginx.conf

**Подключение к поду (3 способа):**

1. Одно значение → одна переменная:
    

yaml

env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: web-config
        key: LOG_LEVEL

2. Все ключи разом → переменные окружения:
    

yaml

envFrom:
  - configMapRef:
      name: web-config

3. Монтирование как файлы:
    

yaml

volumeMounts:
  - name: config
    mountPath: /etc/nginx/conf.d
volumes:
  - name: config
    configMap:
      name: nginx-config

**Обновление ConfigMap:**

- Переменные окружения не обновляются в работающем поде
    
- Файлы обновляются с задержкой, но приложение должно уметь перечитывать конфиг
    
- **Рабочий приём:** `kubectl rollout restart deployment/web` — перекат подов с новым конфигом

### Secrets — для чувствительных данных

Устройство как ConfigMap, но для паролей, токенов, ключей.

bash

kubectl create secret generic db-secret \
  --from-literal=POSTGRES_USER=app \
  --from-literal=POSTGRES_PASSWORD=s3cr3t-pAssw0rd

**Важно:** значения хранятся в **base64**, а не в зашифрованном виде!

bash

echo 'czNjcjN0LXBBc3N3MHJk' | base64 -d
# s3cr3t-pAssw0rd

**Зачем тогда Secret:**

- Права доступа: доступ к Secret уже, чем к ConfigMap
    
- `describe secret` скрывает значения
    
- etcd можно шифровать секреты при хранении
    

**Для удобства — `stringData` (пишется как есть):**

yaml

stringData:
  POSTGRES_USER: app
  POSTGRES_PASSWORD: s3cr3t-pAssw0rd

**Подключение:**

yaml

envFrom:
  - configMapRef:
      name: web-config
  - secretRef:
      name: db-secret

**Секреты и Git:** манифесты секретов с реальными значениями **не коммитятся**. Доставляются через CI/CD или инструменты (Sealed Secrets, External Secrets Operator).

### Namespaces — разделение кластера

Способ разделить один кластер на изолированные части.

bash

kubectl get namespaces
# default, kube-system, kube-public, kube-node-lease

- `kube-system` — служебные компоненты
    
- `default` — всё, что создавали без указания namespace
    

**Создание и использование:**

bash

kubectl create namespace staging
kubectl get pods -n staging
kubectl apply -f deployment.yaml -n staging

yaml

metadata:
  name: web
  namespace: staging

**Имена уникальны в пределах namespace** — можно иметь `web` в `staging` и `production` одновременно.

**DNS с учётом namespace:**

- Короткое имя: `web`
    
- Полное: `web.staging.svc.cluster.local`
    
- Межпространственное: `web.staging`
    

**Переключение рабочего пространства:**

bash

kubectl config set-context --current --namespace=staging

**Важно:** namespace сам по себе **не граница безопасности** — сеть между пространствами открыта. Для ограничений — RBAC и Network Policies.

**Не все объекты живут в namespace:** ноды, кластерные ресурсы.

---

### Полный пример (стенд)

yaml

# staging.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: staging
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
  namespace: staging
data:
  APP_MODE: "staging"
  LOG_LEVEL: "debug"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: staging
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: myapp:1.4
          envFrom:
            - configMapRef:
                name: web-config
            - secretRef:
                name: db-secret

bash

kubectl create secret generic db-secret -n staging --from-literal=POSTGRES_PASSWORD=s3cr3t
kubectl apply -f staging.yaml

### Шпаргалка

bash

# ConfigMap
kubectl create configmap NAME --from-literal=KEY=value
kubectl create configmap NAME --from-file=nginx.conf
kubectl get configmaps
# Secret
kubectl create secret generic NAME --from-literal=KEY=value
kubectl get secret NAME -o yaml   # base64!
# Обновление конфига
kubectl rollout restart deployment/NAME
# Namespaces
kubectl get namespaces
kubectl create namespace staging
kubectl get pods -n staging
kubectl config set-context --current --namespace=staging
