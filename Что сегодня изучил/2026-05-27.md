## 1. Сети в Docker Compose

По умолчанию Compose создаёт одну сеть, где сервисы видят друг друга по именам. Явное управление сетями позволяет изолировать сервисы, разделяя их по разным подсетям, и подключаться к уже существующим внешним сетям.

**Ключевое:**

- Сеть по умолчанию: `<проект>_default`, DNS по имени сервиса.
    
- Явные сети: можно создать несколько (например, `frontend_net`, `backend_net`) и подключать сервисы выборочно для изоляции.
    
- `external: true` — подключение к сети, созданной вне Compose (полезно для общего reverse proxy).
    
- DNS работает только между контейнерами в одной сети.
    
- `ipam` — для статических IP и подсетей (редко нужно).

## 2. Переменные окружения и `.env`

Compose автоматически читает файл `.env` и подставляет переменные в `docker-compose.yml` через синтаксис `${KEY}`. Это позволяет не хранить чувствительные данные прямо в YAML и гибко менять параметры.

**Ключевое:**

- `.env` — для подстановки в YAML; `env_file` — для передачи переменных внутрь контейнера.
    
- `docker-compose config` — проверка итоговой конфигурации после подстановки.
    
- Осторожно: `.env` с секретами нельзя коммитить в репозиторий.

## 3. Профили (profiles)

Профили позволяют выборочно запускать сервисы, задавая им метки. По умолчанию запускается профиль `default`, остальные включаются флагом `--profile`.

**Ключевое:**

- Удобно для разных сред (dev, test) и опциональных сервисов.
    
- Запуск: `docker compose --profile dev up`.
    

---

## 4. Рестарт-политики

Управляют поведением контейнера при остановке или падении. Обеспечивают автоматическое восстановление сервисов без ручного вмешательства.

**Ключевое:**

- `no` — не перезапускать (по умолчанию).
    
- `on-failure` — только при ненулевом коде завершения.
    
- `always` — всегда перезапускать (даже при нормальной остановке).
    
- `unless-stopped` — как `always`, но не перезапускается, если остановлен вручную.
    
- Актуально для продакшн-сервисов: БД, веб-серверы.
    

---

## 5. Секция `build` и override-файлы

Compose может собирать образы на лету через секцию `build`, избавляя от отдельного `docker build`. Файл `docker-compose.override.yml` автоматически объединяется с основным, позволяя разделять конфигурации для разработки и продакшена.

**Ключевое:**

- `build:` с параметрами: `context`, `dockerfile`, `args`.
    
- `docker-compose.override.yml` — переопределяет/дополняет базовый YAML.
    
- Явное объединение: `docker-compose -f docker-compose.yml -f dev.yml up`.
    
- Полезно для CI/CD и локальной разработки с bind mounts и debug-настройками.

## 6. Масштабирование и `--scale`

Флаг `--scale` запускает несколько реплик одного сервиса. Напрямую публиковать порты для всех реплик нельзя — нужен балансировщик.

**Ключевое:**

- `docker-compose up --scale web=3` — три контейнера с одинаковой конфигурацией.
    
- Конфликт портов: маппинг `8080:80` сработает только для одного контейнера.
    
- Решение: внешний прокси (Nginx, Traefik), который распределяет трафик внутри сети.
    
- Для горизонтального масштабирования на разные хосты нужен Swarm/Kubernetes.
