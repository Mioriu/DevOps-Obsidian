# Саммари статей по Docker: Логи, слои и Dockerfile

## Статья 1: Логи и мониторинг контейнеров

### Основная идея

Docker перехватывает **STDOUT/STDERR** приложения — эти данные доступны через `docker logs`. Если приложение пишет в файл (например, `/var/log/app.log`), стандартные команды Docker не покажут эти логи без дополнительных действий.

### Основные команды мониторинга

|Команда|Назначение|Пример|
|---|---|---|
|`docker logs`|Показать логи (STDOUT/STDERR)|`docker logs mynginx`|
|`docker logs -f`|Логи в реальном времени (follow)|`docker logs -f mynginx`|
|`docker logs --tail N`|Последние N строк|`docker logs --tail 100 mynginx`|
|`docker stats`|Метрики ресурсов (CPU/RAM/сеть/диск)|`docker stats`|
|`docker top`|Процессы внутри контейнера|`docker top mynginx`|
|`docker events`|События Docker (запуск/остановка и т.д.)|`docker events`|

### Что делать, если приложение пишет логи в файл?

**Проблема:** приложение пишет в `/var/log/app.log`, `docker logs` пуст.

**Три способа получить эти логи:**

|Способ|Команда|Когда использовать|
|---|---|---|
|**1. Разовый просмотр через exec**|`docker exec myapp cat /var/log/app.log`|Быстрая диагностика|
|**2. Подписаться на файл в реальном времени**|`docker exec myapp tail -f /var/log/app.log`|Отладка в моменте|
|**3. Смонтировать лог-файл на хост**|`-v /host/logs:/var/log`|Постоянное хранение|

### Как перенаправить файловые логи в STDOUT (чтобы работал `docker logs`)

**Временное решение для уже запущенного контейнера:**

bash

docker exec -d <container> sh -c "tail -F /var/log/app.log >&1 &"

**Постоянное решение (в Dockerfile/entrypoint):**

bash

CMD sh -c "/usr/local/bin/start-app & tail -F /var/log/app.log"

**Лучшая практика:** пишите логи сразу в STDOUT/STDERR, чтобы использовать стандартные инструменты Docker.

### Итог

- `docker logs` — читает только STDOUT/STDERR
    
- `docker stats` — метрики ресурсов
    
- `docker top` — процессы внутри
    
- Если приложение пишет в файл → используйте `docker exec` или монтирование томов

## Статья 2: Слои образов (Layers) и Copy-on-Write

### Основная идея

Docker Image — это **набор слоёв** (layers), наложенных друг на друга через **union file system**. Каждая инструкция в Dockerfile создаёт новый слой.

### Архитектура слоёв

text

┌─────────────────────────────┐
│   Слой записи (COW)         │ ← только для контейнера (временные изменения)
├─────────────────────────────┤
│   COPY . /app               │ ← слой 3 (read-only)
├─────────────────────────────┤
│   RUN npm install           │ ← слой 2 (read-only)
├─────────────────────────────┤
│   FROM node:14              │ ← базовый слой (read-only)
└─────────────────────────────┘

### Почему слои удобны?

|Свойство|Объяснение|
|---|---|
|**Кэширование**|При изменении верхнего слоя нижние не пересобираются|
|**Повторное использование**|Один базовый слой (Alpine:3.17) используется во многих образах|
|**Экономия места**|10 контейнеров на одном образе → общие слои не дублируются|

### Copy-on-Write (COW)

При запуске контейнера Docker добавляет **слой записи** поверх всех read-only слоёв:

- Все изменения (создание, удаление, модификация файлов) попадают в этот верхний слой
    
- Базовый образ остаётся нетронутым
    
- При удалении контейнера слой записи удаляется
    

### Базовые образы (Base Images)

**Пример:** `FROM ubuntu:20.04` или `FROM alpine:3.17`

- Официальные образы на Docker Hub (Ubuntu, Alpine, Python, Node, Nginx)
    
- Минимальная система, на которой вы строите своё приложение
    
- Alpine — очень маленький (~5 МБ), популярен для минимизации размера
    

### Итог

- Образ = стопка read-only слоёв
    
- Каждый `RUN`/`COPY`/`ADD` создаёт новый слой
    
- Контейнер добавляет временный слой записи (COW)
    
- Понимание слоёв → оптимизация сборки и экономия места

## Статья 3: Dockerfile — инструкции для сборки образов

### Основные инструкции Dockerfile

|Инструкция|Назначение|Пример|
|---|---|---|
|`FROM`|Базовый слой (с чего начинаем)|`FROM alpine:3.17`|
|`RUN`|Выполнить команду при сборке|`RUN apk add nodejs npm`|
|`COPY`|Скопировать файлы с хоста в образ|`COPY . /app`|
|`ADD`|COPY + распаковка tar + загрузка по URL|`ADD archive.tar.gz /app`|
|`CMD`|Команда по умолчанию (перезаписывается)|`CMD ["npm", "start"]`|
|`ENTRYPOINT`|Главная команда (добавляются аргументы)|`ENTRYPOINT ["python", "app.py"]`|
|`ENV`|Переменные окружения|`ENV NODE_ENV production`|
|`EXPOSE`|Декларация порта (для документации)|`EXPOSE 3000`|
|`WORKDIR`|Сменить рабочую директорию|`WORKDIR /app`|
|`USER`|Сменить пользователя (безопасность)|`USER node`|
|`VOLUME`|Точка монтирования тома|`VOLUME /data`|

### CMD vs ENTRYPOINT — ключевое различие

||`CMD`|`ENTRYPOINT`|
|---|---|---|
|**Перезапись при `docker run`**|Да (полностью)|Нет (только добавление аргументов)|
|**Типичное использование**|Дефолтные аргументы|Главный исполняемый файл|
|**Пример совместного использования**|`ENTRYPOINT ["python", "app.py"]`  <br>`CMD ["--port", "8080"]`||

### Оптимизация: объединение `RUN` команд

**Плохо (много слоёв):**

dockerfile

RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

**Хорошо (один слой):**

dockerfile

RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*

### Пример рабочего Dockerfile

dockerfile

FROM node:18-alpine
WORKDIR /app
# Копируем только package.json (кэширование зависимостей)
COPY package*.json ./
RUN npm install
# Копируем остальной код
COPY . .
ENV NODE_ENV=production
EXPOSE 3000
CMD ["npm", "start"]

### Сборка и запуск

bash

docker build -t my-app .          # собрать образ
docker run -p 3000:3000 my-app    # запустить контейнер

### Итог

- `FROM` → базовый образ
    
- `RUN` → команды сборки (объединять в один слой!)
    
- `COPY`/`ADD` → копирование файлов
    
- `CMD`/`ENTRYPOINT` → запуск контейнера
    
- `ENV`/`EXPOSE`/`WORKDIR`/`USER` → настройка окружения
    

Понимание слоёв и инструкций Dockerfile — ключ к созданию эффективных (быстрых и маленьких) образов.
