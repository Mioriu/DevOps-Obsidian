# Саммари статей по сетевым расширенным темам

## Статья 1: Web Server, Reverse Proxy и балансировка

### Web Server vs Application Server

|Web Server (nginx, Apache)|Application Server (gunicorn, uvicorn, Node.js)|
|---|---|
|Отдаёт статику (HTML, CSS, JS, картинки)|Выполняет код приложения|
|Проксирует запросы к приложениям|Генерирует динамический контент|
|Терминирует SSL|—|

**Типичная схема:** Клиент → Nginx → Gunicorn → Django

### Forward Proxy vs Reverse Proxy

|Forward Proxy (сторона клиента)|Reverse Proxy (сторона сервера)|
|---|---|
|Клиент знает, что использует прокси|Клиент не знает о прокси|
|Выход в интернет из корпсети, обход блокировок|Балансировка, SSL termination, кэширование|
|Сервер не знает реальный IP клиента|Backend-ы не торчат в интернет напрямую|

### Что делает Reverse Proxy

1. **SSL/TLS termination** — расшифровывает HTTPS, передаёт HTTP на backend (сертификаты в одном месте)
    
2. **Отдача статики** — файлы с диска без дёрганья приложения
    
3. **Маршрутизация** — разные URL → разные backend-ы
    
4. **Защиты** — rate limiting, буферизация, скрытие внутренней структуры
    

### Основные инструменты

|Инструмент|Сложность|Авто-SSL|Динамическая конфигурация|Когда использовать|
|---|---|---|---|---|
|**Nginx**|Низкая|Нет (certbot)|Нет|Большинство случаев|
|**Caddy**|Низкая|Да|Частично|Простые проекты, автоSSL|
|**Traefik**|Средняя|Да|Да|Docker, Kubernetes|

### Важные заголовки при проксировании

nginx

proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

## Статья 2: VPN — WireGuard, OpenVPN, IPSec

### Типы VPN

- **Remote Access (client-to-site)** — клиент подключается к сети организации
    
- **Site-to-Site** — соединение двух сетей (офис A — офис B)
    
- **Mesh** — каждый узел соединён с каждым
    

### Сравнение VPN-протоколов

|Характеристика|WireGuard|OpenVPN|IPSec/IKEv2|
|---|---|---|---|
|Скорость|Очень высокая|Средняя|Высокая|
|Сложность настройки|Низкая|Средняя|Высокая|
|Протокол|UDP|UDP/TCP|UDP (ESP+IKE)|
|Поддержка ОС|Linux (ядро), остальные userspace|Все|Все (нативно)|
|Криптография|Фиксированная|Настраиваемая|Настраиваемая|

### Когда что использовать

|Сценарий|Рекомендация|
|---|---|
|Новые проекты, макс. производительность|WireGuard|
|Нужна поддержка TCP (строгие файрволы)|OpenVPN|
|Site-to-site с сетевым оборудованием|IPSec/IKEv2|
|Мобильные клиенты (нативная поддержка)|IKEv2|
|Mesh между серверами|WireGuard + Tailscale/Netmaker|

**WireGuard AllowedIPs** — ключевая концепция: одновременно и фильтр входящих, и таблица маршрутизации.

## Статья 3: Балансировка нагрузки

### L4 vs L7 балансировка

| Характеристика  | L4 (TCP/UDP)  | L7 (HTTP/HTTPS) |
| --------------- | ------------- | --------------- |
| Скорость        | Быстрее       | Медленнее       |
| Протоколы       | Любые TCP/UDP | HTTP/HTTPS      |
| Роутинг по URL  | Нет           | Да              |
| Sticky sessions | По IP         | По cookie       |
| Health checks   | TCP connect   | HTTP endpoint   |

### Алгоритмы балансировки

| Алгоритм                 | Принцип                                  | Когда использовать          |
| ------------------------ | ---------------------------------------- | --------------------------- |
| **Round Robin**          | По очереди                               | Серверы одинаковой мощности |
| **Weighted Round Robin** | По очереди с весами                      | Серверы разной мощности     |
| **Least Connections**    | На сервер с наименьшим числом соединений | Запросы разной длительности |
| **IP Hash**              | hash(IP) % N                             | Простые sticky sessions     |
| **Random**               | Случайный выбор                          | Много запросов, не критично |

### Health Checks

- **TCP check** — попытка установить соединение
    
- **HTTP check** — запрос к `/health`, проверка кода 200
    
- **Глубокий HTTP check** — проверка тела ответа
    

Параметры: Interval, Timeout, Unhealthy/Healthy threshold.

### Основные инструменты

| Инструмент   | Уровень | Когда использовать         |
| ------------ | ------- | -------------------------- |
| **Nginx**    | L7      | Веб, простые случаи        |
| **HAProxy**  | L4/L7   | Высокие нагрузки, TCP      |
| **Envoy**    | L7      | Service mesh, микросервисы |
| **Облачные** | L4/L7   | Облачная инфраструктура    |

## Статья 4: Маршрутизация

### Таблица маршрутизации (`ip route`)

text

default via 192.168.1.1 dev eth0              # маршрут по умолчанию
10.0.0.0/8 via 10.255.0.1 dev eth1           # через gateway
172.16.0.0/16 dev eth1 scope link            # напрямую (без gateway)
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100

### Gateway и default route

- **Gateway (шлюз)** — маршрутизатор, знающий путь к другим сетям
    
- **Default route** — куда отправлять пакеты без специфичного маршрута
    

### Маршрутизация между подсетями

Чтобы сервер маршрутизировал трафик между сетями:

1. Включить IP forwarding (`net.ipv4.ip_forward=1`)
    
2. Убедиться, что файрвол разрешает FORWARD
    
3. На клиентах должен быть маршрут через этот сервер

## Статья 5: CDN (Content Delivery Network)

### Что даёт CDN

- **Скорость** — контент с ближайшего узла
    
- **Снижение нагрузки на origin** — 95% запросов уходит в кэш
    
- **Отказоустойчивость** — при падении origin сайт работает на кэше
    
- **Защита от DDoS** — распределённая сеть поглощает атаки
    

### Как работает CDN

**Подключение через DNS:**

text

example.com.       A       93.184.216.34           # origin напрямую
cdn.example.com.   CNAME   d1234.cloudfront.net.   # через CDN

**Anycast vs GeoDNS:**

- **GeoDNS** — DNS возвращает IP в зависимости от географии клиента
    
- **Anycast** — один IP анонсируется из многих точек, пакеты идут к ближайшему узлу
    

### Кэширование в CDN

**Что хорошо кэшируется:** изображения, CSS, JS, шрифты, видео

**Что обычно не кэшируется:** HTML (персонализирован), API-ответы, POST/PUT/DELETE

CDN смотрит на заголовки `Cache-Control` от origin:

- `public, max-age=86400` → кэшировать 24 часа
    
- `private, no-store` → не кэшировать
    
- `max-age=0, must-revalidate` → всегда проверять у origin
    

### Инвалидация кэша

| Способ              | Описание                                           |
| ------------------- | -------------------------------------------------- |
| **Подождать TTL**   | Просто, но долго                                   |
| **Purge (очистка)** | Принудительно удалить из кэша (секунды-минуты)     |
| **Версионирование** | Менять имя файла при изменении — **рекомендуется** |
| **Cache Tags**      | Инвалидация по тегам (продвинуто)                  |

### Популярные CDN

| CDN                | Особенности                          |
| ------------------ | ------------------------------------ |
| **Cloudflare**     | Бесплатный тариф, DNS + CDN + защита |
| **AWS CloudFront** | Интеграция с AWS, Lambda@Edge        |
| **Fastly**         | Мгновенный purge, VCL для настройки  |
| **Akamai**         | Крупнейший, enterprise               |

### Заголовки для отладки (Cloudflare)

- `cf-cache-status: HIT` — из кэша edge
    
- `cf-cache-status: MISS` — запрошено у origin
    
- `cf-cache-status: EXPIRED` — было в кэше, но протухло
    
- `cf-cache-status: DYNAMIC` — не кэшируется (динамический контент)
