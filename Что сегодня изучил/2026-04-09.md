### Саммари: Cherry-pick — выборочное применение коммитов

**Что такое cherry-pick:**  
Операция, которая берёт изменения из **конкретного коммита** в одной ветке и применяет их к текущей ветке. **Важно:** создаётся **новый коммит** (с новым SHA-1), а не перемещается существующий.

bash

git checkout main
git cherry-pick abc123     # применить коммит abc123 из другой ветки в main

**Как работает:**

1. Git вычисляет diff коммита относительно его родителя
    
2. Применяет эти изменения к текущей ветке
    
3. Создаёт новый коммит с тем же сообщением (но новым хешем)
    

**Основные опции:**

|Команда|Действие|
|---|---|
|`git cherry-pick -n abc123`|Применить изменения без автоматического коммита (добавить в рабочую директорию)|
|`git cherry-pick -x abc123`|Добавить в сообщение коммита строку `(cherry picked from commit abc123...)` для отслеживания происхождения|
|`git cherry-pick abc123 def456`|Применить несколько коммитов в указанном порядке|
|`git cherry-pick A..B`|Применить диапазон коммитов (от A до B, не включая A)|
|`git cherry-pick A^..B`|Применить диапазон коммитов (включая A)|

**Разрешение конфликтов:**

bash

# После разрешения конфликта в файлах
git add <файлы>
git cherry-pick --continue    # продолжить
git cherry-pick --abort       # отменить операцию
git cherry-pick --skip        # пропустить проблемный коммит (при диапазоне)

**Автоматическое разрешение:**

bash

git cherry-pick -X theirs abc123   # при конфликте брать версию из переносимого коммита
git cherry-pick -X ours abc123     # брать текущую версию

**Типичные сценарии:**

1. **Hotfix для нескольких версий** — исправление критического бага применяется к разным release-веткам
    
2. **Перенос изменений между feature-ветками** — нужная утилита из ветки коллеги в свою ветку
    
3. **Восстановление потерянных изменений** — коммит, удалённый при rebase, находится в reflog и восстанавливается через cherry-pick
    

**Важные предостережения:**

- **Дублирование коммитов** — Git не понимает, что оригинальный и cherry-picked коммиты содержат одинаковые изменения. При последующем merge возможны конфликты или повторное применение изменений.
    
- **Используйте `-x`** для документирования происхождения коммита — это помогает избежать путаницы.
    

**Cherry-pick merge-коммитов:**

bash

# merge-коммит имеет 2+ родителей, нужно указать, какой использовать
git cherry-pick -m 1 merge-commit   # 1 = первый родитель (обычно main)
git cherry-pick -m 2 merge-commit   # 2 = второй родитель (обычно feature-ветка)

**Альтернативы cherry-pick:**

- `merge` — когда нужны **все** изменения из ветки
    
- `rebase` — для переноса целой серии коммитов с сохранением истории
    
- Общая ветка — для изменений, нужных нескольким feature-веткам
    

**Итог:** Cherry-pick — хирургический инструмент для точечного переноса изменений. Создаёт новые коммиты, а не перемещает старые. Идеален для hotfix'ов в нескольких версиях и выборочного переноса кода, но требует осторожности из-за риска дублирования при последующих слияниях.
