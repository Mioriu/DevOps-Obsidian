## Статья 1: Установка и базовый рабочий процесс (`init`, `plan`, `apply`, `destroy`)

### Установка

- Terraform — один бинарник. Устанавливается через пакетный менеджер или скачивается с сайта.
    
- `terraform -version` — проверка.
    

**Для работы из России:** реестр провайдеров `registry.terraform.io` может не отдавать плагины на российские IP. Лечится зеркалом через `~/.terraformrc`:

hcl

provider_installation {
  network_mirror {
    url = "https://terraform-mirror.yandexcloud.net/"
    include = ["registry.terraform.io/*/*"]
  }
  direct {
    exclude = ["registry.terraform.io/*/*"]
  }
}

### Базовый рабочий цикл

|Команда|Назначение|
|---|---|
|`terraform init`|Скачивает провайдеры, создаёт `.terraform/` и `.terraform.lock.hcl`|
|`terraform plan`|Показывает, что изменится (dry-run), ничего не меняет|
|`terraform apply`|Применяет изменения (сначала показывает план, требует подтверждения)|
|`terraform destroy`|Удаляет всё, что создано из текущего конфига|

### План — символы изменений

|Символ|Значение|
|---|---|
|`+`|Создать|
|`-`|Удалить|
|`~`|Изменить на месте|
|`-/+`|Пересоздать (удалить и создать заново)|

**Важно:** `-/+` — опасный символ. Для виртуальной машины с данными это удаление всего содержимого.

### Файлы в директории

|Файл|Что это|В Git|
|---|---|---|
|`*.tf`|Код инфраструктуры|✅ Да|
|`.terraform.lock.hcl`|Зафиксированные версии провайдеров|✅ Да|
|`.terraform/`|Скачанные бинарники провайдеров|❌ Нет|
|`terraform.tfstate`|State — учёт созданного|❌ Нет|

## Статья 2: Переменные, outputs, data sources

### Variables — переменные

hcl

# variables.tf
variable "nginx_version" {
  description = "Тег образа nginx"
  type        = string
  default     = "1.25"
}
variable "external_port" {
  description = "Порт на хосте"
  type        = number
  default     = 8080
}

**Использование:**

- `var.nginx_version` — подстановка значения
    
- Внутри строки: `"nginx:${var.nginx_version}"`
    
- Когда переменная — всё значение целиком: `name = var.container_name`
    

### Источники значений (приоритет)

1. `-var` флаг — **самый высокий**
    
2. `terraform.tfvars` (автоматически) или `-var-file=prod.tfvars`
    
3. Переменные окружения `TF_VAR_*`
    
4. `default` в блоке `variable` — **самый низкий**
    

**Секреты:** `sensitive = true` → в выводе плана печатается `(sensitive value)`.

### Outputs — вывод значений

hcl

# outputs.tf
output "container_name" {
  value = docker_container.web.name
}

**Использование:**

bash

terraform output                      # все outputs
terraform output external_port        # одно значение
terraform output -raw external_port   # без кавычек (для скриптов)

### Data sources — чтение существующих объектов

hcl

data "docker_network" "existing" {
  name = "app_net"
}
resource "docker_container" "web" {
  networks_advanced {
    name = data.docker_network.existing.name
  }
}

**Отличие от resource:** data source **читает** существующий объект, но не управляет им. При `destroy` такой объект не будет удалён.

## Статья 3: State, remote backend и блокировка

### Что такое state

`terraform.tfstate` — JSON с учётом созданного: для каждого ресурса записан адрес в коде, ID реального объекта и все атрибуты.

**State в Git не кладут:**

- В нём открытым текстом лежат пароли и токены
    
- При работе вдвоём через Git — гарантированы конфликты
    

**Просмотр state:**

bash

terraform state list                    # все ресурсы
terraform state show docker_container.web   # атрибуты ресурса

### Remote backend — общий state

Локальный state не работает в команде: у каждого своя версия, конфликты.

**Решение:** хранить state в общем удалённом хранилище (S3-совместимом).

**Пример для Yandex Cloud:**

hcl

terraform {
  backend "s3" {
    endpoints = {
      s3 = "https://storage.yandexcloud.net"
    }
    bucket = "myproject-tfstate"
    key    = "infra/terraform.tfstate"
    region = "ru-central1"
    skip_region_validation      = true
    skip_credentials_validation = true
    skip_requests_signing       = true
  }
}

**Ключи доступа** к бакету передаются через переменные окружения `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`.

### Блокировка (Lock)

**Проблема:** два человека одновременно запускают `apply` — один затирает state другого.

**Решение:** блокировка на время операций, меняющих state.

**Для Yandex Cloud** (блокировка через YDB):

hcl

    endpoints = {
      s3       = "https://storage.yandexcloud.net"
      dynamodb = "https://docapi.serverless.yandexcloud.net/..."
    }
    dynamodb_table = "tf-lock"

**Повисшая блокировка** (процесс упал, lock не снят):

bash

terraform force-unlock <ID>

## Статья 4: Модули и переиспользование

### Зачем нужны модули

Упакованный набор ресурсов с переменными на входе и outputs на выходе. Позволяет не копипастить один и тот же код для разных окружений.

### Структура модуля

text

modules/web_container/
├── main.tf          # ресурсы модуля
├── variables.tf     # входные параметры
└── outputs.tf       # выходные значения

### Вызов модуля

hcl

module "site_prod" {
  source        = "./modules/web_container"
  name          = "site-prod"
  external_port = 8080
}
module "site_staging" {
  source        = "./modules/web_container"
  name          = "site-staging"
  nginx_version = "1.27"
  external_port = 8081
}

### Связь между модулями через outputs

hcl

module "network" {
  source = "./modules/network"
  name   = "app-net"
}
module "site_prod" {
  source        = "./modules/web_container"
  name          = "site-prod"
  external_port = 8080
  network_name  = module.network.name   # ссылка на output другого модуля
}

### locals — внутренние константы

hcl

locals {
  project = "myshop"
  sites = {
    prod    = 8080
    staging = 8081
  }
}

Использование: `local.project`, `local.sites`.

### for_each — один блок → несколько вызовов

hcl

locals {
  sites = {
    prod    = 8080
    staging = 8081
  }
}
module "site" {
  for_each = local.sites
  source   = "./modules/web_container"
  name      = each.key
  external_port = each.value
}

Добавить окружение → одна строка в `local.sites`.

### Перенос существующих ресурсов в модуль — `moved`

При рефакторинге ресурс меняет адрес в коде. Без `moved` Terraform предлагает удалить старый и создать новый.

**Решение — блок `moved`:**

hcl

moved {
  from = docker_container.web
  to   = module.site_prod.docker_container.this
}

`plan` покажет перенос, а не пересоздание.

### Источники модулей

- **Локальный путь:** `source = "./modules/web_container"`
    
- **Реестр Terraform:** `source = "terraform-aws-modules/vpc/aws" version = "5.8.1"`
    
- **Git-репозиторий:** `source = "git::https://github.com/myorg/modules.git//network?ref=v1.2.0"`
    

**Версию внешнего модуля всегда фиксируют!**
