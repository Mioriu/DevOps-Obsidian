# Reflog и восстановление потерянных данных

## Основная идея

Git редко теряет данные безвозвратно — большинство операций (`reset --hard`, `rebase`, удаление веток) можно откатить с помощью **reflog** (Reference log). Это локальный дневник всех перемещений `HEAD` и веток, который существует только в вашем репозитории и хранит записи ~90 дней (для достижимых коммитов).

## Ключевые моменты

- **Формат записи**: `хеш HEAD@{n}: действие` (нумерация обратная: `HEAD@{0}` — текущее состояние, `{1}` — предыдущее)
    
- **Восстановление после `reset --hard`**:
    
    bash
    
    git reflog                     # найти нужное состояние
    git reset --hard HEAD@{1}      # вернуться до reset
    
- **Восстановление удалённой ветки**: найти последний коммит ветки в reflog (`git reflog | grep "from branch-name"`) и воссоздать ветку: `git branch branch-name <commit-hash>`
    
- **Отмена `rebase`**: вернуться к состоянию до rebase через `git reset --hard HEAD@{n}`, где `n` — запись сразу перед `rebase finished`
    
- **Временные метки**: можно использовать `HEAD@{1.hour.ago}`, `main@{yesterday}`, `--date=iso`
    

## Ограничения

- **Локальность**: reflog не пушится и не клонируется (у каждого разработчика свой)
    
- **Временное хранение**: настраивается через `gc.reflogExpire` (по умолчанию 90/30 дней)
    
- **Не восстанавливает**: незакоммиченные изменения и файлы вне Git
    

## Продвинутые техники

- `git fsck --lost-found` — найти недостижимые коммиты, которых уже нет в reflog
    
- `git reflog show --all` — посмотреть reflog для всех ссылок (включая stash, удалённые ветки)
    

## Итог

Reflog — страховочная сетка Git, которая делает опасные операции обратимыми. Главное правило: **действовать быстро** (до сборки мусора) и помнить, что данные не удаляются мгновенно.
