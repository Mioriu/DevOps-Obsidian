### Почему резервное копирование так важно

Давайте сначала поймём масштаб проблемы. По статистике, каждый второй жёсткий диск выходит из строя в течение пяти лет эксплуатации. Это не считая других причин потери данных: человеческих ошибок (случайное удаление, неправильная команда), программных сбоев, вирусов-шифровальщиков.

│  └─ Износ SSD                              │

### Правило 3-2-1: золотой стандарт резервного копирования

В индустрии существует проверенное временем правило 3-2-1, которое определяет минимальные требования к надёжному резервному копированию.

Само правило: храните минимум 3 копии важных данных, на 2 разных типах носителей, и минимум 1 копия должна находиться в другом физическом месте.

Три копии нужны потому, что вероятность одновременного отказа трёх независимых копий крайне мала. Два разных типа носителей защищают от систематических проблем. А копия в другом месте защищает от локальных катастроф — пожара, наводнения или кражи.

```undefined
Правило 3-2-1 на практике:
┌─────────────────────────────────────────────────┐
│            Оригинальные данные                  │
│           (рабочий сервер, SSD)                 │
└────────────────┬────────────────────────────────┘
                 │
     ┌───────────┼───────────┬──────────────┐
     ↓           ↓           ↓              ↓
┌─────────┐ ┌─────────┐ ┌─────────┐  ┌──────────┐
│ Копия 1 │ │ Копия 2 │ │ Копия 3 │  │ Копия 4  │
│ Локальн.│ │ Внешний │ │ Облако  │  │ Холодное │
│ RAID    │ │ HDD     │ │ (S3)    │  │ хранение │
└─────────┘ └─────────┘ └─────────┘  └──────────┘
  Тот же      Другой      Другое       Архив в
  сервер      носитель    место        сейфе
```

### Типы резервного копирования

Существует несколько стратегий резервного копирования, каждая со своими преимуществами и недостатками. Выбор зависит от объёма данных, доступного места для хранения и требований к скорости восстановления.

Полное резервное копирование — это копирование всех данных каждый раз. Это самый простой и надёжный метод. Восстановление быстрое — нужна только одна резервная копия. Но он требует много места и времени. Если у вас 1TB данных, каждая полная копия занимает 1TB, и создание копии может занять часы.

Инкрементное копирование сохраняет только изменения с момента последнего резервного копирования любого типа. После полной копии в воскресенье, понедельничная инкрементная копия содержит только файлы, изменённые в понедельник. Это экономит место и время, но усложняет восстановление — нужны все инкрементные копии по цепочке.

Дифференциальное копирование сохраняет изменения с момента последнего полного копирования. Каждая дифференциальная копия растёт со временем, но для восстановления нужны только полная и последняя дифференциальная копии.

```makefile
Сравнение типов копирования за неделю:
День:     Вс    Пн    Вт    Ср    Чт    Пт    Сб

Полное:   1TB   1TB   1TB   1TB   1TB   1TB   1TB
          ↓
Итого: 7TB, восстановление из 1 копии

Инкрементное:
          1TB   10GB  15GB  20GB  12GB  25GB  30GB
          ↓
Итого: ~1.1TB, восстановление из 7 копий

Дифференциальное:
          1TB   10GB  25GB  45GB  57GB  82GB  112GB
          ↓
Итого: ~1.3TB, восстановление из 2 копий
```

### Что именно нужно копировать

Не все данные одинаково важны. Операционную систему можно переустановить, программы — скачать заново, но **пользовательские данные, конфигурации и базы данных — уникальны и незаменимы**. Понимание приоритетов поможет оптимизировать процесс резервного копирования.

Критически важные данные требуют максимальной защиты и частого копирования. Это **базы данных, исходный код, документы, конфигурационные файлы критичных сервисов, SSL-сертификаты и ключи**. 

Важные данные — это **пользовательские файлы, логи за последний период, кэши, которые долго восстанавливаются, конфигурации второстепенных сервисов**.

```less
Типичная структура Linux-сервера и приоритеты:
/
├── etc/        [КРИТИЧНО] Конфигурации системы
├── home/       [КРИТИЧНО] Домашние директории
├── var/
│   ├── www/    [КРИТИЧНО] Веб-сайты
│   ├── lib/
│   │   └── mysql/ [КРИТИЧНО] Базы данных
│   ├── log/    [ВАЖНО] Логи (последние)
│   └── cache/  [НЕ КОПИРОВАТЬ] Кэши
├── usr/        [МОЖНО ВОССТАНОВИТЬ] Программы
├── tmp/        [НЕ КОПИРОВАТЬ] Временные файлы
└── proc/       [НЕ КОПИРОВАТЬ] Виртуальная ФС
```

### Инструменты резервного копирования

В Linux существует множество инструментов для резервного копирования, от простых утилит командной строки до сложных корпоративных систем. Начнём с базовых инструментов, которые есть в любой системе.

Команда `tar` (tape archive) — классический инструмент для создания архивов. `Tar` умеет сохранять права доступа, владельцев файлов и временные метки, что критически важно для системных файлов.

```shell
# Создание полной резервной копии домашней директории
$ tar -czpf backup-home-$(date +%Y%m%d).tar.gz /home/

# Расшифровка флагов:
# c - создать архив
# z - сжать gzip
# p - сохранить права доступа
# f - указать имя файла
```

Инструмент `rsync`. Его главное преимущество — умение копировать только изменившиеся части файлов, что экономит время и трафик. `Rsync` может работать локально, по `SSH`, и поддерживает множество опций для тонкой настройки.

```coffeescript
# Зеркалирование директории на удалённый сервер
$ rsync -avz --delete /var/www/ user@backup-server:/backups/www/

# Флаги:
# a - архивный режим (сохраняет атрибуты)
# v - подробный вывод
# z - сжатие при передаче
# --delete - удалять файлы, которых нет в источнике
```

### Стратегия ротации

Хранить все резервные копии вечно невозможно — место закончится. Но и хранить только последнюю копию опасно — что если проблема обнаружится через месяц? Стратегия Grandfather-Father-Son, `GFS` решает эту дилемму элегантно.

Идея в том, чтобы хранить больше недавних копий и меньше старых. Ежедневные копии хранятся неделю, еженедельные — месяц, ежемесячные — год или дольше.

```less
Схема ротации GFS на 3 месяца:
Месяц 1:
Нд: [Д][Д][Д][Д][Д][Д][Н]  - 6 дневных + 1 недельная
Нд: [Д][Д][Д][Д][Д][Д][Н]
Нд: [Д][Д][Д][Д][Д][Д][Н]
Нд: [Д][Д][Д][Д][Д][Д][М]  - последняя становится месячной

Хранится:
- 7 дневных копий (последняя неделя)
- 4 недельных копии (последний месяц)
- 12 месячных копий (последний год)
Итого: 23 копии вместо 365 ежедневных
```
