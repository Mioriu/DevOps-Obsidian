### Типы сбоев и их последствия

Разные типы проблем требуют разных подходов к восстановлению.

Логические сбои происходят на уровне файловой системы или данных, при этом физический носитель остаётся исправным. Случайно удалили файл? Отформатировали не тот раздел? Повредилась таблица разделов? Всё это логические проблемы, и у них самый высокий шанс успешного восстановления. Данные **физически остаются на диске**, просто система не знает, где они находятся или как к ним обратиться.

Физические сбои связаны с повреждением самого носителя. Жёсткий диск начал умирать, появились bad-сектора, SSD внезапно перестал определяться системой. Это более серьёзные проблемы, требующие особого подхода, а иногда и специализированного оборудования.

Программные сбои включают повреждение данных вирусами, сбои в работе приложений, некорректное завершение работы системы. Например, база данных может повредиться при внезапном отключении машины во время транзакции.

### Первые действия

Самое важное правило при потере данных — немедленно прекратить любую запись на проблемный диск. Каждая операция записи может перезаписать те самые данные, которые вы пытаетесь восстановить.

Вот чек-лист немедленных действий при обнаружении потери данных:

1. Первое — остановите все операции с диском.
2. Второе — если это системный диск, выключите машину.
3. Третье — не пытаться починить проблему стандартными средствами. Команды вроде `fsck` или `chkdsk` могут усугубить ситуацию, если использовать их неправильно.

### Оценка ситуации и планирование восстановления

Надо ответить на ключевые вопросы.

- Что именно было потеряно — отдельные файлы, целый раздел, или вся система?
- Когда примерно произошла потеря — это поможет определить, сколько данных могло быть перезаписано.
- Есть ли резервные копии, даже частичные или устаревшие?
- Какие действия были предприняты после обнаружения проблемы — это важно для оценки шансов на восстановление.

```bash
# Сбор информации о диске (с LiveUSB)
$ sudo fdisk -l /dev/sda

# Проверка SMART-статуса
$ sudo smartctl -H /dev/sda

# Попытка прочитать таблицу разделов
$ sudo parted /dev/sda print
Error: Invalid partition table on /dev/sda -- wrong signature
```

### Создание образа диска — критически важный шаг

Прежде чем пытаться восстановить данные, создайте полный образ проблемного диска. Это страховка — если первая попытка восстановления пойдёт не так, будет возможность начать заново. Работа с образом вместо оригинального диска также защищает от дальнейшего физического износа носителя.

Для создания образа используется специальный инструмент `ddrescue` (не путать с обычным `dd`). В отличие от `dd`, который останавливается при первой ошибке чтения, `ddrescue` продолжает работу, пропуская повреждённые сектора и возвращаясь к ним позже. Это особенно важно при работе с повреждёнными дисками.

```yaml
# Установка ddrescue
$ sudo apt install gddrescue

# Создание образа с умным копированием
$ sudo ddrescue -d -r3 /dev/sda disk_image.img rescue.log

# Параметры:
# -d : прямой доступ к диску (обход кэша)
# -r3 : три попытки чтения bad секторов
# rescue.log : лог для возобновления процесса

# Процесс может выглядеть так:
GNU ddrescue 1.25
Press Ctrl-C to interrupt
     ipos:   500 GB, non-trimmed:        0 B,  current rate:   30 MB/s
     opos:   500 GB, non-scraped:        0 B,  average rate:   45 MB/s
non-tried:   431 GB,  bad-sector:     1024 B,    error rate:     512 B/s
  rescued:   500 GB,   bad areas:        2,        run time:  3h 15m 20s
pct rescued:  53.68%, read errors:        8,  remaining time:  2h 35m
                              time since last successful read:          0s
Copying non-tried blocks... Pass 1 (forwards)
```

Обратите внимание на статистику, которую показывает `ddrescue`. Поле `rescued` показывает, сколько данных успешно скопировано. `Bad-sector` указывает на проблемные области. Если количество `bad` секторов растёт быстро, это признак умирающего диска — нужно действовать быстрее.

### Восстановление удалённых файлов

Когда файл удаляется в Linux, система не стирает его содержимое немедленно. Вместо этого она помечает занимаемое файлом пространство как свободное и удаляет запись из таблицы файловой системы. Сами данные остаются на диске до тех пор, пока не будут перезаписаны новыми файлами. Это даёт нам шанс на восстановление.

Один из самых эффективных инструментов для восстановления — `TestDisk` и его компаньон `PhotoRec`. Несмотря на название, `PhotoRec` восстанавливает не только фотографии, но и сотни других типов файлов.

```shell
# Установка инструментов восстановления
$ sudo apt install testdisk

# Запуск PhotoRec для восстановления файлов
$ sudo photorec disk_image.img

# Интерфейс PhotoRec:
PhotoRec 7.1, Data Recovery Utility
 
Disk disk_image.img - 1000 GB / 931 GiB

     Partition                  Start        End    Size in sectors
   P ext4                          0   1953525167   1953525168

[Search] [ Options ] [ File Opt ] [ Quit ]
                              Start file recovery
```

`PhotoRec` работает на уровне данных, игнорируя файловую систему. Он ищет характерные сигнатуры файлов — например, JPEG файлы всегда начинаются с определённой последовательности байтов. Это позволяет восстанавливать файлы даже с сильно повреждённых файловых систем.

### Восстановление повреждённой файловой системы

Иногда проблема не в удалённых файлах, а в повреждённой структуре файловой системы. Суперблок повреждён, журнал не согласован, потеряны `inodes` — всё это делает раздел немонтируемым, хотя данные физически целы.

Файловая система `ext4` хранит несколько резервных копий суперблока. Если основной суперблок повреждён, можно использовать резервную копию для восстановления. Сначала нужно найти, где находятся эти резервные копии.

```bash
# Поиск резервных суперблоков

$ sudo mke2fs -n /dev/sda1
mke2fs 1.45.5 (07-Jan-2020)
Creating filesystem with 26214400 4k blocks
Superblock backups stored on blocks:
    32768, 98304, 163840, 229376, 294912, 819200, 884736

# НЕ забудьте флаг -n! Он означает "ничего не делать, только показать"

# Попытка восстановления с резервного суперблока
$ sudo e2fsck -b 32768 /dev/sda1

# Если это не помогает, пробуем следующий
$ sudo e2fsck -b 98304 /dev/sda1
```

### Восстановление баз данных

Базы данных имеют свои механизмы восстановления после сбоев. Большинство современных СУБД используют журналирование транзакций, что позволяет восстановить согласованное состояние даже после внезапного отключения питания.

Для MySQL/MariaDB процесс восстановления часто запускается автоматически при старте сервиса. Но иногда требуется ручное вмешательство, особенно если повреждены системные таблицы.

```bash
# Попытка восстановления таблиц MySQL
$ sudo mysqlcheck --all-databases --auto-repair

# Если сервер не запускается
$ sudo mysqld --innodb_force_recovery=1

# Уровни innodb_force_recovery:
# 1 - игнорировать повреждённые страницы
# 2 - не запускать фоновые операции
# 3 - не пытаться откатить транзакции
# 4 - не вычислять статистику
# 5 - не смотреть undo logs
# 6 - не использовать redo logs

# После запуска делаем дамп всех данных
$ mysqldump --all-databases > recovery_dump.sql
```

### Превентивные меры — подготовка к будущим сбоям

Лучшее восстановление — это **то, которое не потребовалось.** После успешного (или неуспешного) восстановления самое время подумать о предотвращении подобных ситуаций в будущем.

Создайте систему резервного копирования, которая работает автоматически. Настройте мониторинг состояния дисков через SMART. Документируйте конфигурацию системы — при восстановлении эта информация бесценна. Регулярно проверяйте, что резервные копии действительно восстанавливаются..
