### Что такое аудит безопасности и зачем он нужен

Аудит безопасности — это регулярный процесс проверки системы на соответствие лучшим практикам безопасности. Даже если ничего не предвещает беды, регулярная проверка помогает выявить проблемы на ранней стадии.

Существует распространённое заблуждение, что если сервер работает и никто не жалуется, значит всё в порядке. На самом деле многие взломы остаются незамеченными месяцами.

```undefined
Этапы типичной атаки на сервер:
┌────────────────────────────────────────────────┐
│  1. Разведка (сканирование портов, сервисов)   │
│                      ↓                         │
│  2. Поиск уязвимостей (старые версии, ошибки)  │
│                      ↓                         │
│  3. Эксплуатация (получение первого доступа)   │
│                      ↓                         │
│  4. Закрепление (установка бэкдоров)           │
│                      ↓                         │
│  5. Скрытая деятельность (майнинг, ботнет)     │
└────────────────────────────────────────────────┘

Аудит помогает обнаружить проблемы на каждом этапе
```

### С чего начать: составление карты системы

Прежде чем искать проблемы, нужно понять, что именно мы защищаем.

Начнём с определения того, какие сервисы работают на сервере и какие порты открыты для внешнего мира.

```ruby
# Проверяем, какие порты слушает наша система
$ sudo ss -tulnp

Netid  State   Recv-Q  Send-Q   Local Address:Port    Peer Address:Port  Process
tcp    LISTEN  0       128      0.0.0.0:22            0.0.0.0:*          sshd
tcp    LISTEN  0       128      0.0.0.0:80            0.0.0.0:*          nginx
tcp    LISTEN  0       128      127.0.0.1:3306        0.0.0.0:*          mysqld
tcp    LISTEN  0       128      0.0.0.0:443           0.0.0.0:*          nginx
```

Разберём, что мы видим. Колонка Local Address показывает, на каком интерфейсе слушает сервис. Адрес 0.0.0.0 означает "**все интерфейсы**" — сервис доступен извне. Адрес 127.0.0.1 означает "**только локально**" — это хорошо для базы данных, которая не должна быть доступна из интернета.

Теперь проверим, как наш сервер выглядит снаружи, используя сканер портов nmap. Это покажет, что видит потенциальный атакующий:

```bash
# Сканируем свой сервер снаружи (с другой машины)
$ nmap -sV your-server-ip

PORT     STATE SERVICE VERSION
22/tcp   open  ssh     OpenSSH 8.2p1 Ubuntu
80/tcp   open  http    nginx 1.18.0
443/tcp  open  https   nginx 1.18.0
```

### Проверка пользователей и доступов

Следующий важный шаг — понять, кто имеет доступ к системе. Неактивные учётные записи, старые аккаунты бывших сотрудников, тестовые пользователи с простыми паролями — всё это **потенциальные точки входа для злоумышленников.**

```objectivec
Схема проверки пользователей:
┌─────────────────────────────────────────────┐
│         Все пользователи системы            │
│                    ↓                        │
│  ┌──────────────┬─────────────┬──────────┐  │
│  │  Системные   │   Обычные   │ Заброшен-│  │
│  │  (< UID 1000)│  (активные) │   ные    │  │
│  └──────────────┴─────────────┴──────────┘  │
│         ↓              ↓             ↓      │
│    Оставить      Проверить     Удалить      │
│                   пароли        или         │
│                  и ключи      заблокировать │
└─────────────────────────────────────────────┘
```

Начнём с получения списка всех пользователей, которые могут входить в систему:

```bash
# Пользователи с возможностью входа

$ getent passwd | awk -F: '$7 !~ /false|nologin/ {print $1":"$3":"$7}'

root:0:/bin/bash
ubuntu:1000:/bin/bash
developer:1001:/bin/bash
oldadmin:1002:/bin/bash
```

Видите пользователя `oldadmin`? Это может быть забытая учётная запись. Проверим, когда пользователи последний раз входили в систему:

```yaml
# Последние входы пользователей
$ lastlog | grep -v "Never"

Username         Port     From             Latest
root             pts/0    10.0.0.5         Fri Nov 20 14:30:22 +0000 2024
ubuntu           pts/1    10.0.0.5         Fri Nov 20 10:15:33 +0000 2024
oldadmin         pts/0    192.168.1.100    Mon Jan 15 09:22:11 +0000 2024
```

Пользователь `oldadmin` не входил с января. Возможно, это учётная запись уволенного сотрудника, которую забыли удалить.

### Анализ sudo-привилегий

Избыточные права `sudo` — большая проблема. Нужно проверить, кто что может делать с повышенными привилегиями. Особенно опасны права на выполнение любых команд или команд, которые могут запускать `shell`.

```bash
# Проверяем sudo-права всех пользователей
$ for user in $(getent passwd | cut -d: -f1); do
    sudo -l -U $user 2>/dev/null | grep -v "not allowed"
  done
```

Обратите внимание на опасные паттерны. Если видите что-то вроде `ALL=(ALL) NOPASSWD: ALL` для обычного пользователя — это серьёзная проблема. Такой пользователь может делать всё что угодно без пароля.

Также опасны права на редакторы (vi, nano), которые могут запускать команды, или на интерпретаторы (python, perl, ruby).

### Анализ сетевых подключений

Необычные сетевые подключения могут указывать на компрометацию системы. Если ваш веб-сервер вдруг подключается к серверу в Китае на порт 6667 (IRC), это явно не нормально.

```shell
# Активные сетевые соединения
$ sudo netstat -tulpna | grep ESTABLISHED

# Более подробный анализ с ss
$ sudo ss -tupna state established
```

**На что обращать внимание:** подключения к необычным портам (особенно высоким, выше 10000), соединения с IP-адресами из необычных стран, большое количество подключений от одного IP (возможная DoS-атака), исходящие подключения от процессов, которые не должны их инициировать.

### Проверка запущенных процессов

Вредоносное ПО часто маскируется под легитимные процессы или использует похожие имена. Процесс с именем "systmd" (вместо systemd) должен вызвать подозрения.

```shell
# Процессы, потребляющие много CPU (майнеры?)
$ top -b -n 1 | head -20

# Все процессы в виде дерева
$ pstree -p

# Процессы, запущенные не от системных пользователей
$ ps aux | awk '$1 !~ /^(root|www-data|mysql|systemd)/ {print}'
```

Признаки подозрительных процессов включают в себя странные имена в квадратных скобках, высокое потребление CPU без видимых причин, процессы с путями из /tmp или /dev/shm, процессы, маскирующиеся под системные с небольшими опечатками.

### Анализ логов системы

Умение читать логи — критически важный навык для аудита безопасности.

```iecst
Ключевые логи для проверки:
┌─────────────────────────────────────────────────┐
│ /var/log/auth.log     - Попытки аутентификации  │
│ /var/log/syslog       - Системные события       │
│ /var/log/apache2/     - Логи веб-сервера        │
│ /var/log/mysql/       - Логи базы данных        │
│ /var/log/kern.log     - События ядра            │
│ /var/log/ufw.log      - Логи файрвола           │
└─────────────────────────────────────────────────┘
```

Начнём с проверки неудачных попыток входа:

```shell
# Неудачные попытки SSH-входа
$ sudo grep "Failed password" /var/log/auth.log | tail -20

# Подсчёт попыток по IP-адресам
$ sudo grep "Failed password" /var/log/auth.log | \
  awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head

# Успешные входы под root
$ sudo grep "Accepted.*root" /var/log/auth.log
```

Если видите тысячи попыток входа с одного IP — это брутфорс-атака. Десятки разных IP с небольшим количеством попыток — распределённая атака. Успешный вход `root` с необычного IP — потенциальная компрометация.

### Проверка конфигурации SSH

SSH — главная дверь в систему, поэтому его безопасность критически важна.

```perl
# Анализ конфигурации SSH
$ sudo sshd -T | grep -E "permitrootlogin|passwordauthentication|port|allowusers"

permitrootlogin no          # Хорошо
passwordauthentication no   # Отлично
port 22                    # Стандартный порт - рассмотрите смену
allowusers alice bob       # Ограничение пользователей - хорошо
```

### Регулярность проведения аудита

Аудит безопасности — не разовая акция. Угрозы постоянно эволюционируют, появляются новые уязвимости, меняется конфигурация системы. Рекомендуемая периодичность: полный аудит — раз в квартал, проверка критичных параметров — еженедельно, мониторинг логов — ежедневно, проверка обновлений — постоянно.
