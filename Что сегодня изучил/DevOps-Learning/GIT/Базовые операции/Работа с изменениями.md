После создания репозитория начинается основная работа — внесение изменений в проект. Git предоставляет набор команд для управления изменениями: отслеживания, подготовки и фиксации. Понимание этих команд формирует основу повседневной работы с системой контроля версий.

### Проверка состояния — git status

Команда `git status` показывает текущее состояние рабочей директории и области подготовки. Это самая часто используемая команда, которая отвечает на вопросы: какие файлы изменены, что готово к коммиту, в какой ветке происходит работа.

```perl
$ git status
On branch main
Changes not staged for commit:
  (use "git add ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
    modified:   README.md

Untracked files:
  (use "git add ..." to include in what will be committed)
    config.json

no changes added to commit (use "git add" and/or "git commit -a")
```

Вывод команды разделён на секции:

- **Текущая ветка** — показывает активную ветку
- **Изменения не в индексе** — файлы изменены, но не подготовлены к коммиту
- **Неотслеживаемые файлы** — новые файлы, о которых Git ещё не знает
- **Изменения в индексе** — файлы, готовые к коммиту (если есть)

Краткая форма вывода доступна с флагом `-s`:

```lua
$ git status -s
 M README.md
?? config.json
```

Символы в первой колонке показывают состояние в индексе, во второй — в рабочей директории. Символ `M` означает модификацию, `??` — неотслеживаемый файл.

### Просмотр изменений — git diff

Команда `git diff` показывает конкретные изменения в файлах. В отличие от `git status`, которая показывает какие файлы изменены, `git diff` показывает что именно изменилось.

```diff
$ git diff
diff --git a/README.md b/README.md
index a5c1966..6d0f3b1 100644
--- a/README.md
+++ b/README.md
@@ -1,3 +1,4 @@
 # Project Title
 
 Description of the project
+Additional information about features
```

Вывод показывает:

- Какие файлы сравниваются
- Индексы файлов в Git
- Изменения: строки с `-` были удалены, с `+` добавлены

Основные варианты использования:

```ruby
# Изменения в рабочей директории (ещё не в индексе)
$ git diff

# Изменения в индексе (подготовленные к коммиту)
$ git diff --staged

# Изменения в конкретном файле
$ git diff README.md

# Сравнение с конкретным коммитом
$ git diff HEAD~1
```

### Добавление в индекс — git add

Команда `git add` переносит изменения из рабочей директории в область подготовки (индекс). Это промежуточный шаг перед созданием коммита, позволяющий точно контролировать, что будет зафиксировано.

```csharp
# Добавить конкретный файл
$ git add README.md

# Добавить несколько файлов
$ git add file1.txt file2.txt

# Добавить все файлы в текущей директории
$ git add .

# Добавить все изменения в репозитории
$ git add -A

# Интерактивное добавление частей файла
$ git add -p
```

После добавления файл переходит в состояние "staged" и будет включён в следующий коммит. Важная особенность: в индекс добавляется текущее содержимое файла. Если после `git add` файл будет изменён снова, новые изменения не попадут в коммит автоматически.

Команда `git add` работает как с новыми файлами (делая их отслеживаемыми), так и с изменёнными файлами (подготавливая изменения к коммиту).

### Создание коммита — git commit

Команда `git commit` создаёт новый коммит из изменений, находящихся в индексе. Коммит фиксирует состояние проекта в истории.

```ruby
# Коммит с сообщением в командной строке
$ git commit -m "Add user authentication feature"
[main a5f3b8c] Add user authentication feature
 2 files changed, 45 insertions(+), 3 deletions(-)

# Коммит с открытием редактора для сообщения
$ git commit

# Коммит всех изменённых отслеживаемых файлов
$ git commit -am "Update configuration files"

# Изменение последнего коммита
$ git commit --amend
```

Структура хорошего сообщения коммита:

```1c
Краткое описание изменения (до 50 символов)

Более подробное описание, если необходимо. Объясняет,
что было изменено и почему. Может содержать несколько
параграфов.

- Можно использовать маркированные списки
- Для перечисления ключевых изменений

Fixes #123
```

Каждый коммит получает уникальный SHA-1 идентификатор и содержит:

- Снимок всех файлов проекта
- Ссылку на родительский коммит
- Информацию об авторе и времени
- Сообщение с описанием изменений

### Рабочий процесс с изменениями

Типичный сценарий работы с изменениями выглядит следующим образом:

```shell
# 1. Проверка текущего состояния
$ git status

# 2. Просмотр конкретных изменений
$ git diff

# 3. Добавление нужных файлов в индекс
$ git add src/auth.js src/auth.test.js

# 4. Проверка что будет включено в коммит
$ git diff --staged

# 5. Создание коммита
$ git commit -m "Implement user authentication"

# 6. Проверка что коммит создан
$ git log -1
```

### Частичное добавление изменений

Git позволяет добавлять в коммит только часть изменений из файла. Это полезно для создания логически связанных коммитов.

```csharp
# Интерактивный режим добавления
$ git add -p filename.js
```

В интерактивном режиме Git показывает каждое изменение и предлагает варианты:

- `y` — добавить изменение в индекс
- `n` — пропустить изменение
- `s` — разбить изменение на более мелкие части
- `e` — редактировать изменение вручную

### Практические советы

Эффективная работа с изменениями основана на нескольких принципах:

**Частые небольшие коммиты** предпочтительнее редких больших. Каждый коммит должен представлять логически завершённое изменение.

**Проверка перед коммитом** с помощью `git diff --staged` помогает убедиться, что в коммит попадут только нужные изменения.

**Информативные сообщения** коммитов упрощают навигацию по истории. Сообщение должно отвечать на вопрос "что и почему изменено".

**Использование индекса** для группировки связанных изменений позволяет создавать чистую историю даже при одновременной работе над несколькими задачами.

## Итог

Четыре команды формируют основу работы с изменениями в Git. `git status` показывает общую картину состояния репозитория. `git diff` детализирует конкретные изменения в файлах. `git add` подготавливает изменения к фиксации. `git commit` создаёт постоянный снимок в истории. Понимание взаимодействия этих команд и концепции индекса позволяет эффективно управлять изменениями и создавать понятную историю проекта.
