Code review — это процесс, когда один разработчик проверяет код другого перед добавлением в основную ветку. Это не просто поиск ошибок. Это способ поделиться знаниями, улучшить код и убедиться, что вся команда понимает, как работает система.

### Зачем нужен code review

Главная цель — найти проблемы до того, как код попадёт в production. Баг, найденный на review, исправляется за минуты. Тот же баг в production может стоить часов работы и недовольства пользователей.

Code review помогает распространять знания в команде. Когда несколько человек видели и понимают код, проект становится устойчивее. Если автор кода заболеет или уйдёт в отпуск, другие смогут поддерживать его код.

Review также поддерживает единый стиль кода. Когда все следуют одним правилам, код легче читать и поддерживать. Новым членам команды проще влиться в проект.

### Как подготовить код к review

Хороший Pull Request начинается с правильного размера. Идеальный PR можно проверить за 30-60 минут. Исследования показывают: после 400 строк кода качество проверки резко падает. Лучше разбить большую задачу на несколько маленьких PR.

```bash
# Плохо: огромный PR
"Implement user management" - 2000 строк, 50 файлов

# Хорошо: серия PR
"Add user model" - 200 строк
"Add user API" - 300 строк
"Add user UI" - 400 строк
```

Перед отправкой на review проверьте код сами. Откройте PR в браузере и посмотрите на него глазами reviewer'а. Часто на этом этапе замечаются забытые console.log, опечатки или неудачные названия переменных.

Напишите хорошее описание PR. Объясните, что сделано и почему. Добавьте инструкцию, как проверить изменения. Для визуальных изменений приложите скриншоты. Укажите номер задачи, если она есть.

### Как проводить code review

При проверке кода обращайте внимание на несколько аспектов. Сначала проверьте корректность — делает ли код то, что должен. Работает ли он с граничными случаями. Обрабатывает ли ошибки.

Оцените читаемость кода. Понятны ли названия переменных и функций. Легко ли понять, что делает код. Достаточно ли комментариев в сложных местах.

Проверьте безопасность. Особенно внимательно смотрите на обработку пользовательского ввода, работу с паролями и правами доступа. Один пропущенный SQL injection может стоить очень дорого.

Убедитесь, что код можно тестировать. Огромные функции на 500 строк невозможно нормально протестировать. Код должен быть разбит на небольшие, понятные части.

### Как давать обратную связь

Хороший feedback фокусируется на коде, а не на человеке. Вместо "Ты написал плохой код" скажите "Этот метод можно упростить". Это профессионально и не обидно.

Всегда объясняйте причину замечания. Не просто "Это неэффективно", а "Этот код делает N запросов к базе данных. Можно сделать один запрос с JOIN, это будет быстрее".

```1c
// Плохой комментарий:
"Переделай"

// Хороший комментарий:
"Здесь может быть деление на ноль, если user.age не задан.
Предлагаю добавить проверку:
if (user.age && user.age > 0) { ... }"
```

Используйте уровни важности для комментариев. MUST — критические проблемы, которые обязательно исправить. SHOULD — желательные улучшения. CONSIDER — идеи для размышления. NIT — мелкие придирки к стилю.

Не забывайте хвалить хорошие решения. Когда видите элегантный код или хороший тест — скажите об этом. Позитивная обратная связь мотивирует не меньше, чем конструктивная критика.

### Что делать при разногласиях

Разногласия — это нормально. Они помогают найти лучшее решение. Важно вести дискуссию профессионально и конструктивно.

Если спор в комментариях затягивается, созвонитесь. Пятиминутный разговор решит вопрос быстрее, чем час переписки. Для сложных архитектурных вопросов привлеките третью сторону — техлида или архитектора.

Умейте уступать в мелочах. Если спор идёт о стиле кода или личных предпочтениях — не стоит тратить время. Сосредоточьтесь на важном: корректности, безопасности, производительности.

### Автоматизация проверок

Многие проверки можно автоматизировать. Это освобождает время для более важных вопросов.

Линтеры проверяют стиль кода. Не нужно спорить о расстановке скобок — пусть это делает ESLint или Prettier. Настройте их один раз для всего проекта.

Автоматические тесты проверяют, что новый код не сломал существующую функциональность. Если тесты не проходят — PR точно не готов к review.

Инструменты статического анализа находят потенциальные баги, неиспользуемый код, уязвимости безопасности. SonarQube, CodeClimate и подобные сервисы экономят время reviewer'ов.

### Review для разных типов изменений

Новая функциональность требует внимания к архитектуре. Вписывается ли решение в общую структуру проекта. Достаточно ли оно гибкое для будущих изменений.

При рефакторинге главное — убедиться, что поведение не изменилось. Должны быть тесты, которые это подтверждают. И код должен стать действительно лучше, а не просто другим.

Для багфиксов проверьте, что исправление решает именно ту проблему, которая заявлена. И не создаёт новых проблем. Обязательно должен быть тест, предотвращающий возвращение бага.

### Создание культуры хорошего review

Code review — это приоритет. Не откладывайте проверку на конец дня или на завтра. Люди ждут ваш feedback, чтобы продолжить работу.

Будьте открыты к обучению. Даже senior разработчики могут научиться чему-то новому от junior коллег. Review — это улица с двусторонним движением.

Помните, что все делают ошибки. Цель review — найти и исправить их, а не пристыдить автора. Создавайте атмосферу, где ошибки — это возможность для улучшения.

### Частые ошибки в code review

Формальное одобрение без реальной проверки убивает смысл процесса. Если нет времени на нормальный review — честно скажите об этом. Пусть проверит кто-то другой.

Придирки к мелочам при игнорировании серьёзных проблем создают негативную атмосферу. Сначала обратите внимание на важное, потом — на детали.

Попытки изменить архитектуру на этапе review обычно приводят к конфликтам. Такие вопросы нужно обсуждать до написания кода, а не после.

### Метрики и улучшение процесса

Измеряйте, как быстро PR получают первый review. Если люди ждут по несколько дней — процесс нужно улучшать.

Следите за размером PR. Если постоянно приходят огромные pull request'ы — обсудите с командой, как их уменьшить.

Но помните: метрики — это инструмент для улучшения процесса, а не для наказания. Быстрый поверхностный review хуже, чем медленный, но качественный.

## Итог

Code review — это инвестиция в качество кода и развитие команды. Хороший review находит проблемы рано, распространяет знания и поддерживает стандарты проекта. Ключ к успеху — создать культуру, где review воспринимается позитивно. Где feedback конструктивен, а ошибки — это возможность для обучения. Автоматизируйте рутину, фокусируйтесь на важном и помните: цель review — сделать код лучше, а не показать своё превосходство.
