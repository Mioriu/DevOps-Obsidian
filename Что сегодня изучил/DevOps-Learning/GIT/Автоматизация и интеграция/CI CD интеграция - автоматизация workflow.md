Современная разработка немыслима без автоматизации. Каждый push должен запускать тесты, каждый merge в main — создавать сборку, каждый тег — разворачивать релиз. CI/CD превращает Git из системы контроля версий в центр управления всем жизненным циклом приложения. GitHub Actions, GitLab CI, Jenkins — эти инструменты читают конфигурацию прямо из репозитория и выполняют любые задачи: от проверки кода до развёртывания в production. Git становится единым источником правды не только для кода, но и для процессов. Это урок о том, как заставить машины делать рутинную работу, оставив разработчикам время для творчества.

### Почему Git стал центром CI/CD

Git изначально создавался для версионирования кода, но его событийная модель идеально подошла для автоматизации процессов разработки. Каждое действие в Git — это потенциальный триггер для запуска автоматизации.

#### От ручных процессов к автоматизации

Представьте традиционный процесс без CI/CD. Разработчик пушит код, затем вручную запускает тесты. Если тесты прошли, он собирает приложение. Потом копирует файлы на сервер, перезапускает сервисы, проверяет работоспособность. Каждый шаг — это потенциальная точка отказа, человеческая ошибка, потерянное время.

CI/CD автоматизирует эту цепочку. Git-события становятся триггерами: push запускает тесты, успешные тесты запускают сборку, merge в main разворачивает staging, тег создаёт production-релиз. Человек только пишет код и делает git push — всё остальное происходит автоматически.

#### Configuration as Code

Ключевая идея современного CI/CD — конфигурация как код. Вместо настройки через GUI, вся автоматизация описывается в файлах, которые лежат в том же репозитории. Это даёт версионирование процессов, возможность code review для изменений в pipeline, откат к предыдущим версиям.

```bash
# Конфигурация хранится вместе с кодом
.github/workflows/ci.yml     # GitHub Actions
.gitlab-ci.yml              # GitLab CI
Jenkinsfile                 # Jenkins
.circleci/config.yml        # CircleCI
```

Изменение процесса деплоя становится таким же прозрачным, как изменение кода. Хотите добавить новый этап тестирования? Создайте pull request с изменениями в CI-конфигурации.

### Основные концепции Git-based CI/CD

#### Pipeline и Jobs

**Pipeline** — это последовательность автоматизированных шагов от коммита до развёртывания. Pipeline состоит из **stages** (этапов), которые выполняются последовательно, и **jobs** (задач) внутри каждого этапа, которые могут выполняться параллельно.

Типичный pipeline выглядит так:

1. **Build** — компиляция кода, сборка артефактов
2. **Test** — unit-тесты, интеграционные тесты, проверка покрытия
3. **Security** — сканирование уязвимостей, проверка зависимостей
4. **Deploy** — развёртывание на различные окружения
5. **Verify** — smoke-тесты, проверка health endpoints

#### Триггеры и условия

CI/CD системы реагируют на Git-события. Основные триггеры:

- **Push** — любой push в репозиторий. Можно фильтровать по веткам, путям, коммит-сообщениям
- **Pull Request/Merge Request** — создание, обновление, merge. Идеально для проверки кода перед вливанием
- **Tag** — создание Git-тегов. Обычно используется для релизов
- **Schedule** — запуск по расписанию (cron). Подходит для ночных сборок, регулярных проверок
- **Manual** — ручной запуск. Важно для production-деплоев с подтверждением
- **Webhook** — внешние события. Позволяет интегрировать с другими системами

#### Артефакты и кеширование

**Артефакты** — это файлы, создаваемые в процессе сборки и передаваемые между jobs или сохраняемые для дальнейшего использования. Это могут быть скомпилированные бинарники, отчёты о тестировании, документация.

**Кеширование** ускоряет pipeline за счёт сохранения зависимостей между запусками. Вместо скачивания npm-пакетов каждый раз, они берутся из кеша.

### GitHub Actions: CI/CD от GitHub

GitHub Actions — это встроенная в GitHub система автоматизации. Её преимущество — глубокая интеграция с GitHub: доступ к API, автоматическая аутентификация, marketplace с готовыми действиями.

#### Как работают Actions

GitHub Actions использует концепцию **workflows** — файлов в формате YAML, описывающих автоматизацию. Workflows состоят из **jobs**, которые выполняются на **runners** — виртуальных машинах с предустановленным софтом.

```yaml
# .github/workflows/example.yml
name: Example Workflow
on: [push]  # Триггер

jobs:
  example:  # Job
    runs-on: ubuntu-latest  # Runner
    steps:  # Шаги внутри job
      - uses: actions/checkout@v4  # Готовое действие
      - run: echo "Hello, World!"  # Shell-команда
```

#### Marketplace и переиспользование

Уникальная особенность GitHub Actions — огромный marketplace готовых действий. Вместо написания скриптов с нуля, можно использовать проверенные решения от сообщества. Действия — это просто репозитории с определённой структурой, их можно создавать и публиковать.

#### Матричные сборки

GitHub Actions поддерживает матричные стратегии — автоматическое создание множества jobs с разными параметрами. Это идеально для тестирования на разных версиях языков, операционных системах, конфигурациях.

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest, macos-latest]
    node: [14, 16, 18]
# Создаст 9 jobs: 3 OS × 3 версии Node.js
```

### GitLab CI/CD: всё в одном

GitLab CI/CD — это интегрированная система, которая является частью GitLab. В отличие от GitHub, где Actions — отдельный продукт, в GitLab CI/CD встроен изначально.

#### Runners и исполнители

GitLab использует концепцию **runners** — агентов, которые выполняют jobs. Runners могут быть:

- **Shared** — предоставляются GitLab.com бесплатно с лимитами
- **Group** — доступны всем проектам в группе
- **Specific** — привязаны к конкретному проекту

Важное преимущество — возможность использовать собственные runners на своей инфраструктуре, что критично для enterprise.

#### Environments и deployments

GitLab имеет встроенную поддержку окружений. Каждый deployment связывается с окружением, GitLab отслеживает, какая версия где развёрнута, позволяет откатываться, видеть историю.

#### Review Apps

Уникальная функция GitLab — автоматическое создание временных окружений для каждого merge request. Это позволяет тестировать изменения в изолированной среде до merge.

### Jenkins: ветеран автоматизации

Jenkins — один из старейших CI-серверов, но до сих пор популярный благодаря гибкости и огромной экосистеме плагинов.

#### Pipeline as Code

Jenkins поддерживает два типа pipeline:

- **Declarative Pipeline** — структурированный, простой в написании, покрывает 90% случаев
- **Scripted Pipeline** — полноценный Groovy-код, максимальная гибкость

Jenkinsfile хранится в репозитории вместе с кодом, что даёт все преимущества версионирования.

#### Распределённые сборки

Jenkins использует архитектуру master-agent. Master управляет процессом, agents выполняют работу. Это позволяет:

- Масштабировать систему горизонтально
- Использовать разные окружения (Windows, Linux, macOS)
- Изолировать сборки друг от друга
- Оптимизировать использование ресурсов

### Стратегии ветвления и CI/CD

Выбор стратегии ветвления напрямую влияет на организацию CI/CD.

#### Git Flow и окружения

При использовании Git Flow естественно мапятся ветки на окружения:

- **feature/*** → временные preview-окружения
- **develop** → dev/integration окружение
- **release/*** → staging окружение
- **main/master** → production
- **hotfix/*** → hotfix окружение с быстрым путём в production

CI/CD конфигурация определяет правила: какие проверки для каких веток, куда деплоить, нужно ли ручное подтверждение.

#### GitHub Flow и continuous deployment

GitHub Flow с его простотой (main + feature branches) идеален для continuous deployment:

1. Feature branch → запуск тестов, создание preview
2. Pull Request → дополнительные проверки, code review
3. Merge в main → автоматический деплой в production

Простота модели позволяет сделать pipeline прямолинейным и быстрым.

#### Trunk-based development

При trunk-based development все работают с main, используя feature flags для изоляции незавершённых функций. CI/CD фокусируется на:

- Очень быстрых проверках (секунды, не минуты)
- Прогрессивном развёртывании (canary, blue-green)
- Мониторинге и автоматическом откате
- Feature flags управлении

### Секреты и безопасность

CI/CD требует доступа к чувствительным данным: паролям баз данных, API-ключам, сертификатам. Управление секретами — критически важный аспект.

#### Хранение секретов

Секреты никогда не должны храниться в репозитории. Современные CI/CD системы предоставляют механизмы:

- **Environment variables** — секреты как переменные окружения
- **Secrets management** — встроенные хранилища секретов
- **External vaults** — интеграция с HashiCorp Vault, AWS Secrets Manager
- **Encrypted files** — зашифрованные файлы в репозитории

#### Принцип наименьших привилегий

Каждый job должен иметь доступ только к необходимым секретам. Production-секреты доступны только production-jobs, staging — только staging-jobs.

### Мониторинг и observability

CI/CD генерирует огромное количество данных о процессе разработки. Правильный мониторинг помогает оптимизировать процессы.

#### Ключевые метрики

- **Build time** — время выполнения pipeline. Долгие сборки снижают продуктивность
- **Success rate** — процент успешных сборок. Низкий процент указывает на проблемы
- **Time to recovery** — время исправления сломанной сборки
- **Deployment frequency** — как часто деплоится код
- **Lead time** — время от коммита до production

#### Интеграция с системами мониторинга

CI/CD должен отправлять метрики в системы мониторинга (Prometheus, DataDog, New Relic). Это позволяет:

- Видеть тренды и аномалии
- Настраивать алерты на проблемы
- Коррелировать с другими метриками
- Строить дашборды для команды

### Оптимизация CI/CD

Медленный CI/CD убивает продуктивность. Разработчики начинают избегать запуска тестов, накапливают изменения, реже делают коммиты.

#### Стратегии ускорения

**Параллелизация** — запуск независимых задач одновременно. Вместо последовательного выполнения unit-тестов, интеграционных тестов и линтера, запускайте их параллельно.

**Инкрементальные сборки** — собирайте только изменённое. Monorepo особенно выигрывают от этого подхода.

**Кеширование агрессивное** — кешируйте всё: зависимости, промежуточные сборки, Docker-слои, результаты тестов для неизменённого кода.

**Fail fast** — быстрые проверки первыми. Нет смысла ждать 20 минут тестов, если код не проходит линтер за 10 секунд.

#### Оптимизация Docker в CI/CD

Docker стал стандартом для CI/CD, но требует оптимизации:

- Многостадийные сборки для уменьшения размера
- Кеширование слоёв между сборками
- Buildkit для параллельной сборки
- Registry mirrors для ускорения загрузки

### GitOps: следующий уровень

GitOps — это эволюция CI/CD, где Git становится единственным источником правды не только для кода, но и для состояния инфраструктуры.

#### Принципы GitOps

1. **Декларативность** — описываем желаемое состояние, а не императивные шаги
2. **Версионирование** — всё состояние версионируется в Git
3. **Автоматизация** — изменения применяются автоматически
4. **Observability** — постоянный мониторинг соответствия

При GitOps, изменение в production — это просто коммит в Git. Специальные операторы (Flux, ArgoCD) следят за репозиторием и приводят реальное состояние к описанному.

### Выбор правильного подхода

Не существует универсального решения. Выбор зависит от множества факторов:

#### Размер команды и проекта

- **Маленькая команда/проект** — GitHub Actions или GitLab CI, простой pipeline
- **Средняя команда** — GitLab CI с собственными runners или managed Jenkins
- **Enterprise** — Jenkins с кастомизацией или enterprise-решения

#### Требования к безопасности

- **Публичные проекты** — осторожность с секретами, ограничения для fork
- **Приватные проекты** — собственные runners, изоляция окружений
- **Regulated industries** — audit trails, approval workflows, compliance

#### Инфраструктура

- **Cloud-native** — Kubernetes-based CI/CD (Tekton, Argo Workflows)
- **Hybrid** — гибкие решения типа Jenkins или GitLab
- **On-premise** — self-hosted варианты всех основных систем

### Культура CI/CD

Технологии — это только часть успеха. CI/CD требует изменения культуры разработки.

#### Ответственность за pipeline

Pipeline — это код, и он требует такого же внимания. Code review для изменений в CI/CD, тестирование pipeline, документация — всё это должно быть частью процесса.

#### Быстрая обратная связь

Цель CI/CD — дать разработчику быструю обратную связь. Если pipeline выполняется час, это не CI/CD, это просто автоматизация. Стремитесь к минутам, не часам.

#### Культура исправления

Сломанный build должен быть приоритетом номер один. Красный pipeline блокирует всю команду. Культура "сначала чиним build, потом продолжаем работу" критически важна.

## Итог

CI/CD интеграция превращает Git из системы версионирования в центр автоматизации разработки. Каждое Git-событие может запускать цепочку автоматических действий: тесты, сборку, развёртывание. Современные инструменты позволяют описать весь процесс как код, версионировать его вместе с приложением. GitHub Actions приносит простоту и интеграцию, GitLab CI — комплексное решение, Jenkins — максимальную гибкость. Выбор инструмента менее важен, чем понимание принципов: автоматизация рутины, быстрая обратная связь, версионирование процессов. Начните с простого — автоматических тестов на push, постепенно добавляя этапы. CI/CD — это не просто инструменты, это изменение подхода к разработке, где качество и скорость идут рука об руку.
