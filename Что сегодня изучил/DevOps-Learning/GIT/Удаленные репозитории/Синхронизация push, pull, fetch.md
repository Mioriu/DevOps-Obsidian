

После настройки удалённых репозиториев необходимо научиться обмениваться изменениями между локальной и удалёнными версиями проекта. Git предоставляет три команды для синхронизации: `fetch`, `pull` и `push`. Понимание того, как именно они работают и чем отличаются, критически важно для эффективной работы.

### Как Git хранит информацию об удалённых ветках

Прежде чем разбирать команды синхронизации, важно понять, как Git организует работу с удалёнными репозиториями. В локальном репозитории существует три типа веток, каждый с особой ролью:

**Локальные ветки** — это обычные рабочие ветки, где происходит разработка. Они полностью под вашим контролем, можно создавать коммиты, переключаться между ними, удалять их.

**Remote-tracking ветки** — это локальные копии веток из удалённого репозитория. Они имеют специальный формат имени: `origin/main`, `origin/develop`. Эти ветки нельзя изменить напрямую — они обновляются автоматически при синхронизации и показывают состояние удалённого репозитория на момент последней синхронизации. Думайте о них как о "закладках", показывающих, где находятся ветки на сервере.

**Удалённые ветки** — это ветки, которые физически находятся в удалённом репозитории. Вы не можете работать с ними напрямую, только через команды синхронизации.

```bash
# Посмотреть все типы веток
$ git branch -a
* main                    # локальная ветка (текущая)
  develop                 # локальная ветка
  remotes/origin/main     # remote-tracking ветка
  remotes/origin/develop  # remote-tracking ветка
```

### Git fetch — получение без изменений

**git fetch** — это самая безопасная команда синхронизации, потому что она никогда не изменяет ваши локальные ветки или рабочую директорию. Она только загружает новую информацию с сервера.

#### Что происходит при выполнении fetch

Когда вы выполняете `git fetch origin`, происходит следующее:

1. Git устанавливает соединение с удалённым репозиторием
2. Запрашивает список всех веток и их текущие позиции (на какие коммиты они указывают)
3. Сравнивает с локальной информацией и определяет, какие коммиты отсутствуют локально
4. Загружает недостающие коммиты и все связанные объекты (файлы, деревья)
5. Обновляет remote-tracking ветки, чтобы они указывали на новые позиции

```bash
# Выполнить fetch и посмотреть, что изменилось
$ git fetch origin
remote: Counting objects: 15, done.
remote: Compressing objects: 100% (8/8), done.
remote: Total 15 (delta 5), reused 15 (delta 5)
Unpacking objects: 100% (15/15), done.
From github.com:user/repository
   a456def..b789ghi  main     -> origin/main
   c123jkl..d456mno  develop  -> origin/develop
```

Эта информация говорит, что ветка `main` на сервере продвинулась от коммита `a456def` до `b789ghi`, и локальная remote-tracking ветка `origin/main` была обновлена соответственно.

#### Почему fetch не меняет рабочую директорию

После fetch ваша локальная ветка `main` всё ещё указывает на старый коммит, а `origin/main` уже указывает на новый. Это позволяет вам:

- Посмотреть, что именно изменилось, перед интеграцией
- Закончить текущую работу без неожиданных изменений
- Выбрать подходящий момент для обновления

```shell
# После fetch можно изучить изменения
$ git log main..origin/main  # что нового на сервере
$ git log origin/main..main  # что есть локально, но нет на сервере
$ git diff main origin/main  # различия в коде
```

### Git pull — автоматическая интеграция

**git pull** делает больше, чем fetch — она не только загружает изменения, но и автоматически интегрирует их в текущую ветку. По сути, `git pull` = `git fetch` + `git merge` (или `git rebase`).

#### Механика работы pull

Процесс выполнения `git pull origin main`:

1. Сначала выполняется `git fetch origin` (получение новых коммитов)
2. Git определяет, какую remote-tracking ветку нужно слить (в данном случае `origin/main`)
3. Проверяет, можно ли выполнить fast-forward merge
4. Если да — просто передвигает указатель локальной ветки
5. Если нет — создаёт merge-коммит или выполняет rebase

#### Три варианта поведения pull

**Fast-forward merge** происходит, когда ваша локальная ветка не содержит уникальных коммитов:

```applescript
# До pull:
      A---B---C  (origin/main)
     /
A---B  (main)

# После pull:
A---B---C  (main, origin/main)
```

**Merge commit** создаётся, когда обе ветки содержат уникальные коммиты:

```applescript
# До pull:
      C---D  (origin/main)
     /
A---B
     \
      E---F  (main)

# После pull:
      C---D
     /     \
A---B       G  (main)
     \     /
      E---F
```

**Rebase** переписывает историю, помещая ваши коммиты поверх полученных:

```lua
# До pull --rebase:
      C---D  (origin/main)
     /
A---B
     \
      E---F  (main)

# После pull --rebase:
A---B---C---D  (origin/main)
             \
              E'---F'  (main)
```

#### Когда pull может вызвать проблемы

Pull изменяет текущую ветку, поэтому требует чистого рабочего состояния. Если есть незакоммиченные изменения, Git откажется выполнять pull:

```applescript
error: Your local changes to the following files would be overwritten by merge:
        src/app.js
Please commit your changes or stash them before you merge.
```

### Git push — отправка на сервер

**git push** — единственная команда, которая изменяет удалённый репозиторий, отправляя ваши локальные коммиты на сервер.

#### Как работает push

При выполнении `git push origin main`:

1. Git определяет, какие коммиты есть локально, но отсутствуют на сервере
2. Проверяет, является ли операция fast-forward для удалённой ветки
3. Если да — отправляет коммиты и обновляет удалённую ветку
4. Если нет — отклоняет операцию для предотвращения потери данных
5. После успешного push обновляет remote-tracking ветку

#### Почему push может быть отклонён

Git отклоняет push, если он не является fast-forward операцией. Это происходит, когда кто-то другой успел отправить коммиты раньше вас:

```applescript
# Ваше представление о репозитории:
A---B---C  (main, origin/main)
         \
          D---E  (ваши новые коммиты)

# Реальное состояние на сервере:
A---B---C---F---G  (origin/main на сервере)

# Push будет отклонён, так как коммиты F и G будут потеряны
```

Сообщение об ошибке:

```vbnet
! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'origin'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart.
```

#### Force push и его опасности

Force push перезаписывает историю на сервере:

```applescript
# Обычный force push (опасно!)
$ git push --force origin main

# Заменяет на сервере:
A---B---C---F---G  (старая версия)
# На:
A---B---C---D---E  (ваша версия)
# Коммиты F и G потеряны!
```

Более безопасный вариант — `--force-with-lease`:

```csharp
$ git push --force-with-lease origin main
```

Эта команда проверяет, что remote-tracking ветка соответствует состоянию на сервере. Если кто-то отправил изменения после вашего последнего fetch, операция будет отклонена.

### Upstream связи и их важность

Upstream (или tracking) связь — это конфигурация, которая говорит Git, какая удалённая ветка соответствует локальной. Это упрощает команды и даёт больше информации о состоянии синхронизации.

#### Как работает upstream

Когда установлена upstream связь:

- `git pull` знает, откуда брать изменения
- `git push` знает, куда отправлять коммиты
- `git status` показывает разницу с удалённой веткой

```shell
# Установка upstream при push
$ git push -u origin feature/new-button

# Что происходит:
# 1. Создаётся ветка feature/new-button на сервере
# 2. Отправляются коммиты
# 3. Устанавливается связь:
#    local: feature/new-button
#    tracks: origin/feature/new-button

# Теперь достаточно коротких команд:
$ git pull    # вместо git pull origin feature/new-button
$ git push    # вместо git push origin feature/new-button
```

#### Информация о синхронизации

```applescript
$ git status
On branch main
Your branch is ahead of 'origin/main' by 2 commits.
  (use "git push" to publish your local commits)
```

Эта информация возможна благодаря upstream связи. Git сравнивает вашу ветку с remote-tracking веткой и сообщает:

- **ahead** — у вас есть коммиты для отправки
- **behind** — на сервере есть новые коммиты
- **diverged** — есть уникальные коммиты в обеих ветках

## Итог

Команды синхронизации работают с тремя уровнями веток: локальными, remote-tracking и удалёнными. `fetch` обновляет только remote-tracking ветки, позволяя безопасно изучить изменения. `pull` дополнительно интегрирует эти изменения в вашу текущую ветку через merge или rebase. `push` отправляет ваши коммиты на сервер, но только если это не приведёт к потере чужих изменений. Понимание того, как именно работают эти команды и какие проверки выполняет Git, позволяет уверенно работать в команде и быстро решать возникающие проблемы синхронизации.
