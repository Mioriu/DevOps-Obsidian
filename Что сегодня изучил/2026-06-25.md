## Статья 1: systemd — управление сервисами и логи

### Что такое systemd

**systemd** — система инициализации и управления сервисами (PID 1). Запускается первой, управляет всем, что работает на сервере: запуск, остановка, перезапуск, логирование, расписания.

### Основные команды systemctl

|Команда|Назначение|
|---|---|
|`systemctl start nginx`|Запустить сервис|
|`systemctl stop nginx`|Остановить сервис|
|`systemctl restart nginx`|Перезапустить (рвёт соединения)|
|`systemctl reload nginx`|Перечитать конфиг **без** даунтайма (SIGHUP)|
|`systemctl status nginx`|Статус + последние логи|
|`systemctl enable nginx`|Включить автозапуск|
|`systemctl disable nginx`|Выключить автозапуск|
|`systemctl enable --now nginx`|Включить автозапуск **и** запустить сейчас|
|`systemctl is-active nginx`|Проверить статус (для скриптов)|
|`systemctl daemon-reload`|Перечитать юнит-файлы (после изменений!)|

### Юнит-файлы (`.service`)

**Где лежат:**

- `/usr/lib/systemd/system/` — от пакетов
    
- `/etc/systemd/system/` — кастомные (приоритет выше)
    

**Структура:**

ini

[Unit]
Description=My Python Application
After=network.target postgresql.service
Wants=postgresql.service
[Service]
Type=simple
User=appuser
Group=appuser
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/venv/bin/python app.py
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5
Environment=APP_ENV=production
EnvironmentFile=/opt/myapp/.env
[Install]
WantedBy=multi-user.target

**Ключевые параметры:**

- `After` — порядок запуска (сначала поднять сеть/БД)
    
- `Wants` — мягкая зависимость (стартанет и без неё)
    
- `Requires` — жёсткая зависимость (если не поднялась — сервис не стартует)
    
- `Type=simple` — основной процесс
    
- `Restart=on-failure` — перезапускать при падении
    
- `$MAINPID` — подставляется systemd
    

### Типы юнитов

|Тип|Расширение|Назначение|
|---|---|---|
|`.service`|Сервис|Основной тип|
|`.timer`|Таймер|Замена cron|
|`.socket`|Сокет|Сокет-активация|
|`.target`|Группа|`multi-user.target` — нормальный режим|
|`.mount`|Точка монтирования|Альтернатива `/etc/fstab`|
|`.slice`|Управление ресурсами|Cgroups|

### journalctl — логи

|Команда|Назначение|
|---|---|
|`journalctl -u nginx`|Логи сервиса|
|`journalctl -u nginx -n 50`|Последние 50 строк|
|`journalctl -u nginx -f`|Следить в реальном времени (tail -f)|
|`journalctl -u nginx --since "1 hour ago"`|За последний час|
|`journalctl -u nginx -b`|Только текущая загрузка|
|`journalctl -u nginx -p err`|Только ошибки|
|`journalctl --disk-usage`|Сколько места жрёт|
|`journalctl --vacuum-size=500M`|Очистить до 500 МБ|

### Таймеры systemd — замена cron

Связка `.timer` + `.service`.

**`/etc/systemd/system/backup.service`:**

ini

[Unit]
Description=Daily backup script
[Service]
Type=oneshot
ExecStart=/opt/scripts/backup.sh
User=backup

**`/etc/systemd/system/backup.timer`:**

ini

[Unit]
Description=Run backup every day at 3 AM
[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
[Install]
WantedBy=timers.target

**Запуск:**

bash

systemctl daemon-reload
systemctl enable --now backup.timer
systemctl list-timers        # все активные таймеры

**Форматы расписания:**

- `OnCalendar=*-*-* *:00:00` — каждый час
    
- `OnCalendar=Mon *-*-* 09:00:00` — каждый понедельник
    
- `OnBootSec=5min` — через 5 минут после загрузки
    
- `OnUnitActiveSec=30min` — каждые 30 минут после последнего запуска
    

### Полезные практики

bash

# Переопределить параметры без редактирования юнит-файла
systemctl edit nginx
# → создаёт оверрайд в /etc/systemd/system/nginx.service.d/
# Посмотреть полный конфиг юнита (с оверрайдами)
systemctl cat nginx
# Стандартный алгоритм дебага:
systemctl status nginx
journalctl -u nginx -n 30
journalctl -u nginx -p err

## Статья 2: Диагностика, порты, файрволлы и SSH

### Основные команды диагностики

|Команда|Назначение|Пример|
|---|---|---|
|`ss -tlnp`|Слушающие TCP порты (+ процессы)|`ss -tlnp`|
|`ss -tnp`|Активные TCP подключения|`ss -tnp \| grep :80`|
|`lsof -i :8080`|Какой процесс на порту|`sudo lsof -i :8080`|
|`ping -c 5 google.com`|Доступность хоста (ICMP)|—|
|`traceroute google.com`|Путь до хоста (роутеры)|—|
|`nc -zv google.com 443`|Проверить открыт ли порт|—|
|`curl -I https://example.com`|HTTP заголовки|—|

### Проверка портов

**Локально:**

bash

ss -tlnp | grep :8080
sudo lsof -i :8080
netstat -tlnp | grep :8080

**Удалённо:**

bash

nc -zv example.com 80
telnet example.com 80
curl -I http://example.com

### Найти и убить процесс, занявший порт

bash

# Найти PID
sudo lsof -i :8080
# или
sudo fuser 8080/tcp
# Убить
sudo kill 5678
sudo kill -9 5678
sudo fuser -k 8080/tcp   # убить сразу

### Файрволлы

**iptables (низкий уровень):**

bash

# Посмотреть правила
sudo iptables -L -n -v
# Разрешить SSH
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT
# Разрешить established соединения
sudo iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT
# Дефолт политика — запретить всё
sudo iptables -P INPUT DROP
# Сохранить
sudo netfilter-persistent save   # Ubuntu
sudo service iptables save       # RHEL

**firewalld (высокоуровневый, RHEL):**

bash

# Открыть порт
sudo firewall-cmd --add-port=8080/tcp --permanent
sudo firewall-cmd --reload
# Открыть сервис
sudo firewall-cmd --add-service=http --permanent
# Заблокировать IP
sudo firewall-cmd --add-rich-rule='rule family="ipv4" source address="192.168.1.50" reject' --permanent

**ufw (простой, Ubuntu):**

bash

sudo ufw enable
sudo ufw allow 22/tcp
sudo ufw allow from 192.168.1.100 to any port 3306
sudo ufw deny 3306/tcp
sudo ufw status numbered
sudo ufw delete 2

### Траблшутинг HTTP ошибок

|Ошибка|Что значит|Проверка|
|---|---|---|
|**502 Bad Gateway**|Прокси не может подключиться к бэкенду|`ss -tlnp \| grep :8080`, `nc -zv localhost 8080`, логи nginx|
|**500 Internal Server Error**|Ошибка в коде приложения|Логи приложения, доступность БД, `df -h`, `top`|
|**504 Gateway Timeout**|Бэкенд не ответил вовремя|`time curl http://localhost:8080`, `proxy_read_timeout` в nginx|

**502:** `connect() failed (111: Connection refused) while connecting to upstream` → бэкенд не слушает

**Диагностика 500:**

- `journalctl -u myapp -f` — логи приложения
    
- `nc -zv db-server 5432` — доступна ли БД
    
- `df -h` — место на диске (логи не забили?)
    
- `top` — память, CPU
    

### SSH — настройка и безопасность

**Конфиг `/etc/ssh/sshd_config`:**

text

PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
Port 2222
AllowUsers deployer admin
ClientAliveInterval 300
ClientAliveCountMax 2

**Генерация и добавление ключа:**

bash

# На локальной машине
ssh-keygen -t ed25519 -C "deploy@myapp"
# Добавить на сервер
ssh-copy-id deployer@server.com
# Проверить права на сервере
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

**SSH для CI/CD (GitLab CI):**

yaml

deploy:
  script:
    - eval $(ssh-agent -s)
    - echo "$SSH_PRIVATE_KEY" | ssh-add -
    - ssh deployer@server "cd /opt/myapp && git pull && sudo systemctl restart myapp"

### Частые проблемы и решения

|Проблема|Причина|Решение|
|---|---|---|
|**Connection refused**|Приложение не запущено или слушает на другом порту/интерфейсе|`systemctl start`, проверить `0.0.0.0`|
|**Connection timeout**|Файрволл блокирует или проблемы с роутингом|`firewall-cmd --add-port`, `traceroute`|
|**SSH Permission denied**|Ключ не добавлен, неправильные права, не тот ключ|`ssh-copy-id`, `chmod 700/600`, явно указать `-i`|
|**Too many open files**|Достигнут лимит открытых файлов|Увеличить `ulimit -n`, `LimitNOFILE` в systemd|

**Частые ошибки на собесах:**

- Путают **connection refused** (порт закрыт/не слушает) и **connection timeout** (файрволл/сеть)
    
- Думают что ufw, firewalld и iptables — это три разных файрволла (firewalld и ufw — это обёртки над iptables)
    

### Главные правила диагностики

1. **Процесс → порт → файрволл → логи**
    
2. `ss -tlnp` (с sudo) — для проверки открытых портов
    
3. `nc -zv` — для быстрой проверки доступности порта
    
4. **Connection refused** = приложение не слушает
    
5. **Connection timeout** = файрволл блокирует или сеть
    
6. SSH ключи требуют правильных прав: `~/.ssh` — 700, `authorized_keys` — 600
