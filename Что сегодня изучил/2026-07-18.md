## Статья 1: Роли — структура и использование

### Что такое роль

Логически завершённый блок (nginx, PostgreSQL, мониторинг). Структурирует код, делает его переиспользуемым.

### Структура роли

text

roles/nginx/
├── tasks/main.yml       # точка входа (обязательно)
├── handlers/main.yml    # обработчики
├── templates/           # Jinja2-шаблоны
├── files/               # статические файлы
├── defaults/main.yml    # переменные по умолчанию (низкий приоритет)
├── vars/main.yml        # константы роли (высокий приоритет)
├── meta/main.yml        # метаданные + зависимости
└── tests/               # тесты

### Ключевые моменты

- **Обязательна только `tasks/`**
    
- `defaults/` — для параметров, которые пользователь может менять
    
- `vars/` — для констант роли
    
- `handlers/` — задачи, выполняемые только при `changed`
    
- `meta/main.yml` — зависимости (выполняются **перед** задачами роли)
    

### Подключение роли

yaml

roles:
  - nginx
  - role: postgresql
    vars:
      postgres_version: 14

### Ansible Galaxy

bash

ansible-galaxy install geerlingguy.nginx -p ./roles/
ansible-galaxy install -r requirements.yml

## Статья 2: Приоритет переменных

**От низшего к высшему:**

1. `role defaults` (`defaults/main.yml`) — **самый низкий**
    
2. `group_vars/all`
    
3. `group_vars/группа`
    
4. `host_vars`
    
5. `play vars`
    
6. `vars_files`
    
7. `role vars` (`vars/main.yml`)
    
8. `task vars`
    
9. `set_facts / registered vars`
    
10. `extra vars` (`-e`) — **самый высокий**
    

**Практическое правило:** `defaults` → легко переопределить, `vars` → сложно переопределить, `-e` → перебивает всё.

## Статья 3: Важные модули (шпаргалка)

|Категория|Модули|Ключевые параметры|
|---|---|---|
|Пакеты|`apt`, `yum`|`name`, `state: present/absent/latest`, `update_cache`|
|Файлы|`copy`, `file`, `template`|`src`, `dest`, `owner`, `group`, `mode`, `state`|
|Сервисы|`service`, `systemd`|`name`, `state: started/stopped/restarted/reloaded`, `enabled`|
|Команды|`command`, `shell`, `script`|`chdir`, `creates`, `removes`|
|Пользователи|`user`, `group`|`name`, `shell`, `groups`, `append`, `state`|
|Git|`git`|`repo`, `dest`, `version`, `force`|
|Docker|`docker_container`, `docker_image` (из `community.docker`)|`name`, `image`, `state`, `ports`, `volumes`|
|Kubernetes|`k8s`, `helm` (из `kubernetes.core`)|`state`, `definition`, `src`, `namespace`|

**Важные различия:**

- `copy` → копирует как есть, `template` → подставляет переменные (Jinja2)
    
- `command` → без shell (без пайпов, переменных), `shell` → через bash
    
- `notify` в `template` → вызывает handler **только при изменении**

## Статья 4: AWX — веб-интерфейс для Ansible

**AWX** — open-source веб-интерфейс + API + RBAC + планировщик для Ansible.

**Что даёт:**

- Веб-UI для запуска playbook'ов
    
- История запусков с логами
    
- RBAC (контроль доступа)
    
- Централизованное хранение credentials
    
- Расписание (cron)
    
- REST API
    
- Workflows (цепочки playbook'ов)
    

**AWX vs Tower:**

- **AWX** — open-source (бесплатный, community)
    
- **Ansible Tower** — коммерческий (Red Hat, платный, с поддержкой)
    

**Когда использовать AWX:**

- Много людей запускают playbook'и
    
- Нужна история и аудит
    
- Нужно расписание
    
- Нужно дать доступ не-DevOps'ерам

## Статья 5: Ansible в DevOps-практиках

### Ansible + Docker

- Коллекция: `community.docker`
    
- Задачи: провиженинг хоста, управление контейнерами, сборка образов
    

yaml

- name: Запустить контейнер
  community.docker.docker_container:
    name: redis
    image: redis:7-alpine
    state: started
    ports:
      - "6379:6379"

### Ansible + Kubernetes

- Коллекция: `kubernetes.core`
    
- Задачи: деплой манифестов, Helm-чарты, пост-установка кластера
    

yaml

- name: Применить манифест
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'deployment.yml.j2') | from_yaml }}"

### Ansible в CI/CD (GitLab CI)

Типичный пайплайн:

1. **Lint** → `ansible-lint`, `yamllint`
    
2. **Check** → `--check --diff` (dry-run)
    
3. **Deploy staging** → автоматически при merge в main
    
4. **Deploy production** → `when: manual`
    

**Секреты в CI:**

- SSH-ключ → переменная GitLab (тип File)
    
- Vault-пароль → переменная GitLab (masked, protected)
    

### Тестирование Ansible-кода

|Инструмент|Назначение|
|---|---|
|`yamllint`|Проверка YAML-синтаксиса|
|`ansible-lint`|Проверка best practices|
|**Molecule**|Фреймворк для тестирования ролей (контейнер → apply → verify → destroy)|
|`Testinfra`|Python-фреймворк для проверки состояния (пакет, сервис, порт, файл)|
|`Goss`|Альтернатива на Go (YAML-описание проверок)|

**Molecule:**

bash

molecule test    # полный цикл: create → converge → verify → destroy
molecule converge && molecule login   # отладка

## Статья 6: Terraform vs Ansible

|Слой|Ansible|Terraform|
|---|---|---|
|Где работает|Настройка **внутри** сервера|Создание **инфраструктуры** (VM, сети, диски)|
|Подключение|SSH к серверам|API облака|
|Язык|YAML|HCL (HashiCorp Configuration Language)|
|Учёт созданного|Нет (сверка с реальностью)|**State-файл**|
|Удаление убранного из кода|Нет|**Да**|

### Ключевые особенности Terraform

1. **State** — фиксирует всё созданное. При каждом запуске код сравнивается с state.
    
2. **Жизненный цикл** — убрали ресурс из кода → при следующем `apply` он удалится.
    
3. **Порядок создания** — вычисляется из зависимостей между ресурсами (не порядком в файле).
    

### HCL — язык Terraform

hcl

resource "docker_image" "nginx" {
  name = "nginx:1.25"
}
resource "docker_container" "web" {
  name  = "web"
  image = docker_image.nginx.image_id   # ссылка на другой ресурс
  ports {
    internal = 80
    external = 8080
  }
}

**Ссылка между ресурсами:** `тип.имя.атрибут` → `docker_image.nginx.image_id` — задаёт зависимость и порядок создания.

**Провайдеры:** плагины для работы с конкретными платформами (Docker, Yandex Cloud, AWS, Selectel). Объявляются в блоке `terraform`, настраиваются в `provider`.
