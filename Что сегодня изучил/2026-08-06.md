## Статья 1: Ingress — маршрутизация HTTP-трафика

### Проблема с LoadBalancer на каждый сервис

1. **Деньги и адреса:** каждый LoadBalancer → платный балансировщик + отдельный внешний IP + DNS-запись
    
2. **Уровень маршрутизации:** Service работает на TCP (не знает про хосты, пути, TLS)
    

### Решение: Ingress + Ingress Controller

|Компонент|Что делает|
|---|---|
|**Ingress**|Объект с правилами маршрутизации (host + path → service)|
|**Ingress Controller**|Реверс-прокси (NGINX, Traefik, HAProxy), который исполняет правила|

**Важно:** Ingress Controller в кластере из коробки **отсутствует**. Его нужно ставить отдельно.

**Схема трафика:**

text

Интернет → LoadBalancer (только для Ingress Controller) → Ingress Controller → Service (ClusterIP) → Pods

### Манифест Ingress

yaml

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80

- `ingressClassName` — какой контроллер обслуживает (забытое поле → одна из частых причин "ничего не происходит")
    
- `pathType`: `Prefix` (начинается с пути), `Exact` (точное совпадение)
    

### Маршрутизация

**По хостам:**

yaml

rules:
  - host: app.example.com
    backend: service web
  - host: api.example.com
    backend: service api

**По путям:**

yaml

rules:
  - host: app.example.com
    paths:
      - path: /api
        backend: service api
      - path: /
        backend: service web

При пересечении префиксов срабатывает более специфичный.

### TLS

bash

kubectl create secret tls web-tls --cert=tls.crt --key=tls.key

yaml

spec:
  tls:
    - hosts:
        - app.example.com
      secretName: web-tls

- TLS заканчивается на контроллере (внутри кластера — HTTP)
    
- Сертификаты обычно автоматизируются через **cert-manager** (Let's Encrypt)
    

### Аннотации — настройка поведения контроллера

yaml

metadata:
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "120"

**Важно:** аннотации специфичны для контроллера (`nginx.*`, `traefik.*`, облачные свои).

### Отладка

bash

kubectl get ingress          # ADDRESS — внешний адрес контроллера
kubectl describe ingress web # правила и бэкенды

**Проверка до DNS:**

bash

curl -H "Host: app.example.com" http://84.201.158.77/

**Симптомы:**

- `404` — запрос не совпал ни с одним правилом (опечатка в хосте, неверный `ingressClassName`)
    
- `503` — правило сработало, но у сервиса нет живых эндпоинтов
    
- Пустой `ADDRESS` — контроллер не назначен или отсутствует

## Статья 2: Другие контроллеры — StatefulSet, DaemonSet, Job, CronJob

### Сравнение контроллеров

|Контроллер|Форма нагрузки|Примеры|
|---|---|---|
|**Deployment**|Взаимозаменяемые копии без состояния|Веб-приложения, API|
|**StatefulSet**|Реплики с именем и своим диском|Базы данных, Kafka|
|**DaemonSet**|По одному поду на каждой ноде|Агенты логов, мониторинг, сетевые плагины|
|**Job**|Выполнить до конца и остановиться|Миграции, разовые расчёты|
|**CronJob**|Job по расписанию|Бэкапы, отчёты, чистка|

---

### StatefulSet — для stateful-нагрузок

**Три отличия от Deployment:**

1. **Стабильные имена:** `db-0`, `db-1`, `db-2` (пересозданный под возвращается с тем же именем)
    
2. **Свой том у каждой реплики:** `volumeClaimTemplates` → каждый под получает свой PVC (`data-db-0`, `data-db-1`)
    
3. **Порядок операций:** создаются по очереди (`db-0` готов → `db-1`), удаление в обратном порядке
    

**Headless-сервис** (`clusterIP: None`):

- DNS на `db` возвращает адреса подов напрямую
    
- Каждый под получает стабильное DNS-имя: `db-0.db`, `db-1.db`
    

**Манифест:**

yaml

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db
  replicas: 3
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: postgres
          image: postgres:16
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 10Gi

---

### DaemonSet — по одному поду на каждой ноде

- Поле `replicas` отсутствует — число подов равно числу нод
    
- Новая нода → новый под автоматически
    
- Удалённая нода → под удаляется
    

**Пример:** `kube-proxy` в `kube-system` реализован именно так.

**Применение:** агенты сбора логов, экспортеры метрик, сетевые плагины. Здесь законное место для `hostPath`.

---

### Job — задача с концом

yaml

apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: myapp:1.5
          command: ["python", "manage.py", "migrate"]

- `backoffLimit` — число повторов при неудаче
    
- `restartPolicy`: `Never` (упавший под остаётся, создаётся новый) или `OnFailure` (перезапуск в том же поде)
    
- После успеха: статус `Completed`
    
- `ttlSecondsAfterFinished` — автоудаление после указанного времени
    

---

### CronJob — задача по расписанию

yaml

apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
spec:
  schedule: "0 3 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: backup
              image: postgres:16
              command: ["pg_dump", "-U", "postgres", "mydb"]
          restartPolicy: Never

- `schedule` — cron-синтаксис (5 полей)
    
- `concurrencyPolicy`: `Allow` (параллельно), `Forbid` (пропустить), `Replace` (убить старый → запустить новый)
    
- `successfulJobsHistoryLimit` / `failedJobsHistoryLimit` — хранение истории
    

**Ручной запуск:**

bash

kubectl create job db-backup-manual --from=cronjob/db-backup

## Статья 3: Helm — пакетный менеджер Kubernetes

### Проблема, которую решает Helm

1. **Одно приложение = 6+ манифестов** (Deployment, Service, Ingress, ConfigMap, Secret, PVC). Для staging и production нужны почти такие же с точечными различиями.
    
2. **Чужой софт** (Ingress Controller, cert-manager, мониторинг) — десятки связанных манифестов.
    

### Основные понятия

|Понятие|Что это|
|---|---|
|**Chart**|Пакет с шаблонами манифестов + values.yaml (параметры по умолчанию)|
|**Release**|Установленный чарт с конкретными параметрами|
|**Values**|Параметры, переопределяющие умолчания|

### Установка чартов

bash

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm install my-db bitnami/postgresql --version 16.2.1 -f my-values.yaml

- `my-db` — имя релиза
    
- `bitnami/postgresql` — чарт
    
- `--version` — фиксация версии чарта
    
- `-f my-values.yaml` — файл с переопределениями
    

**Переопределение параметров:**

- `--set auth.postgresPassword=s3cr3t` — для экспериментов
    
- `-f my-values.yaml` — для жизни (в Git, проходит ревью)
    

### Релизы и ревизии

bash

helm upgrade my-db bitnami/postgresql -f my-values.yaml   # обновить
helm history my-db           # ревизии релиза
helm rollback my-db 1        # откат на ревизию
helm uninstall my-db         # удалить релиз + все объекты

Каждый `upgrade` создаёт новую ревизию. История хранится в секретах namespace.

---

### Устройство чарта

text

myapp/
├── Chart.yaml          # метаданные: name, version, appVersion
├── values.yaml         # параметры по умолчанию
├── templates/          # шаблоны манифестов
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   └── _helpers.tpl    # переиспользуемые куски
└── charts/             # вложенные чарты-зависимости

**Chart.yaml:**

yaml

apiVersion: v2
name: myapp
version: 1.2.0        # версия чарта
appVersion: "1.5.3"   # версия приложения (информационное)

**values.yaml — параметры по умолчанию:**

yaml

replicaCount: 2
image:
  repository: registry.example.com/myapp
  tag: "1.5.3"
resources:
  requests:
    cpu: 100m
    memory: 128Mi

**Шаблоны (Go-шаблоны, похоже на Jinja2):**

yaml

# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          resources:
            {{- toYaml .Values.resources | nindent 12 }}

**Источники значений:**

- `.Values` — из values.yaml + переопределения
    
- `.Release` — данные релиза (`.Release.Name` позволяет ставить чарт несколько раз без конфликтов)
    
- `.Chart` — данные из Chart.yaml
    

**Проверка:**

bash

helm template myapp ./myapp -f values-prod.yaml   # отрендерить локально
helm lint ./myapp                                 # проверить чарт
helm install myapp ./myapp --dry-run --debug      # сухой запуск

---

### Окружения через разные values

bash

# Один чарт, разные values
helm install myapp-staging ./myapp -f values-staging.yaml -n staging
helm install myapp ./myapp -f values-prod.yaml -n production

**CI-команда (идемпотентная):**

bash

helm upgrade --install myapp ./myapp -f values-prod.yaml --set image.tag=$CI_COMMIT_TAG

---

### Границы инструмента

- Go-шаблоны при разрастании читаются тяжело → держите чарты простыми
    
- Альтернатива: **kustomize** (встроен в kubectl) — наложение точечных правок
    
- Стандарт де-факто в индустрии — **Helm**
    

### Шпаргалка

bash

helm repo add bitnami https://charts.bitnami.com/bitnami
helm search repo postgresql
helm show values bitnami/postgresql
helm install NAME CHART -f values.yaml
helm list
helm upgrade NAME CHART -f values.yaml
helm upgrade --install NAME CHART          # CI-команда
helm history NAME
helm rollback NAME 1
helm uninstall NAME
helm create myapp                           # скелет чарта
helm template myapp ./myapp -f values.yaml
helm lint ./myapp
