## Статья 1: Fork и Pull Request workflow

### Основная идея

**Fork** — полная серверная копия чужого репозитория под вашим контролем. В отличие от `clone` (локальная копия), fork позволяет предлагать изменения в проекты без прямого доступа. **Pull Request (PR)** — формальное предложение влить ваши изменения в оригинальный репозиторий.

### Ключевые моменты

- **Настройка удалённых репозиториев**:
    
    bash
    
    git remote add upstream git@github.com:originalowner/project.git
    # origin — ваш fork, upstream — оригинал
    
- **Синхронизация fork** перед работой:
    
    bash
    
    git fetch upstream && git merge upstream/main && git push origin main
    
- **Жизненный цикл PR**: создание → review → правки → разрешение конфликтов (`rebase upstream/main`) → force-push (`--force-with-lease`)
    
- **Важно**: fork не синхронизируется автоматически; feature-ветки после принятия PR удаляются
    

### Применение

Стандарт для open source и корпоративных проектов с жёстким контролем доступа. Альтернативы: Feature Branch workflow (один репозиторий) или Gitflow.

## Статья 2: Code Review

### Основная идея

Code review — не просто поиск багов, а **распространение знаний** и поддержание единого стиля. Баг на review фиксится за минуты, в production — за часы.

### Ключевые моменты

- **Размер PR**: оптимально 30–60 минут проверки, после 400 строк качество падает
    
- **Как давать feedback**:
    
    - Фокус на коде, не на человеке
        
    - Объяснять причину ("почему?")
        
    - Уровни важности: MUST / SHOULD / CONSIDER / NIT
        
- **Что проверять**: корректность (граничные случаи, ошибки), читаемость, безопасность (SQL injection, права), тестируемость
    
- **Автоматизация**: линтеры (ESLint), тесты, статический анализ (SonarQube)
    

### Разногласия

Созвониться при затянувшемся споре. Уступать в мелочах (стиль кода). Главное — корректность и безопасность.

### Итог

Инвестиция в качество и развитие команды. Цель — сделать код лучше, а не показать превосходство.

## Статья 3: Git-теги и семантическое версионирование

### Основная идея

**Тег** — неизменяемая метка на коммите (в отличие от ветки). Используется для релизов: `v1.0.0`, `release-2023-10-15`.

### Типы тегов

|Тип|Команда|Хранит|Когда использовать|
|---|---|---|---|
|Легковесный|`git tag v1.0.0`|только имя|временные метки|
|Аннотированный|`git tag -a v1.0.0 -m "message"`|автор, дату, описание, GPG-подпись|**релизы** (стандарт)|

### Семантическое версионирование (SemVer)

`MAJOR.MINOR.PATCH` (например, 2.1.3)

- **MAJOR** — несовместимые изменения API
    
- **MINOR** — новая функциональность (совместимая)
    
- **PATCH** — исправления багов
    

### Полезные команды

bash

git tag -l "v1.*"                 # фильтр по шаблону
git push origin --follow-tags     # отправить только аннотированные теги
git describe --tags               # показать положение относительно последнего тега

### Итог

Теги — обещание, что версия протестирована. Не удаляйте и не перемещайте опубликованные теги релизов.

## Статья 4: Стратегии ветвления (Git Flow, GitHub Flow, Trunk-Based)

### Сравнение трёх стратегий

|Стратегия|Постоянные ветки|Вспомогательные ветки|Релизы|Подходит для|
|---|---|---|---|---|
|**Git Flow**|`main`, `develop`|`feature/*`, `release/*`, `hotfix/*`|чёткие, редкие (недели/месяцы)|корпоративное ПО, мобильные приложения|
|**GitHub Flow**|только `main`|любые описательные (`add-search`)|continuous deployment (несколько раз в день)|веб-сервисы, SaaS|
|**Trunk-Based**|только `trunk`/`main`|очень короткоживущие (дни)|через feature flags|Google, Facebook (высокая дисциплина)|

### Ключевые правила

- **Git Flow**: `main` всегда стабилен, `develop` — интеграция новых фич. `--no-ff` при слиянии
    
- **GitHub Flow**: код в `main` всегда готов к деплою. PR обязателен перед слиянием
    
- **Trunk-Based**: feature flags вместо долгих веток. Каждый commit должен быть рабочим
    

### Итог

Выбор зависит от продукта, команды и частоты релизов. Консистентность важнее идеальности. Начните с простого (GitHub Flow), усложняйте при необходимости.
