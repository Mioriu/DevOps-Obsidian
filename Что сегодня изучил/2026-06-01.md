Вот краткое саммари статьи «Виртуализация vs Контейнеризация» — с сохранением ключевых различий, архитектурных особенностей и практических выводов.

---

### Основная проблема

На bare-metal сервере нельзя безопасно и стабильно запустить несколько приложений из-за:

- **Конфликта зависимостей** (разные версии библиотек),
    
- **«Шумных соседей»** (одно приложение съедает ресурсы и ломает другие),
    
- **Рисков безопасности** (взлом одного → доступ ко всей ОС).
    

---

### Виртуализация (VM)

- **Гипервизор** делит физический сервер на изолированные виртуальные машины.
    
- **Каждая VM** содержит полноценную гостевую ОС со своим ядром.
    
- **Цена изоляции:** большие накладные расходы (гигабайты диска, гигабайты RAM под ОС, минуты на запуск).
    
- **Плюс:** максимальная изоляция, можно смешивать разные ОС (Linux + Windows).
    
- **Минус:** тяжеловесность, низкая плотность размещения.
    

---

### Контейнеризация

- **Общее ядро хоста** для всех контейнеров.
    
- **Изоляция через Namespaces** (контейнер не видит чужие процессы и файлы).
    
- **Ограничение ресурсов через Cgroups** (жесткие лимиты CPU/RAM).
    
- **Union File System** (слои + общие образы → экономия места и быстрый запуск).
    
- **Размер:** мегабайты, запуск за миллисекунды, тысячи контейнеров на узле.
    
- **Минус:** слабее изоляция, уязвимость ядра хоста угрожает всем контейнерам.
    

---

### Когда что выбирать

|Сценарий|Технология|
|---|---|
|Жёсткая безопасность, разнородные ОС (Windows+Linux), legacy-монолиты|**VM**|
|Микросервисы, CI/CD, высокая плотность, быстрые деплои|**Контейнеры**|

---

### Итог: не «или», а «и»

На практике технологии **комбинируют**:

1. Железо → **гипервизор** (нарезка на VM для аренды в облаке).
    
2. Внутри VM → **контейнеры** (удобство разработки и поставки софта).
    

> **VM делят железо, контейнеры упаковывают софт.**

### Основная идея

Docker построен на **клиент-серверной модели** с тремя главными компонентами: **Client**, **Daemon (dockerd)**, **Registry**. Понимание архитектуры нужно, чтобы правильно управлять контейнерами и отлаживать проблемы.

---

### 1. Docker Client (CLI)

- **Что делает:** принимает команды пользователя (`docker run`, `build`, `pull`), превращает их в REST-запросы и отправляет демону.
    
- **Важно:** клиент и демон **не обязаны** быть на одной машине — можно управлять удалённым сервером через `DOCKER_HOST=tcp://...`.
    

---

### 2. Docker Daemon (dockerd)

- **Что делает:** основная работа — сборка образов, скачивание, запуск/остановка контейнеров, управление сетями и томами.
    
- **Важно:** сам контейнеры не запускает, а делегирует это `containerd`.
    
- **Эволюция:** раньше был монолитом (перезапуск убивал контейнеры), теперь разделён на модули.
    

---

### 3. Container Runtime (containerd + runc)

- **containerd** (высокоуровневый):
    
    - скачивает образы, управляет слоями, создаёт/уничтожает контейнеры, настраивает сеть.
        
    - самостоятельный проект (CNCF), используется Kubernetes без Docker.
        
- **runc** (низкоуровневый):
    
    - вызывает ядро Linux, создаёт **Namespaces** и **Cgroups**, запускает процесс.
        
    - после запуска завершается, контейнер живёт как дочерний процесс containerd.
        
- **Результат:** перезапуск Docker Daemon **не останавливает** работающие контейнеры.
    

---

### 4. Docker Registry (хранилище образов)

- **Docker Hub** — публичный реестр по умолчанию (официальные образы: nginx, postgres и др.).
    
- **Приватные варианты:**
    
    - Docker Hub Private (платный)
        
    - Self-hosted: Harbor, Nexus, Docker Registry
        
    - Облачные: Yandex CR, AWS ECR, Google Artifact Registry, GitLab Container Registry
        
- **Операции:** `pull` (скачать), `push` (загрузить). Перед push нужно сделать `tag` с адресом реестра.
    

---

### Полная картина: что происходит при `docker run nginx`

1. **Client** → REST-запрос к **Daemon**.
    
2. **Daemon** проверяет, есть ли образ `nginx` локально. Нет → идёт в **Registry** (Docker Hub) и скачивает послойно (повторно использует уже имеющиеся слои).
    
3. **Daemon** даёт команду **containerd**: «создай контейнер».
    
4. **containerd** готовит файловую систему (слои), сеть и вызывает **runc**.
    
5. **runc** создаёт Namespaces (PID, NET, MNT), Cgroups, монтирует FS и запускает процесс `nginx`. После этого завершается.
    
6. Контейнер работает. **containerd** следит за его состоянием. Порт 8080 хоста проброшен на 80 контейнера.
    

---

### Ключевой вывод

> **Docker Client → Daemon → containerd → runc → ядро Linux**  
> Клиент управляет, демон оркестрирует, containerd готовит, runc запускает. Registry хранит образы.
