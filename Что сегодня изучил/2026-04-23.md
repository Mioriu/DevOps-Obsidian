
## Статья 1: Git Submodules (Подмодули)

### Основная идея

**Git submodule** — механизм включения одного Git-репозитория как подкаталога другого. Родительский репозиторий хранит **только ссылку на конкретный коммит** подмодуля, а не его файлы. Это позволяет версионировать внешние зависимости независимо.

### Ключевые моменты

**Добавление подмодуля:**

bash

git submodule add https://github.com/company/lib.git lib/lib
# создаётся файл .gitmodules и специальная запись-указатель

**Клонирование с подмодулями:**

bash

git clone --recurse-submodules <url>
# или после обычного clone:
git submodule update --init --recursive

**Работа внутри подмодуля:**

- Подмодуль — полноценный репозиторий, обычно в состоянии **detached HEAD**
    
- После изменений нужно закоммитить их в подмодуль, затем обновить ссылку в родителе:
    
    bash
    
    cd lib/lib && git commit -m "update" && git push
    cd ../.. && git add lib/lib && git commit -m "update submodule reference"
    

**Обновление подмодулей до последней версии:**

bash

git submodule update --remote   # тянет из ветки, указанной в .gitmodules

**Удаление подмодуля** (многошагово):

bash

git submodule deinit -f lib/lib
git rm -f lib/lib
git config -f .gitmodules --remove-section submodule.lib/lib
git commit -m "remove submoldule"
rm -rf .git/modules/lib/lib

### Типичные проблемы

- **Detached HEAD** — решается созданием ветки внутри подмодуля
    
- **Конфликты при merge** — нужно вручную выбрать нужную версию коммита подмодуля
    
- **Подмодули не инициализированы** у коллег — добавить инструкцию в README
    

### Альтернативы

- **Git Subtree** — копирует код в основной репозиторий (проще для потребителя, сложнее для автора)
    
- **Менеджеры пакетов** (npm, pip, Maven) — для публичных библиотек
    
- **Монорепозиторий** (Lerna, Bazel, Nx) — все проекты в одном репозитории
    

### Итог

Подмодули — мощный инструмент для точного контроля версий зависимостей, но требует дисциплины и понимания. Подходят, когда части проекта развиваются независимо, но должны работать в конкретных совместимых версиях.

## Статья 2: Git LFS (Large File Storage)

### Основная идея

Git LFS заменяет большие файлы в репозитории на **текстовые указатели** (pointer files), а сами файлы хранит на отдельном LFS-сервере. Репозиторий остаётся лёгким, версионирование — полным.

### Почему обычный Git плох для больших файлов

- Каждая версия файла хранится **целиком** (изменили байт в 100МБ → ещё 100МБ в истории)
    
- Клонирование качает всю историю всех файлов
    
- Платформы имеют лимиты: GitHub блокирует файлы >100 МБ
    

### Как работает LFS

**Указатель (pointer file):**

text

version https://git-lfs.github.com/spec/v1
oid sha256:4d7a2145b3c3b7f8c8e9d1a2b3c4d5e6...
size 524288000

**Базовые команды:**

bash

git lfs track "*.psd" "*.mp4"          # настроить отслеживание
git add .gitattributes && git commit   # закоммитить настройки!
git add large-file.psd                 # добавляется автоматически через LFS
git lfs ls-files                       # посмотреть LFS-файлы
git lfs pull --include="*.mp4"         # загрузить только определённые типы

**Миграция существующего репозитория:**

bash

git lfs migrate info --everything                     # анализ
git lfs migrate import --include="*.psd,*.mp4" --everything  # миграция
git push --force --all                                # force push после миграции

### Продвинутые возможности

**Блокировка файлов** (для предотвращения конфликтов):

bash

git lfs track "*.psd" --lockable
git lfs lock design.psd
git lfs locks   # посмотреть
git lfs unlock design.psd

**Частичное клонирование** (без автоматической загрузки LFS-файлов):

bash

GIT_LFS_SKIP_SMUDGE=1 git clone <url>
git lfs pull --include="assets/icons/*"

**Очистка:**

bash

git lfs prune --days=7   # удалить старые локальные LFS-файлы

### Лучшие практики

- **Хранить в LFS**: бинарные файлы, которые редко меняются: изображения, видео, датасеты, архивы (>1-5 МБ)
    
- **НЕ хранить в LFS**: исходный код, часто меняющиеся файлы, маленькие бинарные файлы
    
- Всегда коммитить `.gitattributes`
    
- Настроить CI/CD на поддержку LFS
    

### Итог

Git LFS прозрачно решает проблему больших файлов. После настройки вы работаете как с обычными файлами, но репозиторий не раздувается. Ключевое ограничение: требуется поддержка LFS на сервере и у всех участников.

## Статья 3: Git Hooks

### Основная идея

**Git hooks** — скрипты, автоматически запускаемые Git при определённых событиях (commit, push, merge, receive). Позволяют автоматизировать проверки, форматирование, тесты и развёртывание.

### Где находятся hooks

bash

.git/hooks/                    # локальные hooks (не версионируются)
# .sample файлы — примеры, нужно убрать расширение и сделать исполняемым

### Основные клиентские hooks

|Hook|Событие|Типичное использование|
|---|---|---|
|`pre-commit`|перед созданием коммита|линтер, проверка синтаксиса, поиск секретов/console.log|
|`prepare-commit-msg`|перед открытием редактора|добавление номера задачи из ветки, шаблон сообщения|
|`commit-msg`|после ввода сообщения|валидация формата коммита (Conventional Commits)|
|`pre-push`|перед push|запуск тестов, запрет push в protected ветки|
|`post-merge`|после успешного merge|`npm install` при изменении package.json|

### Пример pre-commit (фрагменты)

bash

# Проверка на console.log
if git diff --cached --name-only | xargs grep -l "console\."; then
    echo "❌ Found console.log" && exit 1
fi
# Проверка размера файлов (>5MB)
if [ "$(ls -l "$file" | awk '{print $5}')" -gt 5242880 ]; then
    echo "❌ File too large, use Git LFS" && exit 1
fi

### Серверные hooks

|Hook|Событие|Использование|
|---|---|---|
|`pre-receive`|перед принятием push|запрет force push в main, проверка размера файлов|
|`update`|для каждой ветки|проверка прав пользователя, защита production веток|
|`post-receive`|после успешного push|авторазвёртывание, уведомления в Slack, триггер CI|

### Проблема: hooks не версионируются

**Решения:**

1. Хранить hooks в `.githooks/`, настроить `git config core.hooksPath .githooks`
    
2. Использовать инструменты:
    
    - **Husky** (JS): `npx husky add .husky/pre-commit "npm test"`
        
    - **pre-commit** (Python): `.pre-commit-config.yaml` + `pre-commit install`
        
    - **Lefthook** (универсальный): `lefthook.yml`
        

### Пропуск hooks (для экстренных случаев)

bash

git commit --no-verify -m "emergency fix"
git push --no-verify

### Лучшие практики

- Hooks должны быть **быстрыми** (секунды, не минуты)
    
- Всегда оставлять возможность пропуска (`--no-verify`)
    
- Логировать ошибки в `.git/hooks.log`
    
- Не делать hooks слишком строгими — начните с предупреждений
    

### Итог

Git hooks — встроенный механизм автоматизации, который превращает хаотичную разработку в контролируемый процесс. Правильно настроенные hooks экономят часы code review и предотвращают типичные ошибки. Ключ к успеху: баланс между автоматизацией и гибкостью. Используйте инструменты (Husky, pre-commit) для версионирования и управления hooks в команде.

Очень полезная статья по хукам, есть полезные кейсы, помогает автоматизации процессов поддержания кода в едином стиле, автоматического тестирования, деплоя, триггера CI и т.д
