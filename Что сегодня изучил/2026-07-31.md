## Архитектура кластера: control plane, nodes, зачем оркестратор

### Основная идея

Один сервер и Compose упираются в потолок при росте нагрузки: нет распределения по машинам, нет переезда контейнеров при отказе сервера, обновления вызывают даунтайм. Решает это оркестратор — Kubernetes — слой, который видит пул серверов целиком и декларативно приводит реальность к описанному желаемому состоянию.

### Ключевые моменты

- **Декларативность**: вы описываете `spec` (желаемое), кластер пишет `status` (текущее) и непрерывно сводит одно к другому — в отличие от Ansible/Terraform, где сверка разовая
- **Control plane**: kube-apiserver (единая точка входа, auth/authz/валидация, работает с etcd), etcd (распределённое key-value хранилище всего состояния, Raft-кворум, нечётное число узлов), kube-scheduler (фильтрация → ранжирование нод → назначение), kube-controller-manager (десятки контроллеров, паттерн Watch → Compare → Reconcile)
- **Worker node**: kubelet (агент, запускает контейнеры через CRI), container runtime (containerd/CRI-O), kube-proxy (маршрутизация трафика к сервисам через iptables/IPVS), CNI-плагин (Flannel/Calico/Cilium — плоская сеть между подами)
- **Pod** — минимальная единица Kubernetes, не контейнер напрямую
- Вся координация идёт только через API server и etcd — компоненты не общаются друг с другом напрямую, поэтому независимо перезапускаемы
- Control plane сам работает как поды (static pods) в namespace `kube-system`

### Итог

Понимание архитектуры объясняет, почему кластер самовосстанавливается без ручного вмешательства и как диагностировать, что сломалось (apiserver — нет доступа, etcd — кластер мёртв, scheduler — поды висят в Pending, kubelet — нода NotReady).

## kubectl и первый Pod

### Основная идея

kubectl — тонкий клиент к API server, вся логика в кластере. Показано, как создать под императивно и манифестом, разобраны статусы пода и базовый цикл отладки.

### Ключевые моменты

- **kubeconfig** (`~/.kube/config`) хранит адреса кластеров, доступы и контексты; переключение — `kubectl config use-context`
- Базовый паттерн команд: `kubectl <действие> <тип> <имя>`
- `kubectl run web --image=nginx` — быстрый способ; `-o wide` показывает IP и ноду
- **Отладочная связка**: `get pods` (статус) → `describe pod` (секция Events) → `logs` (причина падения), `--previous` для упавшего контейнера
- Статусы: `Pending`, `ContainerCreating`, `Running`, `Completed`, `ImagePullBackOff` (проблема с образом/registry), `CrashLoopBackOff` (падает само приложение)
- **Голый под смертен**: `kubectl delete pod` не пересоздаётся — за подом без контроллера никто не следит, `restartPolicy: Always` перезапускает только контейнер внутри живой ноды
- Манифест — 4 верхнеуровневых поля: `apiVersion`, `kind`, `metadata`, `spec`; применяется через `kubectl apply -f`
- `spec` пишет пользователь, `status` — кластер (видно через `-o yaml`)
- **Sidecar**-паттерн: несколько контейнеров в поде делят сеть (localhost) и живут/умирают вместе; для независимых сервисов — отдельные поды

### Итог

Голые поды в реальной работе не используются — нужен контроллер (Deployment), который держит желаемое состояние и пересоздаёт поды при сбоях.

## Зачем нужен Deployment

### Основная идея

Deployment — основной рабочий объект для приложений: задаёт шаблон пода и число копий, а кластер постоянно сверяет это состояние с реальностью, обеспечивая self-healing, масштабирование и обновления без даунтайма.

### Ключевые моменты

- Манифест: `apiVersion: apps/v1`, `spec.replicas`, `spec.template` (шаблон пода), `spec.selector.matchLabels` — обязан совпадать с метками в `template.metadata.labels`
- **Иерархия**: Deployment → ReplicaSet (следит, чтобы число подов = replicas, привязан к одной версии шаблона по хэшу) → Pods
- Self-healing: удаление пода под Deployment немедленно компенсируется ReplicaSet; чинить нужно шаблон, а не отдельный под
- Масштабирование: правка `replicas` в манифесте (декларативно) или `kubectl scale --replicas=N` (императивно, но манифест в Git расходится с реальностью); `--replicas=0` — временное отключение без удаления
- **Rolling update**: смена образа → новый ReplicaSet, поэтапный перевод трафика; темп задаётся `maxSurge`/`maxUnavailable` (по умолчанию 25%/25%); готовность пода без probes считается по факту запуска контейнера
- Старый ReplicaSet хранится (масштабирован в 0) для отката: `kubectl rollout undo` (`--to-revision=N`), история — `rollout history`, глубина хранения — `revisionHistoryLimit` (по умолчанию 10)
- Стратегия `Recreate` — грубая (сервис лежит между удалением старых и созданием новых подов), нужна для несовместимых версий/эксклюзивных блокировок; по умолчанию `RollingUpdate`
- `kubectl rollout restart` — перекат подов без изменения шаблона (для перечитывания конфигов/секретов)

### Итог

Решает все проблемы Compose: даунтайм при обновлении устраняется rolling update, смерть ноды/пода компенсируется ReplicaSet. Правило дисциплины: после `scale`/`rollout undo` манифест в Git нужно поправить вручную, иначе следующий `apply` откатит изменения.

## YAML-манифесты, Labels и селекторы

### Основная идея

Манифест — YAML-описание объекта с 4 полями (`apiVersion`, `kind`, `metadata`, `spec`); пара `kind`+`metadata.name` идентифицирует объект. Метки (labels) — единственный механизм группировки объектов в Kubernetes, всё связывание идёт через селекторы, а не через ссылки по именам.

### Ключевые моменты

- `apiVersion` = `группа/версия` (core-группа без имени → просто `v1`); узнать соответствия — `kubectl api-resources`
- `kubectl explain <путь.через.точку>` — встроенная документация по полям, актуальная для версии кластера, `--recursive` — всё дерево
- Несколько объектов в одном файле через `---`; альтернатива — `kubectl apply -f manifests/` на директорию
- Ловушки YAML: значения env обязаны быть в кавычках (иначе `"8080"` станет числом, `"false"` — булевым); `containers` — список (дефис), `matchLabels` — словарь (без дефиса)
- **Labels**: произвольные пары ключ-значение в `metadata`, единственный способ группировки — ReplicaSet находит свои поды по меткам, а не по спискам имён; снятие метки с пода немедленно выбивает его из-под контроллера ("осиротевший" под)
- Управление: `kubectl label pod X debug=true` / `kubectl label pod X debug-` (снять)
- **Селекторы**: флаг `-l` в командах (`app=web`, через запятую — AND, `in (...)` — список значений, `!=` — исключение); в объектах — `matchLabels` (простая форма) или `matchExpressions` с `In`/`NotIn`/`Exists`
- **Annotations** — тоже ключ-значение в metadata, но НЕ участвуют в селекторах; для произвольной информации (описания, ссылки, change-cause). Правило: если по значению нужно будет фильтровать — метка, иначе — аннотация
- `kubectl apply --dry-run=server` (проверка без применения) и `kubectl diff -f` (аналог `git diff`/`terraform plan`)
- Генерация манифестов: `kubectl create ... --dry-run=client -o yaml > file.yaml`, либо `kubectl get ... -o yaml` с последующей зачисткой служебных полей (`status`, `creationTimestamp`, `resourceVersion`, `uid`, `managedFields`)

### Итог

Метки и селекторы — фундаментальный механизм связности объектов Kubernetes; их разрыв (случайное снятие метки) рвёт связь контроллер-под мгновенно и без предупреждений, что важно учитывать при отладке.
