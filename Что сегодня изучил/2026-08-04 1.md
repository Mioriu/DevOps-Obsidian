## Статья 1: Probes — liveness, readiness, startup

### Проблема: `Running` ≠ работает

Статус `Running` означает только то, что главный процесс контейнера существует. При этом приложение может:

- Прогреваться (отвечает ошибками)
    
- Зависнуть в deadlock
    
- Исчерпать пул соединений к БД
    

**Probes** — периодические проверки здоровья контейнера.

### Три пробы

|Проба|Вопрос|Реакция на провал|
|---|---|---|
|**livenessProbe**|Приложение живо?|kubelet **перезапускает** контейнер|
|**readinessProbe**|Готово принимать трафик?|Под убирается из **Endpoints** сервисов|
|**startupProbe**|Стартовало ли вообще?|До успеха остальные пробы выключены|

### Способы проверки

yaml

# HTTP-запрос (для веб-приложений)
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
# TCP-соединение (для БД, брокеров)
livenessProbe:
  tcpSocket:
    port: 5432
# Выполнение команды (код 0 = успех)
livenessProbe:
  exec:
    command: ["pg_isready", "-U", "postgres"]

### Параметры

|Параметр|Что задаёт|По умолчанию|
|---|---|---|
|`initialDelaySeconds`|Пауза перед первой проверкой|0|
|`periodSeconds`|Интервал между проверками|10|
|`timeoutSeconds`|Таймаут на одну проверку|1|
|`failureThreshold`|Сколько провалов подряд до срабатывания|3|
|`successThreshold`|Сколько успехов подряд для восстановления|1|

**Арифметика:** `periodSeconds=10`, `failureThreshold=3` → между поломкой и реакцией до 30 секунд.

### Liveness — проверка живости

- Отвечает на вопрос: **«имеет ли смысл перезапустить процесс?»**
    
- Используется для deadlock, зависаний
    
- **❌ Не проверяет зависимости!** (БД упала → все поды перезапускаются → бесполезный шторм)
    
- **✅ Проверяет только сам процесс**
    

### Readiness — проверка готовности

- Отвечает на вопрос: **«можно ли слать сюда трафик?»**
    
- Провал → под выпадает из **Endpoints** сервиса (трафик не идёт)
    
- Восстановление → под возвращается в строй
    
- **✅ Можно проверять зависимости** (БД недоступна → под не готов)
    
- Закрывает:
    
    - **Прогрев** при старте (READY 0/1, трафик не идёт)
        
    - **Rolling update** — новый под считается готовым только после readiness
        

### Startup — для медленного старта

- Решает проблему: приложение стартует 5 минут, liveness с `initialDelaySeconds=300` слишком долго реагирует на зависания
    
- Пока startup не прошла, liveness и readiness **выключены**
    
- У startup большой бюджет на провалы
    

yaml

startupProbe:
  httpGet:
    path: /healthz
    port: 8080
  periodSeconds: 10
  failureThreshold: 30   # до 5 минут на старт

### Жизнь пода с тремя пробами

1. **Старт** — работает только startup (до 5 минут)
    
2. **Startup прошла** → включаются liveness и readiness
    
3. **Readiness прошла** → под попадает в Endpoints → трафик
    
4. **Liveness** → сторожит зависания, перезапускает при необходимости
    
5. **Readiness** → управляет участием в балансировке
    

### Отладка проб

bash

kubectl describe pod web-xxx

**Events:**

text

Warning  Unhealthy  12s  kubelet  Liveness probe failed: HTTP probe failed with statuscode: 500
Normal   Killing    12s  kubelet  Container web failed liveness probe, will be restarted

## Статья 2: Resources — requests, limits, QoS

### Проблема: контейнеры без ограничений

Без `requests` scheduler не знает, сколько ресурсов нужно поду → размещает вслепую. Без `limits` одно приложение может задавить соседей.

### Requests и limits

|Поле|Что задаёт|
|---|---|
|**`requests`**|Сколько ресурсов **гарантированно** резервируется под контейнер|
|**`limits`**|Потолок, выше которого контейнеру потреблять нельзя|

- **Между requests и limits** — гибкая зона: контейнер может брать свободные ресурсы, пока они есть на ноде.
    

### Единицы

|Ресурс|Единицы|Примеры|
|---|---|---|
|**CPU**|Ядра, millicores (1000m = 1 ядро)|`cpu: "2"`, `cpu: 100m` (0.1 ядра)|
|**Memory**|Mi, Gi (двоичные)|`memory: 512Mi`, `memory: 2Gi`|

**Важно:** в манифестах используют двоичные суффиксы (`Mi`, `Gi`), не десятичные (`M`, `G`).

### CPU и память ведут себя по-разному

||CPU|Memory|
|---|---|---|
|**Сжимаемый?**|Да|Нет|
|**Удар в лимит**|Троттлинг (замедление)|**OOMKilled** (контейнер убит)|
|**Симптом**|Растут задержки|`Restart Count` растёт, `Reason: OOMKilled`|

**OOMKilled:**

text

Last State: Terminated
  Reason: OOMKilled
  Exit Code: 137

### Как считает scheduler

- **Scheduler смотрит только на `requests`.** Сумма requests подов на ноде ≤ ёмкость ноды.
    
- **Limits в планировании не участвуют.** Сумма limits может превышать ёмкость ноды (переподписка).
    

**Следствия:**

- **Завышенные requests** → кластер требует больше нод, чем нужно
    
- **Заниженные/отсутствующие requests** → ноды переполняются фактическим потреблением
    

**`Pending` с причиной:**

text

Events:
  Warning  FailedScheduling  0/3 nodes available: 3 Insufficient memory.

### QoS-классы

|Класс|Условие|Кого выселяют первым|
|---|---|---|
|**Guaranteed**|`requests = limits` по CPU и памяти у всех контейнеров|**Последними**|
|**Burstable**|Есть requests, но не равны limits|Вторыми|
|**BestEffort**|Ресурсы не указаны вообще|**Первыми**|

**Применение:** при нехватке памяти на ноде kubelet выселяет поды. Порядок определяется QoS-классом. `BestEffort` уходят первыми, `Guaranteed` держатся до последнего.

bash

kubectl describe pod web-xxx
# QoS Class: Burstable

### Как выбирать значения

1. Запустить приложение с примерными значениями
    
2. Посмотреть фактическое потребление:
    
    bash
    
    kubectl top pods
    # web-xxx: CPU 12m, Memory 187Mi
    
3. `requests` — по типичному уровню (≈ 200Mi)
    
4. `limits` — по пиковому потреблению + запас
    
5. Периодически пересматривать
    

### LimitRange и ResourceQuota

**LimitRange** — задаёт умолчания и рамки для контейнеров в namespace:

yaml

apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: staging
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      default:
        cpu: 500m
        memory: 512Mi

**ResourceQuota** — ограничивает сумму ресурсов во всём namespace:

yaml

apiVersion: v1
kind: ResourceQuota
metadata:
  name: staging-quota
  namespace: staging
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    pods: "50"

### Производственный Deployment

yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: myapp:1.4
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 200m
              memory: 256Mi
            limits:
              memory: 256Mi       # память: requests = limits
              # CPU без limits — пики берут свободные ядра
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080

### Отладка ресурсов

|Симптом|Где видно|Что означает|
|---|---|---|
|`Pending` + `Insufficient`|`describe pod`, Events|requests > свободного на любой ноде|
|`OOMKilled`, exit code 137|`describe pod`, Last State|Контейнер превысил лимит памяти|
|Растут задержки при живых подах|`kubectl top pods` у потолка CPU|Троттлинг по лимиту CPU|
|Поды внезапно пересоздаются на других нодах|События выселения на ноде|Нехватка памяти на ноде, выселение по QoS|

**Диагностика:** `get` → `describe` → `top` → правка `requests`/`limits`.
