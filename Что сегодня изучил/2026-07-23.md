## Статья 1: GitLab Runners — типы, executor-ы, регистрация

### Что такое Runner

Runner — агент, который выполняет джобы из `.gitlab-ci.yml`. GitLab — интерфейс, раннер — исполнитель.

text

GitLab → Runner → Окружение выполнения

### Shared vs Specific Runners

| Тип          | Описание                                                            | Когда использовать                                  |
| ------------ | ------------------------------------------------------------------- | --------------------------------------------------- |
| **Shared**   | Общий для всех проектов (есть на [gitlab.com](https://gitlab.com/)) | Простые задачи, не нужен доступ к внутренней сети   |
| **Specific** | Привязан к проекту/группе, настраивается вами                       | Доступ к VPN, специфический софт, GPU, безопасность |

### Executor — как Runner выполняет джобы

| Executor       | Как работает                        | Плюсы                             | Минусы                                   | Когда использовать               |
| -------------- | ----------------------------------- | --------------------------------- | ---------------------------------------- | -------------------------------- |
| **Shell**      | Прямо на хосте                      | Просто, быстро, прямой доступ     | Нет изоляции, нужны зависимости на хосте | Деплой, простые скрипты          |
| **Docker**     | Каждая джоба в отдельном контейнере | Полная изоляция, чистое окружение | Оверхед на создание контейнера           | Сборка, тесты — **дефолтный**    |
| **Kubernetes** | Каждая джоба — Pod в K8s            | Автоскейлинг, экономия ресурсов   | Сложнее в настройке                      | Плавающая нагрузка, уже есть K8s |

### Регистрация раннера

bash

# Установка (Ubuntu)
curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | bash
apt install gitlab-runner
# Регистрация (интерактивно)
gitlab-runner register
# Или неинтерактивно
gitlab-runner register \
  --non-interactive \
  --url "https://gitlab.example.com" \
  --token "$RUNNER_TOKEN" \
  --executor "docker" \
  --docker-image "alpine:latest"

Конфиг раннера: `/etc/gitlab-runner/config.toml`

toml

concurrent = 4   # максимум параллельных джоб

### Теги — маршрутизация джоб к раннерам

yaml

# .gitlab-ci.yml
build-job:
  tags:
    - docker
    - linux
  script: make build

Джоба запустится на раннере, у которого есть **все** указанные теги.

## Статья 2: Артефакты, кэш, переменные, environments

### Artifacts vs Cache

||Artifacts|Cache|
|---|---|---|
|**Назначение**|Результат работы джобы (передаётся между стейджами)|Ускорение повторных запусков|
|**Хранение**|В GitLab (можно скачать)|На раннере (или в S3)|
|**Передаётся между**|Разными стейджами одного пайплайна|Разными пайплайнами|
|**Потеря — критично?**|Да (артефакты нужны для деплоя)|Нет (кэш — оптимизация, без него всё работает медленнее)|

### Artifacts

yaml

build:
  script: npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 week   # срок хранения

**Автоматическая передача:** джобы в следующих стейджах получают артефакты автоматически.

**Тестовые отчёты:**

yaml

test:
  artifacts:
    reports:
      junit: report.xml   # в MR появится вкладка с тестами

**С `needs`:**

yaml

test-backend:
  needs:
    - job: build-backend
      artifacts: true      # скачать артефакты

### Cache

yaml

install-deps:
  cache:
    key: ${CI_COMMIT_REF_SLUG}   # отдельный кэш для каждой ветки
    paths:
      - node_modules/
  script: npm install

**Лучший key:**

yaml

cache:
  key:
    files:
      - package-lock.json   # кэш инвалидируется при изменении lock-файла
  paths:
    - node_modules/

**Cache policy:**

- `pull-push` (дефолт) — скачать и загрузить
    
- `pull` — только скачать (для тестов)
    
- `push` — только загрузить (для джобы, обновляющей кэш)
    

### Variables — переменные

**Где задаются:**

- `.gitlab-ci.yml` (для дефолтов)
    
- GitLab UI (Settings → CI/CD → Variables) — для секретов
    
- На уровне группы
    

**Типы в UI:**

- **Variable** — обычная
    
- **File** — GitLab создаёт временный файл, переменная содержит путь к нему (для сертификатов, kubeconfig)
    
- **Masked** — не показывается в логах
    
- **Protected** — доступна только в protected ветках
    

**Предопределённые переменные (самые частые):**

yaml

$CI_COMMIT_SHORT_SHA          # короткий хеш: a1b2c3d4
$CI_COMMIT_BRANCH             # имя ветки: main
$CI_COMMIT_TAG                # тег: v1.2.3
$CI_PIPELINE_SOURCE           # push, merge_request_event, web, schedule
$CI_REGISTRY_IMAGE            # полный путь образа в GitLab Registry
$CI_PROJECT_NAMESPACE         # namespace: mycompany/backend

**Приоритет (от высшего к низшему):**

1. Trigger variables
    
2. Project-level CI/CD variables
    
3. Group-level CI/CD variables
    
4. Instance-level CI/CD variables
    
5. `.gitlab-ci.yml` variables
    
6. `.gitlab-ci.yml` job-level variables
    

### Environments

yaml

deploy-staging:
  environment:
    name: staging
    url: https://staging.example.com
  script: ./deploy.sh staging
deploy-prod:
  environment:
    name: production
    url: https://example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual

**Что даёт:**

- В GitLab → Operate → Environments видно, что задеплоено где
    
- История деплоев (кто, когда, какой коммит)
    
- Кнопка отката
    

**Динамические environments (review apps):**

yaml

deploy-review:
  environment:
    name: review/$CI_MERGE_REQUEST_IID
    url: https://$CI_MERGE_REQUEST_IID.review.example.com
    on_stop: stop-review
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

## Статья 3: Сборка Docker-образов в CI

### Пайплайн сборки

text

git push → build → registry → deploy

### `image` и `services`

**`image`** — Docker-образ для выполнения джобы:

yaml

test:
  image: python:3.11-slim
  script: pytest

**`services`** — дополнительные контейнеры (БД, Redis и т.д.):

yaml

integration-tests:
  image: python:3.11-slim
  services:
    - name: postgres:15
      alias: db        # доступен по хосту db
    - name: redis:7-alpine
      alias: cache
  variables:
    DATABASE_URL: "postgresql://test:test@db:5432/testdb"

### Сборка Docker-образов: DinD vs Kaniko

||Docker-in-Docker (DinD)|Kaniko|
|---|---|---|
|**Как работает**|Поднимает service с Docker-демоном, подключается к нему|Собирает образ без Docker-демона|
|**Требует privileged**|✅ Да|❌ Нет|
|**Безопасность**|Ниже (привилегированный режим)|Выше|
|**Синтаксис**|Привычный `docker build`|Специфичный `/kaniko/executor`|
|**Когда использовать**|Свои раннеры, контролируете окружение|Shared раннеры, безопасность в приоритете|

**DinD:**

yaml

build-image:
  image: docker:24
  services:
    - docker:24-dind
  script:
    - docker build -t myapp:latest .
    - docker push myapp:latest

**Kaniko:**

yaml

build-image:
  image:
    name: gcr.io/kaniko-project/executor:v1.19.2-debug
    entrypoint: [""]
  script:
    - /kaniko/executor
      --context "${CI_PROJECT_DIR}"
      --dockerfile "${CI_PROJECT_DIR}/Dockerfile"
      --destination "${CI_REGISTRY_IMAGE}:${CI_COMMIT_SHORT_SHA}"

### Registry — где хранить образы

**GitLab Container Registry (встроенный):**

yaml

before_script:
  - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
script:
  - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
  - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

**Nexus Repository (self-hosted):**

yaml

variables:
  NEXUS_REGISTRY: nexus.company.internal:5000
before_script:
  - docker login -u $NEXUS_USER -p $NEXUS_PASSWORD $NEXUS_REGISTRY

### Тегирование образов

**Плохо:** только `latest` — не знаете, какой коммит, откат невозможен.

**Правильно: commit SHA:**

yaml

- docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .

**Правильно: semver по git-тегам:**

yaml

- docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_TAG .
rules:
  - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/

**Комбинированный подход (рекомендуется):**

yaml

# Всегда тег коммитом
- docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
- docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
# Если main → latest
- if [ "$CI_COMMIT_BRANCH" == "main" ]; then
    docker tag $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA $CI_REGISTRY_IMAGE:latest
    docker push $CI_REGISTRY_IMAGE:latest
  fi
# Если git-тег → semver
- if [ -n "$CI_COMMIT_TAG" ]; then
    docker tag $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA $CI_REGISTRY_IMAGE:$CI_COMMIT_TAG
    docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_TAG
  fi

**Результат:**

- commit `a1b2c3d4` → `myapp:a1b2c3d4`
    
- main → `myapp:latest`
    
- git-тег `v1.2.3` → `myapp:v1.2.3`
