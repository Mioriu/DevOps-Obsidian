## Проблема: эфемерность возвращается

- Записываемый слой контейнера умирает вместе с контейнером.
    
- В кластере под пересоздаётся при деплое, выселяется, переезжает на другую ноду → данные на диске ноды не помогут.
    

**Задача распадается на два уровня:**

1. **Временные данные** (кэш, обмен между контейнерами) → `emptyDir`
    
2. **Данные, которые должны пережить что угодно** (БД, состояние) → `PV` + `PVC`
    

---

## Тома пода — общая механика

Том объявляется в `volumes` на уровне пода, контейнеры подключают через `volumeMounts`.

---

## emptyDir — временное хранилище

- Пустая директория, создаётся при запуске пода на ноде.
    
- Живёт **столько же, сколько под**.
    
- Контейнер упал и перезапустился → данные на месте. Под удалён или переехал → данные исчезли.
    

yaml

volumes:
  - name: cache
    emptyDir: {}

**Вариант в памяти (tmpfs):**

yaml

volumes:
  - name: scratch
    emptyDir:
      medium: Memory
      sizeLimit: 100Mi

**Применение:** кэш, временные файлы, обмен между контейнерами внутри пода.

---

## hostPath — монтирование с диска ноды

- Монтирует директорию с хоста в контейнер.
    
- Данные привязаны к конкретной ноде.
    
- Scheduler не знает о содержимом.
    

yaml

volumes:
  - name: docker-sock
    hostPath:
      path: /var/run/docker.sock

**Применение:** агенты мониторинга, сбор логов. В манифестах обычных приложений — почти всегда ошибка.

## Постоянное хранилище: PV и PVC

**Проблема:**

- Прямо указывать в манифесте пода ID облачного диска или адрес NFS → жёсткая привязка к инфраструктуре.
    
- Разработчик должен описывать только свои потребности (10 ГБ), а не детали дисков.
    

**Решение: разделение ролей**

|Объект|Кто создаёт|Что содержит|
|---|---|---|
|**PV** (PersistentVolume)|Администратор / StorageClass|Детали хранилища: размер, путь, драйвер|
|**PVC** (PersistentVolumeClaim)|Разработчик приложения|Требования: размер, режим доступа|

Кластер связывает PVC с подходящим PV — это называется **binding**.

**В манифесте пода:**

yaml

volumes:
  - name: data
    persistentVolumeClaim:
      claimName: pgdata

## AccessModes — режимы доступа

|Режим|Сокращение|Что означает|
|---|---|---|
|**ReadWriteOnce**|RWO|Чтение-запись с одной ноды|
|**ReadOnlyMany**|ROX|Только чтение со многих нод|
|**ReadWriteMany**|RWX|Чтение-запись со многих нод|

- **RWO** — рабочая лошадка, поддерживается любым хранилищем.
    
- **RWX** — требует NFS или подобных хранилищ.
    

---

## StorageClass — динамическое создание PV

- Статический путь: администратор создаёт PV руками (неудобно).
    
- Динамический путь: **StorageClass** описывает, как заказывать хранилище (драйвер, тип диска). PVC указывает `storageClassName`, и PV создаётся автоматически.
    

yaml

spec:
  storageClassName: ssd
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi

- В managed-кластерах StorageClass настроен из коробки, один из них — класс по умолчанию.
    
- За создание отвечают CSI-драйверы (Container Storage Interface).
    

bash

kubectl get storageclass

---

## reclaimPolicy — что происходит при удалении PVC

|Политика|Что происходит|
|---|---|
|**Retain**|PV и данные остаются, ждут ручного решения|
|**Delete**|PV удаляется вместе с реальным диском и данными|

**Важно:** у динамических томов по умолчанию `Delete`.  
`kubectl delete pvc pgdata` → удаление диска с БД → безвозвратно!

Для ценных данных политику меняют на `Retain`.

## Пример: Postgres с постоянным хранилищем

yaml

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pgdata
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: db
spec:
  replicas: 1
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: postgres
          image: postgres:16
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: POSTGRES_PASSWORD
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: pgdata

**Важно:** `replicas: 1` — RWO-том подключается только к одной ноде. Масштабирование БД — через StatefulSet или managed-сервис.

## Отладка хранилища

bash

kubectl get pvc
kubectl get pv

**Статусы PVC:**

- `Bound` → связана с PV, всё хорошо.
    
- `Pending` → не с чем связаться. Причина в `kubectl describe pvc`.
    

**Цепочка:**

1. Под висит в `Pending` → событие про unbound claim
    
2. PVC в `Pending` → `describe pvc` → причина (нет StorageClass, нет подходящего PV, неподдерживаемый access mode)
