Задача 1: Знакомство с правами и пользователями

Создай пользователя devops_app. Создай директорию /opt/myapp и выдай права на неё только этому пользователю и группе developers (которую тоже нужно создать). Проверь, что root по-прежнему может зайти в папку, а твой основной пользователь (без прав) — нет.

💡 Подсказки
  • Используй useradd и groupadd с флагом -m или без, в зависимости от нужного тебе профиля.
  • Для изменения владельца: chown.
  • Для прав: chmod 770 (владелец и группа).
  • Проверить можно командой su или sudo -u.
✅ Решение 
# 1. Создаём группу
sudo groupadd developers

# 2. Создаём пользователя и добавляем в группу
sudo useradd -m -G developers devops_app

# 3. Создаём директорию
sudo mkdir -p /opt/myapp

# 4. Меняем владельца и группу
sudo chown devops_app:developers /opt/myapp

# 5. Ставим права (чтение/запись/вход только для владельца и группы)
sudo chmod 770 /opt/myapp

# 6. Проверка
# root может всё:
sudo ls /opt/myapp
# Текущий юзер (если не в группе) - отказ:
ls /opt/myapp  # выдаст Permission denied
# Добавь себя в группу, чтобы проверить доступ:
sudo usermod -aG developers $USER
# (потребуется перелогин)
# Заходим под devops_app:
sudo -u devops_app ls /opt/myapp

Задача 2: Поиск "убийцы" места на диске

Твой диск / заполнен на 95%. Найди топ-5 самых больших файлов в системе и определи, какой процесс прямо сейчас пишет больше всего данных на диск.

💡 Подсказки
  • Используй du в связке с sort и head.
  • Начинай поиск с корня, но исключай /proc и виртуальные ФС.
  • Чтобы найти процесс-писатель: iotop (если установлен) или lsof + find.
  • В крайнем случае смотри в /proc.
✅ Решение

Поиск больших файлов:

sudo find / -type f -size +100M -exec ls -lh {} \; 2>/dev/null | awk '{print $5, $NF}' | sort -hr | head -5
# Или через du (поиск больших директорий):
sudo du -ahx / 2>/dev/null | sort -rh | head -10
# x - оставаться в одной файловой системе

Поиск активного писателя:

# Вариант А: Использовать iotop (нужен пакет iotop)
sudo iotop -oP

# Вариант Б: Через /proc без доп. пакетов
for pid in /proc/[0-9]*; do
    wbytes=$(awk '/write_bytes/ {print $2}' $pid/io 2>/dev/null)
    if [ -n "$wbytes" ] && [ "$wbytes" -gt 0 ]; then
        name=$(cat $pid/comm)
        echo "$wbytes bytes - PID: $(basename $pid) ($name)"
    fi
done | sort -rn | head -5

Задача 4: Bash-скриптинг и анализ логов

Напиши Bash-скрипт analyze_log.sh, который принимает путь к access-логу Nginx (обычный текстовый формат) и выводит:
1) Топ-5 IP по количеству запросов.
2) Топ-5 эндпоинтов (URL).
3) Количество ошибок (коды ответа 4xx и 5xx).

💡 Подсказки
  • Используй awk для разбора колонок. IP — обычно первое поле, URL — седьмое, код — девятое.
  • Формат combined лога: $remote_addr - ... "METHOD /url HTTP/1.1" $status ...
  • sort | uniq -c | sort -rn | head -5 — твои лучшие друзья.
  • Не забудь сделать скрипт исполняемым.
✅ Решение 
#!/bin/bash
LOGFILE=$1

if [ -z "$LOGFILE" ]; then
    echo "Usage: $0 /path/to/access.log"
    exit 1
fi

echo "=== Top 5 IPs ==="
awk '{print $1}' $LOGFILE | sort | uniq -c | sort -rn | head -5

echo -e "\n=== Top 5 Endpoints ==="
awk '{print $7}' $LOGFILE | sort | uniq -c | sort -rn | head -5

echo -e "\n=== Error Count (4xx/5xx) ==="
awk '{print $9}' $LOGFILE | grep -E '^[45][0-9]{2}$' | wc -l

Задача 5: Оживление сервиса

Ты заходишь на сервер и видишь, что systemctl status nginx показывает failed. Ты не можешь просто так переустанавливать пакет. Выясни причину падения и исправь её. (Подсказка: порт 80 уже занят каким-то левым процессом).

💡 Подсказки
  • Смотри полный лог: journalctl -u nginx -n 50 --no-pager.
  • Ошибка: bind() to 0.0.0.0:80 failed (98: Address already in use).
  • Найди процесс, слушающий порт: sudo ss -tulpn | grep :80.
  • Если это левый скрипт на Python, убей его через kill и запусти Nginx.
✅ Решение 
# 1. Смотрим ошибку
sudo journalctl -u nginx --no-pager -n 20
# Видим: "bind() failed (98: Address already in use)"

# 2. Ищем, кто висит на порту 80
sudo ss -tulpn | grep :80
# или
sudo lsof -i :80
# Видим PID, например 12345, команда python3

# 3. Убиваем процесс
sudo kill 12345
# (если не помогает: kill -9 12345)

# 4. Запускаем Nginx
sudo systemctl start nginx
sudo systemctl status nginx

Задача 7: Поиск скрытого процесса (Продвинутый Linux)

Говорят, на машине завёлся майнер, который прячется от команды top (подменяет имя). Используя файловую систему /proc, найди процесс, который больше всего потребляет CPU в данный момент, но в top выглядит безобидно.

💡 Подсказки
  • top и ps читают /proc/[pid]/stat и status. Злоумышленник может менять argv[0], но не скроет сведения ядра.
  • Посмотри на содержимое /proc/[pid]/exe — куда ведёт симлинк.
  • Сравни /proc/[pid]/comm с командой в ps aux.
  • Можно скриптом пройтись по всем PID и вытащить те, где /proc/[pid]/stat показывает высокое значение utime + stime (14 и 15 поля).
✅ Решение 
# Ручная проверка подозрительного PID (допустим, нашли его через top, но имя странное)
PID=12345
ls -l /proc/$PID/exe
cat /proc/$PID/comm
# Если exe указывает на /tmp/.hidden/miner, а comm говорит "bash" - вот он.

# Скрипт для поиска жирных процессов по CPU Usage (тяжело без доп утилит, но можно через /proc/stat):
# Сравниваем /proc/[pid]/stat за интервал.
# Упрощённо: ищем процессы, у которых путь запуска подозрительный:
for pid in /proc/[0-9]*; do
    exe=$(readlink $pid/exe 2>/dev/null)
    comm=$(cat $pid/comm 2>/dev/null)
    if [[ "$exe" == /tmp/* ]] || [[ "$exe" == /dev/shm/* ]]; then
        echo "Suspicious: PID=$(basename $pid) Comm=$comm Exe=$exe"
    fi
done

Задача 9: Бекап и архивация (ротация логов)

Напиши Bash-скрипт, который архивирует директорию /var/log/myapp в tar.gz, добавляя к имени текущую дату, и удаляет архивы старше 7 дней из папки /backups. Добавь скрипт в cron на выполнение каждый день в 3 часа ночи.

💡 Подсказки
  • Формат даты: date +%Y%m%d.
  • Для поиска и удаления старых файлов: find /backups -name "*.tar.gz" -mtime +7 -delete.
  • Cron на системном уровне: положи скрипт в /etc/cron.daily/ или добавь запись в /etc/crontab.
  • Пользовательский cron: crontab -e -> 0 3 * * * /path/to/script.sh.
✅ Решение 
#!/bin/bash
# /opt/scripts/backup-logs.sh
BACKUP_DIR="/backups"
SRC="/var/log/myapp"
DATE=$(date +%Y%m%d)

mkdir -p $BACKUP_DIR
tar -czf $BACKUP_DIR/myapp-$DATE.tar.gz $SRC

# Удаление старее 7 дней
find $BACKUP_DIR -name "*.tar.gz" -mtime +7 -delete

# Cron (пользовательский):
# crontab -e
# 0 3 * * * /bin/bash /opt/scripts/backup-logs.sh

Задача 13: Развертывание статического сайта с Nginx

У тебя есть готовая HTML-страница index.html. Настрой полноценный сайт на Nginx в Ubuntu: создай конфигурационный файл виртуального хоста mysite.local, укажи корневую директорию /var/www/mysite, настрой логи отдельно для этого сайта (access и error). Проверь конфигурацию и перезагрузи Nginx.

💡 Подсказки
  • Конфиги виртуальных хостов лежат в /etc/nginx/sites-available/.
  • Активируются через симлинк в /etc/nginx/sites-enabled/.
  • Для проверки синтаксиса используй nginx -t.
  • Не забудь про server_name и директивы access_log, error_log.
✅ Решение 
# 1. Создаём директорию и простую страницу
sudo mkdir -p /var/www/mysite
echo "<h1>Welcome to MySite!</h1>" | sudo tee /var/www/mysite/index.html
sudo chown -R www-data:www-data /var/www/mysite

# 2. Создаём конфиг
sudo nano /etc/nginx/sites-available/mysite.local

Содержимое конфига:

server {
    listen 80;
    server_name mysite.local www.mysite.local;

    root /var/www/mysite;
    index index.html;

    access_log /var/log/nginx/mysite_access.log;
    error_log /var/log/nginx/mysite_error.log;

    location / {
        try_files $uri $uri/ =404;
    }
}

# 3. Активируем сайт
sudo ln -s /etc/nginx/sites-available/mysite.local /etc/nginx/sites-enabled/

# 4. Проверяем и перезагружаем
sudo nginx -t
sudo systemctl reload nginx

# 5. Тестируем локально
curl -H "Host: mysite.local" http://localhost

Задача 14: Нехватка inode на диске

Команда df -h показывает, что на разделе /var занято всего 30% места, но новые файлы создавать невозможно — ошибка No space left on device. Выясни причину, найди директорию с миллионом мелких файлов и очисти её.

💡 Подсказки
  • Проверь количество использованных inode: df -i.
  • Найди директории с огромным количеством файлов: find /var -xdev -type d -exec sh -c 'echo "$(ls -1 "$1" | wc -l) $1"' _ {} \; или через find с -printf и sort.
  • Частая причина — кеш-файлы сессий PHP или временные файлы.
✅ Решение 
# 1. Диагностика
df -i
# Видим IUse% 100% на /var

# 2. Поиск директории-виновника
sudo find /var -xdev -type d -size +100k 2>/dev/null
# Более точный способ — подсчёт файлов:
for dir in /var/*; do
    count=$(sudo find "$dir" -type f | wc -l)
    echo "$count $dir"
done | sort -rn | head -10

# 3. Допустим, нашли /var/spool/postfix/maildrop с кучей файлов
ls /var/spool/postfix/maildrop | wc -l

# 4. Очистка (осторожно!)
sudo find /var/spool/postfix/maildrop -type f -delete
# Или массово удалить через xargs
# Проверяем:
df -i

Задача 16: Безопасная настройка SSH

Настрой SSH-сервер на Ubuntu так, чтобы:
1) Запретить вход под root.
2) Разрешить вход только пользователю devops (создай его, если нет).
3) Сменить стандартный порт с 22 на 2222.
4) Отключить аутентификацию по паролю, оставить только по ключам.

💡 Подсказки
  • Конфиг SSH: /etc/ssh/sshd_config.
  • Директива: PermitRootLogin no.
  • Директива для пользователей: AllowUsers devops.
  • Директива: PasswordAuthentication no и PubkeyAuthentication yes.
  • Не забудь перезапустить службу: sudo systemctl restart sshd.
  • Перед отключением пароля убедись, что ключ добавлен в ~/.ssh/authorized_keys для пользователя devops.
✅ Решение 
# 1. Создаём пользователя и настраиваем ключи
sudo useradd -m -s /bin/bash devops
sudo passwd devops
sudo su - devops
mkdir -p ~/.ssh
chmod 700 ~/.ssh
# Копируем свой публичный ключ:
echo "ssh-rsa AAAAB3... user@host" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
exit

# 2. Правим конфиг SSH
sudo nano /etc/ssh/sshd_config

Изменяемые/добавляемые строки:

Port 2222
PermitRootLogin no
AllowUsers devops
PubkeyAuthentication yes
PasswordAuthentication no

# 3. Проверяем конфиг и перезагружаем
sudo sshd -t
sudo systemctl restart sshd

# 4. Проверяем (с другого терминала, не закрывая текущий!)
ssh -p 2222 devops@localhost
# Должен пустить по ключу без пароля.

Задача 17: Перехват трафика контейнера

У тебя есть веб-приложение в контейнере, которое ходит во внешний мир через HTTP. Перехвати и проанализируй весь HTTP-трафик, исходящий из этого контейнера, с помощью tcpdump на хосте.

💡 Подсказки
  • Найди сетевой интерфейс контейнера: docker inspect container | grep -i network или ip link show.
  • Обычно это veth... или мост docker0.
  • Можно слушать весь трафик на интерфейсе docker0.
  • tcpdump -i docker0 -A port 80 покажет текстовое содержимое пакетов.

docker ps

sudo tcpdump -i docker0 -w /tmp/container_traffic.pcap 'tcp port 80'

tcpdump -r /tmp/container_traffic.pcap -A

# (требует nsenter или docker exec с tcpdump внутри)

Задача 18: Управление systemd-сервисами

Создай собственный systemd-сервис, который будет запускать простой HTTP-сервер на Python (python3 -m http.server 9000) из директории /srv/files. Сервис должен запускаться от непривилегированного пользователя appuser, автоматически стартовать при загрузке и перезапускаться при падении.

💡 Подсказки
  • Создай unit-файл в /etc/systemd/system/pyserver.service.
  • Используй секции [Unit], [Service], [Install].
  • Директивы: User=, WorkingDirectory=, ExecStart=, Restart=always, WantedBy=multi-user.target.
  • После создания: systemctl daemon-reload, systemctl enable pyserver.
✅ Решение 
# 1. Создаём пользователя и директорию
sudo useradd -r -s /usr/sbin/nologin appuser
sudo mkdir -p /srv/files
sudo chown appuser:appuser /srv/files
echo "Hello from service" | sudo tee /srv/files/index.html

# 2. Создаём unit-файл
sudo nano /etc/systemd/system/pyserver.service

Содержимое:

[Unit]
Description=Simple Python HTTP Server
After=network.target

[Service]
Type=simple
User=appuser
Group=appuser
WorkingDirectory=/srv/files
ExecStart=/usr/bin/python3 -m http.server 9000
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target

# 3. Активируем и запускаем
sudo systemctl daemon-reload
sudo systemctl enable pyserver
sudo systemctl start pyserver

# 4. Проверяем
sudo systemctl status pyserver
curl http://localhost:9000

Задача 19: Сборка Docker-образа с нуля из scratch

Скомпилируй простую программу на C ("Hello World"), которая выводит строку в STDOUT, и упакуй её в минимальный Docker-образ на основе scratch. Образ должен быть статически скомпилирован и весить минимально возможное количество мегабайт.

💡 Подсказки
  • Для статической компиляции в gcc: gcc -static -o hello hello.c.
  • Многоэтапная сборка (multi-stage build): первый этап — компиляция в gcc:alpine, второй — копирование бинарника в scratch.
  • В scratch нет никаких библиотек, поэтому бинарник обязан быть статическим.
✅ Решение

hello.c

#include <stdio.h>
int main() {
    printf("Hello from scratch!\n");
    return 0;
}

Dockerfile

# Этап 1: Компиляция
FROM gcc:alpine AS builder
COPY hello.c /src/
WORKDIR /src
RUN gcc -static -o hello hello.c

# Этап 2: Финальный образ
FROM scratch
COPY --from=builder /src/hello /hello
CMD ["/hello"]

# Сборка и проверка размера
docker build -t hello-scratch .
docker images hello-scratch
# Размер будет около 50-100 КБ (размер самого бинарника)
docker run --rm hello-scratch

Задача 20: Восстановление удалённого файла (по файловому дескриптору)

Кто-то случайно удалил лог-файл /var/log/critical.log, который всё ещё пишется активным процессом. Место на диске продолжает уменьшаться (процесс держит дескриптор). Восстанови содержимое файла и освободи место на диске без перезапуска процесса.

💡 Подсказки
  • Найди процесс, который держит удалённый файл: lsof | grep deleted.
  • У удалённого файла в /proc/[pid]/fd/ есть симлинк с пометкой (deleted).
  • Скопируй данные из файлового дескриптора: cat /proc/[pid]/fd/[number] > /recovered.log.
  • Чтобы освободить место: echo > /proc/[pid]/fd/[number] (обрезать файл) или kill, если процесс можно перезапустить.
✅ Решение 
# 1. Ищем процесс с удалённым файлом
sudo lsof | grep deleted
# Находим процесс python3 с PID 5678 и fd номером 3

# 2. Проверяем
ls -l /proc/5678/fd/3
# lrwx------ 1 user user 64 ... 3 -> /var/log/critical.log (deleted)

# 3. Восстанавливаем содержимое
sudo cat /proc/5678/fd/3 > /tmp/critical_recovered.log

# 4. Освобождаем место (обрезаем файл через дескриптор)
sudo truncate -s 0 /proc/5678/fd/3
# Или:
echo -n | sudo tee /proc/5678/fd/3

# Проверяем df -h — место должно освободиться.

Задача 22: Лимитирование ресурсов контейнера

Запусти стресс-тест контейнер (например, polinux/stress или busybox с dd), но ограничь его потребление: максимум 256 МБ оперативной памяти и 0.5 ядра CPU. Докажи, что лимиты работают, с помощью docker stats.

💡 Подсказки
  • Память: --memory=256m.
  • CPU: --cpus=0.5.
  • Для генерации нагрузки можно использовать busybox sh -c "dd if=/dev/zero of=/dev/null".
  • Открывай второй терминал для docker stats.
✅ Решение 
# Терминал 1: Запускаем контейнер с лимитами
docker run -d --name limited-stress \
  --memory=256m \
  --cpus=0.5 \
  busybox sh -c "dd if=/dev/zero of=/dev/null & stress --vm 1 --vm-bytes 200M --vm-hang 5"

# Терминал 2: Мониторим
docker stats limited-stress
# Видим: MEM USAGE / LIMIT 200MiB / 256MiB, CPU % не поднимается выше ~50%

Задача 23: Анализ узких мест ввода-вывода

Система тормозит при операциях с диском. Используя iostat и iotop, определи, какое блочное устройство перегружено и какой процесс создаёт наибольшую нагрузку на ввод-вывод.

💡 Подсказки
  • iostat -x 1 покажет утилизацию (%util) по устройствам в реальном времени.
  • Высокий await (среднее время ожидания) — признак проблем.
  • iotop (или sudo iotop -oP) покажет процессы, активно читающие/пишущие.
  • Может потребоваться установка пакетов sysstat и iotop.
✅ Решение 
# Установка утилит (если нужно)
sudo apt install sysstat iotop -y

# 1. Смотрим статистику по устройствам
iostat -x 1 5
# Анализируем колонки: %util (близко к 100%), await (высокий, >10-20ms).

# 2. Находим процесс-виновник
sudo iotop -oP
# Видим, что процесс "backup.sh" с PID 9876 читает диск на 50 M/s.

# 3. Анализируем, что именно делает процесс
sudo lsof -p 9876
cat /proc/9876/io

# 4. При необходимости ограничиваем процесс через ionice
sudo ionice -c 2 -n 7 -p 9876  # класс best-effort, низкий приоритет

Задача 24: Создание Docker-тома и миграция данных

У тебя есть контейнер PostgreSQL, который использует анонимный том (данные внутри контейнера в /var/lib/postgresql/data). Создай именованный том pgdata, скопируй туда данные из запущенного контейнера и перезапусти контейнер с использованием этого именованного тома, сохранив данные.

💡 Подсказки
  • Создай том: docker volume create pgdata.
  • Используй временный контейнер с флагом --volumes-from, чтобы скопировать данные.
  • Или используй docker cp для извлечения, а потом копирования через временный контейнер.
  • Простой путь: docker run --rm -v pgdata:/target -v /var/lib/postgresql/data:/source:ro alpine cp -av /source/. /target/ (но это только если данные на хосте, а не в volume контейнера).
  • Для in-container volumes: docker run --rm --volumes-from old-postgres -v pgdata:/target alpine cp -av /var/lib/postgresql/data/. /target/.
✅ Решение 
# 1. Допустим, контейнер с БД называется "old-postgres"
docker ps

# 2. Создаём целевой том
docker volume create pgdata

# 3. Копируем данные через временный контейнер
docker run --rm \
  --volumes-from old-postgres \
  -v pgdata:/target \
  alpine \
  cp -av /var/lib/postgresql/data/. /target/

# 4. Останавливаем старый и запускаем новый с томом
docker stop old-postgres
docker rm old-postgres

docker run -d --name new-postgres \
  -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=mysecretpassword \
  postgres:15

# 5. Проверяем, что данные на месте
docker exec -it new-postgres psql -U postgres -c "\l"
