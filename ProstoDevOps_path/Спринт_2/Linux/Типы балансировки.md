# Типы балансировки

## Зачем это нужно?

У тебя есть приложение и к нему идет много запросов. Проблемы:

- Один сервер не справляется с нагрузкой
- Если сервер упадет — весь сервис недоступен
- Запросы обрабатываются медленно
- Один сервер перегружен, другие простаивают

**Load Balancer** решает эти проблемы — распределяет запросы между несколькими серверами.

## 1. Что такое Load Balancing?

**Load Balancing** — это распределение входящих запросов между несколькими серверами.

**Зачем:**

- Увеличить пропускную способность
- Обеспечить отказоустойчивость
- Равномерно распределить нагрузку

**Схема:**

![Load Balancer → 3 сервера](https://offers.prostodevops.ru/diagrams/linux/lb-simple.png)Load Balancer → 3 сервера

Клиент обращается к Load Balancer, а он направляет запрос на один из серверов.

## 2. Уровни балансировки

### L4 (Transport Layer)

Балансировка на уровне TCP/UDP.

**Что видит:**

- IP адреса
- Порты
- TCP/UDP протокол

**Что НЕ видит:**

- HTTP headers
- URL
- Cookies

**Плюсы:**

- Быстро (не нужно парсить HTTP)
- Меньше ресурсов

**Минусы:**

- Меньше возможностей для роутинга

### L7 (Application Layer)

Балансировка на уровне HTTP/HTTPS.

**Что видит:**

- HTTP headers
- URL
- Cookies
- Content type

**Возможности:**

- Роутинг по URL (если /api → на API сервера, если /static → на статику)
- Роутинг по headers
- SSL termination

**Плюсы:**

- Больше возможностей для роутинга
- Можно анализировать содержимое запросов

**Минусы:**

- Медленнее L4
- Больше ресурсов

## 3. Алгоритмы балансировки

### Round Robin

Запросы распределяются по кругу.

![Схема в материале «Типы балансировки»: Запрос 1 → Server 1](https://offers.prostodevops.ru/diagrams/extras/linux/tipy-balansirovki-6.png)Схема в материале «Типы балансировки»: Запрос 1 → Server 1

**Когда использовать:**

- Все серверы одинаковые по мощности
- Запросы примерно одинаковые по времени обработки

**Проблема:**

- Не учитывает текущую нагрузку на сервер
- Если один сервер медленнее — он получит столько же запросов

### Weighted Round Robin

Как Round Robin, но с весами.

codecopy

```
Server 1 (вес 3) получает 3 запросаServer 2 (вес 2) получает 2 запросаServer 3 (вес 1) получает 1 запрос
```

**Когда использовать:**

- Серверы разные по мощности
- Хочешь направить больше трафика на более мощные серверы

### Least Connections

Запрос идет на сервер с наименьшим количеством активных соединений.

![Схема в материале «Типы балансировки»: Server 1: 5 соединений](https://offers.prostodevops.ru/diagrams/extras/linux/tipy-balansirovki-2.png)Схема в материале «Типы балансировки»: Server 1: 5 соединений

**Когда использовать:**

- Запросы разные по времени обработки
- Учитывает реальную нагрузку

### Least Response Time

Запрос идет на сервер с наименьшим временем ответа.

![Схема в материале «Типы балансировки»: Server 1: 100ms average](https://offers.prostodevops.ru/diagrams/extras/linux/tipy-balansirovki-1.png)Схема в материале «Типы балансировки»: Server 1: 100ms average

**Когда использовать:**

- Серверы в разных датацентрах
- Разная производительность серверов

### IP Hash

Запросы с одного IP всегда идут на один и тот же сервер.

![Схема в материале «Типы балансировки»: Client 192.168.1.10 → всегда Server 1](https://offers.prostodevops.ru/diagrams/extras/linux/tipy-balansirovki-5.png)Схема в материале «Типы балансировки»: Client 192.168.1.10 → всегда Server 1

**Как работает:**

- Берется hash от IP клиента
- По hash определяется сервер

**Когда использовать:**

- Нужна sticky session (сессия привязана к серверу)
- Приложение хранит состояние на сервере

**Проблема:**

- Если сервер упадет — все клиенты с этого hash потеряют сессию

### Random

Случайный выбор сервера.

![Схема в материале «Типы балансировки»: Запрос 1 → Server 2](https://offers.prostodevops.ru/diagrams/extras/linux/tipy-balansirovki-4.png)Схема в материале «Типы балансировки»: Запрос 1 → Server 2

**Когда использовать:**

- Простая настройка
- Все серверы одинаковые

**Плюсы:**

- Простой алгоритм
- Хорошо распределяет при большом количестве запросов

## 4. Health Checks

Load Balancer должен проверять здоровье серверов.

**Типы проверок:**

**Passive (пассивные):**

- Смотрит на ошибки от серверов
- Если много ошибок → сервер помечается как нездоровый

**Active (активные):**

- Периодически отправляет проверочные запросы
- Если сервер не отвечает → помечается как нездоровый

**Что проверять:**

- HTTP endpoint (GET /health)
- TCP connection
- Время ответа

## 5. Session Persistence (Sticky Sessions)

Проблема: пользователь логинится на Server 1, следующий запрос идет на Server 2, где нет его сессии.

**Решения:**

### Cookie-based

Load Balancer добавляет cookie с ID сервера.

![Схема в материале «Типы балансировки»: Первый запрос → Server 1 → LB добавляет cookie: server=1](https://offers.prostodevops.ru/diagrams/extras/linux/tipy-balansirovki-3.png)Схема в материале «Типы балансировки»: Первый запрос → Server 1 → LB добавляет cookie: server=1

### IP-based

Использовать IP Hash алгоритм.

**Лучше:**

- Не использовать sticky sessions
- Хранить сессии в Redis/Memcached
- Stateless приложения

## 6. Популярные Load Balancers

### Nginx

- L7 балансировщик
- Reverse proxy
- Все основные алгоритмы

### HAProxy

- L4 и L7
- Очень быстрый
- Много возможностей

### Kubernetes Service

- Встроенный в Kubernetes
- L4 балансировка
- Round Robin по умолчанию

### Cloud Load Balancers

- AWS ALB/NLB
- Google Cloud Load Balancer
- Azure Load Balancer

## 7. Вопросы на собеседованиях

### Вопрос 1: "Что такое Load Balancer?"

**Ответ:** Load Balancer распределяет входящие запросы между несколькими серверами для увеличения пропускной способности и обеспечения отказоустойчивости.

### Вопрос 2: "В чем разница между L4 и L7 балансировкой?"

**Ответ:**

- **L4** — балансировка на уровне TCP/UDP, видит только IP и порты, быстрее
- **L7** — балансировка на уровне HTTP, видит headers, URL, cookies, больше возможностей для роутинга

### Вопрос 3: "Что такое Round Robin?"

**Ответ:** Алгоритм балансировки, который распределяет запросы по кругу между серверами. Запрос 1 → Server 1, Запрос 2 → Server 2, и так далее.

### Вопрос 4: "Когда использовать Least Connections?"

**Ответ:** Когда запросы разные по времени обработки или есть long-polling соединения. Алгоритм направляет запрос на сервер с наименьшим количеством активных соединений.

### Вопрос 5: "Что такое IP Hash?"

**Ответ:** Алгоритм балансировки, при котором запросы с одного IP всегда идут на один и тот же сервер. Используется для sticky sessions.

### Вопрос 6: "Зачем нужны Health Checks?"

**Ответ:** Чтобы Load Balancer не направлял трафик на упавшие или медленные серверы. Health Check периодически проверяет доступность серверов.

### Вопрос 7: "Что такое Sticky Session?"

**Ответ:** Механизм привязки клиента к конкретному серверу. Все запросы от одного клиента идут на один и тот же сервер. Нужно для stateful приложений.

### Вопрос 8: "Какой алгоритм балансировки выбрать?"

**Ответ:**

- Все серверы одинаковые, простые запросы → **Round Robin**
- Серверы разные по мощности → **Weighted Round Robin**
- Разное время обработки запросов → **Least Connections**
- Нужна sticky session → **IP Hash**

### Вопрос 9: "Что лучше: L4 или L7 балансировка?"

**Ответ:**

- **L4** — если нужна скорость и простота, HTTP роутинг не нужен
- **L7** — если нужен роутинг по URL, headers, или SSL termination

### Вопрос 10: "Как решить проблему со sticky sessions?"

**Ответ:**

- Не хранить сессии на серверах
- Использовать Redis/Memcached для сессий
- Делать приложение stateless
- Или использовать cookie-based или IP-based sticky sessions

## Заключение

**Load Balancing** — это распределение запросов между серверами.

**Основные алгоритмы:**

- **Round Robin** — по кругу
- **Least Connections** — на сервер с меньшими соединениями
- **IP Hash** — по IP клиента
- **Weighted** — с учетом мощности серверов

**Уровни:**

- **L4** — TCP/UDP, быстро
- **L7** — HTTP, больше возможностей

**Важно помнить:**

- Health Checks обязательны
- Sticky sessions усложняют масштабирование
- Лучше делать приложения stateless

На собеседованиях спрашивают про разницу L4/L7, алгоритмы балансировки, health checks и когда какой алгоритм использовать.
