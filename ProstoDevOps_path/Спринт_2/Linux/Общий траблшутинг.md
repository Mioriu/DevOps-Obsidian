# Общий траблшутинг Linux

## Зачем это знать?

Девопсу постоянно приходится разбираться с проблемами:

- **Приложение тормозит** — нужно быстро найти узкое место (CPU? память? диск? сеть?)
- **Сервер не отвечает**
- **Закончилось место на диске** — но где именно и что жрет пространство?
- **Процесс упал** — почему и как это предотвратить?
- **Сеть не работает** — приложение не может подключиться к базе
- **Высокий load average** — но процессор вроде свободен

На собеседованиях обязательно спросят про траблшутинг. Тебе дадут проблему и попросят рассказать последовательность действий.

## 1. Методология траблшутинга

### Общий подход

Когда что-то сломалось, **не надо сразу чинить**. Сначала диагностика.

**Последовательность действий:**

1. **Собрать информацию** — что именно не работает, когда началось, что менялось
2. **Проверить основы** — жив ли сервер, есть ли сеть, запущены ли сервисы
3. **Собрать метрики** — CPU, память, диск, сеть, процессы
4. **Проверить логи** — системные и приложения
5. **Выдвинуть гипотезу** — предположить причину
6. **Проверить гипотезу** — тестами или дополнительной диагностикой
7. **Исправить** — применить фикс
8. **Проверить** — убедиться что проблема решена
9. **Задокументировать** — чтобы в следующий раз быстрее разобраться

### Первые команды при любой проблеме

Это базовый набор команд для быстрой диагностики:

bashcopy

```bash
# Быстрый обзор системыuptime              # load average, время работыtop                 # или htop - что жрет CPU и памятьdf -h               # свободное место на дискахfree -h             # свободная памятьdmesg | tail        # последние сообщения ядра| --- | --- | journalctl -xe      # последние события systemdss -tulpn           # открытые порты и соединения
```

Эти 7 команд дадут общую картину в 90% случаев.

## 2. Диагностика производительности

### Проблема: Высокий CPU

**Симптомы:**

- Приложение тормозит
- `top` показывает высокую нагрузку на CPU
- Load average > количества ядер

**Диагностика:**

Посмотреть что жрет CPU:

bashcopy

```bash
top# 1 чтобы увидеть все ядра# P чтобы отсортировать по CPU
```

Или более удобный вариант:

bashcopy

```bash
htop# F6 - сортировка# F5 - родители процесса
```

Найти топ процессов по CPU:

bashcopy

```bash
ps aux --sort=-%cpu | head -10| --- | --- |
```

Посмотреть что делает конкретный процесс:

bashcopy

```bash
strace -p <PID># системные вызовы в реальном времени
```

Проверить историю нагрузки:

bashcopy

```bash
sar -u 1 10# Показывает CPU usage каждую секунду 10 раз
```

**Типичные причины:**

1. **Бесконечный цикл в приложении** → проверь логи, strace
2. **Слишком много процессов** → проверь количество воркеров/тредов
3. **Вирусы/майнеры** → проверь незнакомые процессы
4. **Неоптимальный код** → профилирование приложения

**Решение:**

bashcopy

```bash
# Убить процесс если он повисkill -9 <PID> # Ограничить CPU для процесса (cpulimit)cpulimit -p <PID> -l 50  # ограничить до 50% одного ядра # Снизить приоритет процессаrenice -n 10 -p <PID>
```

### Проблема: Нехватка памяти

**Симптомы:**

- Процессы падают с OOM Killed
- Система тормозит (свопится)
- `free -h` показывает мало свободной памяти

**Диагностика:**

Посмотреть использование памяти:

free -h

Вывод:

codecopy

```
              total        used        free      shared  buff/cache   availableMem:           7.7G        5.2G        450M        180M        2.1G        2.1GSwap:          2.0G        1.5G        500M
```

**Важно:** Смотри на `available`, а не на `free`

- `free` — полностью свободная память
- `available` — память доступная для приложений (включая кеши которые можно освободить)

Найти что жрет память:

bashcopy

```bash
ps aux --sort=-%mem | head -10| --- | --- |
```

Или через top:

bashcopy

```bash
top# Нажми M чтобы отсортировать по памяти
```

Проверить какие процессы убивал OOM killer:

bashcopy

```bash
dmesg | grep -i "killed process"| --- | --- | # илиjournalctl -k | grep -i "killed process"| --- | --- |
```

Посмотреть swap usage:

swapon --show

**Типичные причины:**

1. **Утечка памяти в приложении** → перезапуск, обновление, профилирование
2. **Слишком много процессов** → уменьшить количество воркеров
3. **Кеши занимают много места** → это нормально, система сама освободит
4. **Недостаточно RAM** → добавить память или оптимизировать

**Решение:**

bashcopy

```bash
# Освободить кеши (обычно не нужно, но иногда помогает)sync; echo 3 > /proc/sys/vm/drop_caches # Посмотреть лимиты процессаcat /proc/<PID>/limits # Убить процесс-пожиратель памятиkill -9 <PID> # Увеличить swap (временно)dd if=/dev/zero of=/swapfile bs=1M count=2048chmod 600 /swapfilemkswap /swapfileswapon /swapfile
```

### Проблема: Высокий Load Average

**Что это значит?**

Load Average — среднее количество процессов в очереди на выполнение.

Вывод `uptime`:

codecopy

```
15:30:24 up 10 days,  3:42,  2 users,  load average: 4.20, 3.85, 2.67                                                       1min  5min  15min
```

**Как интерпретировать:**

- На 4-ядерном сервере load average 4.0 = 100% загрузка
- Load > количества ядер = сервер перегружен
- Load < количества ядер = все ОК

**Диагностика:**

bashcopy

```bash
# Узнать количество ядерnproc# илиlscpu | grep "^CPU(s)"| --- | --- | # Посмотреть load averageuptime # Найти процессы в состоянии D (uninterruptible sleep)ps aux | grep " D "| --- | --- | # D state = процесс ждет I/O (диск, сеть)
```

**Важно:** Высокий load average может быть из-за:

- CPU (процессы в состоянии R - running)
- I/O wait (процессы в состоянии D - disk sleep)

Проверить что это:

bashcopy

```bash
# Если iowait высокий - проблема в дискеiostat -x 1 5
```

### Проблема: Медленный диск

**Симптомы:**

- Приложение тормозит
- Высокий `iowait` в `top`
- Долгие операции чтения/записи

**Диагностика:**

Посмотреть iowait:

bashcopy

```bash
top# Строка %Cpu(s): ... wa - это iowait# Если > 10% - диск тормозит
```

Статистика по дискам:

bashcopy

```bash
iostat -x 1 5# %util - насколько диск загружен (100% = полностью забит)# await - среднее время ожидания операции (в мс)# Если await > 50ms - диск медленный
```

Найти процессы которые жрут диск:

bashcopy

```bash
iotop# илиiotop -o  # показывать только активные процессы
```

Проверить что пишется на диск:

bashcopy

```bash
lsof | grep <device>| --- | --- | # или для конкретного процессаlsof -p <PID>
```

**Типичные причины:**

1. **Много записи в логи** → ротация логов, уменьшить уровень логирования
2. **RAID ребилдится** → подождать или проверить статус RAID
3. **База данных без индексов** → оптимизация запросов
4. **Медленный HDD вместо SSD** → миграция на SSD

**Решение:**

bashcopy

```bash
# Посмотреть что жрет местоdu -sh /* | sort -h| --- | --- | # Найти большие файлыfind / -type f -size +1G -exec ls -lh {} \; # Очистить логиjournalctl --vacuum-size=500Mtruncate -s 0 /var/log/giant.log # Проверить SMART статус дискаsmartctl -a /dev/sda
```

### Проблема: Закончилось место на диске

**Симптомы:**

- `df -h` показывает 100% использование
- Приложения не могут писать файлы
- Ошибки "No space left on device"

**Диагностика:**

bashcopy

```bash
# Проверить использование разделовdf -h # Проверить inode (может закончиться место из-за много мелких файлов)df -i # Найти самые большие директорииdu -sh /* | sort -h | tail -10| --- | --- | --- | # Более детально для конкретной директорииdu -h /var | sort -h | tail -20| --- | --- | --- | # Найти файлы больше 1GBfind / -type f -size +1G -exec ls -lh {} \; 2>/dev/null # Найти удаленные но открытые файлы (они занимают место!)lsof | grep deleted| --- | --- |
```

**Типичная проблема: файл удален но место не освободилось**

Если процесс держит файл открытым, место не освободится пока процесс не закроется.

Найти:

bashcopy

```bash
lsof +L1# Файлы с 0 линков (удалены но открыты)
```

Решение:

bashcopy

```bash
# Перезапустить процесс который держит файлsystemctl restart <service>
```

**Решение:**

bashcopy

```bash
# Очистить логиjournalctl --vacuum-size=500Mfind /var/log -type f -name "*.log" -mtime +30 -delete # Очистить кеши APT (Debian/Ubuntu)apt-get cleanapt-get autoremove # Очистить кеши YUM/DNF (RHEL/CentOS)yum clean alldnf clean all # Очистить Dockerdocker system prune -a --volumes # Очистить /tmpfind /tmp -type f -mtime +7 -delete
```

## 3. Проблемы с процессами

### Проблема: Процесс висит и не отвечает

**Диагностика:**

bashcopy

```bash
# Проверить статус процессаps aux | grep <process_name>| --- | --- | # Посмотреть что делает процессstrace -p <PID> # Посмотреть открытые файлыlsof -p <PID> # Посмотреть стек вызововpstack <PID>  # или gdb -p <PID> -ex bt -ex quit
```

**Решение:**

bashcopy

```bash
# Мягко попросить завершиться (SIGTERM)kill <PID> # Подождать 10 секунд... # Если не помогло - жестко убить (SIGKILL)kill -9 <PID> # Если это сервисsystemctl stop <service>systemctl kill <service>
```

### Проблема: Зомби-процессы

**Что это?**

Зомби (zombie, defunct) — процесс который завершился, но его родитель не забрал exit code.

bashcopy

```bash
ps aux | grep defunct| --- | --- | # илиps aux | awk '$8=="Z"'| --- | --- |
```

**Важно:** Зомби НЕ занимают ресурсы (CPU, память), только запись в таблице процессов.

**Решение:**

Зомби нельзя убить напрямую. Нужно убить родительский процесс:

bashcopy

```bash
# Найти родителя зомбиps -o ppid= -p <zombie_PID> # Убить родителяkill -9 <parent_PID>
```

Или перезапустить родительский сервис:

systemctl restart <parent_service>

### Проблема: Слишком много процессов

**Симптомы:**

- Ошибка "fork: Cannot allocate memory"
- Система тормозит
- Не можешь залогиниться

**Диагностика:**

bashcopy

```bash
# Посмотреть количество процессовps aux | wc -l| --- | --- | # Лимит процессов для пользователяulimit -u # Топ пользователей по количеству процессовps aux | awk '{print $1}' | sort | uniq -c | sort -rn | head -10| --- | --- | --- | --- | --- | --- | # Проверить лимитыcat /proc/sys/kernel/pid_max
```

**Решение:**

bashcopy

```bash
# Убить все процессы пользователяpkill -u <username> # Увеличить лимит (временно)ulimit -u 4096 # Увеличить лимит (постоянно) в /etc/security/limits.confecho "*  soft  nproc  4096" >> /etc/security/limits.confecho "*  hard  nproc  8192" >> /etc/security/limits.conf
```

## 4. Проблемы с сервисами

### Проблема: Сервис не запускается

**Диагностика:**

bashcopy

```bash
# Статус сервисаsystemctl status <service> # Последние логи сервисаjournalctl -u <service> -n 50 --no-pager # Последние ошибкиjournalctl -u <service> -p err -n 20 # Проверить конфигnginx -t                    # для nginxapache2ctl configtest       # для apachesshd -t                     # для sshd
```

**Типичные причины:**

1. **Ошибка в конфигурации** → проверить конфиг
    
2. **Порт уже занят** → проверить `ss -tulpn | grep <port>` | --- | --- |
    
3. **Нет прав на файлы** → проверить владельца и права
    
4. **Не хватает ресурсов** → проверить лимиты в systemd unit
    

**Решение:**

bashcopy

```bash
# Перезапустить сервисsystemctl restart <service> # Если не помогает - посмотреть деталиsystemctl status <service> -l --no-pager # Проверить файл юнитаsystemctl cat <service> # Перечитать конфигурацию systemdsystemctl daemon-reload # Включить автозапускsystemctl enable <service>
```

### Проблема: Сервис постоянно перезапускается

**Диагностика:**

bashcopy

```bash
# Посмотреть историю перезапусковsystemctl status <service># Смотри на поле "Restarts" # Логи за последний часjournalctl -u <service> --since "1 hour ago" # Посмотреть настройки restart в юнитеsystemctl cat <service> | grep Restart| --- | --- |
```

**Типичные причины:**

1. **Приложение падает при старте** → проверить логи приложения
2. **Неправильная команда запуска** → проверить ExecStart в юните
3. **Слишком быстрый restart** → увеличить RestartSec

**Решение:**

bashcopy

```bash
# Остановить сервисsystemctl stop <service> # Запустить вручную чтобы увидеть ошибку/path/to/binary --config /path/to/config # Отредактировать юнит (если нужно изменить restart policy)systemctl edit <service># Добавить:# [Service]# Restart=on-failure# RestartSec=10s
```

## 5. Сетевые проблемы

### Проблема: Нет доступа к удаленному хосту

**Диагностика:**

bashcopy

```bash
# Пингping 8.8.8.8         # проверить интернетping <hostname>      # проверить DNS и доступность # Если пинг не работает - проверить DNSnslookup <hostname>dig <hostname> # Проверить маршрутtraceroute <hostname># илиmtr <hostname>  # более наглядно # Проверить есть ли сеть вообщеip addr showip route show
```

**Типичные причины:**

1. **Нет интернета** → проверить физическое подключение, шлюз
2. **DNS не работает** → проверить /etc/resolv.conf
3. **Фаервол блокирует** → проверить правила iptables/firewalld
4. **Неправильный маршрут** → проверить таблицу маршрутизации

**Решение:**

bashcopy

```bash
# Перезапустить сеть (Debian/Ubuntu)systemctl restart networking # Перезапустить сеть (RHEL/CentOS)systemctl restart NetworkManager # Проверить DNScat /etc/resolv.conf# Должно быть что-то типа:# nameserver 8.8.8.8# nameserver 1.1.1.1 # Временно изменить DNSecho "nameserver 8.8.8.8" > /etc/resolv.conf
```

### Проблема: Порт не слушается / Connection refused

**Симптомы:**

- `telnet <host> <port>` - Connection refused
- Приложение не может подключиться к сервису

**Диагностика:**

bashcopy

```bash
# Проверить слушает ли что-то на портуss -tulpn | grep :<port>| --- | --- | # илиnetstat -tulpn | grep :<port>| --- | --- | # Проверить можно ли подключиться локальноtelnet localhost <port>curl -v telnet://localhost:<port> # Проверить с другого хостаtelnet <remote_host> <port>nc -zv <remote_host> <port> # Проверить фаерволiptables -L -n | grep <port>| --- | --- | # или на RHEL/CentOSfirewall-cmd --list-all
```

**Типичные причины:**

1. **Сервис не запущен** → проверить `systemctl status`
2. **Слушает только на** [**localhost**](http://localhost/) → проверить bind address в конфиге
3. **Фаервол блокирует** → открыть порт
4. **SELinux блокирует** → проверить audit.log

**Решение:**

bashcopy

```bash
# Открыть порт в firewalldfirewall-cmd --permanent --add-port=80/tcpfirewall-cmd --reload # Открыть порт в iptablesiptables -A INPUT -p tcp --dport 80 -j ACCEPTiptables-save > /etc/iptables/rules.v4 # Проверить конфиг приложения (пример nginx)grep listen /etc/nginx/nginx.conf# Должно быть:# listen 80;# НЕ:# listen 127.0.0.1:80;
```

### Проблема: Медленная сеть / высокая latency

**Диагностика:**

bashcopy

```bash
# Проверить пингping -c 10 <hostname> # Проверить пропускную способностьiperf3 -c <remote_host>  # на клиентеiperf3 -s                 # на сервере # Проверить потери пакетовmtr --report <hostname> # Посмотреть сетевые ошибкиip -s linkethtool -S eth0 # Посмотреть активные соединенияss -ti  # показывает TCP info с RTT и retransmits
```

**Типичные причины:**

1. **Перегружена сеть** → QoS, увеличить bandwidth
2. **Много retransmits** → проблемы на сетевом уровне
3. **DNS медленно работает** → сменить DNS
4. **MTU проблемы** → проверить MTU

**Решение:**

bashcopy

```bash
# Проверить MTUip link show eth0ping -M do -s 1472 <host>  # проверить какой максимальный MTU проходит # Изменить MTUip link set eth0 mtu 1400 # Проверить DNStime nslookup google.com# Если долго - сменить DNS в /etc/resolv.conf
```

bashcopy

```bash
# Просмотр файла с конца (последние 20 строк)tail -n 20 /var/log/syslog # Следить за логом в реальном времениtail -f /var/log/nginx/access.log # Поиск по логамgrep ERROR /var/log/application.loggrep -i "out of memory" /var/log/syslog # Поиск с контекстом (5 строк до и после)grep -A 5 -B 5 "error" /var/log/app.log # Посчитать количество ошибокgrep -c ERROR /var/log/app.log # Логи за сегодняjournalctl --since today # Логи за последний часjournalctl --since "1 hour ago" # Логи конкретного сервисаjournalctl -u nginx.service # Логи с ошибками и выше (err, crit, alert, emerg)journalctl -p err # Следить за логами в реальном времениjournalctl -f # Логи конкретного процесса по PIDjournalctl _PID=1234
```

## 7. Проблемы с правами доступа

### Проблема: Permission denied

**Диагностика:**

## 9. Типичные вопросы на собеседовании

### Вопрос 1

**"Пользователи жалуются что сайт медленно работает. Как будешь диагностировать?"**

**Ответ:**

1. Проверю базовые метрики: `uptime`, `top`, `df -h`, `free -h`
2. Проверю нагрузку на сервер: CPU, память, диск, сеть
3. Проверю логи nginx/apache на ошибки и медленные запросы
4. Проверю логи приложения на ошибки
5. Проверю базу данных: долгие запросы, блокировки
6. Проверю сеть: latency, пропускную способность
7. Проверю внешние зависимости: API, другие сервисы

### Вопрос 2

**"Сервер не отвечает по SSH. Что делать?"**

**Ответ:**

1. Проверю доступность сервера: `ping <server>`
2. Если пинг не проходит → проблема с сетью или сервер завис
3. Если пинг проходит → проверю доступность порта SSH: `telnet <server> 22`
4. Если порт недоступен → проблема с sshd или фаерволом
5. Попробую зайти через консоль (IPMI, KVM, web console)
6. Проверю логи: `/var/log/auth.log`, `journalctl -u sshd`
7. Проверю запущен ли sshd: `systemctl status sshd`

### Вопрос 3

**"Закончилось место на диске но** `du` **показывает что места полно. В чем может быть проблема?"**

**Ответ:**

Скорее всего удалены файлы которые еще открыты процессами. Место не освобождается пока процесс не закроет файл.

Проверить:

bashcopy

```bash
lsof +L1# илиlsof | grep deleted| --- | --- |
```

Решение: Перезапустить процессы которые держат удаленные файлы.

### Вопрос 4

**"Load average 10.0 на 4-ядерном сервере, но CPU usage всего 20%. В чем проблема?"**

**Ответ:**

Load average высокий не из-за CPU, а из-за процессов в состоянии D (disk sleep) - ждут I/O операций.

Проверить:

bashcopy

```bash
iostat -x 1 5  # посмотреть iowait и %util дисковiotop          # найти что жрет дискps aux | awk '$8=="D"'  # процессы в D state| --- | --- |
```

Проблема скорее всего в медленном диске или слишком большом количестве операций I/O.

### Вопрос 5

**"Приложение пишет что не может подключиться к базе, но база работает. Как диагностировать?"**

**Ответ:**

1. Проверю доступность базы с сервера приложения: `telnet <db_host> 3306`
2. Проверю DNS: `nslookup <db_host>`
3. Проверю фаервол на сервере приложения и на сервере БД
4. Проверю что БД слушает правильный интерфейс (не только 127.0.0.1)
5. Проверю логи БД на ошибки подключения
6. Проверю учетные данные в конфиге приложения
7. Проверю лимиты подключений в БД: `SHOW PROCESSLIST;` для MySQL

## Вопрос на собеседовании

**"Опиши свой подход к траблшутингу когда 'что-то не работает' на production сервере"**

**Хороший ответ:**

1. **Не паникую** - действую по чек-листу
2. **Собираю информацию:**
    - Что именно не работает?
    - Когда началось?
    - Что менялось недавно?
    - Есть ли мониторинг/алерты?
3. **Базовая диагностика:** `uptime`, `top`, `df -h`, `free -h`, `ss`, логи
4. **Выдвигаю гипотезу** на основе данных
5. **Проверяю гипотезу** дополнительной диагностикой
6. **Применяю фикс** (если знаю решение) или **митигирую** (откатываю изменения, перезапускаю сервис)
7. **Проверяю что проблема решена**
8. **Документирую** для postmortem и базы знаний

Главное: **сначала диагностика, потом действия**. Не надо сразу все перезапускать или менять конфиги наугад.
