## RAID — зачем это нужно

В проде диски сами по себе не живут. Диск — это железка, а железки умирают. SSD деградируют, HDD сыплются, это нормальный процесс. Вопрос не в том, сломается ли диск, а когда он сломается. И чтобы данные не исчезли вместе с диском, используются RAID-массивы.

RAID (Redundant Array of Independent Disks) — это когда несколько физических дисков объединяются в один логический. В зависимости от уровня RAID это даёт либо отказоустойчивость (данные не пропадут при смерти диска), либо скорость, либо и то, и другое.

Собирать RAID с закрытыми глазами от вас никто не требует. Но знать уровни нужно — это спрашивают на собесах, и в работе вы будете видеть RAID на серверах постоянно.

## Уровни RAID

### RAID 0 — чередование (striping)

![RAID 0: чередование данных по дискам (striping)](https://offers.prostodevops.ru/diagrams/linux/raid-0.png)RAID 0: чередование данных по дискам (striping)

Данные разбиваются на куски и записываются поочерёдно на два (или больше) диска. Чтение и запись идут параллельно с обоих дисков, поэтому скорость удваивается. Доступный объём — сумма всех дисков (два диска по 1 ТБ = 2 ТБ).

Проблема: если любой из дисков сдох — вы теряете вообще всё. Не половину данных, а всё, потому что данные размазаны по дискам, и без одного куска они бесполезны.

RAID 0 в чистом виде в проде практически не используется. Это, по сути, ставка на скорость без страховки. Разве что для временных данных, которые не жалко потерять.

### RAID 1 — зеркалирование (mirroring)

![RAID 1: зеркалирование двух дисков](https://offers.prostodevops.ru/diagrams/linux/raid-1.png)RAID 1: зеркалирование двух дисков

Данные пишутся одновременно на два диска. Полная копия. Один диск умер — второй работает как ни в чём не бывало. Заменяете мёртвый диск, массив пересобирается, живём дальше.

Минус — теряете половину объёма. Два диска по 1 ТБ = 1 ТБ доступного пространства. Скорость записи не увеличивается (пишем на оба диска одновременно), а вот скорость чтения может быть выше (можно читать с обоих параллельно).

RAID 1 — простой и надёжный. Часто используется для системного раздела, где лежит ОС.

### RAID 5 — чередование с контрольными суммами

![RAID 5: parity распределена по дискам](https://offers.prostodevops.ru/diagrams/linux/raid-5.png)RAID 5: parity распределена по дискам

Минимум три диска. Данные и контрольные суммы (parity) распределяются по всем дискам. Если один диск умирает — данные можно восстановить из контрольных сумм на оставшихся дисках.

Доступный объём: (N-1) × размер диска. Три диска по 1 ТБ = 2 ТБ доступных. Один диск «уходит» на контрольные суммы (но физически они размазаны по всем трём).

Минус — запись медленнее, чем у RAID 0 и RAID 1, потому что при каждой записи нужно пересчитать контрольную сумму. И если диск сдох, пока массив пересобирается на новом диске — нагрузка высокая, и если в этот момент сдохнет второй диск, всё пропало.

RAID 5 — хороший компромисс между ёмкостью и отказоустойчивостью. Используется для файловых хранилищ, логов, не самых критичных данных.

### RAID 10 (1+0) — зеркалирование + чередование

![RAID 10: зеркало + чередование на 4 дисках](https://offers.prostodevops.ru/diagrams/linux/raid-10.png)RAID 10: зеркало + чередование на 4 дисках

RAID 10 — это комбинация RAID 1 и RAID 0. Сначала диски объединяются в зеркальные пары (RAID 1), а потом пары объединяются в stripe (RAID 0). Получается и скорость, и отказоустойчивость.

Минимум четыре диска. Доступный объём — 50% от общего (как у RAID 1). Четыре диска по 1 ТБ = 2 ТБ доступных.

RAID 10 — самый популярный для баз данных. PostgreSQL, MySQL — им нужна и скорость записи, и надёжность. RAID 10 даёт и то, и другое. Дорого по дискам (половина уходит на зеркала), но для баз данных это оправдано.

## LVM — Logical Volume Manager

Теперь про LVM. Представьте ситуацию: у вас на сервере раздел `/data` на 100 ГБ, и он заполнился. Нужно расширить. Без LVM вам придётся останавливать сервис, возможно перемонтировать раздел, возиться с `fdisk` или `parted`, расширять файловую систему — и это в лучшем случае, если после раздела есть свободное место на диске. Если нет — всё ещё сложнее.

С LVM вы просто добавляете новый диск и расширяете раздел на лету. Без даунтайма, без остановки сервисов. Вот для этого LVM и нужен.

### Три уровня LVM

LVM работает в три слоя. Это нужно понять, потому что терминология встречается постоянно:

![LVM: Logical Volumes → Volume Group → Physical Volumes](https://offers.prostodevops.ru/diagrams/linux/lvm-hierarchy.png)LVM: Logical Volumes → Volume Group → Physical Volumes

**Physical Volume (PV)** — физический диск или раздел, подготовленный для LVM. По сути, вы говорите LVM: «Вот этот диск — бери, он твой».

**Volume Group (VG)** — группа томов. Это пул пространства, собранный из одного или нескольких PV. Все физические диски складываются в одну кучу. VG — это как один большой виртуальный диск, склеенный из нескольких физических.

**Logical Volume (LV)** — логический том. Это то, что вы реально используете — монтируете, форматируете, записываете данные. Нарезается из VG. Аналог обычного раздела, но с возможностью менять размер на лету.

### Базовые команды

**Создание с нуля:**

bashcopy

```bash
# 1. Инициализируем диски как PVpvcreate /dev/sdb /dev/sdc # 2. Создаём VG из этих PVvgcreate vg_main /dev/sdb /dev/sdc # 3. Создаём LV нужного размера из VGlvcreate -L 200G -n lv_data vg_main # 4. Форматируемmkfs.ext4 /dev/vg_main/lv_data # 5. Монтируемmount /dev/vg_main/lv_data /data
```

После этого `/dev/vg_main/lv_data` — это ваш логический том, который можно использовать как обычный раздел. И не забываем про fstab, чтобы он монтировался после ребута.

**Посмотреть информацию:**

bashcopy

```bash
pvs          # Physical Volumes — краткая сводкаvgs          # Volume Groups — краткая сводкаlvs          # Logical Volumes — краткая сводка pvdisplay    # подробная информация о PVvgdisplay    # подробная информация о VGlvdisplay    # подробная информация о LV
```

### Расширение диска без даунтайма

Вот тут главная фишка LVM. Раздел `/data` заполнился, нужно больше места.

**Вариант 1 — в VG ещё есть свободное место:**

bashcopy

```bash
# Расширяем LV на 50 ГБlvextend -L +50G /dev/vg_main/lv_data # Расширяем файловую системуresize2fs /dev/vg_main/lv_data          # для ext4xfs_growfs /data                         # для XFS
```

Всё. Без остановки сервисов, без размонтирования. ext4 и XFS поддерживают расширение на лету.

Обратите внимание — два шага: сначала расширяем LV (контейнер), потом расширяем файловую систему внутри него. Можно объединить в одну команду:

lvextend -L +50G --resizefs /dev/vg_main/lv_data

Флаг `--resizefs` сделает оба шага за вас.

**Вариант 2 — в VG нет свободного места, но есть новый диск:**

bashcopy

```bash
# Инициализируем новый диск как PVpvcreate /dev/sdd # Добавляем его в существующую VGvgextend vg_main /dev/sdd # Теперь в VG появилось место, расширяем LVlvextend -L +100G --resizefs /dev/vg_main/lv_data
```

Подключили новый диск, добавили его в пул, расширили раздел. Сервисы не останавливались, пользователи ничего не заметили. Вот ради этого LVM и нужен.

### Уменьшение тома

Расширять — легко и безопасно. Уменьшать — сложнее и рискованнее. XFS вообще не поддерживает уменьшение. ext4 поддерживает, но том нужно сначала размонтировать:

bashcopy

```bash
umount /datae2fsck -f /dev/vg_main/lv_data          # проверка ФС обязательнаresize2fs /dev/vg_main/lv_data 150G     # уменьшаем ФСlvreduce -L 150G /dev/vg_main/lv_data   # уменьшаем LVmount /data
```

Порядок важен — сначала уменьшаем файловую систему, потом LV. Если сделать наоборот — обрежете файловую систему и потеряете данные. В общем, уменьшение — операция, к которой надо подходить аккуратно, с бэкапом.
