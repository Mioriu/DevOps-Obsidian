# Ansible Vault — управление секретами

Так, давайте поговорим про секреты, потому что рано или поздно в ваших плейбуках появятся пароли, токены, приватные ключи и прочие вещи, которые нельзя хранить в открытом виде. Закоммитить пароль от базы в гит — это, мягко говоря, не лучшая идея. И вот как раз Ansible Vault решает эту проблему. Он позволяет шифровать файлы и отдельные переменные так, что они спокойно лежат в гите, но прочитать их может только тот, у кого есть пароль от волта.

## Шифрование файлов

Самый простой сценарий — зашифровать целый файл с переменными.

### Создать зашифрованный файл с нуля

ansible-vault create vars/secrets.yml

Спросит пароль, откроет редактор. Пишете свои секреты:

yamlcopy

```yaml
db_password: supersecret123api_token: ghp_xxxxxxxxxxxxsmtp_password: mailpass456
```

Сохраняете, закрываете — файл зашифрован. Если откроете его в текстовом редакторе, увидите что-то типа:

codecopy

```
$ANSIBLE_VAULT;1.1;AES25639633834623535613738393836383365...
```

### Зашифровать существующий файл

ansible-vault encrypt vars/secrets.yml

Был обычный YAML — стал зашифрованный.

### Расшифровать обратно

ansible-vault decrypt vars/secrets.yml

### Редактировать зашифрованный файл

ansible-vault edit vars/secrets.yml

Спросит пароль, откроет в редакторе расшифрованный файл. Редактируете, сохраняете — файл автоматически зашифруется обратно. Самый безопасный способ, потому что расшифрованная версия на диск не пишется.

### Посмотреть содержимое, не редактируя

ansible-vault view vars/secrets.yml

## Шифрование отдельных переменных

Иногда шифровать весь файл — перебор. У вас в `group_vars/production.yml` двадцать переменных, из них секретная — одна. Шифровать весь файл ради одного пароля неудобно, потому что тогда `git diff` не покажет, что изменилось в остальных переменных.

Для этого есть `encrypt_string`:

ansible-vault encrypt_string 'supersecret123' --name 'db_password'

Выдаст что-то типа:

yamlcopy

```yaml
db_password: !vault |          $ANSIBLE_VAULT;1.1;AES256          31396637653233303738613064656338...
```

Вот это вставляете прямо в обычный YAML-файл рядом с незашифрованными переменными:

yamlcopy

```yaml
# group_vars/production.ymlapp_port: 8080app_env: productionlog_level: warndb_host: db.company.localdb_password: !vault |          $ANSIBLE_VAULT;1.1;AES256          31396637653233303738613064656338...
```

Файл остаётся обычным, `git diff` работает нормально для всех переменных. Только `db_password` зашифрован. При запуске плейбука Ansible расшифрует его на лету.

## Запуск плейбуков с Vault

Когда в проекте есть зашифрованные данные, при запуске нужно указать пароль. Три способа.

### Ввести пароль вручную

ansible-playbook site.yml --ask-vault-pass

Спросит пароль в консоли. Нормально для ручного запуска, но для CI/CD не подходит.

### Файл с паролем

bashcopy

```bash
echo 'my_vault_password' > .vault_passchmod 600 .vault_passansible-playbook site.yml --vault-password-file .vault_pass
```

Или прописать в `ansible.cfg`:

inicopy

```ini
[defaults]vault_password_file = .vault_pass
```

Тогда не нужно каждый раз указывать флаг. Файл `.vault_pass` обязательно добавьте в `.gitignore` — сам пароль в гит попасть не должен.

### Скрипт, который отдаёт пароль

ansible-playbook site.yml --vault-password-file ./get_vault_pass.sh

Где `get_vault_pass.sh` — исполняемый скрипт, который может, например, достать пароль из переменной окружения или из менеджера секретов:

bashcopy

```bash
#!/bin/bashecho "$ANSIBLE_VAULT_PASSWORD"
```

Вот это — основной способ для CI/CD. В пайплайне задаёте переменную окружения `ANSIBLE_VAULT_PASSWORD` через секреты GitLab/GitHub, а скрипт её отдаёт Ansible'у.
