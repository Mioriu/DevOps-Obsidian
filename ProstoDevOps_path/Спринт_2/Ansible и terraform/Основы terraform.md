## Установка

Terraform – это один бинарник. Ставится через пакетный менеджер или скачивается с сайта, проверка обычная:

terraform -version

Для работы из России есть нюанс: реестр провайдеров [registry.terraform.io](http://registry.terraform.io/) не отдает плагины на российские IP, и `init` падает на скачивании. Лечится зеркалом – у Yandex Cloud есть публичное зеркало реестра, оно прописывается один раз в файле `~/.terraformrc`:

HCL

Копировать

```hcl
# ~/.terraformrc
provider_installation {
  network_mirror {
    url     = "https://terraform-mirror.yandexcloud.net/"
    include = ["registry.terraform.io/*/*"]
  }
  direct {
    exclude = ["registry.terraform.io/*/*"]
  }
}
```

После этого провайдеры скачиваются через зеркало, а все остальное работает как обычно.

## init

Берем конфиг из прошлого урока – Docker-провайдер, образ и контейнер – и кладем его в пустую директорию как `main.tf`. Первая команда в любой директории с Terraform-кодом:

![Workflow Terraform: init, plan, apply, destroy](https://prostodevops.ru/api/uploads/lessons/terraform-workflow-init-plan-apply-destroy-01.webp)Workflow Terraform: init, plan, apply, destroy

`init` читает блок `required_providers`, скачивает указанные провайдеры и кладет их в скрытую директорию `.terraform/`. Заодно создается файл `.terraform.lock.hcl` – в нем фиксируются точные версии и хэши скачанных провайдеров, чтобы у всех, кто работает с этим кодом, версии совпадали. Lock-файл коммитится в Git, та же логика, что с requirements-файлами. А `.terraform/` – это скачанные бинарники, им место в `.gitignore`.

Запускается `init` не перед каждой командой, а когда меняется состав зависимостей: первый раз в директории, после добавления нового провайдера или модуля. Все остальное время про него можно не вспоминать – если `init` нужен, об этом прямо скажет ошибка следующей команды.

## plan

Главная команда для нас – `plan`:

terraform plan

Код сравнивается с учетом созданного, и выводится план: что будет создано, изменено и удалено, если этот код применить. Для нашего конфига на чистой директории план выглядит так (сокращенно):

Копировать

```
Terraform will perform the following actions:

  # docker_image.nginx will be created
  + resource "docker_image" "nginx" {
      + name = "nginx:1.25"
      ...
    }

  # docker_container.web will be created
  + resource "docker_container" "web" {
      + name  = "web"
      ...
    }

Plan: 2 to add, 0 to change, 0 to destroy.
```

Каждое действие помечено символом, и читать план – значит в первую очередь смотреть на них:

Символ Действие `+` Создать `-` Удалить `~` Изменить на месте `-/+` Пересоздать: удалить и создать заново

![Символы плана: плюс, минус, тильда, пересоздание](https://prostodevops.ru/api/uploads/lessons/terraform-workflow-init-plan-apply-destroy-02.webp)Символы плана: плюс, минус, тильда, пересоздание

При этом `plan` ничего не меняет – это чистый предпросмотр, тот же принцип, что `--check` в Ansible. Итоговая строка `Plan: 2 to add, 0 to change, 0 to destroy` – короткая сводка, по которой сразу видно масштаб изменений. Ожидали одну правку, а в плане десять удалений – значит что-то пошло не так, и хорошо, что это видно до применения.

## apply

Применение кода:

terraform apply

`apply` сначала выводит тот же план и запрашивает подтверждение – выполнение начинается только после введенного руками `yes`. Дальше ресурсы создаются, и в конце сводка:

Apply complete! Resources: 2 added, 0 changed, 0 destroyed.

После первого `apply` в директории появляется файл `terraform.tfstate` – тот самый state, учет созданного. Проверить результат можно командой `docker ps`: контейнер `web` запущен, порт 8080 проброшен.

Повторный `apply` без правок кода ничего не сделает:

No changes. Your infrastructure matches the configuration.

Код совпадает с учетом – делать нечего. Та же идемпотентность, что в Ansible, только сверка идет не с реальностью, а со state.

Для автоматических запусков есть флаг `-auto-approve` – применение без вопроса. В CI без него никак, а вот руками с ним лучше не работать.

## Изменения и пересоздание

Допустим решили поправить код, меняем имя контейнера с `web` на `frontend` и запускаем `plan`:

Копировать

```
  # docker_container.web must be replaced
-/+ resource "docker_container" "web" {
      ~ name  = "web" -> "frontend" # forces replacement
      ...
    }

Plan: 1 to add, 0 to change, 1 to destroy.
```

Вот тут проявляется символ `-/+`. Не все изменения возможны на живом объекте: имя работающему контейнеру не поменять, поэтому старый удаляется и создается новый с нужным именем. План помечает аргумент, из-за которого это происходит: `# forces replacement`.

Для контейнера пересоздание безболезненно – он эфемерен, как мы выяснили еще в модуле про Docker. А вот для виртуальной машины с данными на диске или для базы `-/+` означает удаление вместе со всем содержимым. Безобидная на вид правка одного аргумента может обернуться пересозданием, поэтому план читается перед каждым `apply`, и в первую очередь в нем ищутся `-` и `-/+`.

## destroy

Обратная команда – удалить все, что числится в state:

terraform destroy

Выводится план удаления со всеми ресурсами под знаком `-`, запрашивается подтверждение, после `yes` инфраструктура сносится. Сводка зеркальная: `Destroy complete! Resources: 2 destroyed`.

Звучит как команда на крайний случай, но используется она постоянно. Тестовый стенд под эксперимент, окружение под демо, песочница. Раз все описано кодом, окружение перестает быть ценностью, которую страшно трогать: его в любой момент можно поднять заново тем же `apply`.

## Файлы в директории

После полного цикла в директории лежит такой набор:

Файл Что это В Git `main.tf` Код инфраструктуры Да `.terraform.lock.hcl` Зафиксированные версии провайдеров Да `.terraform/` Скачанные бинарники провайдеров Нет `terraform.tfstate` State, учет созданного Нет

![Файлы Terraform-проекта: что коммитится в Git](https://prostodevops.ru/api/uploads/lessons/terraform-workflow-init-plan-apply-destroy-03.webp)Файлы Terraform-проекта: что коммитится в Git

С кодом и lock-файлом все понятно. `.terraform/` – это просто кэш, он восстанавливается любым `init`. А вот `terraform.tfstate` в Git не кладут по двум причинам: в нем открытым текстом лежат все атрибуты ресурсов, включая пароли и токены, и при работе вдвоем над одним state через Git гарантированы конфликты с расхождением учета. Куда state девать правильно – тема отдельного урока, пока он остается локальным файлом.
