# Firewalls и iptables/nftables

## Зачем это знать?

Файрвол — это базовый инструмент сетевой безопасности. Он решает кто может подключаться к твоему серверу, куда может ходить сервер, и какой трафик разрешён между сетями. Без понимания файрволов ты будешь постоянно натыкаться на "не работает, не знаю почему".

## 1. Что такое файрвол

Файрвол (firewall, межсетевой экран) — это фильтр сетевого трафика. Он смотрит на каждый пакет и решает: пропустить, отбросить или отклонить.

Три основных действия:

- **ACCEPT** — пропустить пакет
- **DROP** — молча выбросить (отправитель не узнает что произошло)
- **REJECT** — отклонить и отправить ответ об ошибке

Разница между DROP и REJECT важна. DROP — пакет просто исчезает, клиент висит в ожидании таймаута. REJECT — клиент сразу получает ошибку "Connection refused" или ICMP-сообщение.

DROP безопаснее для внешнего трафика: сканер портов не узнает, есть ли вообще что-то на этом порту. REJECT удобнее для внутренней сети: сразу понятно что доступ закрыт, не надо ждать таймаут.

### Где работает файрвол

В Linux файрвол работает на уровне ядра, в подсистеме Netfilter. Это не отдельная программа — это часть ядра, которая обрабатывает каждый сетевой пакет.

iptables и nftables — это утилиты для настройки Netfilter. Они просто передают правила в ядро. Сами по себе они ничего не фильтруют.

### Stateful vs Stateless

Современные файрволы — stateful. Они отслеживают состояние соединений.

Что это значит на практике: ты разрешаешь исходящий HTTP. Когда твой сервер делает запрос на внешний сайт, файрвол запоминает это соединение. Когда приходит ответ — файрвол понимает, что это ответ на разрешённый запрос, и пропускает его. Тебе не нужно явно разрешать входящий трафик для ответов.

Stateless файрвол не помнит соединения. Ему пришлось бы разрешать весь входящий трафик с порта 80/443, что небезопасно.

В iptables/nftables за отслеживание состояния отвечает модуль conntrack. Состояния пакетов:

- **NEW** — первый пакет нового соединения
- **ESTABLISHED** — пакет в рамках уже установленного соединения
- **RELATED** — связанный пакет (например, ICMP-ошибка для существующего соединения)
- **INVALID** — пакет, который не удалось классифицировать

## 2. iptables

iptables — стандартный инструмент управления файрволом в Linux уже больше 20 лет. Да, есть nftables, но iptables ты встретишь везде: в документации, в скриптах, в Docker, в Kubernetes.

### Структура: таблицы, цепочки, правила

iptables организован в три уровня:

**Таблицы** — группы правил по назначению:

- `filter` — основная фильтрация (по умолчанию)
- `nat` — трансляция адресов и портов
- `mangle` — модификация пакетов
- `raw` — обработка до conntrack

**Цепочки** — точки обработки пакетов:

- `INPUT` — входящие пакеты для этого хоста
- `OUTPUT` — исходящие пакеты от этого хоста
- `FORWARD` — транзитные пакеты (проходящие через хост)
- `PREROUTING` — до решения о маршрутизации
- `POSTROUTING` — после решения о маршрутизации

**Правила** — конкретные условия и действия.

### Порядок правил

Важно: правила проверяются по порядку. Первое совпавшее правило срабатывает, остальные игнорируются.

Плохой порядок:

bashcopy

```bash
iptables -P INPUT DROPiptables -A INPUT -p tcp --dport 22 -j ACCEPT  # Это правило никогда не сработает!
```

Политика DROP применяется если ничего не совпало, но пакет должен дойти до этой проверки.

Хороший порядок:

bashcopy

```bash
# Сначала разрешающие правилаiptables -A INPUT -i lo -j ACCEPTiptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPTiptables -A INPUT -p tcp --dport 22 -j ACCEPTiptables -A INPUT -p tcp --dport 80 -j ACCEPT # Политика по умолчанию — в концеiptables -P INPUT DROP
```

### NAT с iptables

NAT настраивается в таблице nat. Основные случаи:

**SNAT/Masquerade** — исходящий трафик от внутренней сети через внешний IP:

bashcopy

```bash
# Включить форвардингecho 1 > /proc/sys/net/ipv4/ip_forward # Маскарадинг на интерфейсе eth0 (для динамического IP)iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE # Или SNAT для статического IPiptables -t nat -A POSTROUTING -o eth0 -j SNAT --to-source 203.0.113.1
```

**DNAT/Port forwarding** — перенаправление входящего трафика:

bashcopy

```bash
# Перенаправить порт 8080 на внутренний сервер 10.0.0.10:80iptables -t nat -A PREROUTING -p tcp --dport 8080 -j DNAT --to-destination 10.0.0.10:80 # Не забыть разрешить форвардiptables -A FORWARD -p tcp -d 10.0.0.10 --dport 80 -j ACCEPT
```

## 3. nftables

nftables — замена iptables, включённая в ядро с версии 3.13 (2014). Сейчас это стандарт в новых дистрибутивах. Debian 10+, Ubuntu 20.04+, CentOS 8+ используют nftables по умолчанию.

Почему nftables лучше:

- Единый синтаксис для IPv4, IPv6, ARP, мостов
- Атомарные обновления правил (весь набор правил меняется разом)
- Лучшая производительность на больших наборах правил
- Более читаемый синтаксис

### Основные концепции

В nftables структура немного другая:

- **Таблицы** — контейнеры для цепочек (нет предопределённых, ты создаёшь свои)
- **Цепочки** — содержат правила, привязаны к hook-точкам
- **Правила** — условия и действия

Hook-точки (аналоги цепочек iptables):

- `prerouting`
- `input`
- `forward`
- `output`
- `postrouting`

На многих системах iptables — это уже обёртка над nftables (iptables-nft). Проверить:

bashcopy

```bash
iptables -V# iptables v1.8.7 (nf_tables)  ← nftables backend# или# iptables v1.8.7 (legacy)     ← старый backend
```

## 4. firewalld и ufw: обёртки

На практике ты редко пишешь правила iptables/nftables руками. Обычно используются обёртки.

### firewalld (CentOS/RHEL/Fedora)

firewalld работает с зонами. Зона — это набор правил для определённого уровня доверия.

Основные зоны:

- `drop` — входящие отбрасываются, исходящие разрешены
- `block` — входящие отклоняются с ICMP-ответом
- `public` — публичная сеть, минимум сервисов
- `work` — рабочая сеть, больше доверия
- `home` — домашняя сеть
- `trusted` — всё разрешено

### ufw (Ubuntu/Debian)

ufw (Uncomplicated Firewall) — простая обёртка над iptables.

bashcopy

```bash
# Включитьufw enable # Статусufw status verbose # Политика по умолчаниюufw default deny incomingufw default allow outgoing # Разрешить SSHufw allow ssh# илиufw allow 22/tcp # Разрешить из подсетиufw allow from 10.0.0.0/8 to any port 22 # Разрешить диапазон портовufw allow 6000:6007/tcp # Удалить правилоufw delete allow 80/tcp # Сброс всех правилufw reset
```

Важно: при включении ufw убедись, что SSH разрешён, иначе потеряешь доступ.

## 5. Файрволы и контейнеры

### Docker

Docker создаёт свои правила iptables. Когда ты публикуешь порт `-p 8080:80`, Docker добавляет:

- DNAT в таблице nat для перенаправления
- Правила в цепочке DOCKER для разрешения трафика

Проблема: Docker вставляет свои правила в PREROUTING, до INPUT. Твои правила в INPUT не влияют на опубликованные порты контейнеров.

Если нужно ограничить доступ к контейнеру, варианты:

1. Биндить на 127.0.0.1: `-p 127.0.0.1:8080:80`
2. Использовать цепочку DOCKER-USER:

bashcopy

```bash
iptables -I DOCKER-USER -i eth0 -p tcp --dport 80 -j DROPiptables -I DOCKER-USER -i eth0 -s 10.0.0.0/8 -p tcp --dport 80 -j ACCEPT
```

### Kubernetes

В Kubernetes сетевые политики (Network Policies) — это файрвол для подов. Реализуется через CNI-плагин (Calico, Cilium, и др.).

## Типичные проблемы и решения

### Проблема 1: "Connection timed out" при подключении к серверу

Симптомы:

- `curl` висит и отваливается по таймауту
- `telnet` не подключается
- Приложение на сервере работает, порт слушается

Типичные причины:

- Политика INPUT DROP, нет правила для порта → добавить правило
- firewalld/ufw включён, порт не открыт → добавить сервис/порт
- Облачный файрвол (AWS Security Group, GCP Firewall) → проверить в консоли облака

### Проблема 2: Потеря SSH-доступа после настройки файрвола

Симптомы:

- Настроил файрвол, SSH отвалился
- Сервер пингуется, но SSH не подключается

Предотвращение:

Перед настройкой:

bashcopy

```bash
# Запланировать сброс правил через 5 минутecho "iptables -F" | at now + 5 minutes
```

Если уже потерял доступ:

- Консоль облачного провайдера (VNC/Serial console)
- Recovery mode если физический сервер
- Смонтировать диск к другой VM, отредактировать /etc/iptables/rules.v4

### Проблема 3: Docker-контейнер доступен извне, хотя не должен быть

Симптомы:

- Добавил правило DROP в INPUT
- Контейнер всё равно доступен снаружи

Причина: Docker использует PREROUTING и FORWARD, не INPUT.

Решение:

bashcopy

```bash
# Ограничить через DOCKER-USERiptables -I DOCKER-USER -i eth0 ! -s 10.0.0.0/8 -j DROP
```

Или при запуске контейнера биндить на localhost:

docker run -p 127.0.0.1:8080:80 nginx

### Проблема 4: Сервер не может подключиться к внешним ресурсам

Симптомы:

- `curl google.com` — тишина или ошибка
- DNS не резолвится

Диагностика:

Шаг 1: Проверить политику OUTPUT:

iptables -L OUTPUT -n

Шаг 2: Проверить, разрешён ли DNS:

iptables -L OUTPUT -n | grep 53

Типичные причины:

- Политика OUTPUT DROP, нет правила для DNS/HTTP → добавить правила
- Нет правила для ESTABLISHED → `iptables -A OUTPUT -m state --state ESTABLISHED -j ACCEPT`

## Что запомнить

1. **Файрвол фильтрует пакеты** — ACCEPT (пропустить), DROP (молча отбросить), REJECT (отклонить с ответом)
    
2. **Netfilter — в ядре, iptables/nftables — утилиты** для передачи правил в ядро
    
3. **Порядок правил важен** — первое совпавшее срабатывает
    
4. **Stateful файрвол** отслеживает соединения — правило для ESTABLISHED,RELATED обязательно
    
5. **iptables правила в памяти** — нужно сохранять явно через iptables-save или iptables-persistent
    
6. **nftables — современная замена** с единым синтаксисом и лучшей производительностью
    
7. **firewalld и ufw — обёртки** для удобства, под капотом тот же iptables/nftables
    
8. **Docker обходит INPUT** — ограничивать доступ к контейнерам через DOCKER-USER или биндинг на localhost
    
9. **Перед настройкой файрвола** — убедись что SSH разрешён, запланируй откат
    
10. **Один инструмент** — либо firewalld, либо iptables напрямую, не оба сразу
