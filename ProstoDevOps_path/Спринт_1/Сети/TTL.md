# TTL (Time To Live)

## Зачем это знать?

TTL встречается в двух совершенно разных контекстах, и путаница между ними — частый источник ошибок.

Ситуация первая: ты поменял A-запись для домена, а часть пользователей всё ещё идёт на старый сервер. Это DNS TTL — запись закэширована, и резолверы не будут запрашивать новую, пока не истечёт время.

Ситуация вторая: `traceroute` показывает путь до сервера, и ты видишь, через какие роутеры идут пакеты. Это работает благодаря IP TTL — счётчику, который уменьшается на каждом хопе.

Одно название, совершенно разная механика.

## 1. Два разных TTL

||IP TTL|DNS TTL|
|---|---|---|
|Что это|Счётчик хопов в IP-пакете|Время кэширования DNS-записи|
|Единица измерения|Хопы (переходы между роутерами)|Секунды|
|Где находится|Заголовок IP-пакета|DNS-ответ (для каждой записи)|
|Кто уменьшает|Каждый роутер на пути|Время (автоматически)|
|Что происходит при нуле|Пакет отбрасывается, отправитель получает ICMP Time Exceeded|Резолвер запрашивает запись заново|
|Зачем нужен|Защита от бесконечных петель маршрутизации|Баланс между актуальностью и нагрузкой на DNS|

## 2. IP TTL: счётчик хопов

### Как работает

Когда пакет создаётся, в его IP-заголовок записывается TTL — обычно 64, 128 или 255. Каждый роутер, через который проходит пакет, уменьшает TTL на единицу. Если TTL становится нулём, роутер отбрасывает пакет и отправляет отправителю ICMP-сообщение "Time Exceeded".

![Схема в материале «Фундамент 3: TTL»: Пакет: TTL=64](https://offers.prostodevops.ru/diagrams/extras/seti/fundament-3-ttl-3.png)Схема в материале «Фундамент 3: TTL»: Пакет: TTL=64

### Зачем это нужно

Защита от петель маршрутизации. Если в сети ошибка конфигурации и пакеты ходят по кругу (A → B → C → A → ...), без TTL они бы циркулировали вечно, забивая сеть. TTL гарантирует, что пакет умрёт максимум через N хопов.

### Как traceroute использует TTL

`traceroute` отправляет пакеты с TTL=1, потом TTL=2, потом TTL=3 и так далее.

![Схема в материале «Фундамент 3: TTL»: TTL=1: Первый роутер отбрасывает пакет, шлёт ICMP → мы узнаём его IP](https://offers.prostodevops.ru/diagrams/extras/seti/fundament-3-ttl-2.png)Схема в материале «Фундамент 3: TTL»: TTL=1: Первый роутер отбрасывает пакет, шлёт ICMP → мы узнаём его IP

Пример вывода:

bashcopy

```bash
traceroute example.com  1  192.168.1.1 (192.168.1.1)  1.234 ms 2  10.0.0.1 (10.0.0.1)  5.678 ms 3  72.14.215.85 (72.14.215.85)  12.345 ms 4  93.184.216.34 (93.184.216.34)  15.678 ms
```

### Начальные значения TTL

Разные ОС используют разные начальные TTL:

|ОС|Начальный TTL|
|---|---|
|Linux|64|
|Windows|128|
|macOS|64|
|Cisco IOS|255|

По TTL в ответе можно примерно определить ОС удалённого хоста и сколько хопов до него:

bashcopy

```bash
ping example.com # Получили TTL=52 в ответе# Вероятно: Linux (64 - 52 = 12 хопов) или Windows (128 - 52 = 76 хопов)# 12 хопов правдоподобнее, значит скорее всего Linux
```

### Посмотреть и изменить TTL

bashcopy

```bash
# Увидеть TTL в ответах pingping -c 3 example.com # Установить TTL для исходящих пакетовping -t 10 example.com  # macOS/BSDping -c 3 --ttl=10 example.com  # Linux # В tcpdumptcpdump -v -i eth0 icmp# Покажет ttl=64 в выводе
```

## 3. DNS TTL: время кэширования

### Как работает

Каждая DNS-запись имеет TTL в секундах. Когда резолвер получает ответ, он кэширует его на время TTL. Пока TTL не истёк, резолвер отдаёт ответ из кэша, не обращаясь к авторитетному серверу.

codecopy

```
Запрос: example.com A?Ответ: 93.184.216.34, TTL=3600 Следующие 3600 секунд (1 час):- Резолвер отдаёт 93.184.216.34 из кэша- Авторитетный сервер не опрашивается После 3600 секунд:- Резолвер запрашивает заново
```

### Где задаётся

В зонном файле или панели управления DNS:

codecopy

```
example.com.    300   IN  A     93.184.216.34                ^^^                TTL = 300 секунд = 5 минут
```

### Типичные значения

|TTL|Секунды|Когда использовать|
|---|---|---|
|60|1 минута|Активная миграция, failover|
|300|5 минут|Часто меняющиеся записи|
|3600|1 час|Стандартный выбор|
|86400|1 сутки|Стабильные записи (NS, MX)|
|604800|1 неделя|Очень стабильные записи|

### Посмотреть TTL записи

bashcopy

```bash
dig example.com ;; ANSWER SECTION:example.com.        3600    IN      A       93.184.216.34                    ^^^^                    TTL в секундах
```

Важно: это TTL, который вернул резолвер. Он уменьшается со временем. Если запись была закэширована 1000 секунд назад с TTL=3600, сейчас dig покажет TTL=2600.

Чтобы увидеть оригинальный TTL, спроси авторитетный сервер напрямую:

bashcopy

```bash
# Сначала узнать NSdig NS example.com +short # Потом спросить его напрямуюdig @ns1.example.com example.com
```

## 4. Частые ошибки

### Путать единицы измерения

IP TTL — хопы (целое число, обычно 64/128/255). DNS TTL — секунды (от 60 до 604800 и больше).

Когда говорят "TTL 300", в контексте DNS это 5 минут. В контексте IP это очень много хопов (и бессмысленно, т.к. интернет не такой большой).

### Ожидать мгновенного обновления DNS

Поменял запись — а она не обновляется час. Это не баг, это TTL. Старая запись закэширована у резолверов по всему миру.

Правильный подход к миграции:

1. Узнать текущий TTL: `dig example.com`
2. Уменьшить TTL до 300 секунд
3. Подождать старый TTL (чтобы везде закэшировался новый низкий TTL)
4. Сделать изменение
5. После стабилизации вернуть TTL обратно

### Думать, что DNS TTL — гарантия

TTL — это _рекомендация_. Некоторые резолверы его игнорируют:

- Могут кэшировать дольше (экономия трафика)
- Могут принудительно увеличивать минимальный TTL
- Браузеры имеют свой кэш с своими правилами

Поэтому даже с TTL=60 нельзя гарантировать обновление за минуту.

## Что запомнить

1. **IP TTL — счётчик хопов** (64/128/255), уменьшается на каждом роутере, защищает от петель
    
2. **DNS TTL — секунды кэширования** (60-86400+), определяет, как долго резолверы хранят ответ
    
3. **traceroute работает через IP TTL** — отправляет пакеты с TTL=1, 2, 3... и собирает ICMP-ответы
    
4. **Перед миграцией снижай DNS TTL заранее** — иначе часть трафика будет идти на старый IP весь период старого TTL
    
5. **DNS TTL — рекомендация, не гарантия** — резолверы и браузеры могут вести себя по-своему
