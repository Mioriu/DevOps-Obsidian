# CDN

## Зачем это знать?

Сервер в Москве, а пользователь во Владивостоке. Каждый запрос идёт через всю страну — 100+ мс задержки только на сеть. Подключаешь CDN — статика отдаётся с ближайшего узла, страница грузится в три раза быстрее.

Другая ситуация: вышел релиз, на сайт пришло в 50 раз больше трафика. Без CDN сервер лёг бы под нагрузкой. С CDN — 95% запросов ушло в кэш, сервак даже не заметил.

## 1. Что такое CDN

CDN (Content Delivery Network) — географически распределённая сеть серверов, которая кэширует и отдаёт контент с ближайшей к пользователю точки.

![CDN: без CDN vs с CDN — сравнение latency](https://offers.prostodevops.ru/diagrams/network/cdn-compare.png)CDN: без CDN vs с CDN — сравнение latency

**Origin** — исходный сервер с контентом.

**Edge (PoP, Point of Presence)** — узел CDN, географически близкий к пользователю. Их сотни по всему миру.

### Что даёт CDN

- **Скорость.**
- **Снижение нагрузки на origin.**
- **Отказоустойчивость.**
- **Защита от DDoS.**
- **Масштабирование.**

## 2. Как работает CDN

### Подключение через DNS

Типичная схема: домен указывает на CDN, CDN проксирует к origin.

### CNAME на CDN

codecopy

```
# DNS-записиexample.com.       A      93.184.216.34      # origin напрямуюcdn.example.com.   CNAME  d1234.cloudfront.net.  # через CDN # В HTML<img src="https://cdn.example.com/images/logo.png">
```

### Полное проксирование

Современные CDN могут проксировать весь сайт:

example.com.  CNAME  example.com.cdn77.org.

Весь трафик идёт через CDN. CDN решает, что кэшировать (статику), а что проксировать напрямую (API, динамику).

### Anycast vs GeoDNS

**GeoDNS** — DNS возвращает разные IP в зависимости от географии клиента. Пользователь из Европы получает IP европейского узла.

**Anycast** — один IP анонсируется из многих точек мира через BGP. Пакеты автоматически идут к ближайшему узлу по маршрутизации.

Большинство крупных CDN используют Anycast — он надёжнее и точнее.

## 3. Кэширование в CDN

### Что кэшировать

**Хорошо кэшируется (статика):**

- Изображения (JPEG, PNG, WebP, SVG)
- CSS и JavaScript
- Шрифты
- Видео и аудио
- PDF и другие файлы

**Обычно не кэшируется:**

- HTML (часто персонализирован)
- API-ответы (зависят от пользователя)
- POST/PUT/DELETE запросы
- Контент с `Set-Cookie`

### Как CDN решает, что кэшировать

CDN смотрит на заголовки от origin:

Cache-Control: public, max-age=86400

→ Кэшировать на 24 часа, можно на CDN.

Cache-Control: private, no-store

→ Не кэшировать на CDN.

Cache-Control: max-age=0, must-revalidate

→ Всегда проверять у origin (условный запрос).

### TTL и переопределение

CDN обычно позволяет переопределить TTL:

- **Respect origin headers** — делать как говорит origin
- **Override TTL** — игнорировать origin, кэшировать N секунд
- **Browser TTL vs Edge TTL** — разные сроки для браузера и CDN

Пример: origin говорит `max-age=60`, но ты настроил CDN кэшировать на час. CDN будет держать в кэше час, но браузеру отдаст `max-age=60`.

### Cache Key

CDN решает, один это ресурс или разные, по cache key. По умолчанию:

Cache key = URL (scheme + host + path + query string)

`/api/data?page=1` и `/api/data?page=2` — разные записи в кэше.

Можно настроить:

- Игнорировать query string (для статики с версиями: `style.css?v=123`)
- Добавить заголовки в key (разный кэш для разных `Accept-Encoding`)
- Добавить cookies (разный кэш для разных сессий — осторожно!)

## 4. Инвалидация кэша

Контент изменился — как заставить CDN отдавать новую версию?

### Способ 1: Подождать TTL

Самый простой. Если TTL = 1 час, через час все получат новую версию.

Минус: долго ждать, если нужно срочно.

### Способ 2: Purge (очистка)

Принудительно удалить из кэша:

bashcopy

```bash
# Cloudflare APIcurl -X POST "https://api.cloudflare.com/client/v4/zones/ZONE_ID/purge_cache" \     -H "Authorization: Bearer TOKEN" \     -H "Content-Type: application/json" \     -d '{"files":["https://example.com/style.css"]}' # Или очистить всё-d '{"purge_everything":true}'
```

Минус: занимает время (секунды-минуты), не мгновенно на всех edge.

### Способ 3: Версионирование (рекомендуется)

Меняешь имя файла при изменении:

htmlcopy

```html
<!-- Было --><link rel="stylesheet" href="/css/style.css"> <!-- Стало --><link rel="stylesheet" href="/css/style.v2.css"><!-- или --><link rel="stylesheet" href="/css/style.css?v=abc123">
```

Новый URL = новый cache key = запрос к origin = свежий контент.

Для этого используют:

- Хэш содержимого в имени: `style.a1b2c3d4.css`
- Версию или timestamp: `style.css?v=1705312800`

Build-системы (Webpack, Vite) делают это автоматически.

### Способ 4: Cache Tags (продвинуто)

Некоторые CDN (Fastly, Cloudflare Enterprise) поддерживают теги:

codecopy

```
# Origin отдаёт заголовокSurrogate-Key: product-123 category-electronics # Потом можно инвалидировать по тегуcurl -X POST ".../purge" -d '{"tags":["product-123"]}'
```

Инвалидируются все ресурсы с этим тегом.

## 7. CDN для динамического контента

CDN полезен не только для статики:

### Оптимизация соединений

Даже без кэширования CDN ускоряет:

- **TCP-оптимизация** — edge держит постоянные соединения с origin
- **TLS-терминация** — TLS handshake с ближайшим edge, а не с далёким origin
- **HTTP/2 и HTTP/3** — CDN может поддерживать, даже если origin не поддерживает

![CDN: HTTP/3 от пользователя к edge, HTTP/1.1 от edge к origin](https://offers.prostodevops.ru/diagrams/network/cdn-protocols.png)CDN: HTTP/3 от пользователя к edge, HTTP/1.1 от edge к origin

### Edge Computing

Примеры использования:

- A/B тестирование
- Геолокация и редиректы
- Персонализация без обращения к origin
- Валидация и трансформация запросов

## 8. Типичные проблемы

### Проблема 1: Старый контент в кэше

Симптомы:

- Обновил файл, а пользователи видят старую версию
- `cf-cache-status: HIT`, но контент устаревший

Решения:

- Purge кэша через панель или API
- Использовать версионирование файлов
- Уменьшить TTL для часто меняющегося контента

### Проблема 2: Контент не кэшируется

Симптомы:

- `cf-cache-status: BYPASS` или `DYNAMIC`
- Каждый запрос идёт на origin

Решения:

- Исправить заголовки на origin
- Настроить override в CDN
- Убрать `Set-Cookie` для статики

### Проблема 3: Разный контент для разных пользователей

Симптомы:

- Пользователь A видит контент пользователя B
- Персонализированные данные утекают

Причина: закэшировался ответ с персональными данными.

Решение:

- Никогда не кэшировать персонализированный контент
- Разделять статику и динамику по разным путям/доменам

### Проблема 4: CORS ошибки через CDN

Симптомы:

- API работает напрямую, не работает через CDN
- Браузер блокирует из-за CORS

Причина: CDN кэширует ответ без CORS-заголовков, потом отдаёт его кросс-доменному запросу.

Решение:

- Добавить `Vary: Origin` на origin
- Или настроить CORS-заголовки на уровне CDN
