# Ad-hoc команды в Ansible

Так, мы установили Ansible, настроили подключение, разобрались с inventory. Теперь давайте поговорим про ad-hoc команды, потому что это, по сути, самый быстрый способ что-то сделать на серверах через Ansible. Без плейбуков, без YAML-файлов, без ничего. Просто одна команда в терминале — и она выполняется на всех нужных серверах разом.

**Ad-hoc** — это, если переводить, что-то типа _"для конкретного случая"_. То есть, это одноразовые команды, которые вы запускаете прямо из консоли, когда нужно быстро что-то посмотреть, что-то поправить или потушить какой-нибудь прод. Это не замена плейбукам — для повторяемых задач мы будем писать плейбуки. Но когда нужно прямо сейчас, быстро, на двадцати серверах что-то сделать — ad-hoc незаменим.

## Общий синтаксис

Прежде чем разбирать конкретные модули, давайте зафиксируем общую структуру команды, чтобы она в голове отложилась:

ansible <хосты> -m <модуль> -a "<аргументы>"

- **`<хосты>`** — это кого трогаем (группа из inventory, конкретный хост или `all`).
- **`-m`** — какой модуль используем.
- **`-a`** — какие аргументы передаём этому модулю.

Всё остальное — это флаги, типа `-b` для sudo, `-f` для параллелизма и так далее. Их разберём чуть позже.

## Модуль `command`

Это модуль по умолчанию. То есть, если вы не указываете `-m`, Ansible использует именно `command`. Он просто выполняет команду на удалённом сервере.

ansible all -m command -a "uptime"

Или, так как command — модуль по умолчанию, можно короче:

ansible all -a "uptime"

Результат будет одинаковый. Ansible подключится к серверам, выполнит `uptime` и покажет вам вывод.

Ещё примеры:

bashcopy

```bash
# посмотреть свободное местоansible all -a "df -h" # посмотреть памятьansible all -a "free -m" # посмотреть кто залогиненansible all -a "who" # посмотреть версию ядраansible all -a "uname -r"
```

Но тут есть **важный нюанс**. Модуль `command` не прогоняет команду через shell. Что это значит? Это значит, что всякие штуки типа пайпов (`|`), перенаправления вывода (`>`), переменные окружения (`$HOME`), подстановки (`*`) — это всё не будет работать в `command`. То есть, вот такое упадёт:

bashcopy

```bash
# НЕ сработает через commandansible all -a "cat /var/log/syslog | tail -20"
```

Потому что пайп `|` — это фича шелла, а `command` шелл не использует. И вот тут на сцену выходит следующий модуль.

## Модуль `shell`

`shell` — это, по сути, то же самое, что `command`, но он прогоняет команду через `/bin/sh`. То есть, все шелловые фишки тут работают:

bashcopy

```bash
# пайпы работаютansible all -m shell -a "cat /var/log/syslog | tail -20" # перенаправление работаетansible all -m shell -a "echo 'hello' > /tmp/test.txt" # переменные окружения работаютansible all -m shell -a "echo $HOME" # подстановки работаютansible all -m shell -a "ls /var/log/*.log"
```

**`command` vs `shell` — когда что использовать?** `command` безопаснее, потому что он не интерпретирует спецсимволы. Если вам не нужны пайпы и перенаправления — используйте `command`. Если нужны — `shell`. Вот такое простое правило.

## Модуль `copy`

Этот модуль копирует файлы с вашей машины на удалённые серверы. Очень часто используется. Допустим, у вас есть конфиг, который нужно раскидать на все серверы:

ansible all -m copy -a "src=./nginx.conf dest=/etc/nginx/nginx.conf owner=root group=root mode=0644"

Разберём аргументы:

- **`src`** — путь к файлу на вашей машине (control node).
- **`dest`** — куда положить на удалённом сервере.
- **`owner`** — владелец файла.
- **`group`** — группа.
- **`mode`** — права на файл. Вот тут осторожно: если написать `mode=644` без нуля в начале — Ansible может интерпретировать это как десятичное число, и права будут совсем не те, что вы ожидали. Поэтому всегда пишем `mode=0644` с нулём.

Ещё один полезный кейс — быстро создать файл с каким-то содержимым без копирования:

ansible all -m copy -a "content='Hello from Ansible\n' dest=/tmp/hello.txt"

Тут вместо `src` мы используем `content`, и Ansible просто создаст файл с этим текстом на всех серверах.

## Модуль `file`

Этот модуль про управление файлами и директориями. Не про содержимое, а именно про сами файлы — создать директорию, поменять права, удалить что-то и так далее.

Создать директорию:

ansible all -m file -a "path=/opt/myapp state=directory owner=root group=root mode=0755"

Поменять права на файл:

ansible all -m file -a "path=/etc/nginx/nginx.conf owner=www-data group=www-data mode=0644"

Удалить файл или директорию:

ansible all -m file -a "path=/tmp/garbage state=absent"

Вот этот **`state=absent`** — запомните. Это общий паттерн в Ansible. Когда нужно что-то удалить, вы не пишете `rm -rf`, а говорите _"state=absent"_, то есть, этот файл должен отсутствовать. Если его нет — Ansible ничего не делает. Если есть — удаляет. Это и есть та самая **идемпотентность**, о которой мы говорили в первом материале.

Создать симлинк:

ansible all -m file -a "src=/opt/myapp/current dest=/opt/myapp/latest state=link"

## Модули `apt` и `yum`

Это модули для установки пакетов. `apt` — для Debian/Ubuntu, `yum` — для CentOS/RHEL. По сути, они делают то же, что `apt install` или `yum install`, но через Ansible.

Установить пакет на Ubuntu/Debian:

ansible all -m apt -a "name=nginx state=present update_cache=yes"

- **`name=nginx`** — какой пакет ставим.
- **`state=present`** — пакет должен быть установлен. Если уже стоит — Ansible ничего не делает. Опять идемпотентность.
- **`update_cache=yes`** — перед установкой обновить кэш пакетов (аналог `apt update`). Это важно, потому что без обновления кэша apt может не найти пакет или поставить старую версию.

Удалить пакет:

ansible all -m apt -a "name=nginx state=absent"

Опять `state=absent` — тот же паттерн. Установить конкретную версию:

ansible all -m apt -a "name=nginx=1.24.0-1~jammy state=present"

Для CentOS/RHEL всё то же самое, только модуль `yum`:

ansible all -m yum -a "name=nginx state=present"

Есть, кстати, ещё модуль `package`, который сам определяет, какой пакетный менеджер использовать. Но на практике обычно явно пишут `apt` или `yum`, потому что у них разные фишки и параметры.

## Модуль `service`

Этот модуль управляет сервисами — запустить, остановить, перезапустить, включить автозагрузку. На практике используется постоянно.

Запустить сервис:

ansible all -m service -a "name=nginx state=started"

Обратите внимание — не `start`, а **`started`**. Это потому что мы описываем состояние, а не действие. _"Nginx должен быть запущен."_ Если он уже запущен — Ansible ничего не делает. Если остановлен — запускает.

Остановить сервис:

ansible all -m service -a "name=nginx state=stopped"

Перезапустить:

ansible all -m service -a "name=nginx state=restarted"

А вот `restarted` — это исключение. Тут Ansible перезапустит сервис всегда, даже если он уже работает. Это не идемпотентная операция, по сути. Поэтому в playbook'ах перезапуск обычно делают через handlers, но об этом позже.

Включить автозагрузку:

ansible all -m service -a "name=nginx enabled=yes"

Можно комбинировать:

ansible all -m service -a "name=nginx state=started enabled=yes"

То есть: nginx должен быть запущен и включён в автозагрузку. Одна команда — два действия.

## Модуль `user`

Управление пользователями. Создать, удалить, добавить в группу и так далее.

Создать пользователя:

ansible all -m user -a "name=deploy shell=/bin/bash createhome=yes"

Создать пользователя и добавить его в группу sudo:

ansible all -m user -a "name=deploy shell=/bin/bash groups=sudo append=yes"

Вот тут важно — **`append=yes`**. Без него Ansible заменит все группы пользователя на ту, что вы указали. То есть, если пользователь был в группах `docker`, `www-data`, а вы написали `groups=sudo` без `append=yes` — он вылетит из docker и www-data. Это частая ошибка, имейте в виду.

Удалить пользователя:

ansible all -m user -a "name=olduser state=absent remove=yes"

`remove=yes` — удалить вместе с домашней директорией.

## Параллелизм — флаг `-f`

По умолчанию Ansible выполняет задачи на **пяти серверах одновременно**. То есть, если у вас двадцать серверов — он возьмёт первые пять, выполнит команду, потом следующие пять и так далее. Четыре пачки по пять.

Но этим можно управлять через флаг `-f` (fork):

bashcopy

```bash
# выполнить на 20 серверах одновременноansible all -m ping -f 20 # выполнить на 50 серверах одновременноansible all -a "uptime" -f 50
```

На практике, если у вас много серверов и задача простая (типа посмотреть uptime или пропинговать), можно смело ставить `-f` побольше, хоть 50, хоть 100. Ansible просто откроет больше SSH-соединений параллельно. Но если задача тяжёлая (типа установки пакетов), то слишком большой `-f` может нагрузить вашу control node.

Значение по умолчанию, кстати, можно поменять в `ansible.cfg`:

inicopy

```ini
[defaults]forks = 20
```

И тогда не нужно каждый раз писать `-f`.

## Become — выполнение с правами sudo

Многие операции на серверах требуют прав суперпользователя. Ставить пакеты, менять конфиги в `/etc`, управлять сервисами — всё это нужен root. Если вы подключаетесь под обычным пользователем, вам нужен **become**.

bashcopy

```bash
# с флагом -b (become)ansible all -m apt -a "name=htop state=present" -b # или полная формаansible all -m apt -a "name=htop state=present" --become --become-method=sudo
```

Флаг `-b` — это короткая форма `--become`. Ansible выполнит команду от имени root через sudo.

Если для sudo нужен пароль:

ansible all -m apt -a "name=htop state=present" -b -K

Флаг `-K` (`--ask-become-pass`) — Ansible спросит пароль для sudo перед выполнением. На практике обычно настраивают sudo без пароля для ansible-пользователя, чтобы не вводить пароль каждый раз. Но для обучения `-K` — нормальный вариант.

Если вы подключаетесь сразу под root, то become вам не нужен — вы и так уже root. Но если в команде или в проекте есть правило не ходить под рутом (а на нормальных проектах такое правило обычно есть), то become — это ваш способ получить привилегии.

## Практические кейсы

Ладно, хватит теории. Давайте разберём реальные ситуации, в которых ad-hoc команды прямо спасают.

### Кейс 1: потушить сервис на 20 серверах за 5 секунд

Допустим, пришёл алерт — какой-то сервис жрёт ресурсы на всех серверах. Нужно его быстро остановить. Без Ansible вы бы подключались по SSH к каждому серверу по очереди, писали `systemctl stop`, ждали, переходили на следующий. Двадцать серверов — это минут десять минимум, если быстро бегать.

С Ansible:

ansible webservers -m service -a "name=problematic-service state=stopped" -f 20

Всё. Одна команда, пять секунд, сервис остановлен на всех двадцати серверах параллельно.

### Кейс 2: узнать, где заканчивается место на диске

Помните из блока про Linux — `df` и `du`? Вот:

ansible all -m shell -a "df -h / | tail -1"

Моментально видите процент занятого места на каждом сервере. Увидели, что где-то 95% — идём туда копать:

ansible problem_server -m shell -a "du -sh /var/log/* | sort -rh | head -10"

И вот мы нашли, что какой-нибудь nginx access.log раздулся до 50 гигов, потому что кто-то забыл настроить ротацию логов.

### Кейс 3: быстро раскидать SSH-ключ нового сотрудника

Пришёл новый девопс, ему нужен доступ ко всем серверам:

ansible all -m authorized_key -a "user=deploy key='ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... new_guy@company' state=present"

Модуль `authorized_key` добавит его публичный ключ на все серверы. Сотрудник уволился — меняем `state=present` на `state=absent`, и ключ удалён отовсюду.

### Кейс 4: проверить, что сервис запущен на всех серверах

Утром пришли на работу, хотите убедиться, что nginx жив везде:

ansible webservers -m shell -a "systemctl is-active nginx"

Если где-то не `active` — сразу видно.

### Кейс 5: массовое обновление пакета

Нашли критическую уязвимость в OpenSSL, нужно срочно обновить:

ansible all -m apt -a "name=openssl state=latest" -b

`state=latest` — это значит _"должна стоять последняя доступная версия"_. Если стоит старая — Ansible обновит. Если уже последняя — ничего не сделает.

### Кейс 6: перезагрузить все серверы

Ну, иногда и такое нужно:

ansible all -m reboot -a "reboot_timeout=300" -f 5

Тут, обратите внимание, `-f 5` — не двадцать, не пятьдесят, а именно пять. Потому что перезагружать все серверы одновременно — это, мягко говоря, не лучшая идея. Лучше пачками по пять, чтобы сервис не лёг полностью.

## Полезные флаги, которые стоит знать

Напоследок — несколько флагов, которые часто пригождаются:

bashcopy

```bash
# выполнить только на конкретных серверах из группыansible webservers -a "uptime" --limit "server1,server2" # посмотреть, что Ansible сделает, но НЕ выполнять (dry run)ansible all -m apt -a "name=nginx state=present" --check # увидеть подробный вывод (для дебага)ansible all -m ping -v # ещё подробнееansible all -m ping -vvv # совсем подробно (для совсем тяжёлых случаев)ansible all -m ping -vvvv
```

Флаг **`--check`** — это прямо суперполезная штука. Ansible покажет, что он собирается сделать, но ничего реально не выполнит. То есть, вы можете сначала прогнать в check-режиме, убедиться, что всё выглядит правильно, и только потом запустить по-настоящему. На проде это спасает от очень многих проблем.
