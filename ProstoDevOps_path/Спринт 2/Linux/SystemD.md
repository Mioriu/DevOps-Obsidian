## Что такое systemd и зачем он нужен

Так, мы разобрались с процессами, научились их находить и убивать. Для управления сервисами в Linux существует **systemd** — это, по сути, главная система инициализации и управления всем, что крутится на вашем сервере.

Помните, мы говорили про PID 1? Вот systemd — это и есть PID 1. Он стартует первым при загрузке системы, а дальше поднимает всё остальное — сеть, логирование, ваши сервисы, базы данных, всё. И потом он за всем этим следит — если сервис упал, systemd может его автоматически перезапустить. Если нужно посмотреть логи — systemd их собирает. Если нужно что-то запустить по расписанию — systemd умеет и это.

## systemctl — основные команды

`systemctl` — это главная команда для управления сервисами через systemd. Вот базовый набор, без которого никуда:

**Запустить сервис:**

systemctl start nginx

**Остановить:**

systemctl stop nginx

**Перезапустить:**

systemctl restart nginx

Тут важно — `restart` убивает процесс и поднимает заново. Все текущие соединения рвутся. Для nginx это означает, что клиенты, которые в данный момент качали файл или ждали ответ, получат обрыв.

**Перечитать конфиг без перезапуска:**

systemctl reload nginx

А вот `reload` — это то, что мы обсуждали в теме сигналов. Под капотом systemd отправляет процессу SIGHUP, и тот перечитывает конфиг на лету. Никакого даунтайма, соединения не рвутся. Всегда, когда вы поменяли конфиг сервиса и хотите его применить — сначала пробуйте `reload`. И только если reload не поддерживается или не помог — тогда `restart`.

**Посмотреть статус:**

systemctl status nginx

Она показывает вам всё сразу — запущен сервис или нет, с каким PID работает, сколько памяти жрёт, и последние несколько строк логов. То есть, когда что-то не работает, первое, что вы делаете — `systemctl status название-сервиса`. В девяти случаях из десяти прямо в выводе status будет видно, в чём проблема — либо сервис упал с ошибкой, либо не смог стартануть, и там же в логах написано почему.

**Включить автозапуск при загрузке системы:**

systemctl enable nginx

**Выключить автозапуск:**

systemctl disable nginx

`enable` и `disable` не запускают и не останавливают сервис прямо сейчас. Они только управляют тем, будет ли сервис подниматься автоматически при перезагрузке сервера. Если нужно и включить автозапуск, и запустить прямо сейчас:

systemctl enable --now nginx

Флаг `--now` делает обе вещи одновременно.

**Посмотреть все сервисы:**

bashcopy

```bash
systemctl list-units --type=service            # запущенныеsystemctl list-units --type=service --all       # вообще все, включая неактивные
```

**Проверить, запущен ли сервис (для скриптов):**

bashcopy

```bash
systemctl is-active nginxsystemctl is-enabled nginx
```

Возвращает просто `active`/`inactive` или `enabled`/`disabled`. Удобно использовать в bash-скриптах для проверок.

## Юнит-файлы: структура

Окей, а как systemd вообще знает, что такое nginx, как его запускать и что делать, если он упал? Для этого существуют **юнит-файлы**. Юнит-файл — это конфигурационный файл, который описывает сервис. Это обычный текстовый файл с расширением `.service`.

Где они лежат:

- `/usr/lib/systemd/system/` — юнит-файлы, которые пришли из пакетов. То есть, когда вы делаете `apt install nginx`, юнит-файл nginx ставится сюда.
- `/etc/systemd/system/` — кастомные юнит-файлы и оверрайды. Вот сюда мы пишем свои сервисы. Файлы отсюда имеют приоритет над `/usr/lib/systemd/system/`.

Давайте разберём структуру на примере. Допустим, у нас есть Python-приложение, и мы хотим сделать из него нормальный сервис:

inicopy

```ini
[Unit]Description=My Python ApplicationAfter=network.target postgresql.serviceWants=postgresql.service [Service]Type=simpleUser=appuserGroup=appuserWorkingDirectory=/opt/myappExecStart=/opt/myapp/venv/bin/python app.pyExecReload=/bin/kill -HUP $MAINPIDRestart=on-failureRestartSec=5Environment=APP_ENV=productionEnvironmentFile=/opt/myapp/.env [Install]WantedBy=multi-user.target
```

Три секции. Разберём каждую.

### [Unit] — описание и зависимости

- **Description** — человекочитаемое описание, что это за сервис. Показывается в `systemctl status`.
- **After** — после чего запускаться. В нашем случае — после того как поднялась сеть и PostgreSQL. Это именно порядок запуска, не зависимость. То есть, systemd сначала поднимет network и postgresql, а потом уже наш сервис.
- **Wants** — мягкая зависимость. «Хотелось бы, чтобы PostgreSQL тоже был запущен». Если PostgreSQL не запустится — наш сервис всё равно стартанёт. Есть ещё **Requires** — жёсткая зависимость. Если зависимость не поднялась, наш сервис тоже не стартует. Но `Wants` используют чаще, потому что он менее агрессивный.

### [Service] — как запускать

- **Type** — тип сервиса. Об этом подробнее ниже.
- **User/Group** — от какого пользователя запускать. Никогда не запускайте свои приложения от root, если это не требуется. Создайте отдельного пользователя.
- **WorkingDirectory** — рабочая директория. Оттуда сервис будет запущен.
- **ExecStart** — главная команда запуска. Тут всегда указываем полный путь до бинарника. Не `python app.py`, а `/opt/myapp/venv/bin/python app.py`. Systemd не использует ваш PATH из `.bashrc`, поэтому полный путь обязателен.
- **ExecReload** — команда для `systemctl reload`. `$MAINPID` — переменная, которую systemd сам подставляет, это PID основного процесса.
- **Restart** — политика перезапуска. `on-failure` означает «перезапусти, если сервис упал с ошибкой». Есть ещё `always` — перезапускать всегда, даже если сервис завершился корректно. Для продакшен-сервисов обычно ставят `on-failure` или `always`.
- **RestartSec** — пауза перед перезапуском. Пять секунд — нормально. Без паузы, если сервис будет падать в цикле, он будет бесконечно рестартить и забьёт логи.
- **Environment** — переменные окружения прямо в юнит-файле.
- **EnvironmentFile** — или из файла, что удобнее для продакшена, потому что туда можно положить секреты и не светить их в юнит-файле.

### [Install] — куда встроить

- **WantedBy=multi-user.target** — это, по сути, означает «запускать в нормальном многопользовательском режиме». В 99% случаев для серверных сервисов вы пишете именно `multi-user.target`. Именно эта секция отвечает за то, что происходит при `systemctl enable` — systemd создаёт симлинк, который привязывает ваш сервис к указанному target.

### После создания или изменения юнит-файла

Каждый раз, когда вы создали новый юнит-файл или изменили существующий, нужно сказать systemd перечитать конфигурацию:

systemctl daemon-reload

Без этого systemd не увидит ваши изменения. Забыть `daemon-reload` — одна из самых частых ошибок. Поменяли юнит-файл, делаете `restart` — а сервис стартует со старыми параметрами. Потому что забыли `daemon-reload`.

## Типы юнитов

Мы пока говорили только про `.service`, но systemd работает не только с сервисами. Есть несколько типов юнитов:

- **.service** — сервисы, основной тип. Nginx, PostgreSQL, ваше приложение.
- **.timer** — таймеры, замена cron. Об этом ниже.
- **.socket** — сокет-активация. Systemd слушает порт, и когда приходит соединение — запускает сервис. Экономит ресурсы, если сервис нужен редко.
- **.mount** — точки монтирования. По сути, альтернатива `/etc/fstab`, но через systemd.
- **.target** — группы юнитов. `multi-user.target` — это, по сути, набор сервисов, которые должны быть запущены для нормальной работы сервера. Аналог runlevel из старых систем.
- **.path** — отслеживание изменений в файловой системе. Когда файл появился или изменился — запускает сервис.
- **.slice** — управление ресурсами через cgroups. Можно ограничить группу сервисов по CPU и памяти.

В повседневной работе вы будете иметь дело в основном с `.service` и `.timer`. Остальные — реже, но знать, что они существуют, нужно.

## journalctl — логи

Systemd собирает логи всех сервисов в единое хранилище, которое называется **journal**. И работать с ним нужно через команду `journalctl`. Это, по сути, замена ковыряния в `/var/log/` по отдельным файлам — всё в одном месте.

**Посмотреть логи конкретного сервиса:**

journalctl -u nginx

Флаг `-u` — это unit, указываете имя сервиса. Это команда номер один для дебага. Сервис не стартует — `journalctl -u название` — и вы видите, что именно пошло не так.

**Последние логи (хвост):**

journalctl -u nginx -n 50

Покажет последние 50 строк. По умолчанию без `-n` покажет вообще всё с начала времён, а вам обычно нужны именно последние записи.

**Следить за логами в реальном времени:**

journalctl -u nginx -f

Флаг `-f` — это как `tail -f`. Логи бегут в реальном времени, вы сидите и смотрите. Удобно, когда воспроизводите проблему — в одном терминале делаете действие, в другом смотрите логи.

**Логи с определённого времени:**

bashcopy

```bash
journalctl -u nginx --since "2025-01-29 10:00" --until "2025-01-29 12:00"journalctl -u nginx --since "1 hour ago"journalctl -u nginx --since today
```

**Логи после последнего запуска системы:**

journalctl -u nginx -b

Флаг `-b` — только текущая загрузка. Полезно, когда перезагрузили сервер и хотите понять, что происходило именно после ребута.

**Логи по приоритету (только ошибки):**

journalctl -u nginx -p err

Приоритеты: `emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`. Когда у вас гигабайты логов и нужно быстро найти проблемы — `-p err` покажет только ошибки и выше.

**Сколько места жрёт journal:**

journalctl --disk-usage

Journal, кстати, тоже может разрастись. Помните, мы говорили, что `/var` — главный пожиратель места на диске? Логи journal лежат в `/var/log/journal/`, и если их не ограничить, они могут съесть кучу места. Ограничить можно в конфиге `/etc/systemd/journald.conf`:

inicopy

```ini
[Journal]SystemMaxUse=500M
```

Или почистить руками:

bashcopy

```bash
journalctl --vacuum-size=500M    # оставить логов на 500 мегабайтjournalctl --vacuum-time=7d      # оставить логи только за последнюю неделю
```

## Таймеры systemd — замена cron

Cron — это классика, он существует десятилетия, и все его знают. Но у systemd есть свои таймеры, и они в ряде вещей удобнее.

Чем таймеры лучше cron:

- Логи автоматически попадают в journal. Не нужно отдельно настраивать, куда писать вывод скрипта.
- Можно посмотреть `systemctl status mytimer.timer` и сразу увидеть, когда последний раз срабатывал и когда следующий запуск.
- Если сервер был выключен в момент, когда таймер должен был сработать, systemd может выполнить пропущенный запуск при включении (опция `Persistent=true`).
- Зависимости, ограничение ресурсов, всё то же самое, что и для обычных сервисов.

Таймер — это связка из двух файлов: `.timer` и `.service`. Таймер описывает расписание, сервис описывает что делать.

Допустим, нам нужно каждый день в 3 часа ночи запускать бэкап. Создаём два файла:

**`/etc/systemd/system/backup.service`:**

inicopy

```ini
[Unit]Description=Daily backup script [Service]Type=oneshotExecStart=/opt/scripts/backup.shUser=backup
```

`Type=oneshot` — это значит, что сервис запускается, делает своё дело и завершается. Для скриптов по расписанию — всегда `oneshot`. Секции `[Install]` тут нет — сервис не должен запускаться сам по себе, его запускает таймер.

**`/etc/systemd/system/backup.timer`:**

inicopy

```ini
[Unit]Description=Run backup every day at 3 AM [Timer]OnCalendar=*-*-* 03:00:00Persistent=true [Install]WantedBy=timers.target
```

- **OnCalendar** — расписание. Формат `год-месяц-день часы:минуты:секунды`. Звёздочки — любые значения. `*-*-* 03:00:00` — каждый день в три ночи. Можно писать и проще: `OnCalendar=daily` или `OnCalendar=weekly`.
- **Persistent=true** — если сервер был выключен в 3 ночи, бэкап запустится при включении. Без этого пропущенный запуск просто потеряется.

Активируем:

bashcopy

```bash
systemctl daemon-reloadsystemctl enable --now backup.timer
```

Обратите внимание — `enable` и `start` делаем для `.timer`, не для `.service`. Таймер сам запустит сервис по расписанию.

**Посмотреть все активные таймеры:**

systemctl list-timers

Покажет таблицу — когда каждый таймер сработал в последний раз, когда следующий запуск, и какой сервис он дёргает.

Ещё несколько примеров расписаний:

inicopy

```ini
OnCalendar=*-*-* *:00:00          # каждый часOnCalendar=Mon *-*-* 09:00:00     # каждый понедельник в 9 утраOnCalendar=*-*-01 00:00:00        # первого числа каждого месяца
```

Можно и через интервалы, без привязки к конкретному времени:

inicopy

```ini
OnBootSec=5min                     # через 5 минут после загрузкиOnUnitActiveSec=30min              # каждые 30 минут после последнего запуска
```

`OnBootSec` удобен для задач, которые нужно выполнить один раз после перезагрузки. `OnUnitActiveSec` — для периодических задач, где важен интервал, а не конкретное время.

## Полезные практики

Несколько вещей, которые стоит знать для реальной работы:

**Переопределение параметров без редактирования юнит-файла:**

systemctl edit nginx

Это создаст файл-оверрайд в `/etc/systemd/system/nginx.service.d/override.conf`. Туда можно добавить или переопределить параметры, не трогая оригинальный юнит-файл из пакета. Это правильный подход, потому что при обновлении пакета оригинальный юнит-файл может перезаписаться, а ваш оверрайд останется.

inicopy

```ini
[Service]LimitNOFILE=65535Environment=WORKER_CONNECTIONS=4096
```

**Посмотреть полный результирующий конфиг юнита (со всеми оверрайдами):**

systemctl cat nginx

**Посмотреть, почему сервис не стартует:**

bashcopy

```bash
systemctl status nginx          # первым деломjournalctl -u nginx -n 30       # подробнееjournalctl -u nginx -p err      # только ошибкиsystemctl show nginx             # все параметры, включая коды выхода
```

Вот эта последовательность — status, потом journalctl, потом show — это, по сути, стандартный алгоритм дебага любого сервиса в systemd.
