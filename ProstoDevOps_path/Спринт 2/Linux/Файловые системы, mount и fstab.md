## Типы файловых систем

Когда вы создаёте раздел на диске, его нужно отформатировать — то есть создать на нём файловую систему. Файловая система определяет, как данные хранятся на диске, как организованы директории, как работают права доступа. В Linux есть несколько типов файловых систем, и нужно понимать, чем они отличаются и когда какую использовать.

### ext4

Самая распространённая файловая система в Linux. Если вы поставили Ubuntu или Debian и ничего специально не выбирали — у вас ext4. Она стабильная, проверенная, хорошо работает для большинства задач.

Основные характеристики:

- Максимальный размер файла — 16 ТБ.
- Максимальный размер раздела — 1 ЭБ (экзабайт, но на практике вы такого не встретите).
- Поддерживает журналирование — если сервер внезапно выключился, файловая система восстановит целостность данных при следующей загрузке.
- Количество инодов задаётся при создании и не меняется потом. Это фиксированное значение.

### XFS

XFS — файловая система, которая лучше подходит для работы с большими файлами и большими объёмами данных. В CentOS/RHEL она используется по умолчанию.

Чем отличается от ext4:

- Лучше работает с большими файлами. Если у вас база данных, которая хранит файлы по 10-100 ГБ, или видеохранилище — XFS будет эффективнее.
- Лучше параллельный I/O. Когда много потоков одновременно пишут на диск — XFS справляется лучше.
- Можно увеличить размер раздела на лету (как и ext4), но нельзя уменьшить. ext4 позволяет и то, и другое.
- Иноды выделяются динамически — не нужно заранее думать о количестве. В ext4 иноды фиксированы при создании.

Когда XFS: базы данных, хранилища больших файлов, системы с интенсивной записью, серверы с большими разделами.

Когда ext4: всё остальное, универсальные серверы, небольшие разделы, если нет причин выбирать что-то другое.

### tmpfs

tmpfs — это файловая система, которая живёт в оперативной памяти. Данные не пишутся на диск вообще. Это значит две вещи: во-первых, она работает очень быстро (скорость RAM, а не диска), во-вторых, при перезагрузке всё теряется.

Где используется:

- `/tmp` — на многих системах монтируется как tmpfs. Временные файлы, которые не жалко потерять.
- `/dev/shm` — shared memory, используется приложениями для межпроцессного взаимодействия.
- `/run` — runtime-данные, PID-файлы, сокеты.

Посмотреть tmpfs в системе:

df -h | grep tmpfs

tmpfs не занимает память, пока в неё ничего не записано. Если у вас tmpfs на 4 ГБ, но файлов в ней на 100 МБ — она занимает только 100 МБ оперативки. Но если кто-то нагенерирует туда файлов на 4 ГБ — они реально окажутся в RAM и могут создать проблему с памятью.

### overlay

Overlay (overlayfs) — файловая система, которая накладывает один слой поверх другого. Работает по принципу — есть нижний слой (read-only) и верхний слой (read-write). Когда вы читаете файл — он берётся из нижнего слоя. Когда пишете — изменения записываются в верхний слой, не трогая нижний.

Где это используется? В Docker. Каждый слой Docker-образа — это read-only слой overlay. Когда контейнер запускается, поверх всех слоёв образа создаётся один read-write слой, куда пишутся все изменения. Именно поэтому образы можно шарить между контейнерами — нижние слои общие, а каждый контейнер имеет свой верхний слой.

## Inodes

Мы уже затрагивали иноды в теме дисков, но тут разберём подробнее, потому что тема сама по себе заслуживает отдельного объяснения.

Inode (index node) — это структура данных в файловой системе, которая хранит метаинформацию о файле:

- Владелец и группа
- Права доступа
- Размер файла
- Временные метки (создание, изменение, доступ)
- Указатели на блоки данных на диске

Обратите внимание — имя файла в иноде **не хранится**. Имя файла хранится в директории, которая, по сути, является таблицей «имя → номер инода». Это, кстати, объясняет, как работают хардлинки — два разных имени указывают на один и тот же инод, то есть на одни и те же данные.

Каждый файл и каждая директория занимает один инод. Количество инодов ограничено. Посмотреть:

df -i

codecopy

```
Filesystem      Inodes   IUsed   IFree IUse% Mounted on/dev/sda1      6553600  524288 6029312    8% /
```

На ext4 количество инодов фиксируется при создании файловой системы (обычно один инод на каждые 16 КБ). На XFS иноды выделяются динамически, по мере необходимости.

Когда иноды кончаются — вы не можете создать новые файлы, даже если на диске полно свободного места. `df -h` показывает 50% свободного, а `touch test.txt` выдаёт `No space left on device`. Без `df -i` такую проблему можно долго искать.

Типичная причина — миллионы мелких файлов. Сессии в `/tmp`, кэш-файлы, мелкие логи, накопившиеся артефакты CI/CD. Каждый файл по несколько байт, но инод на каждый. Тысяч сто таких файлов — и инодов нет.

## Команда mount

В Linux любой диск, флешка, сетевое хранилище — это просто блочное устройство. Чтобы им пользоваться, его нужно **примонтировать** — то есть привязать к какой-то директории в файловом дереве.

Базовый синтаксис:

mount /dev/sdb1 /mnt/data

Это берёт раздел `/dev/sdb1` и делает его доступным через директорию `/mnt/data`. После этого всё, что вы запишете в `/mnt/data`, физически окажется на диске `sdb1`.

Посмотреть, что сейчас примонтировано:

mount | grep "^/dev"

Или проще:

lsblk

Размонтировать:

umount /mnt/data

Обратите внимание — `umount`, не `unmount`. Без `n`. Историческое наследие.

Если диск не размонтируется и ругается `target is busy` — значит, кто-то использует файлы на этом диске. Найти, кто:

lsof +D /mnt/data

Или принудительно (осторожно):

umount -l /mnt/data

Флаг `-l` (lazy) — «ленивое» размонтирование. Устройство отвяжется от дерева, но физически размонтируется, когда все процессы отпустят файлы.

Монтирование с опциями:

bashcopy

```bash
mount -o ro /dev/sdb1 /mnt/data           # read-onlymount -o rw,noexec /dev/sdb1 /mnt/data    # read-write, но без права запуска файловmount -t xfs /dev/sdb1 /mnt/data          # явно указать тип ФС
```

## /etc/fstab — автомонтирование при загрузке

Вот тут мы подходим к классическому вопросу. Вы примонтировали диск через `mount`, записали туда данные, всё работает. Перезагрузили сервер — и данные «пропали». Не потому что удалились, а потому что диск не примонтировался обратно. Данные физически на диске есть, но директория `/mnt/data` теперь пустая, потому что к ней ничего не подключено.

Команда `mount` работает только на текущую сессию. После перезагрузки всё сбрасывается. Чтобы диск монтировался автоматически при каждой загрузке, нужно прописать его в `/etc/fstab`.

`/etc/fstab` — это файл, который systemd читает при загрузке и монтирует всё, что в нём указано:

cat /etc/fstab

codecopy

```
# <device>                                <mountpoint>  <type>  <options>       <dump> <pass>UUID=a1b2c3d4-e5f6-7890-abcd-ef1234567890  /            ext4    defaults        0      1UUID=f9e8d7c6-b5a4-3210-fedc-ba0987654321  /data        xfs     defaults        0      2UUID=1a2b3c4d-5e6f-7890-abcd-ef1234567890  swap         swap    defaults        0      0tmpfs                                       /tmp         tmpfs   defaults,size=2G 0     0
```

Разберём каждое поле:

- **device** — что монтировать. Лучше использовать UUID, а не `/dev/sdb1`, потому что имена устройств могут меняться после перезагрузки (sdb станет sdc, если подключили ещё один диск). UUID — это уникальный идентификатор раздела, он не меняется. Узнать UUID: `blkid`.
- **mountpoint** — куда монтировать.
- **type** — тип файловой системы (ext4, xfs, swap, tmpfs).
- **options** — опции монтирования. `defaults` — стандартный набор (rw, suid, dev, exec, auto, nouser, async).
- **dump** — используется утилитой dump для бэкапов. Практически всегда 0. Можно не думать об этом.
- **pass** — порядок проверки файловой системы при загрузке. 1 для корня, 2 для остальных, 0 — не проверять.

Добавить новый диск в fstab:

bashcopy

```bash
# Узнаём UUIDblkid /dev/sdb1
```

/dev/sdb1: UUID="f9e8d7c6-b5a4-3210-fedc-ba0987654321" TYPE="xfs"

bashcopy

```bash
# Создаём точку монтированияmkdir -p /data # Добавляем строку в fstabecho 'UUID=f9e8d7c6-b5a4-3210-fedc-ba0987654321 /data xfs defaults 0 2' >> /etc/fstab # Проверяем, что всё корректно, монтируем всё из fstabmount -a
```

`mount -a` — монтирует всё, что прописано в fstab, но ещё не примонтировано. Это, по сути, проверка — если `mount -a` отработал без ошибок, значит после перезагрузки всё будет в порядке.

### Осторожно с fstab

Ошибка в fstab может привести к тому, что сервер не загрузится. Если вы прописали несуществующий UUID или указали неправильный тип файловой системы — при загрузке systemd попытается примонтировать, не сможет, и сервер может уйти в emergency mode. Поэтому всегда проверяйте через `mount -a` перед перезагрузкой.

Если сервер уже ушёл в emergency mode из-за кривого fstab — не паникуйте. Вы попадёте в консоль recovery, где можно отредактировать fstab и убрать проблемную строку:

bashcopy

```bash
# В emergency mode корень примонтирован read-only, перемонтируем в rwmount -o remount,rw / # Редактируем fstabvi /etc/fstab # Перезагружаемсяreboot
```

### Опция nofail

Чтобы защититься от проблем с загрузкой, можно добавить опцию `nofail`:

UUID=f9e8d7c6-b5a4-3210-fedc-ba0987654321 /data xfs defaults,nofail 0 2

`nofail` означает: если диск не удалось примонтировать — продолжай загрузку, не останавливайся. Система загрузится, просто `/data` будет пустой. Для некритичных дисков это правильный подход.

Формулировка: «Я подключил новый диск к серверу, примонтировал, записал данные. Перезагрузил сервер — данные пропали. Что произошло и как исправить?»
