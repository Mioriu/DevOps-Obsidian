## Пакетные менеджеры — apt, yum, dnf

Так, давайте разберёмся с пакетами. Когда вам нужно что-то поставить на Linux — nginx, Docker, PostgreSQL, да что угодно — вы не идёте на сайт скачивать какой-то `.exe`, как в Windows. Вы используете пакетный менеджер. Это, по сути, такая штука, которая знает, откуда скачать нужный софт, какие зависимости ему нужны, и сама всё разруливает.

Какой именно пакетный менеджер — зависит от дистрибутива. Тут два основных:

**Debian/Ubuntu** — используют `apt`. Это то, с чем вы, скорее всего, будете работать чаще всего

**CentOS/RHEL/Rocky/Alma** — используют `yum` или `dnf`. `dnf` — это, по сути, следующее поколение `yum`, и в новых версиях этих дистрибутивов `yum` — это просто симлинк на `dnf`. То есть, разницы для вас, по сути, нет. Пишете `yum install nginx` или `dnf install nginx` — результат одинаковый.

### Базовые команды

Вот набор команд, который нужно знать.

**Установка пакета:**

bashcopy

```bash
# Debian/Ubuntuapt install nginx # CentOS/RHELyum install nginx
```

**Удаление пакета:**

bashcopy

```bash
apt remove nginx        # удалит пакет, но оставит конфигиapt purge nginx         # удалит пакет вместе с конфигами yum remove nginx
```

Разница между `remove` и `purge` в apt — важная. `remove` оставляет конфиги на диске, то есть, если вы потом заново поставите этот же пакет, конфиги подхватятся старые. `purge` сносит вообще всё. В yum/dnf такого разделения нет — `remove` убирает и пакет, и конфиги.

**Обновление:**

bashcopy

```bash
# Обновить список доступных пакетов (что вообще есть в репозиториях)apt update # Обновить сами пакеты до последних версийapt upgrade # В CentOS/RHELyum update       # делает и то, и другое сразу
```

Вот тут важный момент — `apt update` и `apt upgrade` это две разные команды, и их постоянно путают. `apt update` — это не обновление системы. Это обновление индекса, то есть система идёт в репозитории и смотрит, какие версии пакетов сейчас доступны. А `apt upgrade` — это уже непосредственно обновление установленных пакетов до тех версий, которые нашлись после `update`. То есть, сначала всегда `update`, потом `upgrade`.

**Поиск пакета:**

bashcopy

```bash
apt search nginxyum search nginx
```

**Посмотреть информацию о пакете:**

bashcopy

```bash
apt show nginxyum info nginx
```

**Посмотреть, какие пакеты установлены:**

bashcopy

```bash
apt list --installedyum list installed
```

## Репозитории

Окей, а откуда пакетный менеджер вообще берёт эти пакеты? Из репозиториев. Репозиторий — это, по сути, сервер, на котором лежат пакеты. Когда вы делаете `apt install nginx`, система лезет в те репозитории, которые у неё прописаны, ищет там nginx и скачивает.

По умолчанию в системе уже есть набор стандартных репозиториев — это официальные репозитории дистрибутива. Но далеко не всё лежит в стандартных репозиториях. Например, хотите поставить свежий Docker — его нет в стандартных репо Ubuntu, нужно добавить репозиторий Docker. Хотите свежий PostgreSQL — аналогично, добавляете репо от PostgreSQL.

### Как добавить сторонний репозиторий

**В Ubuntu/Debian:**

Тут есть несколько способов. Самый типичный — вы идёте в документацию нужного софта, и там написано что-то типа:

bashcopy

```bash
# 1. Добавляете GPG-ключ репозитория (чтобы система доверяла пакетам оттуда)curl -fsSL https://download.docker.com/linux/ubuntu/gpg | gpg --dearmor -o /usr/share/keyrings/docker.gpg # 2. Добавляете сам репозиторийecho "deb [signed-by=/usr/share/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" > /etc/apt/sources.list.d/docker.list # 3. Обновляете индексapt update # 4. Ставите пакетapt install docker-ce
```

Смотрите, что тут происходит. GPG-ключ — это такая штука для проверки подлинности пакетов, чтобы вам не подсунули какой-нибудь левак. Сам репозиторий добавляется как файл в `/etc/apt/sources.list.d/`. Помните, мы говорили, что конфиги живут в `/etc`? Вот, и настройки репозиториев — тоже там. Основной файл — `/etc/apt/sources.list`, а дополнительные кладутся в `/etc/apt/sources.list.d/` отдельными файлами.

Ещё есть команда `add-apt-repository`, которая упрощает добавление PPA-репозиториев:

bashcopy

```bash
add-apt-repository ppa:deadsnakes/ppaapt updateapt install python3.12
```

Но PPA — это чисто Ubuntu-шная история

**В CentOS/RHEL:**

Тут всё проще. Репозитории описываются файлами в `/etc/yum.repos.d/`. Можно создать файл руками, а можно поставить через rpm:

bashcopy

```bash
# Например, добавить EPEL (популярный доп. репозиторий)yum install epel-release # Или через rpmrpm -ivh https://example.com/some-repo-release.rpm
```

После этого пакеты из нового репо становятся доступны через `yum install`.

## dpkg и rpm — работа с отдельными пакетами

Теперь про низкоуровневые инструменты. `apt` и `yum` — это, по сути, обёртки. Под капотом `apt` использует `dpkg`, а `yum`/`dnf` использует `rpm`. Разница вот в чём: `apt`/`yum` умеют разруливать зависимости и работать с репозиториями, а `dpkg`/`rpm` — нет. Они просто ставят конкретный пакет. Один файл — один пакет.

Когда это нужно? Ну вот, допустим, вам дали `.deb` файл, который кто-то собрал руками или скачал откуда-то. Или вендор прислал свой пакет, которого нет ни в каком репозитории. Тогда вы ставите его через `dpkg` или `rpm` напрямую.

**dpkg (Debian/Ubuntu):**

bashcopy

```bash
# Установить пакет из файлаdpkg -i package.deb # Удалить пакетdpkg -r package_name # Посмотреть все установленные пакетыdpkg -l # Посмотреть, какому пакету принадлежит файлdpkg -S /usr/bin/nginx # Посмотреть содержимое пакета (какие файлы он ставит)dpkg -L nginx
```

`dpkg -S` — это вообще полезнейшая команда. Допустим, у вас на сервере лежит какой-то бинарник, и вы не понимаете, откуда он взялся. `dpkg -S /usr/bin/что-то-там` — и вы видите, из какого пакета этот файл прилетел.

**rpm (CentOS/RHEL):**

bashcopy

```bash
# Установить пакетrpm -ivh package.rpm # Удалить пакетrpm -e package_name # Посмотреть все установленные пакетыrpm -qa # Узнать, из какого пакета файлrpm -qf /usr/bin/nginx # Посмотреть, какие файлы пакет ставитrpm -ql nginx
```

По сути, то же самое, только флаги другие. Логика одинаковая.

## Зависимости и конфликты версий

Вот это, пожалуй, самая больная тема в пакетах. Зависимости. Любой пакет может зависеть от других пакетов. Nginx зависит от OpenSSL, Python-приложение зависит от кучи библиотек, и так далее. Когда вы ставите что-то через `apt install` — он сам вытягивает все зависимости. Вы даже не думаете об этом. Написали `apt install nginx` — он поставил nginx плюс ещё десять пакетов, от которых nginx зависит. Всё автоматически.

Проблемы начинаются, когда вы ставите пакет через `dpkg -i`. Потому что `dpkg` зависимости не разруливает. То есть, вы ставите пакет, а он вам говорит — «мне нужна библиотека libfoo версии 2.0, а у тебя её нет». И всё, пакет не встал. Классическая ситуация. Решение тут такое:

bashcopy

```bash
# Ставите пакет, он ругается на зависимостиdpkg -i package.deb # Доустанавливаете недостающие зависимостиapt install -f
```

`apt install -f` — это, по сути, «почини мне зависимости». Он смотрит, чего не хватает, и доставляет из репозиториев. Очень полезная команда

Теперь про конфликты версий. Допустим, у вас стоит приложение А, которое требует `libfoo` версии 1.x. И вы хотите поставить приложение Б, которое требует `libfoo` версии 2.x. А `libfoo` 1.x и 2.x несовместимы между собой. Добро пожаловать в dependency hell.

В реальной работе девпоса такое встречается, и именно поэтому, в принципе, появился Docker. Это одна из причин. Когда каждое приложение живёт в своём контейнере со своими зависимостями и не конфликтует с другими.

Что можно сделать:

Первое — можно посмотреть, какие зависимости у пакета, до того как его ставить:

bashcopy

```bash
apt depends nginxapt rdepends nginx    # обратные зависимости — кто зависит от nginx yum deplist nginx
```

Второе — можно поставить конкретную версию пакета:

bashcopy

```bash
apt install nginx=1.18.0-0ubuntu1yum install nginx-1.18.0
```

Третье — можно зафиксировать версию пакета, чтобы при `apt upgrade` его не обновляло:

bashcopy

```bash
apt-mark hold nginx         # зафиксироватьapt-mark unhold nginx       # разфиксировать
```

В yum/dnf аналогично через `yum versionlock` (нужен плагин) или через `exclude` в конфиге.

Зафиксировать версию — это прямо must have для продакшена. Потому что бывает так: у вас всё работает, прилетает `apt upgrade`, обновляет какую-нибудь библиотеку, и всё ломается. А вы потом сидите и думаете — «я же ничего не менял, почему сломалось?» А потому что автоапдейт поменял. Вот `hold` как раз от этого спасает.

## Чистка кэша

Пакетные менеджеры кэшируют скачанные пакеты, и этот кэш может жрать место. Особенно если вы часто что-то ставите и обновляете.

bashcopy

```bash
# Удалить кэш скачанных пакетовapt clean               # удаляет всёapt autoclean           # удаляет только устаревшие # Удалить пакеты, которые были установлены как зависимости, но больше никому не нужныapt autoremove # В CentOS/RHELyum clean all
```

`apt autoremove` — штука полезная. Со временем в системе накапливаются «осиротевшие» пакеты — те, которые ставились как зависимости для чего-то, а потом то «что-то» удалили, а зависимости остались висеть. `autoremove` их чистит.
