# Установка Ansible и первое подключение

В этом материале мы поставим Ansible, настроим SSH-подключение к серверу и запустим первую команду, чтобы убедиться, что всё работает. Плюс сразу разберём конфиг `ansible.cfg`, потому что там есть несколько вещей, которые прямо с самого начала лучше настроить, чтобы потом не страдать.

## Что нам нужно для начала

Давайте сразу определимся, что у нас должно быть.

Во-первых, нам нужна машина, с которой мы будем запускать Ansible. Это называется **control node**. В принципе, это может быть ваш ноутбук, может быть отдельная виртуалка — без разницы. Главное условие — это должен быть Linux или macOS. На Windows Ansible напрямую не ставится, то есть, если у вас Windows, вам нужно либо поставить WSL, либо завести виртуалку с Linux. Я рекомендую просто Ubuntu поставить, не париться.

Во-вторых, нам нужен хотя бы один сервер, которым мы будем управлять. Это называется **managed node**. Тут подойдёт любая виртуалка — хоть на Timeweb, хоть на Selectel, хоть локально в VirtualBox. Главное, чтобы на ней был SSH и вы могли до неё достучаться по сети.

## Установка Ansible

Тут есть два основных способа. Через пакетный менеджер и через pip. Давайте разберём оба.

### Через пакетный менеджер (apt)

Самый простой вариант, если у вас Ubuntu или Debian:

bashcopy

```bash
sudo apt updatesudo apt install ansible -y
```

Всё, ansible поставился. Проверяем:

ansible --version

Если видите версию — значит, всё норм. Но тут есть нюанс. В репозиториях Ubuntu часто лежит не самая свежая версия Ansible. То есть, может быть какая-нибудь 2.14, а актуальная уже 2.17 или выше. Для обучения это, в принципе, не критично, но если хотите свежую версию — ставьте через pip.

### Через pip (рекомендуемый способ)

Это, на самом деле, более правильный способ, и именно его рекомендуют в официальной документации. Суть простая — Ansible написан на Python, поэтому ставится через pip как обычный Python-пакет.

bashcopy

```bash
sudo apt updatesudo apt install python3 python3-pip -ypip3 install ansible
```

Или, если у вас pip ругается на _externally-managed-environment_ (это на свежих Ubuntu бывает):

pip3 install ansible --break-system-packages

Либо, что более правильно, можно завести виртуальное окружение:

bashcopy

```bash
python3 -m venv ~/ansible-venvsource ~/ansible-venv/bin/activatepip install ansible
```

После установки так же проверяем:

ansible --version

Должны увидеть версию, путь к конфигу и прочую информацию. Если видите — всё, Ansible установлен, идём дальше.

## Настройка SSH-ключей

Вот это прямо важный момент, потому что без SSH-ключей работать с Ansible будет больно. Можно, конечно, по паролю подключаться, но это, во-первых, неудобно, во-вторых, небезопасно, и, в-третьих, на реальной работе так никто не делает.

Если у вас ещё нет SSH-ключа, генерируем:

ssh-keygen -t ed25519

Он спросит, куда сохранить — жмём Enter, оставляем по умолчанию (`~/.ssh/id_ed25519`).

Теперь закидываем публичный ключ на сервер:

ssh-copy-id user@IP_ВАШЕГО_СЕРВЕРА

Эта команда берёт ваш публичный ключ и прописывает его в `~/.ssh/authorized_keys` на удалённом сервере. После этого вы сможете подключаться без пароля.

Проверяем, что всё работает:

ssh user@IP_ВАШЕГО_СЕРВЕРА

Если подключились без запроса пароля — отлично, SSH настроен. Если всё ещё просит пароль — значит, что-то пошло не так. Проверьте права на папку `.ssh` (должно быть `700`) и на файл `authorized_keys` (должно быть `600`) на удалённом сервере.

## Первый inventory

Ansible должен знать, к каким серверам подключаться. Для этого нужен **inventory-файл**. Inventory мы детально разберём в следующем материале, а сейчас просто создадим самый простой вариант, чтобы запуститься.

Создаём рабочую директорию и файл inventory:

bashcopy

```bash
mkdir ~/ansible-practicecd ~/ansible-practice
```

Создаём файл `inventory.ini`:

inicopy

```ini
[servers]server1 ansible_host=IP_ВАШЕГО_СЕРВЕРА ansible_user=root
```

Вот и всё. Мы сказали Ansible: у нас есть группа `servers`, в ней один хост `server1`, его IP такой-то, подключаемся под пользователем `root`. Если вы подключаетесь не под рутом, а под обычным пользователем — пишете его имя вместо root.

## Первый запуск — ansible ping

Запускаем первую команду и проверяем, что Ansible видит наш сервер и может к нему подключиться:

ansible all -i inventory.ini -m ping

Давайте разберём, что тут написано, потому что это важно:

- **`ansible`** — ну, это сам Ansible, запускаем ad-hoc команду (то есть, одноразовую команду, без playbook).
- **`all`** — это значит _"выполни на всех хостах из inventory"_. Можно вместо `all` написать название группы, типа `servers`, или даже конкретный хост.
- **`-i inventory.ini`** — указываем путь к нашему inventory-файлу.
- **`-m ping`** — указываем модуль. Модуль `ping` — это такой специальный модуль, который проверяет, что Ansible может подключиться к серверу, выполнить Python-код и вернуть ответ. Это не то же самое, что обычный сетевой ping, имейте в виду. Это именно проверка, что Ansible полноценно работает.

Если всё настроено правильно, вы увидите что-то типа:

codecopy

```
server1 | SUCCESS => {    "changed": false,    "ping": "pong"}
```

Вот этот `SUCCESS` и `"pong"` — это значит, что всё работает. Ansible подключился по SSH, выполнил модуль и получил ответ.

### Если видите ошибку — не паникуем

Самые частые проблемы:

- **"Permission denied"** — SSH-ключ не закинут, либо неправильный пользователь. Проверяем, что `ssh user@IP` работает без пароля.
    
- **"Host key verification failed"** — вы ни разу не подключались к этому серверу по SSH, и Ansible не может подтвердить его отпечаток. Просто подключитесь один раз вручную через `ssh user@IP`, подтвердите отпечаток, и потом Ansible заработает. Либо можно это отключить в конфиге — об этом прямо сейчас.
    
- **"No module named ansible"** — Ansible не установлен или не в PATH. Проверяем установку.
    

## Конфиг `ansible.cfg` — что настроить сразу

У Ansible есть конфигурационный файл `ansible.cfg`, и есть несколько вещей, которые прямо с первого дня лучше настроить, чтобы жизнь была проще. Создаём файл `ansible.cfg` в нашей рабочей директории:

inicopy

```ini
[defaults]inventory = inventory.inihost_key_checking = Falseremote_user = root [privilege_escalation]become = Truebecome_method = sudo
```

Теперь разберём, что тут что.

### `inventory = inventory.ini`

Это путь к inventory-файлу по умолчанию. То есть, теперь вам не нужно каждый раз писать `-i inventory.ini` при запуске. Ansible сам подхватит этот файл.

### `host_key_checking = False`

Помните ошибку _"Host key verification failed"_? Эта настройка её убирает. По сути, Ansible перестаёт проверять отпечаток SSH-ключа сервера. Для боевых продакшн-серверов это, наверное, не лучшая практика с точки зрения безопасности, но для обучения и для работы с динамической инфраструктурой, где серверы постоянно создаются и удаляются, это нормально. И, честно говоря, в большинстве компаний этот параметр тоже стоит в `False`, потому что иначе замучаешься подтверждать отпечатки на каждый новый сервер.

### `remote_user = root`

Пользователь, под которым Ansible будет подключаться к серверам по умолчанию. Если у вас все серверы доступны под одним пользователем — задаём его тут и не дублируем в inventory на каждой строке. На проде обычно это какой-нибудь `ansible` или `deploy` пользователь, а не root, но для обучения root — нормально.

### `become = True` и `become_method = sudo`

Это про повышение привилегий. `become = True` означает, что Ansible будет выполнять команды с правами суперпользователя (через sudo). `become_method = sudo` — собственно, метод, через который он это делает. Если вы подключаетесь сразу под root, то become вам, в принципе, не нужен. Но если подключаетесь под обычным пользователем — без этого ничего работать не будет, потому что ставить пакеты, менять конфиги и так далее обычный пользователь не может.

## Где Ansible ищет конфиг

Тут тоже важный момент, чтобы понимать. Ansible ищет конфиг в следующем порядке:

1. **Переменная окружения `ANSIBLE_CONFIG`** — если задана, берёт оттуда.
2. **`ansible.cfg` в текущей директории** — вот мы его как раз создали.
3. **`~/.ansible.cfg`** — в домашней директории пользователя.
4. **`/etc/ansible/ansible.cfg`** — глобальный конфиг.

То есть, если вы находитесь в директории проекта и там лежит `ansible.cfg` — Ansible подхватит именно его. Это удобно, потому что у вас может быть разный конфиг для разных проектов. На практике чаще всего конфиг лежит именно в директории проекта, рядом с playbooks и inventory.

## Проверяем, что конфиг работает

Теперь, когда у нас есть `ansible.cfg` с прописанным inventory, можем запустить ping короче:

ansible all -m ping

Без `-i`, без указания пользователя — всё подхватится из конфига. Если видите `SUCCESS` и `pong` — значит, конфиг работает, всё настроено.

Можно ещё проверить, какой конфиг Ansible подхватил:

ansible --version

В выводе будет строка `config file = /home/ваш_юзер/ansible-practice/ansible.cfg`. Если видите путь к вашему конфигу — всё правильно.

## Пара ad-hoc команд для проверки

Раз уж мы подключились, давайте попробуем ещё пару команд, чтобы прочувствовать, как это работает.

Посмотреть uptime на всех серверах:

ansible all -m command -a "uptime"

Посмотреть свободное место на диске (помните из блока про Linux — `df -h`):

ansible all -m command -a "df -h"

Посмотреть, сколько памяти:

ansible all -m command -a "free -m"
