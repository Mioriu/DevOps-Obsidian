# Первый playbook в Ansible

Так, ad-hoc команды мы разобрали, поняли, как быстро что-то сделать на серверах из консоли. Но вот проблема — ad-hoc команды это одноразовые штуки. Набрали, выполнили, забыли. А в реальной работе нам нужно, чтобы наши действия были описаны в файле, сохранены в git, воспроизводимы. Чтобы коллега мог посмотреть, что происходит на серверах, не залезая на каждый по SSH.

Playbook — это, по сути, файл, в котором вы описываете: на каких серверах что должно быть сделано. Написали один раз — запускаете сколько угодно. И вот тут нам нужно разобраться с YAML, потому что плейбуки пишутся именно на нём.

## YAML — не бойтесь, тут всё просто

YAML — это формат данных, который читается почти как обычный текст. Никакого программирования, никаких скобок, фигурных скобок, точек с запятой. Просто отступы и тире. Но именно с отступами связана главная боль в YAML, и я вас сразу предупреждаю — отступы тут значимые. Это не просто красота кода, это синтаксис. Неправильный отступ — и всё сломается.

Вот основные правила, которые нужно запомнить прямо сейчас:

**Отступы — только пробелы, никогда табы.** Вот это прямо железное правило. Если где-то в YAML-файле затесается таб — Ansible упадёт с ошибкой, и эту ошибку бывает непросто найти, потому что таб визуально выглядит как пробелы. Настройте свой редактор так, чтобы таб автоматически заменялся на два пробела

**Стандартный отступ — два пробела.** Можно четыре, но два — это стандарт в Ansible-сообществе. Все примеры в документации с двумя пробелами, все роли в Galaxy с двумя пробелами.

**Списки начинаются с тире.** Вот так:

yamlcopy

```yaml
- первый элемент- второй элемент- третий элемент
```

**Словари — это пары ключ-значение:**

yamlcopy

```yaml
имя: Ansibleверсия: 2.17язык: Python
```

Вот, собственно, и весь YAML, который нам нужен для старта.

## Структура playbook'а

Давайте сразу напишем простейший playbook и разберём каждую строчку. Создаём файл `playbook.yml`:

yamlcopy

```yaml
---- name: Настройка веб-серверов  hosts: webservers  become: true   tasks:    - name: Установить nginx      apt:        name: nginx        state: present        update_cache: yes     - name: Запустить nginx      service:        name: nginx        state: started        enabled: yes
```

Вот это — полноценный плейбук. Давайте разберём по частям.

### Три тире в начале

---

Это просто маркер начала YAML-документа. Не все его пишут, но это хороший тон. Ansible и без него поймёт, но лучше ставить.

### Play

yamlcopy

```yaml
- name: Настройка веб-серверов  hosts: webservers  become: true
```

Вот эта штука называется **play**. Play — это, по сути, набор задач, привязанный к определённой группе серверов. То есть, мы говорим: "Вот эти задачи выполняй на вот этих серверах."

— `name` — просто описание, что этот play делает. — `hosts` — на каких серверах выполнять. Тут указываем группу из inventory, конкретный хост, или `all`. — `become: true` — выполнять задачи с правами суперпользователя (через sudo). Это то же самое, что флаг `-b` в ad-hoc командах, только тут мы прописываем это в файле.

В одном плейбуке практически всегда плеев. Например, первый play настраивает веб-серверы, второй — базы данных:

yamlcopy

```yaml
---- name: Настройка веб-серверов  hosts: webservers  become: true  tasks:    # задачи для веб-серверов - name: Настройка баз данных  hosts: databases  become: true  tasks:    # задачи для баз данных
```

### Tasks — задачи

yamlcopy

```yaml
  tasks:    - name: Установить nginx      apt:        name: nginx        state: present        update_cache: yes
```

Tasks — это список конкретных действий, которые Ansible должен выполнить. Каждая задача — это вызов одного модуля. Вот эта задача вызывает модуль `apt` с определёнными параметрами.

— `name` — описание задачи. Это не обязательный параметр, Ansible будет работать и без него. Но писать name нужно всегда. Во-первых, чтобы при запуске в логах видеть, что сейчас происходит. Во-вторых, чтобы коллега, открыв ваш плейбук, сразу понял, что тут к чему. Без name в логах будет просто "TASK [apt]" — и пойди разберись, что оно делает.

— `apt` — имя модуля. Дальше идут его параметры с отступом.

Задачи выполняются по порядку, сверху вниз. Сначала установит nginx, потом запустит его. Если задача упала — Ansible остановится и дальше не пойдёт (по умолчанию).

## Модуль debug

Прежде чем двигаться дальше, давайте познакомимся с модулем `debug`. Этот модуль просто выводит сообщение в консоль. Казалось бы, зачем? А на практике он используется постоянно — для отладки, для проверки значений переменных, для понимания, что вообще происходит.

yamlcopy

```yaml
---- name: Пример с debug  hosts: all  become: false   tasks:    - name: Вывести приветствие      debug:        msg: "Привет! Ansible работает на хосте {{ inventory_hostname }}"     - name: Вывести информацию об ОС      debug:        msg: "ОС: {{ ansible_os_family }}, Версия: {{ ansible_distribution_version }}"
```

`{{ inventory_hostname }}` — это переменная. Двойные фигурные скобки — это синтаксис Jinja2, шаблонизатора, который использует Ansible. `inventory_hostname` — это имя хоста из inventory. `ansible_os_family` и `ansible_distribution_version` — это факты, которые Ansible автоматически собирает с серверов при запуске. Факты мы детально разберём позже, но суть простая — Ansible подключается к серверу, собирает информацию о нём (какая ОС, сколько памяти, какие диски и так далее) и делает эту информацию доступной через переменные.

Ещё debug умеет выводить переменные через `var`:

yamlcopy

```yaml
    - name: Вывести все IP-адреса хоста      debug:        var: ansible_all_ipv4_addresses
```

Разница между `msg` и `var` простая: `msg` — это произвольный текст с подстановками, `var` — это вывод конкретной переменной целиком (удобно, когда переменная — список или словарь).

## Идемпотентность — ещё раз

Мы уже говорили про идемпотентность в первом материале, но сейчас, когда мы пишем плейбуки, это понятие выходит на первый план. Давайте посмотрим на конкретном примере.

Вот наш playbook, который ставит и запускает nginx. Запускаем его первый раз:

codecopy

```
TASK [Установить nginx] ****************************************************changed: [server1] TASK [Запустить nginx] ******************************************************changed: [server1]
```

Видите статус `changed`? Это значит, что Ansible реально что-то сделал — поставил пакет и запустил сервис. А теперь запускаем тот же playbook второй раз:

codecopy

```
TASK [Установить nginx] ****************************************************ok: [server1] TASK [Запустить nginx] ******************************************************ok: [server1]
```

Теперь статус `ok`. Ansible проверил — nginx уже стоит, уже запущен. Делать ничего не нужно. Вот это и есть идемпотентность.

А вот пример **неидемпотентного** подхода — когда вместо модулей используют `shell`:

yamlcopy

```yaml
    # ТАК ДЕЛАТЬ НЕ НАДО    - name: Добавить строку в конфиг      shell: echo "server_name example.com;" >> /etc/nginx/conf.d/site.conf
```

Каждый запуск будет добавлять строку в файл. Запустили три раза — три одинаковых строки. Вот это уже проблема. Правильно тут использовать модуль `lineinfile`, который проверит, есть ли строка, и добавит только если её нет. Но это мы разберём позже.

Общее правило: если для задачи есть специальный модуль — используйте его, а не `shell` или `command`. Модули написаны так, чтобы быть идемпотентными. `shell` — нет.

## Запуск плейбука

Запускается playbook командой `ansible-playbook`:

ansible-playbook playbook.yml

Вот и всё. Если у вас в `ansible.cfg` прописан inventory — он подхватится автоматически. Если нет — указываем явно:

ansible-playbook -i inventory.ini playbook.yml

После запуска вы увидите примерно такой вывод:

codecopy

```
PLAY [Настройка веб-серверов] *********************************************** TASK [Gathering Facts] ******************************************************ok: [server1] TASK [Установить nginx] ****************************************************changed: [server1] TASK [Запустить nginx] ******************************************************changed: [server1] PLAY RECAP ******************************************************************server1                    : ok=3    changed=2    unreachable=0    failed=0
```

Разберём, что тут что.

**PLAY** — показывает, какой play сейчас выполняется. Вот зачем мы писали `name`.

**TASK [Gathering Facts]** — это первая задача, которую Ansible выполняет автоматически. Он подключается к серверу и собирает факты — информацию об ОС, IP, памяти и так далее. Если вам факты не нужны (а для простых задач часто не нужны), можно отключить:

yamlcopy

```yaml
- name: Настройка веб-серверов  hosts: webservers  gather_facts: false  tasks:    # ...
```

Это, кстати, ускоряет выполнение, особенно если серверов много.

**PLAY RECAP** — итоговая сводка. Сколько задач выполнено (`ok`), сколько что-то изменили (`changed`), сколько серверов недоступно (`unreachable`), сколько ошибок (`failed`). Вот на эту строку нужно смотреть в первую очередь. Если `failed=0` и `unreachable=0` — значит, всё прошло хорошо.

## Полезные флаги ansible-playbook

Теперь про флаги, которые прямо нужно знать, потому что они используются постоянно.

### --check (dry run)

ansible-playbook playbook.yml --check

Ansible покажет, что он собирается сделать, но ничего реально не выполнит. То есть, вы видите: "вот тут я бы установил пакет, вот тут я бы перезапустил сервис" — но на серверах ничего не меняется.

Перед тем как запускать плейбук на боевых серверах, всегда прогоняйте в `--check`.

Но есть нюанс. Некоторые задачи в check-режиме могут показывать ошибки, потому что они зависят от результатов предыдущих задач, которые реально не выполнились. Например, если первая задача создаёт директорию, а вторая копирует туда файл — в check-режиме вторая задача упадёт, потому что директория реально не создалась. Это нормально, просто имейте в виду.

### --diff

ansible-playbook playbook.yml --diff

Показывает разницу между тем, что есть на сервере, и тем, что Ansible собирается изменить. Особенно полезно для файлов — вы видите, какие строки будут добавлены, удалены, изменены. Прямо как `git diff`, только для серверов.

Обычно `--diff` комбинируют с `--check`:

ansible-playbook playbook.yml --check --diff

Вот это сочетание — вообще лучшая штука для ревью изменений. Вы видите: "Ansible хочет поменять вот эту строку в конфиге nginx с X на Y, и ничего больше." И принимаете решение — запускать или нет. На проде без этого лучше не работать.

### --limit

ansible-playbook playbook.yml --limit server1

Ограничивает выполнение только указанными хостами. Даже если в плейбуке написано `hosts: all` или целая группа — выполнится только на `server1`.

Зачем это нужно? Допустим, вы написали playbook и хотите сначала проверить его на одном сервере, прежде чем раскатывать на все двадцать. Вот `--limit` для этого и существует.

Можно указать несколько серверов:

ansible-playbook playbook.yml --limit "server1,server2"

Или целую группу:

ansible-playbook playbook.yml --limit webservers

### -v, -vv, -vvv — verbose

bashcopy

```bash
# чуть подробнееansible-playbook playbook.yml -v # ещё подробнееansible-playbook playbook.yml -vv # прямо совсем детально (SSH-команды, переданные данные)ansible-playbook playbook.yml -vvv
```

Чем больше букв `v` — тем больше информации. `-v` покажет результаты задач, `-vv` добавит детали подключения, `-vvv` покажет вообще всё, включая SSH-команды. На практике `-v` хватает в большинстве случаев. `-vvv` — это уже для совсем тяжёлого дебага, когда непонятно, почему что-то не работает.

### --tags и --skip-tags

Это мы детально разберём в отдельном материале, но кратко — можно размечать задачи тегами и запускать только определённые:

bashcopy

```bash
ansible-playbook playbook.yml --tags "nginx"ansible-playbook playbook.yml --skip-tags "database"
```

## Полноценный пример — playbook для настройки сервера

Давайте напишем что-то поближе к реальности. Плейбук, который готовит свежий сервер к работе:

yamlcopy

```yaml
---- name: Базовая настройка сервера  hosts: all  become: true  gather_facts: true   tasks:    - name: Обновить кэш пакетов      apt:        update_cache: yes        cache_valid_time: 3600     - name: Установить базовые пакеты      apt:        name:          - htop          - curl          - wget          - git          - vim          - net-tools          - unzip        state: present     - name: Создать пользователя deploy      user:        name: deploy        shell: /bin/bash        groups: sudo        append: yes        createhome: yes     - name: Закинуть SSH-ключ для пользователя deploy      authorized_key:        user: deploy        key: "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... ваш_ключ"        state: present     - name: Настроить sudo без пароля для deploy      copy:        content: "deploy ALL=(ALL) NOPASSWD:ALL\n"        dest: /etc/sudoers.d/deploy        owner: root        group: root        mode: "0440"     - name: Установить nginx      apt:        name: nginx        state: present     - name: Запустить и включить nginx в автозагрузку      service:        name: nginx        state: started        enabled: yes     - name: Вывести IP-адрес сервера      debug:        msg: "Сервер {{ inventory_hostname }} настроен. IP: {{ ansible_default_ipv4.address }}"
```

Вот это уже реальный playbook, который можно запустить на свежем сервере и получить готовую к работе систему. Обновили пакеты, поставили всё нужное, создали пользователя, закинули ему ключ, настроили sudo, поставили nginx. И всё это — один файл, одна команда:

ansible-playbook setup.yml

Запустите второй раз — всё будет `ok`, потому что idempotent. Покажите коллеге — он сразу поймёт, что происходит, потому что каждая задача подписана. Закоммитьте в git — у вас есть история изменений. Вот в этом, собственно, вся суть Infrastructure as Code.
