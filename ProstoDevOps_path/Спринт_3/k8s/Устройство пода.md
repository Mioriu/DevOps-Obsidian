# Pod Изнутри

## 1. Из чего состоит Pod

### Определение

## **Pod** — это минимальная развёртываемая единица в Kubernetes, а именно - **группа из одного или нескольких контейнеров**, у которых общее сетевое пространство и хранилище.  
**Ключевой момент:** `Pod` это не просто контейнер. **Это обёртка** вокруг контейнеров с общими ресурсами.

### Архитектура Pod (схема)

## ![Pod изнутри: Pause Container, Init/Main/Sidecar, Volumes](https://offers.prostodevops.ru/diagrams/k8s/pod-internals.png)Pod изнутри: Pause Container, Init/Main/Sidecar, Volumes

### Компоненты Pod

## **1. Pause контейнер (infracontainer)**  
Первый контейнер который запускается в поде. Его задача - держать Linux namespace's и настраивать сеть.  
**2. Init контейнеры**  
Выполняются последовательно перед основными контейнерами. Нужны для подготовки окружения.  
**3. Основные контейнеры**  
Контейнеры с твоим приложением. Запускаются параллельно **после** init контейнеров.  
**4. Volumes**  
Общие директории доступные всем контейнерам в поде.

## 2. Pause контейнер - основа пода

### Что это и зачем

**Pause контейнер** — это минимальный контейнер который просто спит и держит namespace.  
**Зачем нужен:**  
Проблема без pause:

- Запускаешь контейнер A - создаётся `network namespace`
- Запускаешь контейнер B - он должен использовать тот же `namespace`
- Контейнер A умирает - `namespace` удаляется
- Контейнер B теряет сеть

Решение с pause:

- Pause контейнер создаёт и держит `network namespace`
- Все остальные контейнеры присоединяются к нему
- Если контейнер A упал - `pause` держит `namespace`, контейнер B работает.

## Все контейнеры пода используют эти же namespace'ы.

### Что делится между контейнерами

**Общее:**  
**Network Namespace:**

- ✅ IP адрес один на весь под
- ✅ Все контейнеры видят друг друга на localhost
- ✅ Порты общие (нельзя двум контейнерам слушать :8080)

**IPC Namespace:**

- ✅ Shared memory между контейнерами
- ✅ Семафоры и очереди сообщений

**UTS Namespace:**

- ✅ Общее имя хоста (hostname)

**Раздельное:**

- ❌ Process Namespace - каждый контейнер видит только свои процессы
- ❌ Mount Namespace - каждый контейнер имеет свою файловую систему
- ❌ User Namespace - пользователи раздельные

### Практический пример

**Pod с двумя контейнерами:**

codecopy

```
apiVersion: v1kind: Podmetadata:  name: shared-networkspec:  containers:  - name: app    image: nginx:1.21    ports:    - containerPort: 80   - name: sidecar    image: curlimages/curl:latest    command: ['sh', '-c', 'while true; do curl localhost:80; sleep 5; done']
```

**Что происходит:**

1. Создаётся pause контейнер с IP `10.244.1.5`
2. Запускается nginx - слушает на `0.0.0.0:80` (в network namespace пода)
3. Запускается curl - обращается к `localhost:80` и видит nginx

**Проверка:**

codecopy

```
kubectl apply -f shared-network.yaml # Зайти в sidecar контейнерkubectl exec -it shared-network -c sidecar -- sh # Внутри контейнераcurl localhost:80
```

## Работает! Потому что оба контейнера в одном network namespace.

## 3. Init контейнеры

### Зачем нужны

**Init контейнеры** — контейнеры которые выполняются **до** запуска основных контейнеров.  
**Типичные задачи:**

- Миграции базы данных
- Загрузка конфигурации из внешнего источника
- Ожидание доступности зависимостей (БД, API)
- Подготовка файлов и директорий
- Настройка прав доступа

**Особенности:**

- Выполняются последовательно (один за другим)
- Основные контейнеры запустятся только если все init успешно завершились
- Имеют доступ к тем же volumes что и основные контейнеры

### Пример 1: Ожидание базы данных

**Задача:** Приложение не должно стартовать пока БД не доступна.

codecopy

```
apiVersion: v1kind: Podmetadata:  name: myappspec:  initContainers:  - name: wait-for-db    image: busybox:1.35    command:    - 'sh'    - '-c'    - |      echo "Waiting for database..."      until nc -z postgres-service 5432; do        echo "Database not ready, waiting..."        sleep 2      done      echo "Database is ready!"   containers:  - name: app    image: myapp:1.0    env:    - name: DB_HOST      value: postgres-service
```

**Что происходит:**

1. Запускается init контейнер `wait-for-db`
2. Проверяет доступность PostgreSQL
3. Если недоступен - ждёт и повторяет
4. Когда БД доступна - init завершается
5. Запускается основной контейнер `app`

### Пример 2: Миграции базы данных

codecopy

```
apiVersion: v1kind: Podmetadata:  name: webappspec:  initContainers:  - name: run-migrations    image: myapp:1.0    command: ['python', 'manage.py', 'migrate']    env:    - name: DB_HOST      value: postgres-service    - name: DB_PASSWORD      valueFrom:        secretKeyRef:          name: db-secret          key: password   containers:  - name: webapp    image: myapp:1.0    ports:    - containerPort: 8000
```

## Миграции выполнятся один раз перед стартом приложения.

### Пример 3: Подготовка конфигурации

codecopy

```
apiVersion: v1kind: Podmetadata:  name: nginx-with-configspec:  volumes:  - name: config    emptyDir: {}   initContainers:  - name: generate-config    image: busybox:1.35    command:    - 'sh'    - '-c'    - |      cat > /config/nginx.conf <<EOF      server {        listen 80;        location / {          proxy_pass http://backend:8080;        }      }      EOF    volumeMounts:    - name: config      mountPath: /config   containers:  - name: nginx    image: nginx:1.21    volumeMounts:    - name: config      mountPath: /etc/nginx/conf.d      readOnly: true
```

## Init контейнер генерирует конфиг, основной контейнер его использует.

## 4. Sidecar контейнеры

### Паттерн Sidecar

**Sidecar** — дополнительный контейнер который расширяет функциональность основного.  
**Типичные use case:**

- Логирование (fluentd, filebeat)
- Мониторинг (prometheus exporter)
- Service mesh (envoy, linkerd)
- Кеширование
- Синхронизация данных

### Пример 1: Sidecar для логов

**Задача:** Основное приложение пишет логи в файл, sidecar отправляет их в Elasticsearch.

codecopy

```
apiVersion: v1kind: Podmetadata:  name: app-with-loggingspec:  volumes:  - name: logs    emptyDir: {}   containers:  - name: app    image: myapp:1.0    volumeMounts:    - name: logs      mountPath: /var/log/app    command:      - sh      - -c      - while true; do echo "Log message" >> /var/log/app/app.log; sleep 5; done   - name: log-shipper    image: fluent/fluent-bit:1.9    volumeMounts:    - name: logs      mountPath: /var/log/app      readOnly: true    env:    - name: FLUENT_ELASTICSEARCH_HOST      value: elasticsearch
```

## Оба контейнера видят `/var/log/app` через shared volume.

### Пример 2: Nginx + Certbot sidecar

**Задача:** Nginx отдаёт сайт, certbot обновляет SSL сертификаты.

codecopy

```
apiVersion: v1kind: Podmetadata:  name: nginx-with-certbotspec:  volumes:  - name: certs    emptyDir: {}  - name: webroot    emptyDir: {}   containers:  - name: nginx    image: nginx:1.21    ports:    - containerPort: 80    - containerPort: 443    volumeMounts:    - name: certs      mountPath: /etc/nginx/ssl    - name: webroot      mountPath: /var/www/html   - name: certbot    image: certbot/certbot    command:    - 'sh'    - '-c'    - |      while true; do        certbot renew --webroot -w /var/www/html        sleep 86400  # Проверять раз в день      done    volumeMounts:    - name: certs      mountPath: /etc/letsencrypt    - name: webroot      mountPath: /var/www/html
```

## 5. Статические поды (Static Pods)

### Что это

**Static Pod** — это под который создаётся напрямую kubelet на конкретной ноде, а именно - **без участия API server**.  
**Ключевые отличия:**

- Создаются из YAML файлов в `/etc/kubernetes/manifests/`
- Управляются напрямую kubelet, не через API server
- Нельзя удалить через `kubectl delete` (только удалить файл)
- Используются для **control plane** компонентов

### Зачем нужны

**Проблема:** Как запустить `kube-apiserver` если он сам работает в Kubernetes?  
**Решение:** Static pods  
На master нодах в `/etc/kubernetes/manifests/` лежат манифесты:

- `kube-apiserver.yaml`
- `kube-controller-manager.yaml`
- `kube-scheduler.yaml`
- `etcd.yaml`

## `kubelet` читает эти файлы и запускает поды напрямую.

### Создание Static Pod

**Задача:** Создать static pod с nginx.  
**Шаг 1: Найти директорию манифестов**

codecopy

```
# Посмотреть конфиг kubeletsudo cat /var/lib/kubelet/config.yaml | grep staticPodPath
```

**Вывод:**

staticPodPath: /etc/kubernetes/manifests

**Шаг 2: Создать манифест**

sudo nano /etc/kubernetes/manifests/static-nginx.yaml

codecopy

```
apiVersion: v1kind: Podmetadata:  name: static-nginxspec:  containers:  - name: nginx    image: nginx:1.21    ports:    - containerPort: 80
```

**Шаг 3: Подождать ~20 секунд**  
kubelet автоматически обнаружит новый файл и запустит под.

kubectl get pods

**Вывод:**

codecopy

```
NAME                    READY   STATUS    RESTARTS   AGEstatic-nginx-node-1     1/1     Running   0          15s
```

### Static Pods vs DaemonSets

|Параметр|Static Pods|DaemonSets|
|---|---|---|
|Управление|kubelet напрямую|API server + controller|
|Создание|Файл в /manifests/|kubectl apply|
|Удаление|Удалить файл|kubectl delete|
|Use case|Control plane|Мониторинг, логирование|
|Перенос на другую ноду|Нет|Да|
