# kubectl и первый Pod

Тип: Урок · Статус: вычитано Обновлено: 07.06.2026, 09:23

## kubectl

В прошлом уроке любое взаимодействие с кластером упиралось в `kube-apiserver`. **kubectl** – это консольный клиент к нему. Каждая команда kubectl превращается в HTTP-запрос к API server, и больше kubectl ничего не делает.

![kubectl - консольный клиент к api-server: каждая команда это HTTP-запрос; адрес и доступы из kubeconfig](https://prostodevops.ru/api/uploads/lessons/kubectl-pod-deployment-service-01.webp)kubectl - консольный клиент к api-server: каждая команда это HTTP-запрос; адрес и доступы из kubeconfig

Никакой собственной логики и состояния у него нет, вся работа происходит в кластере.

Ставится kubectl на вашу как обычный бинарник – через пакетный менеджер или скачиванием с сайта Kubernetes. Проверка стандартная:

kubectl version --client

## kubeconfig

Адрес кластера и доступы kubectl берет из файла `~/.kube/config`, его называют **kubeconfig**. Внутри три вещи.

Секция Что хранит `clusters` Адреса API server и их сертификаты `users` Учетные данные – сертификаты или токены `contexts` Связки `кластер + пользователь`, между которыми можно переключаться

Руками этот файл обычно не пишут. Managed-кластер в облаке отдает готовый kubeconfig одной командой своего CLI, `minikube` и `kind` прописывают себя в него сами при создании кластера. Когда кластеров несколько – рабочий, тестовый, локальный – между ними переключаются контекстами:

Bash

Копировать

```bash
kubectl config get-contexts        # список доступных контекстов
kubectl config use-context dev     # переключиться на контекст dev
kubectl config current-context     # на какой кластер смотрим сейчас
```

## Команды

Почти все команды kubectl устроены одинаково:

kubectl <действие> <тип объекта> <имя>

Действия – `get`, `describe`, `delete`, `logs`, `exec` и еще десяток. Типы объектов – `pod`, `node`, `service` и другие, по мере модуля список будет расти. Первая команда на любом новом кластере – посмотреть его ноды:

kubectl get nodes

Копировать

```
NAME       STATUS   ROLES           AGE   VERSION
master     Ready    control-plane   12d   v1.30.1
worker-1   Ready    <none>          12d   v1.30.1
worker-2   Ready    <none>          12d   v1.30.1
```

Если таблица вернулась – связь с API server есть, доступы работают, кластер отвечает.

## Первый под

Запустим в кластере nginx. Самый короткий способ – команда `run`:

kubectl run web --image=nginx:1.25

Здесь `web` – имя пода, `--image` – образ из registry, тот же самый, что вы запускали через `docker run`. Смотрим, что получилось:

kubectl get pods

Копировать

```
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          15s
```

Под работает. В колонке `READY` видно 1/1 – один контейнер из одного готов. Если успеть с `get pods` в первые секунды, статус будет `ContainerCreating` – образ еще скачивается на ноду.

Флаг `-o wide` добавляет в таблицу колонки, которых не хватает почти сразу:

kubectl get pods -o wide

Копировать

```
NAME   READY   STATUS    RESTARTS   AGE   IP           NODE
web    1/1     Running   0          40s   10.244.1.7   worker-2
```

Появились IP пода и нода, на которой он работает. И за этой строчкой произошло все, что мы разбирали в прошлом уроке. kubectl отправил объект на API server, тот записал его в etcd, scheduler выбрал `worker-2`, kubelet этой ноды скачал образ и запустил контейнер через containerd, CNI-плагин выдал поду адрес `10.244.1.7`.

## describe и события

Таблица `get pods` отвечает на вопрос `что есть`. Следующий уровень детализации – `describe`:

kubectl describe pod web

Вывод длинный. В нем метаданные пода, нода и IP, описание контейнеров с образами и портами, состояние и число рестартов. Но самая ценная часть – секция `Events` в конце:

Копировать

```
Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  2m    default-scheduler  Successfully assigned default/web to worker-2
  Normal  Pulling    2m    kubelet            Pulling image "nginx:1.25"
  Normal  Pulled     2m    kubelet            Successfully pulled image
  Normal  Created    2m    kubelet            Created container web
  Normal  Started    2m    kubelet            Started container web
```

Это журнал жизни пода. Scheduler назначил ноду, kubelet потянул образ, создал и запустил контейнер. Когда с подом что-то не так, ответ почти всегда лежит здесь – в событиях будет написано, что образ не скачивается, что не хватило ресурсов, что контейнер падает.

## Логи и exec

Две команды, которые вы уже знаете по докеру, просто с другим префиксом.

Bash

Копировать

```bash
kubectl logs web          # логи контейнера в поде
kubectl logs -f web       # следить в реальном времени
kubectl logs --tail=20 web
```

Работает это по той же причине, что и `docker logs` – приложение пишет в stdout, а вывод перехватывается и доступен снаружи.

kubectl exec -it web -- bash

Знакомая пара флагов `-it` и команда после разделителя `--`. Внутри пода тот же контейнер, что был бы при `docker exec`, с той разницей, что физически он может работать на любой ноде кластера – kubectl сам дотянется до нужной машины через API server. Для одноразовой команды без захода внутрь:

kubectl exec web -- nginx -v

## port-forward

Под получил адрес `10.244.1.7`, но это адрес из внутренней сети кластера. С вашего ноутбука он недоступен, и это нормально – наружу поды публикуются через отдельные механизмы, которыми займемся в уроке про Services. А для отладки есть туннель:

kubectl port-forward pod/web 8080:80

Пока команда работает, обращения на `localhost:8080` уходят на порт 80 пода. Открываем второй терминал:

curl localhost:8080

Приветственная страница nginx на месте – приложение в кластере работает и отвечает.

## Голый под смертен

Теперь важный эксперимент. Удалим под:

Bash

Копировать

```bash
kubectl delete pod web
kubectl get pods
```

No resources found in default namespace.

Под исчез, и никто его не пересоздал. Хотя весь прошлый урок был про самочинящийся кластер.

![Голый под смертен: kubectl delete не пересоздаст под без контроллера; под под Deployment чинится self-healing](https://prostodevops.ru/api/uploads/lessons/kubectl-pod-deployment-service-02.webp)Голый под смертен: kubectl delete не пересоздаст под без контроллера; под под Deployment чинится self-healing

Как мы помним кубер сводит текущее состояние к желаемому. Команда `delete` изменила желаемое состояние – пода больше не должно быть. Кластер привел реальность в соответствие, все честно. Самовосстановление случается тогда, когда желаемое состояние требует существования объекта, а кто-то следит за этим требованием.

За голым подом не следит никто. У kubelet есть параметр `restartPolicy` со значением `Always` по умолчанию – если внутри пода упадет контейнер, kubelet перезапустит его на той же ноде. Но это все. Удалили под – его нет. Умерла нода вместе с подом – под не переедет, потому что нет контроллера, в чьем желаемом состоянии записано «копий этого приложения должно быть N». Поэтому в реальной работе голые поды руками почти не создают. Поды порождаются контроллерами, которые и держат то самое желаемое состояние, и ближайшие уроки модуля посвящены именно им.

## Манифест пода

Команда `run` – императивный способ. Рабочий способ в Kubernetes другой – описать объект в YAML-файле и отдать кластеру. Вот тот же nginx манифестом:

YAML

Копировать

```yaml
# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
    - name: web
      image: nginx:1.25
      ports:
        - containerPort: 80
```

У любого манифеста Kubernetes четыре верхнеуровневых поля, и они будут в каждом YAML до конца обоих модулей.

Поле Что задает `apiVersion` Версия API для этого типа объекта. Для пода – `v1` `kind` Тип объекта. `Pod`, дальше будут `Deployment`, `Service` и другие `metadata` Имя, метки, служебная информация `spec` Желаемое состояние объекта – его содержательная часть

В `spec` пода главное – список `containers`. У контейнера есть имя, образ и порты. `containerPort` здесь играет ту же роль, что `EXPOSE` в Dockerfile – это декларация порта, а не проброс. В `metadata` появились `labels`, метки. Сейчас метка `app: web` просто висит на поде, а в уроке про манифесты и селекторы станет понятно, что на метках держится вся связность объектов Kubernetes.

Применяется манифест командой `apply`:

kubectl apply -f pod.yaml

pod/web created

`apply` читает файл, отправляет объект на API server, дальше цепочка та же. Повторный `apply` того же файла ничего не изменит, а `apply` после правки файла донесет до кластера только изменения.

Удаляется объект тоже по файлу:

kubectl delete -f pod.yaml

## spec и status живьем

В прошлом уроке у каждого объекта были `spec` и `status` – желаемое и текущее. Теперь их можно потрогать. Флаг `-o yaml` выводит объект целиком, как он лежит в кластере:

kubectl get pod web -o yaml

В выводе виден ваш `spec` – то, что было в манифесте, плюс значения по умолчанию, которые кластер дописал сам, тот же `restartPolicy: Always`. А ниже – `status`, которого в манифесте не было:

YAML

Копировать

```yaml
status:
  phase: Running
  podIP: 10.244.1.7
  hostIP: 192.168.1.12
  conditions:
    - type: Ready
      status: "True"
```

Это та часть, которую пишет кластер. Фаза, адреса, готовность контейнеров, время запуска. Все таблицы `kubectl get` – это, по сути, выжимки из `status` разных объектов.

## Статусы пода

В колонке `STATUS` за жизнь пода можно увидеть разное.

Статус Что значит `Pending` Под принят, но не запущен. Чаще всего scheduler не нашел ноду с ресурсами `ContainerCreating` Нода назначена, идет скачивание образа и создание контейнера `Running` Под работает `Completed` Контейнер отработал и завершился успешно, нормально для разовых задач `ImagePullBackOff` Образ не скачивается. Опечатка в имени, несуществующий тег, нет доступа к registry `CrashLoopBackOff` Контейнер запускается и падает, снова запускается и снова падает

![Статусы пода: нормальный цикл Pending - ContainerCreating - Running - Completed и проблемы ImagePullBackOff/CrashLoopBackOff](https://prostodevops.ru/api/uploads/lessons/kubectl-pod-deployment-service-03.webp)Статусы пода: нормальный цикл Pending - ContainerCreating - Running - Completed и проблемы ImagePullBackOff/CrashLoopBackOff

Про два последних стоит сказать подробнее, вы будете встречать их регулярно.

`ImagePullBackOff` почти всегда означает проблему с именем образа или доступом к registry. Слово `BackOff` в названии – это пауза. Kubelet не долбит registry непрерывно, а повторяет попытки с растущим интервалом.

`CrashLoopBackOff` означает, что с образом все в порядке, а падает само приложение. Kubelet честно исполняет `restartPolicy: Always`, перезапускает контейнер, тот снова падает, и пауза между перезапусками растет от секунд до минут. Идти тут надо в `kubectl logs` – причина падения написана в логах приложения. Если контейнер умирает так быстро, что логов нет, флаг `--previous` покажет логи предыдущей, упавшей попытки:

kubectl logs web --previous

Связка для любой проблемы с подом получается короткая. Сначала `kubectl get pods` – увидеть статус. Потом `kubectl describe pod` – прочитать Events. Потом `kubectl logs` – посмотреть на само приложение. Эти три команды закрывают большую часть отладки на годы вперед.

## Несколько контейнеров в поде

В прошлом уроке прозвучало, что под может содержать несколько контейнеров. Посмотрим, как это выглядит и что дает:

YAML

Копировать

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-with-helper
spec:
  containers:
    - name: web
      image: nginx:1.25
    - name: helper
      image: busybox:1.36
      command: ["sh", "-c", "while true; do wget -q -O- localhost; sleep 30; done"]
```

В `containers` два элемента. Контейнеры одного пода делят сетевое пространство, поэтому `helper` обращается к nginx просто по `localhost` – никаких адресов и портов наружу, это общение внутри пода. Жить и умирать они тоже будут вместе, на одной ноде.

Паттерн называется **sidecar** – к основному контейнеру подселяется помощник. В жизни так подселяют агентов сбора логов, прокси, обновлялки конфигов. Для приложений правило обратное. Веб-сервер и база данных – это два пода, а не два контейнера в одном, иначе они теряют возможность масштабироваться и переезжать независимо.
