
## Балансировщик на каждый сервис

Урок про сервисы закончился оговоркой – внешних точек входа в реальных системах мало, обычно одна. Пора объяснить, как это устроено, потому что LoadBalancer на каждое приложение упирается в два тупика сразу.

Первый тупик – деньги и адреса. В проекте веб-приложение, API, админка и пара внутренних панелей. Пять сервисов типа LoadBalancer означают пять платных балансировщиков у облака и пять внешних IP, на каждый из которых нужна своя DNS-запись. Расходы растут линейно с числом приложений, хотя трафика на всех может быть с гулькин нос.

Второй тупик – уровень маршрутизации. Service работает на уровне TCP, он умеет доставить пакет до пода и распределить нагрузку. А снаружи задачи формулируются в терминах HTTP – запросы на `app.example.com` в одно приложение, на `api.example.com` в другое, путь `/api` отдельно от остального, и все это по HTTPS с одним сертификатом. Service про хосты, пути и TLS не знает ничего.

Обе задачи – классическая работа reverse proxy, и nginx в этой роли уже был в курсе. Kubernetes дает способ описать такую маршрутизацию объектом кластера.

## Ingress и Ingress Controller

**Ingress** – объект с правилами маршрутизации HTTP-трафика: какой хост и путь в какой сервис направлять. Это именно описание, набор правил в etcd, и сам по себе он не обрабатывает ни одного пакета.

Исполняет правила **Ingress Controller** – реверс-прокси, развернутый в кластере и следящий за объектами Ingress. Самый распространенный вариант – NGINX Ingress Controller, и внутри него буквально тот самый nginx из модуля про веб-серверы. Контроллер читает объекты Ingress и превращает их в конфигурацию nginx – за каждым правилом по сути стоят знакомые `server` и `location`, только их генерация автоматизирована. Есть и альтернативы – Traefik, HAProxy, облачные контроллеры managed-кластеров, – устройство у всех общее: правила из объектов Ingress, исполнение своим прокси.

![Объект Ingress и Ingress Controller: правила, исполнитель и терминация TLS](https://prostodevops.ru/api/uploads/lessons/k8s-ingress-marshrutizatsiya-03.webp)Объект Ingress и Ingress Controller: правила, исполнитель и терминация TLS

Ingress Controller – отдельный компонент, в кластере из коробки его нет. Создали Ingress, а трафик никуда не идет и адрес не назначается – в девяти случаях из десяти в кластере просто отсутствует контроллер. В managed-кластерах он включается опцией или ставится готовым манифестом, в minikube – командой `minikube addons enable ingress`, в k3s контроллер Traefik встроен.

## Как идет трафик

Точка входа при этом остается одна – Service типа LoadBalancer теперь нужен только контроллеру:

![Как идет трафик: одна точка входа через Ingress Controller к сервисам](https://prostodevops.ru/api/uploads/lessons/k8s-ingress-marshrutizatsiya-01.webp)Как идет трафик: одна точка входа через Ingress Controller к сервисам

Все приложения сидят на ClusterIP, наружу не выставлен никто, кроме контроллера. Новое приложение добавляется без нового балансировщика и без нового IP – пишется еще один объект Ingress, контроллер подхватывает правило, DNS-запись указывает на тот же адрес. Оба тупика из начала урока закрыты одной конструкцией.

## Манифест

YAML

Копировать

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
```

Группа API новая – `networking.k8s.io/v1`, сетевые объекты из урока про манифесты. Поле `ingressClassName` указывает, какой контроллер обслуживает этот Ingress: контроллеров в кластере может быть несколько, и каждый берет только свои объекты. Забытое поле – вторая по частоте причина «создал Ingress, ничего не происходит».

Дальше `rules`, список правил. Правило привязано к хосту, внутри – пути, у каждого пути бэкенд в виде имени сервиса и порта. Поле `pathType` определяет сравнение пути: `Prefix` – запросы, начинающиеся с указанного пути, `Exact` – только точное совпадение. Рабочее значение почти всегда `Prefix`.

После применения у объекта появляется адрес:

kubectl get ingress

Копировать

```
NAME   CLASS   HOSTS             ADDRESS         PORTS   AGE
web    nginx   app.example.com   84.201.158.77   80      2m
```

`ADDRESS` – внешний адрес контроллера, и DNS-запись хоста должна указывать именно на него. Запись создается руками у провайдера либо той же связкой с ExternalDNS – аннотация на Ingress работает так же, как работала на сервисе.

## Маршрутизация по хостам и путям

Сила Ingress раскрывается на нескольких правилах. Разводка по доменам – два хоста на два сервиса:

![L7-маршрутизация Ingress по host и path к сервисам-бэкендам](https://prostodevops.ru/api/uploads/lessons/k8s-ingress-marshrutizatsiya-02.webp)L7-маршрутизация Ingress по host и path к сервисам-бэкендам

Разводка по путям – один домен, API под своим префиксом:

YAML

Копировать

```yaml
    - host: app.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
```

При пересечении префиксов срабатывает более специфичный – запрос на `/api/users` уйдет в `api`, все остальное в `web`. Та же логика выбора location, что была в nginx, и это не совпадение, под капотом она и работает.

Правила можно держать в одном объекте или разносить по объектам – например, Ingress на каждое приложение рядом с его Deployment и Service. Контроллер собирает правила из всех объектов своего класса в одну конфигурацию, так что это вопрос организации файлов, как с `---` в уроке про манифесты.

## TLS

HTTPS в этой схеме заканчивается на контроллере – он принимает TLS-соединение, расшифровывает и дальше внутрь кластера трафик идет обычным HTTP. Сертификат и ключ хранятся в секрете специального типа:

kubectl create secret tls web-tls --cert=tls.crt --key=tls.key

И подключаются секцией `tls` в Ingress:

YAML

Копировать

```yaml
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - app.example.com
      secretName: web-tls
  rules:
    # ...
```

С этого момента контроллер обслуживает `https://app.example.com` с указанным сертификатом, а HTTP-запросы по умолчанию перенаправляет на HTTPS. Выпуск и продление сертификатов руками – занятие на любителя, поэтому в кластерах массово живет cert-manager: компонент, который сам выпускает сертификаты через Let's Encrypt и сам кладет их в секреты по аннотации на Ingress. Знакомая логика сверки желаемого с текущим, примененная к сертификатам, – встретите его практически в каждом кластере с публичным трафиком.

## Аннотации

Поведение контроллера сверх базовых правил настраивается аннотациями на объекте Ingress:

YAML

Копировать

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "120"
```

Здесь поднят лимит размера тела запроса – без него загрузка файла больше мегабайта упрется в `413 Request Entity Too Large`, одна из самых частых первых проблем с Ingress, – и увеличен таймаут чтения ответа для медленных ручек. Аннотаций у NGINX-контроллера десятки, от редиректов до rate limiting.

Важная оговорка – префикс `nginx.ingress.kubernetes.io` выдает их природу. Аннотации специфичны для контроллера, у Traefik свои, у облачных свои. Сам объект Ingress переносим между контроллерами, его аннотации – нет.

## Все вместе

Полная публикация приложения теперь выглядит так:

YAML

Копировать

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
---

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - app.example.com
      secretName: web-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
```

Сервис без типа, обычный ClusterIP. Цепочка до приложения собирается из пройденного: DNS ведет на адрес контроллера, контроллер терминирует TLS и по правилу хоста передает запрос в сервис, сервис по эндпоинтам – в готовый под, готовность которого сторожит readiness из урока про пробы. Каждое звено разобрано, магии в цепочке не осталось.

## Отладка

Проверять маршрутизацию можно до настройки DNS – хост передается заголовком:

curl -H "Host: app.example.com" http://84.201.158.77/

Контроллер выбирает правило по заголовку `Host`, так что запрос по голому IP с нужным заголовком проходит весь путь маршрутизации. Прием экономит часы при отладке, особенно пока DNS-записи еще не расползлись.

Дальше по симптомам. Ответ `404` от самого контроллера означает, что запрос не совпал ни с одним правилом – опечатка в хосте, неверный путь или Ingress не подхвачен из-за `ingressClassName`. Состояние объекта смотрится через `kubectl describe ingress`, там видны правила и бэкенды с их эндпоинтами. Ответ `503` означает, что правило сработало, а отправлять запрос некуда – у сервиса нет живых эндпоинтов, и дальше работает связка из урока про сервисы и пробы: `kubectl get endpoints`, готовность подов, readiness. Пустой `ADDRESS` у Ingress – признак отсутствующего или не назначенного контроллера, круг замыкается на грабле номер один.
